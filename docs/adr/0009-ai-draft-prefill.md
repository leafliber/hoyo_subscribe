# ADR-0009：审核队列引入 AI 草稿预填，模型只写草稿，发布仍由人工批准

- **状态**：已接受（P3-17 实施）；"模型 profile"与"单次预占"两项被 ADR-0010 取代（改用 glm-5.3-flash、按实际输入预占）
- **日期**：2026-10-04
- **提出者**：验收方提出，所有者决定方向
- **需要所有者批准**：是，已批准。所有者 2026-10-04 在对话中要求"按建议两步走，先做 AI 预填、人工一键批准"，并要求直接完成实现、合并与部署。
- **编号说明**：0004 仍留给暂停中的 P3-13 提议。

## 背景

首次关闭门部署后（2026-10-03），三个公告源都在正常采集，但到 2026-10-04 公开 publication 仍为 null。
线上待审候选 66 条（原神 39、星铁 12、绝区零 15），公开 `/api/v2/events` 一直返回 503，首页只显示"日程正在准备中"。

原因不在故障，而在首版的设计边界：

- 主方案 §3.4 规定三条路径："已通过测试的结构化字段/明确日期模板 → 确定性候选；需要语义理解 → 批准的模型 profile → 结构化候选；图片、矛盾、超预算或无可用模型 → 人工审核队列"。
- 所有者 2026-09-30 决定首版不带模型抽取（P3-09 暂不进首版），`AI_BILLING_PROFILE_CONFIGURED = false`。
- 规则白名单只有两种模板。带图片的公告，以及写了"版本更新后""预计"之类相对时间的公告，一律生成 `classification: "uncertain", events: []` 的空候选。而米哈游的活动与卡池公告大多带横幅图，也大多写"X.Y版本更新后 ~ 结束时刻"。
- 空候选不能直接批准（`decideCandidate` 拒绝 uncertain）。审核员只能在 F6-01 的 JSON 文本框里手写整份候选，包括逐字引文、块号和 TimeValue，实际上不可用。

所有者的目标是"通过 Workers AI 自动审核每条消息，然后抽取成日历"，并同意分两步：先让 AI 预填、人工一键批准；以后再按合同评估自动发布。

## 受影响的合同

沿用 ADR-0005/0006 的记录方式：主方案原文不改，本 ADR 作为已批准增补；运行时唯一值源仍是 contracts 注册表。

| 文档 | 章节 | 现有规定 | 本次增补 |
| --- | --- | --- | --- |
| 主方案 v2.1 | §3.4 | 模型路径产出结构化候选；人工可直接依据官方材料创建/修正候选 | 新增"AI 草稿"：人工路径的辅助输入，不是第四条发布路径，也不是候选。草稿只有经管理员显式"采用"（一次带理由、带审计的修正）才进入候选；发布仍需管理员批准，`actor_path` 仍为 manual |
| 主方案 v2.1 | §3.5、附录 A.3 | `MODEL_MAX_INPUT` / `MODEL_MAX_BILLED_OUTPUT` 未填写前，依赖模型**自动调用**的能力默认关闭 | 草稿路径不翻转 `AI_BILLING_PROFILE_CONFIGURED`，也不填这两个 P0 值。它用请求本身强制的上限（输入字节、`max_tokens`）算出单次最大预占；自动发布路径（P3-09）维持关闭 |
| 主方案 v2.1 | 附录 A.3 / A.5 | 只有 `AI_SOFT_DAY` / `AI_HARD_DAY` | 增补 `AI_INCLUDED_DAY`、`AI_DRAFT_PROFILE`、`AI_DRAFT_RESERVATION`，以及两条启动等式 |
| F6-01 | 关键约束 | 不做自动批准或批量裁定；每个裁定由人点击并填写理由 | **不变**。一键批准 = 管理员在单条候选上点击，提交"采用草稿"与"批准"两次写操作，都带同一理由、都进审计 |

## 决策

1. **草稿与候选分离。**新表 `ai_drafts` 按候选保存模型草稿、提示与用量。草稿永远不直接改 candidates、events 或公共快照。管理员点"采用草稿"时，服务端从库里取草稿（不接受客户端 JSON），按管理员勾选排除事件或节点，再走统一候选校验，以 `candidate_adopt_draft` 审计做一次普通修正。随后由同一点击触发普通批准，发布结果照常显示 `publication.outcome`。
2. **模型 profile。**`@cf/qwen/qwen3-30b-a3b-fp8`（§3.5 的原候选），提示词版本 `draft-prompt-v1`，`/no_think`，temperature 0.2。模型只拿到官方正文的可读文本与固定说明，没有用户数据、秘密、网络工具或写库权限，也不知道任何 Event ID：草稿一律不带 `change_relation`，也不产出 `retracted`。
3. **服务端确定性转换，不信模型。**模型只输出中间形状：分类、事件类型、节点类型、块号与逐字时间文本。服务端负责：
   - 时间文本必须是所引块原始内容的子串。找不到的节点直接丢弃，并给审核员留下说明；块号写错但全文只有一处出现时，按原文更正。
   - 完整时刻用 `parseAnnouncementExactTime`，纯日期转 DateOnly，其余保留原文、精度 unknown。"预计"一律记 `official_estimate`，绝不推算。
   - 事件键与节点键按顺序确定性生成，标题按公共节点字段预算截断。
   - 最后过 `validateCandidateAgainstArticle`。
4. **账本先预占、后结算。**新表 `ai_usage_days` 是所有 profile 共用的日账本。
   - 每次调用前，按 `AI_DRAFT_RESERVATION` 做条件预占。草稿路径的日上限取 `AI_SOFT_DAY`，触线即停到下一个 UTC 日，把软线到硬线之间留给以后的 P3-09。
   - 调用后按平台回报的 `usage.neurons`（无则按 token 与单价计）向上取整结算。失败与超时按整笔预占结算。
   - 不做结构修复调用：草稿失败时人工路径照常可用。网络失败按 `MODEL_NETWORK_RETRIES` 在后续 watchdog 周期重试。
5. **开关。**沿用已有 `model_enabled`，同时要求 `outbound_enabled` 为真且未处于 `read_only`。默认关闭，由所有者在管理端打开。Worker 未配置 AI 绑定时，草稿任务停在"未配置"，不重试、不计费。
6. **审核页可读化。**改动如下：
   - 队列一次查询带回标题、游戏、来源与草稿状态，去掉逐条读详情的 N+1。
   - 详情页把正文按块显示成可读文本（表格一行一行），原始 HTML 收进折叠区。
   - 草稿按事件、节点列出时间（北京时间）与逐字引文，支持勾选排除。
   - 歧义需要勾选确认；理由可从预设中选择，也可手填。
   - JSON 编辑器保留在"高级"折叠区。

## 价值

- 66 条积压从"逐条手写 JSON"变成"对照原文点一次"，日历可以有内容；每一条发布仍有人逐条核对。
- 模型看错或编造的时间进不了草稿：逐字核对丢弃了它，审核员会看到"已丢弃"说明。
  真实调用中，维护预告的"预计5个小时完成"被模型推算成"2026/09/23 11:00"，这条就会被丢弃。
- 每次"采用 + 批准"都留下"草稿 → 人工排除 → 发布"的完整记录。它可以作为 P0-03b 质量评估的人工标注来源，为第二步（是否开放模型自动发布）积累证据。

## 成本

- 新迁移 0027（两张表、一个索引），只进不退；不改任何已发布数据、UID 或 SEQUENCE。
- PipelineDO 新增一种待办 `pipeline_draft`，每次 alarm 仍只处理一个工作单元；每次调用实测 0.3–3.7 秒，远低于 `EXECUTOR_BATCH_WALL_LIMIT`。
- 所有者需要：在私有部署配置加 AI 绑定、远端执行迁移 0027、重新部署，然后在管理端打开 `model_enabled`。

## 安全影响

- **新增能力：Worker 可以用账户的 Workers AI 额度。**程序错误最坏的后果是耗费额度：有日账本条件预占兜底，草稿路径不超过 `AI_SOFT_DAY`，另有 `model_enabled` 一键停止。
- **提示词注入。**公告正文是官方材料，但仍按不可信数据处理：
  - 模型没有工具和写权限，输出只能变成待审草稿；
  - 草稿逐字核对后才展示，前端一律按文本渲染（不进 innerHTML）；
  - 被注入的公告最多产出一份错误草稿，而它必须经人工批准才会发布。
- 管理端写路径的鉴权不变（管理员会话 + 会话绑定 CSRF + CAS + 理由 + 审计）。新增的 `adopt-draft` 走同一外壳，CSRF 绑定与 `expected_updated_at` 一致。它不接受客户端提交的候选 JSON，只能从已保存的草稿中排除条目，不能借它写入任意内容。
- 不新增秘密，不新增供应商：Workers AI 属于同一 Cloudflare 账户与 Workers 套餐。日志字段仍走白名单，不记录正文或模型原文。

## 预算与容量影响

| 项 | 值 |
| --- | --- |
| 单价（官方价目页 2026-10-01） | 4,625 Neurons/百万输入 token；30,475 Neurons/百万输出 token |
| 单次预占上限 | 输入 ≤ 24,000 字节。字节级 BPE 每个 token 至少 1 字节，所以 token 数 ≤ 字节数，另加模板开销 64；输出 `max_tokens` = 3,000。预占 = ⌈(24,064 × 4,625 + 3,000 × 30,475) / 10⁶⌉ = **203 Neurons** |
| 实测（2026-10-04，6 次真实调用，约 79 Neurons） | 7.2–18.9 Neurons/篇；输入 1,185–1,369 token、输出 27–416 token。平台回报的 `usage.neurons` 与上式逐位一致。`/no_think` 生效，思考输出为空 |
| 日上限 | 草稿 ≤ `AI_SOFT_DAY` = 6,000 < `AI_HARD_DAY` = 8,000 < `AI_INCLUDED_DAY` = 10,000（免费额度，账户内所有应用共用） |
| 零额外费用的前提 | 同账户其他应用每日 Workers AI 用量 < 4,000 Neurons（2026-10-04 查询为 0）。所有者若在其他项目使用 Workers AI，须同时控制 |

邮件四池、账号存量、Feed 容量不受影响。A.5 新增 `ai-hard-within-included` 与 `ai-draft-reservation-within-soft` 两条等式。

## 回退

- 立即停止：管理端关闭 `model_enabled`。在途的一次调用结束后，不再有新的预占与调用。
- 代码回滚：`ai_drafts`、`ai_usage_days` 两张表留在库里无害，旧代码不读它们。已经"采用 + 批准"的候选与普通人工修正、普通发布没有区别，需要时用现有撤回路径处理。
- 不可逆：已发布的事件及其 UID、已被日历客户端下载的副本、已消耗的 Neurons。

## 备选方案

- **直接做 P3-09 自动发布**：需要先完成 P0-03b 的 120 篇人工标注，所有者选择先做第一步。
- **扩充规则模板**：规则对版式变化很脆，"版本更新后"与带图公告仍会大量落空，解决不了积压。
- **让模型直接写 pending 候选**：会把模型输出混进候选表，干扰规则重放与人工接管判断（`run_id`、`human_locked`），审计上也说不清是谁写的内容。独立草稿表边界更清楚。
- **用 JSON Mode**：官方 JSON Mode 支持列表不含该模型。纯 JSON 指令加严格解析在实测中 6/6 可解析，失败时回到人工路径即可。

## 待确认

- 第二步（模型候选不经人工、直接自动发布）不在本 ADR 范围。须另立 ADR，并以 P0-03b 质量门槛（`EXTRACTION_EVAL_MIN`、`KEY_EVENT_RECALL`、`AUTO_PUBLISH_TIME_ERRORS`）为前提。

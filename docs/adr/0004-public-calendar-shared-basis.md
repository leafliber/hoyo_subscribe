# ADR-0004：活跃快照裁剪须保留共享旧投影依据

- **状态**：提议；所有者已选定“保持逐字节一致，授权另行设计共享旧投影依据”，以下具体存储与执行设计待定案。
- **日期**：2026-09-30
- **提出者**：P3-13 执行者 Agent
- **需要所有者批准**：是（涉及 P3-13 范围及共享存储设计，不涉及收费、供应商或权限扩大）

## 背景

P3-06（PR #35，`1a6f41d`）已经合入。本卡按方案 A 裁剪公共快照，但旧快照还承担了另一个职责：它是构建器判断官方更正时的旧投影依据。

需要同时满足的规定：

- P3-13：“本卡让每一代只复制仍可能影响某个 Feed 输出的节点”。
- P3-13：“只对保留集合做更正对比”。
- P3-13：“同一时刻、同一配置、同一公共事实下，裁剪前后每个 Feed 的响应与 ETag 完全一致，只允许读写量变化”。
- 主方案 §6.3：“有明确新时间的改期……同 UID 输出真实新时间和更高公共版本”；更正还提供真实原因与保留期限。
- AGENTS.md §2.8：“合同冲突或做不到时，停手并写 ADR。不自行改动业务含义来让实现通过。”

不能仅在现有构建器中删除旧节点就宣告符合逐字节要求。`calendar_projections` 只有当前投影；`milestones` 保存当前时间。`event_revisions.diff_json` 有事件 before/after 与发生公共变化的节点 ID，没有旧节点时间和完整旧投影，不能从这些表无损恢复比较依据。

### 已执行的反例

在真实本地 D1 中，以同一个合成历史节点分别运行“保留旧模板”和“旧模板已裁掉”两条分支。历史节点在第一次裁剪前已远离过去窗口，无更正。随后将当前投影改到明天、公共版本递增，调用现有 `buildPublicSnapshot`，经真实 Feed handler 获取结果：

| 检查 | 保留旧投影 | 裁掉旧投影 |
| --- | --- | --- |
| 第一次裁剪时的 Feed 正文与 ETag | 相同 | 相同 |
| 改回窗口后的 HTTP 状态 | 200 | 200 |
| UID、SEQUENCE 与 VEVENT 数 | 相同 | 相同 |
| 当前更正 | `rescheduled` | 无 |
| DESCRIPTION | 含“已公布新时间” | 无该更正原因 |
| 正文字节数 | 547 | 527 |
| 正文与 ETag 逐字节比较 | 不相同 | 不相同 |

可复跑用例：`apps/worker/src/calendar/feed/handler.test.ts` 的“A-P3-TRIM / 待裁定反例：已裁历史节点改回窗口时，现有构建器的响应与 ETag 不同”。该用例断言差异来保存反例；它通过只表示反例复现成功，**不表示 A-P3-TRIM 验收通过**。裁剪通过测试夹具模拟，生产裁剪尚未实现。

延长有限证据余量只能把同类问题推迟：任意更早的历史节点仍可获得官方更正。永久保留全部旧快照节点又违背方案 A 的读写与内存目标。

## 决策

所有者已决定保持逐字节一致，并授权设计共享旧投影依据。建议用**每个 Milestone 一份、跨用户共享的最近一次成功公共构建投影**作为比较依据，活跃快照仍只含保留集合。这是设计提案，尚未新增表或改生产读写路径。

### 数据职责

1. 事实表继续保存当前官方事实。
2. 共享依据保存旧构建器原本会留在当前完整模板中的完整节点信息，包括筛选属性、投影、公共版本、实际公共变更时间、原始投影 JSON、更正决定和墓碑状态。不能只保存旧时间，否则分类纠正、恢复及更正原因仍会变化。
3. 每个节点最多一份共享依据；不按 Feed、用户或客户端建行，不保存个人配置或取消记录，不设节点版本的代次区间，不恢复任何全局日历取号。
4. 新快照按 contracts 的保留纯函数生成；日期按日期比较，未来不设上界，未知时间保留，未到期补偿保留。证据余量拟复用 `CAL_PATCH_MIN_DAYS`，覆盖最多该参数天数的常规拉取间隔；具体边界须以回归证明，不能仅凭该天数声称所有更正情形都覆盖。
5. 共享依据不是私人 Feed 可回退的旧响应，只能服务更正对比与缩水证据。输出仍以当前完整代次为唯一来源。

### 构建、初始化与条件提交

- 首次启用时，必须在覆盖任何旧模板之前，从当前完整快照建立依据；不能拿已被事实发布器覆盖的当前投影冒充旧依据。初始化按字节分块并可恢复，完成前保持旧路径。首次迁移的 O(H) 成本单列，不能并入稳态低成本数字。
- 此后只对新节点、投影/版本/筛选属性有变化的节点、被删除的节点及到期补偿做比较；从共享依据恢复旧值后，沿用 `decideCalendarPatch`。变化候选的发现必须覆盖删除，不能只遍历还存在的当前投影。
- 共享依据的更新、补偿变化、清待办及当前代次切换须处于同一最终 CAS 效果边界。不能先覆盖依据再发现构建失败，否则重试将丢失补偿。
- 大节点 JSON 与候选集合均沿用 `PUBLIC_SNAPSHOT_WRITE_PROFILE` 分块；不得用单个历史 JSON 参数规避绑定数限制。初始化、候选读取也须分页，避免构建时又把 H 条历史全部读进 JS 内存。
- 最终守卫同时核对变化候选没有竞态，以及“按保留规则应输出的节点”一个不缺、一个不多。判定及时间边界只在 contracts 定义，SQL 如使用派生检索列，必须从同一规则生成并核验，不能另写一份近似业务规则。
- 正常历史依据不随每代复制；墓碑按旧构建器成功重建时的行为清理。尤其不能先按 TTL 删除依据再处理同次恢复，改变原本应产生的 `restored` 补偿。不是对 `retain_until` 做不加区分的后台删除。

### 缩水证据

仅保存用于更正的旧投影还不够证明整个 Feed 响应不变：基线代次回收后，当前实现会用当前模板中未在基线成功后改变的节点重算基线集合；裁剪会减少这些证据。

建议常规拉取仍用快照的证据余量。在基线代次已不可读且证据不足时，从共享依据补齐**当前构建语义下仍存在、公共变更时间不晚于基线、在基线时刻可能可见**的公共节点，得到裁剪前相同的证据输入，再调用现有守卫。查询应使用派生时间边界与公共变化时间索引定位候选，由 contracts 做完整筛选；不得为一次 Feed 请求读取整张历史表。

交接回归还证明，任务卡中“最长约 211 天”不能作为所有补偿形状的固定上界：展示时间为本次时刻、事实时间为未来 `FEED_FUTURE_DAYS + CAL_PATCH_MIN_DAYS` 天的取消补偿，成功标量须覆盖更晚的事实时间退出。不得据此近似值缩短余量或标量；导航文字交验收方核定。

此设计应保持“重算超额拦截、已知缺席项逐项证明、差额最坏未解释、超比例才用自然退出标量”的既有算法。补证据不能更新成功基线、当作当前输出，或越过当前代次的最终 CAS。若实现证明无法做到同一证据集合，应再次提交具体反例，不能自行放宽 §6.5。

## 价值

历史节点重新改期、取消、分类纠正或恢复时，仍能计算与未裁剪构建器一致的补偿；快照正常复制、Feed 冷读与公共缓存则只容纳活跃集合。原有完整快照删除、UID、SEQUENCE、ETag 计算不变。

## 成本

需要新增共享存储与索引、可恢复的初始化、原子更新及故障恢复测试。旧路径当前没有这套依据，不能只改一个过滤条件。初始化和回滚期间不得回收仅存的完整旧依据。

既有 Feed 地址与 namespace 不变；不会增加私人节点集合。方案定案后，必须对两条真实构建路径进行逐字节对照，不能只拿同一份已经算好补偿的节点数组过滤前后比较。

## 安全影响

存储只接受已有发布器产出的公共事实，比较时仍受发布版本与最终 CAS 保护；不写入用户身份、Feed token、邮箱、Push endpoint 或个人配置。新增表不直接对外开放。额外风险是共享依据损坏或与当前代次不一致导致错误补偿，须有完整性校验及失败关闭测试，不能以补证据名义放行旧代输出。

## 预算与容量影响

下列为设计公式，**不是实测**。令 H 为累计公共历史节点数、A 为本次活跃及证据集合、C 为公共变化候选数：

- 稳态快照写入/回收目标由 O(H) 降到 O(A)；另增加 O(C) 的共享依据维护及其索引写入。无事实变化的重建不得重写 H 行依据。
- 共享依据存量 O(H)，不能声称全部存储都按活跃集合封顶。需计入 D1 容量和 P5 回收/备份；有到期墓碑但不任意丢弃正常历史比较依据。
- Feed 冷读内存目标 O(A)；需要补证据的请求按其公共候选集合计量，必须同时测 rows_read，不能用返回行少证明扫描行少。
- 初始化 O(H) 独立报告，失败重试上界也要计量。
- 每次插入/更新/删除的预算按定案和合入时的实际索引计算。2026-09-30 本分支基线 `1a6f41d` 尚无 P3-14 的两个表达式索引；不能拿它的旧系数冒充未来合入结果。
- 本次没有多年历史的新旧实现成本实测，也没有月度节省结论；实施后必须补齐真实尺寸、构建/回收 rows_written、冷读 rows_read、JS/运行时内存和月度估算。
- 不涉及邮件池、模型调用、账号存量或新增业务阈值；A.5 的新工程依赖如有必要须另行登记，不在本提案中偷偷增加参数。

## 回退

当前 PR 只有测试、变异探针与本提案，回退到 `1a6f41d` 即可恢复之前的源码状态，无线上数据变化。

实施后的回退不能简单切回旧构建器：已经裁掉的当前模板缺少比较依据。须由共享依据重建完整模板、核验后再切回，并保留当前 UID/公共版本/Feed 版本。已下载的日历无法回收，因此所有逐字节验证须在启用裁剪之前完成。

## 备选方案

- 仅延长快照证据余量：有限天数不能解决任意历史节点再次更正；不选作旧投影依据的替代品。
- 永久保留历史快照或在每次 Feed 冷读加载全部历史：与方案 A 的目标冲突。
- 删除更正文案、忽略 ETag 差异或放宽缩水守卫：所有者已经选择保持逐字节一致，不采用。
- 节点版本加代次区间：方案 B，仍不在本卡范围。

## 待确认

1. 是否批准上述具体共享存储与初始化设计，以及扩展迁移、索引/schema 测试等实施路径。
2. “只对保留集合做更正对比”按本提案明确为变化候选先补偿判定、再裁剪活跃输出；由验收方更新任务卡，执行者未自行修改。
3. 共享历史依据的容量、备份和未来回收口径：不能在不证明补偿等价的情况下给它补一个任意 TTL。
4. 设计定案后的实现仍需完成全部 A-P3-TRIM 场景、CAS 竞态与故障注入、过长拉取间隔的响应一致性，以及多年历史下的实测。当前 P3-13 未完成，不应据此放行。

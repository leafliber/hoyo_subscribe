# ADR-0016：公告接口的图文资讯目录纳入现有来源；米游社来源下线

- **状态**：已接受（P3-23 实施）
- **日期**：2026-10-05
- **提出者**：验收方（部署后核对线上数据与一份外部审查时发现）
- **需要所有者批准**：是，已批准。所有者 2026-10-05 在会话里逐项决定：
  - 读取 `pic_list` 算作现有来源范围内的扩展，不按 P0 流程重新登记；
  - 删除米游社来源的代码；
  - "卡池"继续包括"装扮等抽取类卡池"（提示词口径不变）；
  - 已发布事件不重新推导时间，保持现状（ADR-0011 第 6 条、ADR-0013 不变）。
- **与已有 ADR 的关系**：ADR-0013 年份参照的第三级（来源载荷里的真实发布时间）只有米游社提供过。规则保留，现役来源都不提供这一项。

## 背景

2026-10-05 部署 `c700b34` 后核对线上：

- 崩铁站上唯一的"卡池"是活动里用潮玩礼券抽宠物的玩法，绝区零一个也没有。当时正在进行的崩铁「4.6版本活动跃迁（其一）」、绝区零「3.2版本限时频段（下期）」都不在站上。
- 一份外部审查判断为"匿名公告接口拿不到，需要所有者决定新增来源"。核对 P0-02 真实样本（2026-09-21 采集）与当天的官方响应后，结论不同：
  - 同一个 `getAnnList` / `getAnnContent` 响应里有两个目录：`data.list`（按栏目分组：游戏公告、活动公告）和 `data.pic_list`（图文资讯：崩铁「资讯」、绝区零「丽都资讯」）；
  - 跃迁、调频和一部分活动公告只在 `pic_list`。正文接口的 `pic_list` 同样带正文，时间写得明确，例如「本期活动跃迁时间为 2026/09/12 12:00:00 - 2026/09/28 03:59:00」；
  - 适配器只读 `data.list`，这个做法来自 P0-02 探针，登记的条数（41/14/18）也只计 `data.list`。没有任何文档把 `pic_list` 列为范围外，也不涉及访问控制；
  - 两个目录各自编号：绝区零样本里 `ann_id` 238、239、242 两边都有，是不同的公告。
- 米游社官方资讯：P0-02 实测正文接口 `getPostFull` 返回 403，按规则 6 只登记列表并标维护（`maintenance-required-list-only`）。列表只有标题和封面，条目永远不完整、不能批准；原神的版本公告与活动正文已由游戏内公告覆盖。管理端一直写着"通常不需要开启"，线上来源状态一直是 unknown（没有过成功抓取）。

## 受影响的合同

| 文档 | 章节 | 现有规定 | 本 ADR |
| --- | --- | --- | --- |
| 主方案 | §3.1 来源适配 | 四条来源线索，含"米游社官方资讯 `post/wapi/getNewsList`" | 生产注册表只保留三个游戏内公告源。米游社不再注册；线索与 P0-02 登记作为历史证据保留 |
| 主方案 | §3.1 | 后三项的列表/正文方法为 `getAnnList/getAnnContent`，不得把列表展示时间当成活动时间 | 不变。同一响应的 `data.list` 与 `data.pic_list` 都读，不增加请求、参数或端点 |
| P0-02 登记 | `fixtures/sources/registry.draft.json` | 四个来源 | 文件不改（证据）。生产注册表按"登记减去已下线来源"逐字段核对 |
| 附录 A.1 | `SOURCE_LIMIT_PROFILE.responseCapsBytes` | 四个来源各一项 | 删除 `miyoushe-news`，其余不变：P0-02 观测的响应体积本来就含 `pic_list` |
| ADR-0013 | 年份参照第三级 | 来源载荷里的真实发布时间 | 规则不变；现役来源都不提供，只有历史版本可能带着 |

## 决策

1. **图文资讯目录纳入现有来源**：
   - 适配器读取列表与正文响应的 `data.pic_list`：列表是"分组 → `type_list[]` → `list[]`"三层，正文是扁平数组，条目字段与 `data.list` 相同；
   - 外部 ID 加前缀 `pic-`（`PIC_LIST_ID_PREFIX`），与 `data.list` 分开编号；文章身份仍是 `(source_id, external_id)`；
   - 标题去噪、完整性判定、抽取、AI 草稿和人工审核都沿用现有流程。没有标题、没有正文的纯图片条目照现有规则记"来源暂空"，不丢弃；
   - 不改响应上限、不改轮询节奏。
2. **米游社来源下线**：
   - 删除适配器、注册项、偏移量游标与轮询批次、"仅列表"能力位、正文通道不可用的抓取分支、响应上限参数与管理端标签；
   - 库里的来源行、历史文章与轮询待办保留：文章外键指向来源行，不代清理生产。注册表新增已下线名单 `RETIRED_SOURCE_IDS`：
     - 轮询待办直接结束，记 `source_retired`，不再续排；
     - 公开状态不列已下线来源；
     - 读取其历史文章即报"来源已下线"，管线按终止处理不重试，不能再用于抽取、审核或发布；
   - 既不在注册表、也不在下线名单的来源 ID 仍按数据错误处理；
   - 通用规则保留：完整性状态 `gap-channel-unavailable`、公开状态对 `maintenance-required-list-only` 的映射、日历来源筛选的可选字段 `contentChannelDisabled`。它们描述历史数据或通用能力，现役来源不再产生；
   - P0-02 的米游社登记、样本与探针保留为历史证据，生产代码和测试不再引用。
3. **口径不变（所有者确认）**：
   - "卡池"按提示词 `draft-prompt-v2` 包括"自选、装扮等抽取类卡池"；
   - 已发布事件不随版本时间表或年份补全自动改动，需要时走更正流程。

## 价值

- 崩铁跃迁、绝区零调频进入审核与日程，卡池提醒不再只对原神可用；只在图文资讯里发布的活动公告也能收录。
- 撞号的两篇公告不会被当成同一篇的不同版本。
- 删去一条永远产不出可批准条目的来源，以及约一千行专用代码与测试；管理端不再出现无用的开关。

## 成本

- 不需要迁移，不新增请求、参数、端点或计费项。
- 部署后第一次轮询，两个游戏现存的图文资讯条目（当天各 9 条）作为新文章入库，产生待审候选，模型开关打开时还会起草。之后只有新增或变化的条目入账。这不是首轮补录，批准后照常发新事件通知（目前未开放注册，没有接收者）。
- 米游社的已有数据不删，占少量存储。

## 安全影响

- 读的是同一官方响应里的另一个字段：主机、路径、参数和请求次数都不变。图文资讯条目的 `href`、`img`、内嵌图集等跳转字段不进入条目（字段白名单测试覆盖）。
- 下线来源的主机从注册表移除，不再发出任何请求。
- 已下线来源的历史文章读取即终止，不能借旧数据发布。

## 预算与容量影响

- 每批仍是列表与正文各一次请求，响应体积不变；等式 `max(responseCapsBytes) <= responseCapCeilingBytes` 仍成立。
- AI 草稿：图文资讯按版本周期更新，当天两个游戏合计 18 条在列。草稿用量仍受 `AI_SOFT_DAY` 日上限约束。

## 回退

- 图文资讯：还原适配器即可。已入库的 `pic-` 文章保留，可在审核里驳回，不影响 `data.list` 条目。
- 米游社：恢复代码与注册项后，库里的来源行与水位还在；但已结束的轮询待办不会被 watchdog 复活（补排用 `ON CONFLICT DO NOTHING`），需要把该待办改回 pending 或删除后由 watchdog 重建。

## 备选方案

1. **按 P0 流程把 `pic_list` 登记为新来源**：同一请求同一响应，没有新的连通性或访问控制问题。所有者决定作为现有来源的扩展。
2. **外部 ID 不加前缀，改用（目录, `ann_id`）复合键**：要改文章身份与表结构。前缀让 `(source_id, external_id)` 保持不变。
3. **删除库里的米游社数据**：文章外键指向来源行，删除要级联且不可逆。保留数据、在代码层隔离。
4. **保留米游社代码、默认关闭**：仍是一条永远不能批准的来源，维护成本和误开风险都在。

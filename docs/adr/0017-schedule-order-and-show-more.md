# ADR-0017：日程从上到下按时间先后；时间范围收进「筛选」；末行「显示更多」逐档续读

- **状态**：已接受（F1-08 实施）
- **日期**：2026-10-05
- **提出者**：所有者（看 PR #98 后提出 5 条）
- **需要所有者批准**：是，已批准。所有者 2026-10-05 原话：
  1. 所有的日期从上到下都是日期从小到大，从开始到结束；
  2. "已显示完当前范围"改为具体的筛选，比如"已显示完近7天"；
  3. "正在加载日程"往上面放，现在看不到；
  4. 上面的日期筛选放入更多筛选菜单，并更名为"筛选"；
  5. 时间线最下边"已显示完近7天"那行加"显示更多"按钮，点一次加大一个筛选档位（3 天变 7 天、7 天变 30 天等），页面不要全部刷新，而是接着从该行出现后续的日程。
- **与已有 ADR / 决定的关系**：改变 D1′ 中昨天带的位置（见"受影响的合同"）；ADR-0015 的时间轴、待定折叠等其余部分不变。

## 背景

线上与本地核对时发现几处顺序问题：

- 首页"回看昨天"按 D1′ 放在列表最下方，排在今天和以后的日期下面。
- "时间待定"按节点身份排序，同一活动的"结束"可能在"开始"之前。
- "近期重要变更"按变更保留期倒序排列。
- 详情页"完整时间线"按接口的 milestone 顺序显示，出现过"活动结束"排在"活动开始"之前。例如「无神怜爱的冻土」的开始写着"7.0版本更新后"，时间未定，结束有明确时刻。

"正在加载日程…"放在时间线末尾，列表一长就看不到。

公开分页按节点身份排序而不是按时间（P3-14），浏览窗口都从今天起（D1′），大档包含小档。

## 受影响的合同

| 文档 | 章节 | 现有规定 | 本 ADR |
| --- | --- | --- | --- |
| 前端 | §4.1 页面骨架 | 筛选行"游戏选择 时间范围 临近截止 更多筛选"；末尾"继续加载 / 已显示完当前范围" | 筛选行改为"游戏选择 临近截止 筛选"，时间范围在「筛选」弹层里，按钮上写明当前档位；末行写"已显示完{档位}"并提供"显示更多" |
| 前端 | §4.2 筛选 | 事件类型、节点类型等低频筛选放入"更多筛选"，折叠后仍显示已选摘要 | 弹层更名"筛选"，时间范围放在最上面；折叠后按钮显示当前档位与低频筛选计数。"清除这些条件"一并恢复默认档位 |
| 前端 | §4.3 条目与排序 | 精确节点按时间排序，同时间按稳定身份；未知日期节点放在独立区域，不编造排序日期 | 不变，补充"从开始到结束"：同时间按开始 → 阶段 → 结束 → 奖励截止；未知日期节点仍不编造日期，只决定先后位置——未知的开始排在最前、未知的结束类排在最后 |
| F1-02 卡 | D1′ 昨天带 | "列表最下方固定附加一条'昨天'分组……排在最下方而非顶部，是为了不让已过去的内容占据首屏的黄金位置" | 昨天带移到时间线顶部（标题之下、今天之上），仍默认折叠，折叠时只占一行 |

业务枚举、窗口档位与默认档、公开接口、提醒与日历语义都不变。

## 决策

1. **顺序**：contracts 新增 `compareScheduleNodes`，作为唯一的先后规则：
   - 有日期的按日期升序；同一天精确时刻在前（按时刻），只有日期的在后；
   - 时间未知的开始节点排在最前，结束类（结束、预计结束、实际结束、奖励截止）排在最后，阶段解锁在两者之间；
   - 同一位置按开始 → 阶段 → 结束 → 预计结束 → 实际结束 → 奖励截止，再按稳定身份。

   比较键是一组有序字段，结果确定。使用它的地方：
   - 首页的按日分组、时间待定、近期重要变更；
   - 详情页的完整时间线；
   - 详情页的变更记录跟随时间线的顺序。

   首页时间线的版面改为：标题 → 回看昨天 → 当前范围逐日 → 末行 → 时间待定。
2. **末行**：写明已显示到哪一档："已显示完今天 / 近3天 / 近7天 / 近30天"，"全部"写"已显示完全部日程"。读屏播报同一句。
3. **加载提示**：首次加载、续页与"显示更多"的提示都放在时间线标题行（"正在加载日程…" / "正在加载近7天…"）。首次加载和续页期间不显示末行。
4. **筛选**：
   - 时间范围的分段控件移入弹层最上方，弹层更名"筛选"；
   - 按钮上始终显示当前档位，窄屏也显示；
   - "试试下一档"之后，焦点落到这个按钮上。
5. **显示更多**：
   - 末行按钮读取下一档：今天 → 近3天 → 近7天 → 近30天 → 全部。地址与按钮上的档位立即改为下一档；
   - 已显示的条目保留，下一档在后台读完全部分页后整体换上。逐页替换会让已显示的条目先消失，因为分页按身份而不是时间；
   - 换上时以列表最后一天为锚保持视口：上方区块（即将截止、过期提示）变高也不跳，新日期出现在原末行的位置；
   - 读取期间按钮保留、标为不可用（焦点不丢）；
   - 读取失败时保留已显示的条目，末行给出原因与重试；
   - 到"全部"后不再提供按钮，焦点留在末行；
   - 只重读日程，不重读目录与状态；
   - 当前范围为空时，空态已有"试试下一档"，末行不再重复按钮。

## 价值

- 首页、详情页从上到下都按时间先后读，同一活动先开始后结束。
- 列表很长时也能看到正在加载。
- 末行说清已经看到哪一档，想看更远不必回到顶部改筛选，页面不闪不跳。
- 筛选栏只留高频项，单行更宽松。

## 成本

- 不需要迁移，不改公开接口、参数或 Worker 行为。
- "显示更多"每次重读下一档的全部分页（大档包含小档），读量与直接选该档相同。
- 昨天带在顶部多占一行（折叠时约 44 px）。

## 安全影响

- 只改网页呈现与 contracts 中的纯函数排序，不涉及身份、凭据或私人数据。
- 地址里的 `range` 仍按白名单解析，"显示更多"只在首页档位之间前进。

## 预算与容量影响

无新增。公开读取仍是 `no-cache`。"显示更多"的请求次数等于用户逐档切换范围。

## 回退

还原网页与 contracts 中的排序即可，没有不可逆的数据。昨天带回到底部需同时回退 D1′ 的这一条。

## 备选方案

1. **"显示更多"只请求新增的那几天**：公开接口没有"从某天起"的参数，加参数要改接口合同与读量基准。大档包含小档，重读整档最简单。
2. **逐页替换、边读边显示**：分页按身份排序，第一页可能不含已显示的条目，会出现条目先消失再回来。不采用。
3. **昨天带保留在底部**：与"从上到下按时间先后"冲突。改为顶部、默认折叠，兼顾 D1′ 不占首屏的初衷。
4. **时间待定按活动分组**：活动之间没有可比的日期，分组顺序仍是任意的。统一用同一条先后规则更一致。

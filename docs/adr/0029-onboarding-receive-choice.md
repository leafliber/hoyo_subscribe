# ADR-0029：登录后引导的第 2 步改为"选择接收方式"——浏览器通知、日历订阅、邮件通知任选一种，推荐前两项

- **状态**：已接受（所有者 2026-10-07 提出）
- **日期**：2026-10-07
- **提出者**：所有者。原话："登陆后第二步不是'添加到日历'，而是浏览器、日历和邮件三选一（推荐浏览器和日历），帮我优化界面"。
- **需要所有者批准**：是，已由所有者提出。不涉及收费、供应商或权限扩大。
- **与已有 ADR 的关系**：修改 ADR-0026 决策 2 的引导第 2 步（"添加到日历"）。ADR-0026 的其余内容（恢复码可选、两个标签页）不变。

## 背景

ADR-0026 把「我的订阅」的引导缩成两步：保存订阅内容 → 添加到日历。第 2 步只有一个"去添加到日历"按钮，只有日历订阅启用后才算完成。

2026-10-07 正式站点的公开能力是：日历 `open`、浏览器通知 `open`、邮件新席位 `closed`。浏览器通知已经可用，引导却只指向日历。用户只想要浏览器通知时，引导一直停在第 2 步不消失。

合同原文：

- 前端 §7.1 主流程（ADR-0026 修订后）："保存订阅 → 启用日历"；"邮件与 Push 不附带开启"。
- 前端 §9 开头："未开放的 Push 不占据主流程"。
- 前端 §9.3："用户主动点击前，不申请系统权限、不创建 Push 绑定、不发送测试"。
- 前端 §9.4："同时使用日历、邮件和 Push 时可能重复提醒"。

## 受影响的合同

| 文档 | 章节 | 现有规定（含 ADR-0026） | 本 ADR |
| --- | --- | --- | --- |
| 前端 | §7.1 主流程 | 保存订阅 → 启用日历 | 保存订阅 → **选择一种接收方式**（浏览器通知、日历订阅、邮件通知），任一种开启即完成引导 |
| 前端 | §6.1 页面结构 | 引导两步：保存订阅内容 → 添加到日历 | 第 2 步为"选择接收方式"，下方列出三个入口，浏览器通知与日历订阅标"推荐" |

§9 各通道卡片本身、Push 未开放时不占主流程、点击前不申请权限、邮件与 Push 不附带开启，都不变。

## 决策

1. **第 2 步**改名"选择接收方式"，说明"浏览器通知、日历订阅、邮件通知，任选一种"。保存订阅后、该步为当前步时，在步骤下方列出三个入口，顺序为浏览器通知、日历订阅、邮件通知；前两项标"推荐"。原"去添加到日历"按钮删除。
2. **入口只跳转**：点击后切到「接收方式」标签页，定位到对应卡片，卡片加高亮边框。不开启任何通道，不申请浏览器权限，开启仍在各卡片里由用户确认（§7.1、§9.3 不变）。
3. **按公开能力（`/api/v2/status`）显示**：
   - Push 不是 `open` 时不列浏览器通知入口（§9"未开放的 Push 不占据主流程"）；
   - 浏览器不支持通知时，入口置灰并写"当前浏览器不支持通知"；iPhone、iPad 未从主屏幕打开时提示先添加到主屏幕；
   - 日历为 `closed` 时置灰并写"暂未开放"；邮件新席位为 `closed` 时置灰并写"暂未开放新的邮件名额"；
   - `unknown` 不当作不可用，入口照常可点，卡片里有准确状态。
4. **完成条件**：日历订阅地址已启用、邮件席位已开启、或账号下有一个验证通过的浏览器，任一成立即完成，引导隐藏。页面加载时按账号摘要（`/api/v2/me` 的邮件与 Push 计数）判断；各卡片读到或改变状态时通知引导，在本页开启后引导立即完成。
5. **文案**：页首说明改为"选好关注的游戏和提醒，再选择用浏览器通知、日历或邮件接收"；「接收方式」标签说明改为"浏览器通知、日历订阅和邮件"；入口下方写明"任选一种就能用，之后可以在「接收方式」里增加或关闭；同时开启几种可能收到重复提醒"（§9.4）。
6. **不改**「接收方式」标签页里三张卡片的版式与顺序，也不改任何通道的服务端规则。

## 价值

- 只想用浏览器通知的用户，开启后引导就完成，不会一直被要求"添加到日历"。
- 新用户在一屏内看到三种接收方式和各自是否可用。邮件名额关闭时，入口直接写明原因，不用点进去才发现。

## 成本

- 纯前端：引导标记与样式、一个呈现入口的小模块（`features/subscription/receive-choice.ts`），邮件与 Push 卡片各加一个状态回调。无接口、无迁移、无参数。
- 引导在第 2 步时多读一次公开的 `/api/v2/status`（每页一次；Push 卡片本来也读）。

## 安全影响

- 没有新的写操作或权限申请：入口是页内锚点；状态回调只在页面内传递布尔值，并沿用各卡片已有的身份核对，旧身份卡片的迟到结果不会更新引导。
- 公开能力读取不带 Cookie（`credentials: "omit"`）。

## 预算与容量影响

无。不改变邮件席位、Push 外发预算或日历容量；入口不开启任何通道。

## 回退

恢复 ADR-0026 的"添加到日历"一步与按钮即可，纯前端，无数据影响。

## 备选方案

- **入口直接开启通道**（例如点"浏览器通知"就申请权限）：违反 §9.3"用户主动点击前不申请系统权限"的本意（点的是选择，不是"在当前浏览器开启通知"），也绕过各卡片的状态与说明。不采用。
- **只推荐日历**：所有者要求浏览器通知与日历都推荐。不采用。
- **Push 未开放时也列出入口并写"暂未开放"**：违反 §9"未开放的 Push 不占据主流程"。不采用。
- **按「接收方式」标签页的卡片顺序重排**：标签页仍按"日历为主通道"排版（主方案的通道定位未变），本 ADR 只改引导。

## 待确认

- 浏览器通知的真实客户端取证（P6-03）尚无记录。引导把它标为"推荐"是所有者的决定；卡片里"激活通过也不承诺以后每条都送达"的说明照旧。
- 日历订阅的客户端说法超出实测是已登记的已知问题（修正卡 F3-06 暂不派发）。本 ADR 的入口文案只写"添加到日历应用、自动同步"，不声称提醒可用。

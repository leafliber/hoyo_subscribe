# ADR-0018：管理端增加「跳过审核」开关，开启后通过全部检查的 AI 草稿由系统批准发布

- **状态**：已接受（P3-25 实施）
- **日期**：2026-10-06
- **提出者**：所有者
- **需要所有者批准**：是，已批准。所有者 2026-10-06 原话："后台增加一个选择，跳过审核，默认关闭，可以直接免审核直接发布"。
- **与已有 ADR / 决定的关系**：
  - ADR-0009 规定"草稿不自动发布"。本 ADR 不改它的默认状态：开关默认关闭，关闭时一切照旧。
  - BUILD_PLAN 记载"模型候选自动发布是第二步，须另立 ADR 并通过 P0-03b"。本 ADR 就是这份另立的 ADR。
  - **P0-03b（120 篇人工标注的质量评估）没有做。** 所有者打开开关，即表示接受 AI 草稿在没有质量评估、没有人工核对的情况下直接上线。

## 背景

- 主方案 §3.4 设计了三条发布路径：规则模板、批准的模型 profile、人工审核。原文："候选 → 统一来源/证据/时间校验 → 原子发布"。
- 自动发布原来只开给规则白名单。原文："只有明确事件类别、完整时间和区域均有证据的白名单模式可自动发布，模板不匹配就审核"。
- 现状：AI 草稿（ADR-0009/0010）只预填，必须人工点「采用草稿并批准」。
- 2026-10-06，图文资讯目录接入后，首批 18 条待审全部要人工逐条处理。所有者希望在自己认为合适的时候免去这一步。

## 受影响的合同

| 文档 | 章节 | 现有规定 | 本 ADR |
| --- | --- | --- | --- |
| 主方案 | §3.4 | 自动发布只对已通过测试的规则白名单模板；模型路径需"批准的模型 profile"（P0 质量与费用测试） | 增加一个默认关闭的开关。开启时，AI 草稿通过下文全部检查后，由系统批准为**模型抽取路径**的候选，再按原有统一校验与原子发布上线 |
| 主方案 | §10.1 观测与开关 | "独立开关覆盖注册、新邮件名额、常规提醒邮件层、业务邮件、全部外发、Push、模型、自动发布……" | 新增 `review_skip_enabled`（"跳过审核"）。只在 AI 草稿可用（外发总闸开、非只读、模型开关开）时生效 |
| ADR-0009 | 决策 | 草稿不自动发布 | 开关关闭时不变；开启时按本 ADR |
| BUILD_PLAN | G-P0-MODEL / P3-09 | 模型候选自动发布须通过 P0-03b | 所有者决定不等 P0-03b，以开关形式提供，由所有者自行决定何时打开 |

## 决策

1. **开关**：
   - 新增运行开关 `review_skip_enabled`，管理端显示为「跳过审核」，放在「数据管线」组。
   - 默认关闭。首次部署之后才加的开关没有初始化行：合同里登记默认值 `false`，没有这一行时读作关闭。读取出错仍是"未知"。
   - 管理端据此显示"关"，开启时以版本 0 写入首行；服务端条件写入挡住覆盖已有行。
   - 开关写入沿用现有流程：需要管理员会话、绑定 CSRF、选择理由、页面内二次确认，并写入审计。
2. **只作用于新草稿**：草稿待办写好一份新草稿时，若开关开启，系统立即检查并决定是否批准。开启前已在队列里的条目不受影响，仍由人工处理。
3. **系统只批准，不直接发布**：
   - 批准的含义：把规则入队的 pending 候选，改为挂在一条模型抽取运行上（`extractor = 'model'`，profile 即草稿 profile）的已批准候选。审核者记为 `system:review_skip`，并写入系统审计。
   - 发布交给原有的发布待办：候选更新后，巡检唤醒停放的待办。只读模式、非关键发布暂停、版本推导过期、人工锁等检查全部照旧。
   - 发布待办重抽时，按"人工 > 模型 > 规则"取同一条候选，不会另建待审候选。
4. **发布不加人工锁**：模型路径发布的事件与节点 `human_locked = 0`，修订记录的发布路径为 `model`。之后官方改了公告、出了新草稿，可以继续自动更新；人工更正（correct）、撤回（retract）照常可用。人工一旦裁定，就加锁，之后自动路径遇锁只留给人工。
5. **以下情况一律留给人工**，候选原样留在审核队列：
   - 草稿分类为"不确定"，或带有歧义；
   - 任一节点时间未定（例如"X.Y版本更新后"而版本时间没有确认）；
   - 统一校验、版本推导一致性或文本长度检查没过；
   - 目标事件或其任一节点已被人工锁定；
   - **疑似重复**：同一游戏、同一区域里，已发布且未撤回的别篇公告事件，标题比较键相同、日期范围有交叠。比较键的算法：全角半角统一，去掉空白、标点与符号，再去掉结尾的"活动""活动说明"。2026-10-06 首批图文资讯 18 条里有 8 条是版本公告已收录活动的说明，事件身份按文章区分，不拦就会各发一份。
     - 主方案 §3.6 原文："标题相似不足以自动合并"。这里只用标题拦下来交给人工，从不据此合并或建立关联；
   - 人工已接手（候选已被修正为人工候选）或已经裁定。
6. **无日程草稿**：草稿分类为"无日程"时，系统同样确认，与人工点「确认无日程」相同，不产生任何发布。

## 价值

所有者打开开关后，新公告不必逐条人工批准就能上线，审核队列只剩真正需要人看的条目：疑似重复、时间未定、有歧义、已人工锁定的。

## 成本

- 不需要迁移，不新增资源、供应商或付费项目。
- 模型调用次数不变：只对已经生成的草稿做检查，不额外调用模型。
- 每次检查多几次 D1 读取：校验、锁定检查、按日期范围查同游戏事件。量级与人工打开一条候选相当。

## 安全影响

- **主要风险是错误内容直接上线并通知用户**：
  - 草稿内容与原文不符、但通过了证据与时间校验时（例如事件类型或标题理解偏差），会直接出现在公开日程；
  - 订阅者的日历会随之更新，开启了新活动邮件的用户可能收到通知。
  - 这是所有者知情接受的风险：P0-03b 没有做。
- **缓解措施**：
  - 证据逐字核对与时间解析校验和人工批准时完全相同；
  - 时间未定、有歧义、疑似重复、遇人工锁定的一律留给人工；
  - 发布不加人工锁，人工可随时更正或撤回；
  - 每次系统批准都写入系统审计（`candidate_review_skip`）。
- **权限面不变**：模型仍然拿不到用户数据、秘密、网络或写库权限。批准由 Worker 内的确定性代码完成；开关只能由管理员带理由、经页面内确认后写入。

## 预算与容量影响

- 模型日预算不变：草稿本来就会生成，本 ADR 不增加调用。
- 四个邮件池的规则不变。自动发布的新事件与人工发布的一样，按原规则进入通知；数量取决于公告量，不另设额度。
- 不涉及 A.5 等式。

## 回退

- 关闭开关即停止自动批准，之后的新草稿回到人工审核。
- 已由系统批准、尚未发布的条目（最多一个巡检周期内的）关闭开关后仍会发布，可以人工撤回。
- 已发布的内容可以用更正或撤回处理。已同步到用户日历的变更与已发出的邮件不可撤销，撤回会按原规则再同步一次。
- 代码回退到合入前的提交即可。表结构没有变化，留下的模型抽取运行与系统审计行对旧代码无害。

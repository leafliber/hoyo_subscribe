# ADR-0026：恢复码改为可选、只在账号设置里管理；「我的订阅」按功能分成两个标签页

- **状态**：已接受（所有者 2026-10-07 提出）；代码在工作区完成，待验收与部署
- **日期**：2026-10-07
- **提出者**：所有者。原话："登陆后的体验不太好，因为操作复杂，且页面显示混乱……删除恢复码的强制性，只进入用户的设置页面；页面明确区各个功能；整体布局优化。"
- **需要所有者批准**：是，已由所有者提出。不涉及收费、供应商或权限扩大。
- **与已有 ADR / 决定的关系**：修改主方案 §4.6 首段与前端 §7.1、§7.3 的"首次开启长期通道前必须保存恢复码"；修改 D3 §2.6、§2.7、§2.8 里三个通道视图的恢复码事实；修改前端 §6.1 的页面结构示意与 §10.1 的账号页组织。§4.6 的恢复登录受限会话、紧急停用不消费恢复码、轮换须最近认证都不变。

## 背景

2026-10-07 所有者在已登录的正式站点上走了一遍登录后的流程。验收方在 Chrome 里复核，问题如下：

1. **恢复码是硬门槛。**「我的订阅」顶部是"三步完成订阅"，第 2 步"保存恢复码"要跳到恢复页 `/recover#save` 完成；不保存就不能启用日历订阅、邮件提醒和浏览器通知。服务端同样拒绝：`recovery_code_not_saved`（主方案 §4.6"首次开启长期 Feed、邮件或 Push 前要求完成保存确认"，前端 §7.3）。
2. **首次生成只有登录后 10 分钟的窗口。**普通会话只能在激活后 `RECENT_AUTH_TTL`（600 秒）内首次生成恢复码，过了就只能重新登录。这是把保存恢复码塞进登录后主流程的原因，也意味着恢复码一旦不强制、用户以后想补建就没有路径。
3. **一页塞了所有功能。**「我的订阅」从上到下是引导、四张内容设置卡、保存栏、导入导出、冲突比较、右侧日历预览，再往下是日历订阅、邮件通知、浏览器通知三张通道卡，功能之间没有分界。
4. **页面底部有约 7000px 空白。**日历预览列表里每条都带一段读屏文字（`.sr-only`，绝对定位）。预览的滚动容器不是定位祖先，这些元素逃出滚动区，按自身静态位置把整页撑长（正式站点实测 113 条时页面高 10820px，页脚在 3523px）。
5. **账号页条目让人困惑。**"账号与设备"的账号信息里有"邮件通知：未知"（从未开过邮件时摘要给 unknown）、"邮件名额租期：服务端未记录租期"等不适用的行；恢复码只能"管理恢复码"跳去恢复页。

## 受影响的合同

## 决策

1. **服务端**：日历启用与重置、邮件开启、Push 开启不再检查是否已保存恢复码；contracts 删去 `recovery_code_not_saved`（`UnauthorizedReason`、`ACTION_BLOCK_REASONS`、邮件与 Push 的受阻原因）以及三个通道视图里的 `recovery_code_saved`。`POST /api/v2/auth/recovery/code` 的 `generate` 接受可选 `proof_id`：会话不在最近激活窗口时，须是本会话未消费、未过期的 `recovery_code_rotate`/`current` 证明，生成与消费在同一条件提交里完成；已确认的码仍返回 409，只能轮换。
2. **我的订阅**：去掉恢复码步骤与"保存恢复码"按钮；分成「订阅内容」「接收方式」两个标签页，内容页有未保存修改时标签上显示"未保存"；预览滚动容器设为定位祖先，修掉底部空白。
3. **账号设置**：恢复码在本页创建（登录超过 `RECENT_AUTH_TTL` 时先验证当前邮箱，验证后自动继续）、确认保存、更换（沿用已有的两步轮换）。交付的明文只在页面内存，身份变化与离开页面即清除。
4. **恢复页**：只保留恢复登录、紧急停用，以及受限恢复会话的新码保存；原来给普通会话用的轮换区移到账号设置。

## 价值

- 新用户登录后两步就能用上日历（保存订阅 → 添加到日历），不再被迫先处理一个与订阅无关的凭证。
- 想要恢复码的人任何时候都能在账号设置里创建，不再只有登录后 10 分钟的窗口。
- 订阅内容与接收方式分开，每一屏只做一类事；页面不再有一大段空白。

## 成本

- 代码：contracts、Worker 三个通道服务与恢复码生成、网页三页与相关 E2E。无迁移，`sessions.recovery_code_required` 等列不变。
- 已上线用户：已保存的恢复码照常有效；没保存的不再被拦。旧链接 `/recover#save` 对普通会话转到账号设置。
- 部署：网页与 Worker 同一次部署，无迁移。日历、邮件、Push 视图删去了 `recovery_code_saved`，部署前已打开、未刷新的旧页面读到新视图时会把邮件或浏览器通知显示为"状态未知"，刷新即恢复。

## 安全影响

- **没有恢复码的账号增多。**这些账号的邮箱长期无法使用时，没有离线找回路径（只能等邮箱恢复，或在仍登录的设备上换邮箱）。所有者知情接受；账号设置的恢复码分区与帮助页写明这一后果。
- **会话被盗不能借此铸造恢复码。**首次创建仍要求最近激活或本会话的最近认证证明（当前邮箱验证码）；证明绑定会话、用途与目标摘要，单次消费；已确认的码只能轮换，不能经生成端点覆盖。与改动前相比，新增的只是"凭邮箱验证码在较老会话里首次创建"，强度与已有的轮换相同。
- **受限恢复会话不变。**恢复登录消费旧码后，新码确认前仍不能开通道、换邮箱（§7.4 的准入条件）；紧急停用仍不消费恢复码。
- 通道开启不再查恢复码，不改变 Feed token、退订 token、Push receipt 的授权范围。

## 预算与容量影响

无参数变化。恢复码首次创建如需邮箱验证，会走已有的认证邮件（auth 池）与最近认证限速，与轮换相同。

## 回退

恢复门槛：在 contracts 恢复 `recovery_code_not_saved` 与视图字段、在三个通道的写守卫里恢复 `recovery_credentials` 条件即可，无数据迁移。回退后，期间没有保存恢复码就开了通道的账号不会被关闭通道，只是之后新开通道会再被要求保存。标签页与账号设置的改动是纯前端，可单独回退。

## 备选方案

- **只去掉引导步骤、保留服务端门槛**：用户仍会在点"启用日历订阅"时被拦，问题没解决。
- **普通会话去掉最近认证，随时可首次生成**：会话被盗即可铸造恢复码并借它换邮箱接管账号，不采用。
- **恢复登录后也不再强制保存新码**：恢复登录是用户主动动用恢复码的场景，§7.4 把保存新码定为准入条件，防止"既无旧码也无新码"；所有者这次要求针对的是普通登录后的流程，保持不变。如需取消，另行决定。
- **把接收方式拆成独立页面或放进账号设置**：日历、邮件的开启依赖同页的草稿与保存状态（§8.4"保存后继续"），拆页要重写这部分协调；标签页保留同一页面与同一状态机。

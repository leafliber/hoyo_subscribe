# ADR-0033：来源开关没有记录时读作关闭；直播兑换码来源以自动发现为主、手动登记为备用

- **状态**：已接受（所有者 2026-10-08 提出）
- **日期**：2026-10-08
- **提出者**：所有者。原话："填写直播间ID是手动获取方案，正常是全自动获取，只需要开启开关即可，当前的开关无法开启，请帮我分析原因并修复"。
- **需要所有者批准**：是，已由所有者提出。改 contracts `OPERATIONAL_CONTROL_DEFAULTS`（运行开关的读取规则）；不涉及收费、供应商、权限或迁移。
- **与已有 ADR 的关系**：补充 ADR-0018（首次部署之后才加的开关读作关闭）到来源开关；落实 ADR-0030 的"管理员可登记直播链接兜底"在管理端的呈现。

## 背景

#104（ADR-0030）部署后，所有者在管理端「运行开关」页看到三个直播兑换码来源（`genshin-live`、`hsr-live`、`zzz-live`）都标"未知"，"开启"按钮点不了。

原因（按代码核对）：

- 来源开关存在 `system_state` 的 `source:<source_id>` 行里。三个公告来源的行是 2026-10-03 首次关闭门初始化时逐项写入的；直播兑换码来源是之后才登记的，没有行。
- `readControl` 查询成功但没有行时取 `OPERATIONAL_CONTROL_DEFAULTS[control]`，其中只有 `review_skip_enabled`（ADR-0018），没有 `source_enabled`，于是读作 `unknown`。
- 管理端对 `unknown` 的开关禁用"开启"按钮（读取出错时不能盲写）。服务端本身允许以 `expected_updated_at = 0` 写入第一行，但页面没有给出入口。

另外，原来的页面把"官方直播页链接或活动 ID"输入框与"登记"按钮直接摆在每个直播来源下面，读起来像必须手动填写。实际设计是：开关打开后，每次轮询从米游社首页自动发现前瞻直播并取码；登记只在首页没有放出直播入口时备用。

## 受影响的合同

| 文档 | 章节 | 现有规定 | 本 ADR |
| --- | --- | --- | --- |
| CONTRACTS_BASELINE | §13 运行开关，`source:<source_id>` 行 | 没有记录时"未知 → 关闭" | 没有记录时**合同默认 false**（`OPERATIONAL_CONTROL_DEFAULTS`）；读取出错仍是未知 |
| 主方案 | §10.1 观测与开关 | 开关值只接受 JSON boolean；默认值只能是 false | 不变：新增的默认值同样是 false，不借默认值打开任何能力 |

## 决策

1. contracts `OPERATIONAL_CONTROL_DEFAULTS` 增加 `source_enabled: false`：任一来源的开关没有记录时读作关闭、版本 0；管理端因此显示"关"并允许以版本 0 写入第一行（服务端条件写入照旧挡住覆盖已有行）。读取出错仍是 `unknown`，"开启"仍不可点。
2. 全局开关（外发总闸、注册、只读等）没有记录时仍是未知：它们必须在首次关闭门初始化时逐项写入，不改。
3. 管线照旧只在值为 `true` 时抓取（还要求外发总闸开、只读关）；没有记录与 `false` 一样不抓取。打开开关后，下一轮管线自动建立来源行与抓取任务，不需要其他操作。
4. 管理端直播兑换码来源的呈现：
   - 说明改为"开启后全自动：每次轮询从米游社首页发现前瞻直播，读取官方直播页的兑换码……正常情况下不需要手动登记"；
   - "正在跟踪的直播：暂无"后注明"开启后自动从米游社首页发现"（已开启时为"每次轮询自动……"）；
   - 登记表单收进默认收起的"备用：手动登记直播"，展开后说明何时使用（官方已公布直播、但开启后一直没有出现在"正在跟踪的直播"里），重绘后保持展开状态。
5. 顺带：说明文字较长时，开关按钮不再被挤成竖排（"开/启"）。

## 价值

- 部署后直接在「运行开关」页打开三个直播来源即可开始自动采集，不需要先手工写库或登记直播。
- 页面写清楚自动是常态、登记是备用，不再误导为必须手动填写。

## 成本

contracts 一行默认值、管理端一处呈现与样式；无迁移、无参数、无新接口。

## 安全影响

默认值是 false，只让"没有记录"从"未知"变为"关闭"，不打开任何能力；写入仍要求管理员会话、绑定 CSRF、理由与条件写入，并写审计。

## 预算与容量影响

无。打开直播来源后的请求量见 ADR-0030（`REDEEM_LIVE_TRACK_MAX`、轮询策略不变）。

## 回退

还原本 ADR 的提交即可：没有记录的来源开关重新读作未知。已经写入的开关行不受影响。

## 备选方案

- **迁移里为新来源补写 `false` 行**：每加一个来源都要配一条迁移，且要求迁移知道来源注册表；默认值规则一次覆盖以后所有新来源。不采用。
- **管理端对"未知"也允许开启**：读取出错时也会放开按钮，可能在状态不明时盲写。不采用。

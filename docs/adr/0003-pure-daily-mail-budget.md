# ADR-0003：邮件预算改为纯日额度模型；取消月度池、envelope 与 carry

- **状态**：已接受
- **日期**：2026-09-22
- **提出者**：所有者决定（"月度池连产品意义都不需要"），验收方执行
- **需要所有者批准**：是 —— **已批准**
- **取代**：ADR-0002（其"固定 UTC 自然月"的折中不再需要）

## 背景

ADR-0002 处理的是"账单周期不存在 → envelope 的分母 `D` 未定义"，当时采取了保守折中：
把周期改成固定 UTC 自然月，保留月度池与 envelope，理由是它们"保护产品承诺而非账单"。

ADR-0002 自己写明了这个取舍待定：

> 如果所有者认为月度池连产品意义也不需要，那是一个更彻底的简化……
> **那应当是一份单独的 ADR**，需要先回答「内测期要不要自我限速」这个产品问题。

所有者 2026-09-22 给出了答案：**不需要**。本 ADR 执行该决定。

## 决策

**邮件预算改为纯日额度模型。**每个 UTC 日独立，不跨日结转，不存在月度维度。

### 删除

| 项 | 原值 |
| --- | --- |
| `MAIL_TOTAL_MONTH` | 2,700 |
| `MAIL_EXISTING_AUTH_MONTH` | 1,000 |
| `MAIL_SIGNUP_AUTH_MONTH` | 300 |
| `MAIL_BASE_MONTH` | 700 |
| `MAIL_URGENT_MONTH` | 700 |
| §9.2 的 envelope 公式、`carry`、`E = 1` 兜底 | — |
| §9.2 的认证软线 `S = 剩余月额 / 剩余片段数` | — |
| §9.2 的"月末半日片段"处理 | — |

### 变更

| 参数 | 原值 | 新值 | 理由 |
| --- | --- | --- | --- |
| `MAIL_SEATS_MAX` | 50 | **100** | 所有者决定；平台侧 1,000/日 完全容得下 |
| `MAIL_ROUTINE_SEATS_MAX` | 20 | **40** | 所有者决定一起放大（修订一） |
| `MAIL_BASE_DAY` | 25 | **50** | 随子名额抬高，保留 1.25x 重试余量（修订一） |
| `MAIL_URGENT_DAY` | 60 | **120** | 必须满足"一次官方取消当天覆盖全部席位"+ 留出 floor，见下 |
| `MAIL_TOTAL_DAY` | 175 | **260** | = 90 + 50 + 120 |
| `MAIL_AUTH_FLOOR` | 200（月） | **20（日）** | 口径从月改日，保留同一档降级行为 |
| `MAIL_URGENT_FLOOR` | 150（月） | **20（日）** | 同上 |

### 新增

| 参数 | 值 | 说明 |
| --- | --- | --- |
| `PLATFORM_MAIL_DAY_LIMIT` | **1,000** | 实测值（`GET /accounts/{id}/email/sending/limits`）。随平台变动须重跑 `params:verify` |

### 不变

`MAIL_AUTH_DAY = 90`、`MAIL_SIGNUP_AUTH_DAY = 10`、
`MAIL_USER_BASE_DAY = 1`、`MAIL_USER_URGENT_DAY = 2`、
`MAIL_SEAT_LEASE = 90 天`、`MAIL_DIGEST_WINDOW = 600 秒`。

**优先级阶梯、四池划分、同批次合并、公平游标、两层邮件同意全部不变。**

## `MAIL_URGENT_DAY` 为什么必须跟着动

§9.1 要求「一次官方取消需要当天覆盖全部席位」。席位从 50 涨到 100，`MAIL_URGENT_DAY = 60`
立刻不够——一次取消只能通知到 60 个人，剩下 40 个收不到，**而取消正是邮件唯一不可替代的价值**。

同时 `MAIL_URGENT_FLOOR` 需要真正起作用：如果 `MAIL_URGENT_DAY` 恰好等于 `MAIL_SEATS_MAX`，
一次全量取消就把当天打空，floor 永远来不及触发。所以：

```text
MAIL_URGENT_DAY >= MAIL_SEATS_MAX + MAIL_URGENT_FLOOR
120             >= 100            + 20                ✅（取等号）
```

这样一次全量取消之后当天还剩 20 封，恰好落到 floor 上，自动收紧为只发取消/撤回——
**降级行为在日模型下依然成立**。

## 新的日额度模型

```text
每个 UTC 日开始时，三个池各自重置为固定日额度：
  认证池 MAIL_AUTH_DAY = 90       （其中新注册子额度 MAIL_SIGNUP_AUTH_DAY = 10）
  基础池 MAIL_BASE_DAY = 50
  紧急池 MAIL_URGENT_DAY = 120

池之间不互借。当日用尽即当日停发，次日自动恢复。

降级（口径从"月剩余"改为"当日剩余"，行为不变）：
  当日紧急池剩余 < MAIL_URGENT_FLOOR(20)
    → 收紧为只发取消/撤回这一最高档
  当日认证池剩余 < MAIL_AUTH_FLOOR(20)
    → 只接受既有账号的首次登录意图；暂停新注册发信与全部重发；页面标示认证降级
```

**恢复入口仍然不依赖发信预算**（§9.2）——认证降级期间用户取回控制权的唯一保障，不变。

## 价值

1. **删掉了一套没有约束对象的机制。**平台不按月计量，月度池保护的是一个不存在的稀缺资源。
2. **跨日保护反而更强。**月度模型下，几天的异常流量能烧掉整月的登录能力，`MAIL_AUTH_FLOOR`
   触发后要等到下个月才恢复。日模型下最坏情况只影响当天，**次日自动恢复**。
3. **可实现性。**`carry` 持久化、月末半日片段、跨账单周期的预留释放与重新预占——
   这些是 §9.2 里最容易写错的部分，现在整块消失。
4. 席位与常规子名额双双翻倍，`MAIL_TOTAL_DAY = 260` 仍只占平台日上限的 26%。

## 成本

**必须诚实记下丢失的能力：跨日结转没有了。**

月度模型里，某天没发满的额度通过 `carry` 留到后面用。日模型下今天没用完就是没用完。
对基础池（常规提醒，价值低、可丢弃）影响可忽略；对紧急池的影响是：
**连续两天各有一次全量取消，两天都能覆盖；但一天内发生两次全量取消，第二次只能覆盖 20 个席位。**

这个场景的概率与后果由所有者接受：同一天两次官方取消在本产品的事实模型里极罕见，
且第二次取消的用户会在日历里看到 CANCELLED 条目（VALARM 通道不受邮件预算约束）。

## 安全影响

无新增攻击路径。`MAIL_AUTH_FLOOR` 的保护语义不变，仅口径从月改日——
**且如上所述，日口径下的恢复速度更快，抗持续消耗的能力更强**。

## 预算与容量影响

| 项 | 值 | 校验 |
| --- | --- | --- |
| `MAIL_TOTAL_DAY` | 260 | ≤ `PLATFORM_MAIL_DAY_LIMIT` 1,000 ✅（占 26%） |
| 基础池容量 | `MAIL_BASE_DAY 50 >= MAIL_ROUTINE_SEATS_MAX 40 × MAIL_USER_BASE_DAY 1` | ✅（1.25x 重试余量） |
| 紧急池容量 | `MAIL_URGENT_DAY 120 >= MAIL_SEATS_MAX 100 + MAIL_URGENT_FLOOR 20` | ✅（取等号） |
| 认证量估算（§9.3） | 500 账号 × 2 设备 × 30 / `SESSION_IDLE_TTL` 90 ≈ 11 封/日 | ≤ `MAIL_AUTH_DAY` 90 ✅（余量 8 倍） |

**修订一（2026-09-22，所有者决定）**：`MAIL_ROUTINE_SEATS_MAX` 一并放大至 **40**，
`MAIL_BASE_DAY` 同步抬至 **50**。

`MAIL_BASE_DAY` 取 50 而非刚好够用的 40，是因为 §9.1 规定**重发与明确失败后的新调用也占各自用途预算**：
卡在 40 的话，一次投递失败就会挤掉一个用户当天的发送机会。50 保留了原设计 25/20 = 1.25 的重试余量。

§7.5「常规提醒邮件默认关闭」的论证**不受影响**——放大的是愿意显式开启的用户上限，
默认值仍是关闭，理由（对已启用日历提醒的用户是重复通知）依然成立。

## 回退

改回参数值与 A.5 等式即可。本 ADR 在 P1-03 实现参数注册表**之前**落地，无代码依赖旧模型，
无数据迁移。`usage_periods` 表的 `envelope` / `carry` 列由 P1-04 建表时直接不建。

## 备选方案

| 方案 | 为何未采用 |
| --- | --- |
| 维持 ADR-0002 的自然月折中 | 所有者明确月度池无产品意义；保留等于维护一套没有约束对象的机制 |
| 席位涨到 100 但 `MAIL_URGENT_DAY` 不动 | 一次官方取消只能覆盖 60/100 席位，违反 §9.1 |
| 同时把 `MAIL_ROUTINE_SEATS_MAX` 放大 | 超出所有者本次决定；且与 §7.5「常规提醒邮件多为重复通知」的论证相悖 |

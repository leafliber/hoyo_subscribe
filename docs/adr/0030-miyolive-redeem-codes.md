# ADR-0030：米游社直播兑换码——新来源、「兑换码」事件类型与首页「有效兑换码」条

> 第 3、4、5、6 条被 [ADR-0034](0034-redeem-expiry-and-status-checks.md) 修订：取到兑换码才进日程；管理员可照官方说明登记截止时间；直播收尾后有截止时间的不再请求、没有的按北京时间整点核对；取消 24 小时显示上限（`REDEEM_CODE_UNDATED_DISPLAY` 删除）；首页没有截止时间时写"请尽快兑换"。其余不变。

- **状态**：已接受（所有者 2026-10-07 提出）
- **日期**：2026-10-07
- **提出者**：所有者。原话："增加一个bar，有效兑换码，当有兑换码生效的时候显示，来源为米游社官方的接口，兑换码事件的开始和过期加入日历"；来源线索："米游社官方直播接口 miyolive：官方直播页通过活动 ID 获取 code_ver，再用 refreshCode 读取 code_list……最优先验证的自动采集候选。活动发现和直播期间取码还需实测"。
- **需要所有者批准**：是，已由所有者提出。不新增供应商、收费项或权限；**含一次破坏性迁移**（重建 `events` 表以扩充 CHECK 约束，见"成本"与"回退"），应用前按备份手册先做备份。

## 背景

- 主方案 §1.1 的内容范围是前瞻、维护、限时活动、卡池；§3.3 事件类型只有 `livestream / maintenance / limited_event / gacha`。兑换码不在任何类型里。
- §3.1 来源适配只登记游戏内公告（ADR-0016 后）。米游社官方资讯因正文接口 403 下线（ADR-0016），与本 ADR 用到的接口不同。
- 2026-10-07 实测（详见 [`docs/evidence/p3/miyolive-redeem-codes.md`](../evidence/p3/miyolive-redeem-codes.md)）：
  - 米游社官方直播页（`webstatic.mihoyo.com/bbs/event/live/index.html?act_id=…`）的公开脚本调用两个接口：`api-takumi.mihoyo.com/event/miyolive/index`（请求头 `x-rpc-act_id`，返回直播标题、`code_ver` 与页面模板）、`api-takumi-static.mihoyo.com/event/miyolive/refreshCode?version=<code_ver>&time=<按 20 秒取整的秒数>`（返回 `code_list`：`code`、奖励说明 `title`、发放时刻 `to_get_time`；未到发放时刻的 `code` 为空）。兑换码有效期只出现在页面模板的说明文字 `codeTipText` 里，没有结构化字段。
  - 不存在或已结束的活动，两个接口都返回 `retcode -500012`"活动已结束"。
  - 米游社三个游戏的首页接口（`bbs-api.miyoushe.com/apihub/api/home/new?gids=2/6/8`）匿名可读，响应里有直播卡片 `lives`、导航 `navigator` 与轮播 `carousels`；当天三个游戏都没有直播入口。
  - 游戏内公告只给直播的 B 站预约链接，不给米游社直播页的活动 ID。
  - 下一次取证机会：绝区零 3.3 前瞻特别节目，2026-10-09 19:30（公告 ann_id 252 写明"节目直播期间还将发放限定兑换码福利"）。

## 决策

1. **来源与请求**。每个游戏一个来源（`<game>-live`），主机白名单为 `bbs-api.miyoushe.com`、`api-takumi.mihoyo.com`、`api-takumi-static.mihoyo.com`；官方直播页只作展示链接，本站不请求它。每次轮询：首页 1 次（发现活动）+ 每个跟踪中的活动 2 次（`index` 取 `code_ver` 与说明，`refreshCode` 取兑换码），同时跟踪的活动至多 `REDEEM_LIVE_TRACK_MAX`（4）个。诚实 UA、不跟随重定向、不重试；受限 fetch 只额外放行 `x-rpc-act_id` 一个请求头，取值必须是活动 ID 的形状。遇到 401/403/407 或信封写着需要登录、验证码等，整个来源标维护（规则 6）。
2. **发现**。只认首页 `lives`（直播卡片的链接或 `act_id` 字段）、`navigator`、`carousels` 里指向官方直播页 `webstatic.mihoyo.com/bbs/event/live/index.html` 的链接（米游社应用内链接 `mihoyobbs://webview?link=` 先解开一层）。同主机的签到、征集等活动页不算。**兜底**：管理员可在运行开关页为某个来源登记官方直播页链接或活动 ID（`POST /api/v2/admin/redeem-lives`，带理由、条件写入并审计；同一来源至多保留 `REDEEM_LIVE_TRACK_MAX` 个，`REDEEM_LIVE_TRACK_DAYS` 天后失效）；登记只把活动 ID 交给下一次采集，采集照常经受限请求与官方接口校验。
3. **跟踪**。被发现或登记的活动记在来源水位里；官方返回"活动已结束"后记下时刻、不再请求；首次发现满 `REDEEM_LIVE_TRACK_DAYS`（7）天的移出。有尚未发放的兑换码时，下一次采集排在官方发放时刻后 `REDEEM_CODE_REVEAL_GRACE`（60 秒）；发放时刻过了仍没取到就每 60 秒再取，直到 `SOURCE_HOT_POLL`（10 分钟）为止，之后回到常规间隔 `SOURCE_POLL`。
4. **「有效兑换码」条**。已发放的兑换码随采集立即写入 `redeem_codes`（码、奖励说明、发放时刻、有效期、官方活动结束的观察时刻），**不经审核**——它们是官方接口原样给出的公开字段。公开读取 `GET /api/v2/redeem-codes` 只返回 contracts `redeemCodeVisible` 判定为显示中的条目：已发放；官方写了有效期的到期即止；没写有效期的，官方活动结束或发放满 `REDEEM_CODE_UNDATED_DISPLAY`（24 小时）即止——这只是显示上限，页面写"官方未写有效期，请尽快兑换"，**不声称有效期**。首页在筛选栏之后显示这一条：按选中的游戏筛，没有可显示的兑换码时整块不出现、不占位；每条可一键复制；到点自动移除，不必重新请求。
5. **有效期的认定**。只认官方说明里"有效期至……""……前有效""……过期/失效""请于……前""兑换截止……"一类写法后面的完整日期（contracts `redeemExpiryExpression`）：带年份的斜线/横线完整时刻、"YYYY年M月D日 HH:MM"是官方明确时间；没写年份的"M月D日( HH:MM)"按同一正文里最早写明年份的日期补全年份（ADR-0013，`deterministic_derived`）。认不出、或写了两个不同的日期时按"没写有效期"处理，**不猜"次日中午"之类的惯例**（主方案 §3.3）。只写日期的，条里截到当天北京时间结束，日历里是日期精度的结束节点。
6. **日历里的兑换码事件**。有兑换码条目的活动写成一篇文章版本：本站按官方结构化字段逐行写成（标题、"发放时间：YYYY/MM/DD HH:MM｜兑换码：…｜奖励：…"、"兑换码说明：…"），内容不变不产生新版本。规则模板 `miyolive-redeem-codes-v1` 从中生成一个 `redeem_code` 事件："<直播标题>兑换码"，开始节点"兑换码发放"= 第一个兑换码的官方发放时刻（`official_explicit`），结束节点"兑换码过期"= 第 5 条认出的有效期（认不出就没有结束节点）；事件简介列出已发放的兑换码。证据引用、时间校验、发布、公共快照、个人 Feed 与通知都沿用现有流程。
7. **发布门**。直播兑换码来源的规则候选随来源开关发布（`source:<id>` 开着、外发总闸开、非只读），不经「自动发布」开关：兑换码通常一天内失效，等人工审核就失去意义；候选只来自官方结构化字段，不是正文抽取。公告的规则模板仍受「自动发布」约束。三个新来源与其他来源一样**默认关闭**，部署后由所有者在运行开关页开启。
8. **不是日历的所需来源**。注册项带 `freshnessExempt`：contracts `requiredCalendarSources` 不把它们算进个人 Feed 与日历预览的来源新鲜度。兑换码来源暂时取不到时，Feed 不因此 503，照常输出已发布的事实（兑换码事件的时间都是官方给定的精确时刻）。
9. **公开状态**。`/api/v2/status` 的来源条目增加 `kind`（`announcement` / `live_codes`）。日程是否受来源异常影响只看 `announcement`；首页"数据状态"只列公告源；服务状态页逐来源列出并写明用途。
10. **事件类型**。contracts `EVENT_TYPES` 增加 `redeem_code`（名称"兑换码"，开始"兑换码发放"，结束"兑换码过期"；结束节点算截止，进"即将截止"与"只看截止"）。D1 `events.event_type` 的 CHECK 约束随之扩充（迁移 0030 重建 `events` 表）。提醒规则（附录 A.6）不变：兑换码没有提前提醒规则。`DEFAULT_CALENDAR_EVENT_TYPES` 加入 `redeem_code`，只影响新配置的界面预选；**已保存的订阅不变**，想在日历里看到兑换码的用户要在"日历显示内容"里勾选"兑换码"（主方案 §5.1：不替用户写入没选过的配置）。

## 价值

- 前瞻直播期间，玩家打开首页就能看到并一键复制仍有效的兑换码；过期自动消失。
- 订阅了兑换码的日历里有"兑换码发放"与（官方写了有效期时的）"兑换码过期"，简介里列出兑换码。
- 发现入口没出现时，所有者贴一个官方直播页链接即可，不必改代码。

## 成本

- **迁移 0030**：重建 `events` 表扩充 CHECK 约束（D1 不能关闭外键检查：先复制到暂存表，删除旧表，以原名建新表并插回，提交时外键计数回到 0；`migration-0030.test.ts` 在有子表引用的库上验证了行、版本号与外键原样保留，并用对照证明"先建新表再改名"的顺序会提交失败）。另建 `redeem_codes` 表。应用前按 [备份手册](../runbooks/backup-restore.md) 先做备份。
- 请求量：每个开启的来源每 30 分钟 1 次首页请求；有直播时每个活动每轮 2 次，发放时刻附近每 60 秒一轮、持续到取到兑换码或 10 分钟。三款游戏合计约 150 次/天的首页请求，直播日另加几十次。官方接口是匿名公开接口（兑换码接口在 CDN 上，官方页面本身每 20–40 秒刷新一次）。
- D1：每轮写入至多几行；公开读取每次一条有界查询（按发放时刻、跟踪期内）。首页多一个公开请求 `/api/v2/redeem-codes`（ADR-0032 起跨页复用）。
- 代码：一个适配器、一个采集分支、一个规则模板、一个公开接口、一个管理端接口与表单、首页一个组件。

## 安全影响

- 新请求只到三个白名单主机；受限 fetch 只多放行 `x-rpc-act_id` 这一个请求头，不带 Cookie、Referer 或伪装 UA；不跟随重定向、限时、限体积。
- 兑换码与奖励说明都是官方公开的文本；页面按文本写入，奖励说明里的官方 HTML 先去掉标签。
- 管理端登记要求管理员会话、CSRF、闭合理由，条件写入并审计；只接受官方直播页链接或活动 ID 的形状，非直播来源一律拒绝。
- 不读取或保存任何玩家账号数据；兑换要玩家自己在游戏或官方兑换页完成。

## 预算与容量影响

不涉及邮件、模型与 Push 预算。新增两条参数等式；`SOURCE_LIMIT_PROFILE` 的三个新上限（256 KiB）低于统一安全界。兑换码事件很少（每个版本每款游戏一场直播），对 Feed 节点数与公共快照的影响可以忽略。

## 回退

- 关闭三个 `source:<game>-live` 开关即停止采集与发布；已显示的兑换码按显示期自然消失。
- 代码回退：**还没有兑换码事件发布时**可以直接回退到上一版本（`events` 的 CHECK 只是更宽，旧代码照常写入原有四种类型；`redeem_codes` 表闲置即可）。**已有兑换码事件发布后**，旧代码的公开接口与 Feed 校验不认识 `redeem_code`，读到它会失败——这时不直接回退，改为前向修复：先关闭三个直播来源开关，再修代码；确需回退时，由所有者在备份后删除兑换码事件的公共投影并重建公共快照，再回退。
- 迁移不可逆（只进不退）。

## 备选方案

- **把兑换码当作 `limited_event` 或 `livestream` 的节点**：不用改表，但节点会显示成"活动结束""前瞻开始"，限时活动的"结束前 1 天"提醒会在兑换码发放前触发，用户也没法单独选择要不要兑换码。不采用。
- **兑换码只进首页条、不进日历**：不满足"开始和过期加入日历"。不采用。
- **兑换码事件也等人工审核或受「自动发布」约束**：兑换码一天内失效，审核延迟让它失去意义；候选只来自官方结构化字段。不采用（所有者可随时关闭来源开关）。
- **没写有效期时按"次日 12:00"惯例**：是猜测，违反主方案 §3.3；页面改为如实说明"官方未写有效期"。不采用。
- **用第三方兑换码聚合站或社群消息**：违反 §3.1（第三方聚合后端不能冒充官方来源）。不采用。
- **从米游社资讯帖子正文找直播链接**：帖子正文接口 403（ADR-0016），按规则 6 不绕过。不采用。

## 待确认

- **直播期间的真实样本尚未取得**：活动与兑换码接口的字段形状来自官方页面脚本，测试用合成样本（标明 `synthetic`）。2026-10-09 绝区零 3.3 前瞻是第一次取证机会；字段不符时适配器按"格式不符"失败（不猜），需要按真实样本修正。
- 首页发现入口在直播期间是否出现、出现在哪个字段，同样待实测；没出现时用管理员登记兜底。
- 官方说明 `codeTipText` 的实际写法待实测；认不出时日历只有"兑换码发放"、条里按显示上限。

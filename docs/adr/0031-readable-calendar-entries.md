# ADR-0031：日历条目写可读信息——标题写明节点动作，描述写时间与依据，链接指向本站活动详情

- **状态**：已接受（所有者 2026-10-07 提出）
- **日期**：2026-10-07
- **提出者**：所有者。原话："日历当前的详细信息是原文链接，是不可读的，请帮我将日程的详细信息改为日程的可读信息"。
- **需要所有者批准**：是，已由所有者提出。不涉及收费、供应商或权限；无迁移、无新参数。

## 背景

2026-10-07 核对线上（第 16 代，`GET /api/v2/events/{id}` 只读）与代码：

- 个人 Feed 的 `URL` 是 `events.official_url`。三个公告来源的这个值都是取材端点——例如
  `https://hk4e-ann-api.mihoyo.com/common/hk4e_cn/announcement/api/getAnnContent?game=hk4e&…&uid=100000000`，
  打开是一份约 250 KB、含全部公告的 JSON，同一来源的所有活动都是同一个地址。日历应用把它显示在"链接/详细信息"里，读不懂，也点不到对应公告。
- `DESCRIPTION` 只有事件简介加仍在保留期的更正理由；规则路径与 AI 草稿路径的简介恒为空，所以绝大多数条目的描述是空的。
- `SUMMARY` 是"活动名 · 节点标题"；节点标题常与活动名相同，例如「涌浪叙歌」祈愿的开始与结束两条都显示为"「涌浪叙歌」祈愿 · 「涌浪叙歌」祈愿"，在日历里分不出哪条是开始、哪条是结束。
- 私人预览（`/api/v2/me/calendar/preview` 的字节核对）与启用前的确认列表、"我的订阅"预览列表，也按同样的"活动名 · 节点标题"写法组装。

## 受影响的合同

| 文档 | 章节 | 现有规定 | 本 ADR |
| --- | --- | --- | --- |
| 主方案 | §6.5 格式 | 一个节点一个 VEVENT；字段内容未逐项规定（`publishing.ts` 注释：事件简介、原始表达、来源时区、时间依据 → DESCRIPTION，官方地址 → URL） | DESCRIPTION 写可读信息（见决策）；**URL 改为本站活动详情页**，官方取材接口地址不再进日历 |
| D2 | 预览与真实日历一致 | 预览列表标题与日历条目同写法 | 仍一致：两边都用 contracts `calendarEntryTitle` |

UID、SEQUENCE、DTSTAMP/LAST-MODIFIED、DTSTART、VALARM、STATUS、完整快照与缩水守卫都不变。

## 决策

1. 日历条目给人看的文字只在 contracts `calendarEntryText` 定义，真实 Feed 与私人预览共用（字节一致）；Worker 只做 RFC 5545 转义与折行。
2. **标题**（`calendarEntryTitle`）："活动名 · 节点说明"。节点说明是节点动作（卡池开启、卡池结束、活动开始、活动结束、奖励领取截止、维护开始、前瞻开始、兑换码发放……，contracts `nodeAction`）；阶段解锁用节点自己的标题（同一活动可能有好几个阶段），去掉与活动名重复的前缀。"我的订阅"的预览列表与日历启用前的确认列表用同一函数，看到的就是日历里的标题。
3. **描述**，逐行：
   - 游戏 · 类型 · 节点说明（如"原神 · 卡池 · 卡池结束"）；
   - 时间：北京时间完整写法（"2026年10月13日 周二 17:59（北京时间）"；只有日期的写"（具体时间未公布）"，官方预计的加"预计"）；
   - 官方原文：原始时间写法；确定性推导的另写推导依据（与活动详情页同一句：`versionDerivationBasis` / `yearCompletionBasis`）；
   - 仍在保留期的更正写"更正：理由（原时间 …）"；没有更正时，取消、撤回、延期写状态；
   - 事件简介（有才写；兑换码事件是已发放的兑换码）；
   - "详情与官方公告原文：<本站活动详情页>"；
   - "时间与安排以官方公告为准。"
4. **链接**：本站活动详情页 `<站点>/events/<eventId>`（`eventDetailUrl`）。站点取部署配置的 `SITE_ORIGIN`，无效或缺省时取请求自身的源（与日历管理接口相同）。详情页有本站保存的官方公告原文（ADR-0014）与官方链接。
5. **不增加版本号**：这是输出格式的变化，不是公共事实的变化，不提高 `public_ical_revision`、不改 SEQUENCE 与 LAST-MODIFIED。Feed 正文与 ETag 随之变化，日历应用下次拉取时取到新文字。

## 价值

- 日历里点开条目就能看到是什么活动、哪个节点、北京时间几点、官方原文怎么写、有没有更正；开始与结束不再同名。
- 链接直达本站活动详情（含官方公告原文），不再是一段读不懂的接口地址。
- 预览列表与日历显示一致。

## 成本

- 典型条目（「涌浪叙歌」祈愿 · 卡池结束，带一个提醒）序列化后由 677 字节增至 847 字节：描述多了约 330 字节，链接从约 250 字节的接口地址缩短为约 100 字节的详情页地址。上限 `FEED_RESPONSE_MAX_BYTES`（2 MiB）不变：基础与更正条目都到各自上限（共 2,000 条）时约 1.7 MB。超过时照旧返回 503 与设置页说明，不截断（主方案 §6.5）。
- 代码：contracts 一个模块；Feed 与预览各改一处组装；两处网页预览改用同一标题函数。无迁移、无参数。

## 安全影响

只输出已经公开的事实与本站公开页面地址；不含 Feed token、用户信息或任何凭证。站点地址来自部署配置或请求自身的源，不取请求参数。文本照旧经 RFC 5545 转义（控制字符丢弃、换行转义）。

## 预算与容量影响

见"成本"：单条约增加 170 字节，在现有字节上限内。无请求量、存储或计费变化。

## 回退

还原本 ADR 的提交即可，无数据变化；日历应用下次拉取时恢复原来的文字。

## 备选方案

- **链接保留官方地址、只补描述**：官方地址是取材接口，对人没用；公告在游戏外没有逐篇的官方网页地址可链（P0-02 未核验到单篇官方页 URL 模式）。不采用。
- **同时提高 SEQUENCE**：只为让个别客户端刷新文字而改公式，要动主方案 §6.4 的序列合同；订阅日历按整份替换，不需要。不采用。
- **描述里贴公告全文**：条目体积会大幅增加，容易触发字节上限；全文在详情页里看。不采用。

## 待确认

- 各日历客户端对多行描述与链接字段的显示方式不同（Apple 日历显示"备注"与"URL"，部分客户端只显示其一），未逐一实测；文字内容不依赖某个客户端。

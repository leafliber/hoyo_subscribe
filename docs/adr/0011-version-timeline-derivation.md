# ADR-0011：建立版本时间表，"X.Y版本更新后/版本结束"按管理员确认的版本时间确定性推导

- **状态**：已接受（P3-19 实施）
- **日期**：2026-10-04
- **提出者**：验收方根据线上后台情况提出（ADR-0010 "待确认"）
- **需要所有者批准**：是，已批准。所有者 2026-10-04 选择"做，接着实施"版本时间表，并要求同时"优化一下后台审核的界面，与设置页面分开"。
- **与 ADR-0010 的关系**：落实 ADR-0010 "待确认"中的版本时间表；ADR-0010 的模型、提示词、预占与采用 CAS 不变。

## 背景

2026-10-04 在所有者登录的管理端里只读盘点待审草稿：

- 17 条草稿的开始写作"X.Y版本更新后"；
- 5 条草稿的结束写作"X.Y版本结束"。

这些节点都只能存成"未定时刻"，日历和提醒都用不上。可是同一游戏的版本更新说明里写着这些时间：

- 三款游戏都写了更新开始时刻和"预计5个小时完成"；
- 星铁 4.6、绝区零 3.2 还写了版本结束时刻。

ADR-0010 已让模型在版本公告里摘出 `version_window`，并逐字核对，但这份摘录只写进说明。

合同原文的约束：

- 主方案 §3.3："只有日期不补成精确午夜；"预计维护五小时"不是实际开服；"更新后开放"不能猜固定时刻。"
- 主方案 §3.3："提醒只使用精确、证据通过的明确时间或确定性推导。"
- 前端 §4.4：确定性推导要"显示结果，详情提供原始表述与推导依据"，禁止"伪称官方直接公布了该精确时刻"。
- ADR-0009：时间只认所引块里逐字存在的文本，模型不得跨公告推算。

## 受影响的合同

| 文档 | 章节 | 现有规定 | 本 ADR |
| --- | --- | --- | --- |
| 主方案 | §3.3 时间依据 | 有 `deterministic_derived`，没有规定哪些表达可以推导 | 新增两条推导规则（见决策 3），只用管理员确认过的版本时间 |
| 主方案 | §8.1 逻辑数据契约 | — | 新增两张表（迁移 0028）：版本时间建议、确认后的版本时间 |
| 前端 | §4.4 | 确定性推导在详情给出原始表述与推导依据 | 公开详情的"时间依据"里加一行"推导依据" |

枚举、公式、预算等式都不变。

## 决策

1. **建议表** `game_version_suggestions`：
   - 来源是 ADR-0010 的 `version_window` 逐字核对通过的部分，在起草成功时写入；
   - 记录出处（文章版本、块引用、原文摘录）；
   - 不可变，同一文章版本的同一版本号只记一次；
   - 模型只能产生建议，不能写确认值。
2. **确认表** `game_versions`：每个游戏、区服、版本一行，"更新开始"和"版本结束"各自确认。
   - 值只能来自两处，不提供手填时刻：
     - 一条已核对的建议；
     - 版本结束可取"下一个已确认版本的更新开始"，记为 `next_update`。
   - 每次写入都带 CAS（`expected_updated_at`）和理由，并记审计 `version_confirm` / `version_clear`，出处写在 `detail_ref`。
   - 结束不晚于开始的写入被拒绝。
3. **推导规则**：唯一定义在 `@hoyo/contracts` 的 `deriveVersionTime`。
   - **原始表达必须整体就是锚点**，夹带其他文字的不推导；版本号两侧允许「」或“”。
   - **更新锚点**："X.Y版本更新后 / 更新完成后 / 更新开始后 / 上线后 / 开启后"，可带前缀"自"。
     - 推导为该版本更新开始当天的**日期**（北京时间，precision `date`）。
     - 不推出几点：§3.3 规定预计时长不是实际开服。
     - 日期型不进提醒（`time.ts` 已规定提醒只用 datetime）。
   - **结束锚点**："X.Y版本结束 / 结束前 / 结束时"。
     - 推导为确认过的版本结束**时刻**（precision `datetime`），可用于提醒。
     - 不认"结束后"：用在开始节点时等于"下一版本更新后"，推成时刻就是在猜开服时间。
   - 两类的 `time_basis` 都是 `deterministic_derived`，原始表达原样保留。
   - 只改"未定时刻"的节点。所需字段未确认时保持未定，并在说明里提示去版本时间表确认。
4. **推导在读取和采用时做，不改写草稿**：
   - 审核详情按当前的版本时间表推导，返回推导后的草稿、推导说明、`derived_count` 和 `derivation_key`。
   - `derivation_key` 是本次用到的版本行及其 `updated_at`。
   - 采用必须带审核员看到的 `expected_derivation_key`，版本时间表在他打开后被改过时返回 409。
   - 不需要重新起草，也就不额外消耗 Neurons。
5. **人工写入与批准都核对一致**：
   - 适用于创建、修正、采用，以及批准、更正、关联。
   - 版本锚点节点要么保持未定，要么与当前确认值的推导完全一致，否则返回 400 `version_derivation_mismatch`。
   - 因此审核员不能手填一个时刻冒充推导；采用之后版本时间被改或被清除时，批准会拦下过期的推导值，不会发布出去。
   - 撤回不受此限，避免阻塞纠错。
6. **已发布事件不随版本时间表自动改动**：
   - 版本时间改了以后，已发布的事件走现有的更正流程（新公告 → 变更关系 → 更正），与官方明确时间改期的处理相同。
   - 版本时间表页面在确认或清除后明确提示这一点。
7. **展示推导依据**：
   - 公开详情的"时间依据"里，版本锚点节点多一行"推导依据"，例如"取 4.6 版本的结束时间，按官方版本公告核对确认"。
   - 管理端版本时间表列出每个值的出处公告和原文摘录。
8. **管理端拆页**：拆成三页，共用同一个登录会话；三页都不进普通导航。
   - 「审核」`/admin/`：队列与详情并排，可按游戏和草稿状态筛选，处理完一条自动打开下一条。
   - 「版本时间表」`/admin/versions/`。
   - 「运行开关」`/admin/settings/`。

## 价值

- 按 2026-10-04 的盘点，确认 3 个版本的更新开始后：
  - 17 个"版本更新后"的开始节点得到日期；
  - 星铁、绝区零的版本结束确认后，对应结束节点得到可提醒的时刻。
- 原神 7.1 的版本结束可以等 7.2 公告写明后再确认，或取 7.2 的更新开始。
- 每个版本只确认两项，约六周一次，不必在每条候选里重复判断。
- 推导值与原文、出处一起展示，不冒充官方直接公布的时刻。

## 成本

- 一个迁移（0028）、两张表。每个游戏每个版本一行，年增十余行；作为推导依据长期保留，不清理。
- 每次打开详情、采用、修正或批准，各多一次按 `(game, region)` 的小查询。
- 版本时间表页面的读取以 `PUBLIC_READ_LIMITS.scanPage` 和 `pendingCandidates` 为上界。
- 不新增模型调用、绑定、秘密或供应商。

## 安全影响

- 新增的写接口沿用管理员会话、CSRF、CAS、理由与审计，没有新凭证，也不扩大权限。
- 不接受自由输入的时刻：确认值只能是已逐字核对的建议或"下一版本的更新开始"。模型输出要经过原文核对和管理员确认两道关，才可能影响发布。
- `derivation_key` 防止采用审核员没看过的推导结果；批准前的一致性核对防止发布过期的推导值。
- 推导规则是纯函数，只匹配整体为锚点的原始表达，没有跨公告的自由推断。

## 预算与容量影响

- 邮件池、模型日预算、账号存量、Feed 容量都不受影响；附录 A.5 的等式不需要重算。
- 版本结束推导出的 datetime 会进提醒，与官方明确时刻的提醒走同一套预算。

## 回退

- **清除某项确认**：
  - 尚未采用的草稿恢复为未定时刻；
  - 已采用、未批准的候选在批准时被拦下，要重新采用或修正。
- **代码回退**：两张表可以保留不用；回退后人工写入不再核对版本锚点。
- **不可逆的部分**：已发布事件里的推导时间、已下载的日历副本、已发出的提醒。这些按现有更正流程处理。

## 备选方案

- **让模型直接把版本时间填进每条候选**：违反 ADR-0009 "时间只认所引块里的原文"，属于跨公告推算；不采用。
- **核对通过的建议自动生效、不经管理员确认**：一次摘录错误会扩散到整个版本的事件和提醒。每版本确认两项成本很低，不采用。
- **"更新后"推导为更新开始加预计时长**：§3.3 明确预计时长不是实际开服；不采用。
- **起草时把推导值写进草稿**：版本时间往往在草稿生成之后才确认，要重新起草，还会多耗 Neurons；不采用。

## 待确认

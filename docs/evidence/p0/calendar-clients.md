# P0-04 · 日历客户端实测记录

> 验收 ID：**A-P0-CAL**｜门禁：**G-P0-CAL**
> 合同：主方案 §1.2、§6.2、§6.4、§6.5、§10.3 客户端条目、[R11]
> **每个客户端单独一行结论，不共用一份"支持"表述。**未实测的格子写"未测"，不写"应该可以"。

## 为什么这项排在最前面

完整快照语义下，一条目缺席 = **向客户端下达删除指令**。如果没有任何客户端能正确处理"移除后再加入"，
主方案 §6.2 要求 **P0 重新评估日历主通道**——而日历是主通道、邮件只是补充（§1.2）。
这个假设不成立的话，订阅模型、邮件两层设计、四池预算划分全部要重做。**越早发现越便宜。**

## 怎么跑

```bash
node scripts/probes/calendar-clients/serve.mjs
```

- 订阅地址 `http://127.0.0.1:8800/cal.ics`。控制台输入步骤号 + 回车切换，或打开 `http://127.0.0.1:8800/` 点按钮。
- **Apple Calendar / Outlook 桌面版**由客户端本机拉取，localhost 直接可用。
- **Google Calendar 由 Google 服务器拉取，必须公网可达**。另开一个终端：
  ```bash
  cloudflared tunnel --url http://127.0.0.1:8800
  ```
  用它给出的 `https://xxx.trycloudflare.com/cal.ics` 订阅。
- 每次请求都会记到 `docs/evidence/p0/calendar-poll-log.jsonl`（含时间、UA、是否带 If-None-Match、返回码），
  **刷新延迟从这里读真实值，不靠感觉估**。

## 步骤与观察点

| 步骤 | 内容 | 要观察什么 |
| --- | --- | --- |
| 0 | 基线 6 条 | 全部出现；【C】显示为整日事件不带时刻；【D】中文与 emoji 不乱码不截断 |
| 1 | **完整快照删除**（B 缺席） | B 是否从日历中消失。**这一步不过，该客户端就是"未支持"** |
| 2 | **重新加入**（B 同 UID 同 SEQUENCE 回来） | B 是否重新出现；是否被当成新事件重复了一条 |
| 3 | **改期**（E 移到 +9 天，SEQUENCE 0→1） | 时间是否更新；旧时间是否残留 |
| 4 | **取消**（F 变 STATUS:CANCELLED，SEQUENCE 0→1） | 如何显示：划线 / 移除 / 无变化 |
| 5 | **503**（模拟缩水守卫拦截） | **日历是否保留上一次成功结果**。若清空 = 守卫兜底在该客户端上不成立 |
| 6 | 恢复 200 | 503 期间有没有丢内容 |
| — | **VALARM**（【A】开始前 15 分钟） | 闹钟是否真的弹出。客户端可能默认忽略订阅日历的提醒，要到设置里确认 |

每步切换后**等到日志里看见该客户端的新请求**再判读。客户端刷新节奏差别很大：Apple Calendar 可设为
每 5 分钟到每天；Google Calendar 自行决定、常见数小时一次，快不了也催不动。

## 判定

- **至少一个客户端在步骤 1、2、3 全部通过** → G-P0-CAL 开，P3-06 可按完整快照实现。
  ✅ **2026-09-22 已满足**（Apple Calendar / macOS）。
- **全部失败** → 停下来写 ADR，重新评估日历主通道。
  **不得因为测不过就偷偷恢复个人撤销池**（§6.2，AGENTS.md 禁止清单第 1 条）。
- VALARM 单独判定：**闹钟不通过不影响完整快照结论**，但"日历提醒可用"这句话就不能对外说（§1.2）。
- 步骤 5 失败（客户端在 503 时清空日历）要单独记：缩水守卫的兜底假设在该客户端上不成立，
  需要在 `docs/HOYO_SUBSCRIPTION_FRONTEND_DESIGN_v1.0.md` §9.1 的客户端说明里写明。

## 已知限制

本测试台用的是**手工构造的固定序列**，不是真实 Feed 输出。它验证客户端行为，不验证服务端组装正确性——
后者是 P3-06 的 A-P3-ICS。两者都要过，不能互相替代。

# P0-05 · 平台资格、发件域与反馈链路 · 所有者操作手册

> 验收 ID：**A-P0-MAIL**｜门禁：**G-P0-MAIL**
> 合同：主方案 §2.2、§2.3、§2.4、§7.4—§7.7、[R01]—[R06]
> ⚠ 标记的步骤会产生费用或改动真实资源。**Agent 不执行这里的任何一步。**

## 0. 先理解为什么这些数字重要

附录 A.4 的 `MAIL_TOTAL_MONTH = 2,700` 是**贴着** Cloudflare 每账单周期含 3,000 封设计的，
只留了 300 封余量。所以下面三件事任何一件对不上，整套预算基线就不成立，A.5 的等式要重算：

- 账单周期不是自然月（`MAIL_BASE_MONTH` 的等式要用"本账单周期相交 UTC 日期数"）；
- **账户里其他应用也在发信**，共享同一份包含量；
- 账户**实际日发送权限**低于预期——§2.2 明说这个数**不能从月包含量推导**。

## 2. ⚠ 站点与发件域

按 §2.2：

1. 确定一个**稳定 HTTPS origin**（站点主域）。
2. **认证与业务使用不同发件子域**，例如 `auth.<域>` 与 `mail.<域>`。两个都要单独在控制台添加。
3. DNS **按控制台实际生成的记录**配置。
   ⚠ **不要覆盖已有收信系统**——如果该域已在收邮件，先确认现有 MX/SPF/DKIM 记录不被顶掉。
4. **关闭认证域的 Email preview**。
5. **两个用途都关闭"静默丢弃受抑制收件人"**——关掉之后发送被阻止才会返回明确错误，
   否则应用会把"被丢弃"当成"已发送"。

> Email Routing 只是可选入站转发，**不负责本站用户认证**，也不能用它的 verified destination
> 代替面向普通用户的发送验证（§2.2）。

## 3. ⚠ 真实收件人发送测试（这一步是门禁的核心）

**给 routing verified destination 发成功不算数**（§2.4）。必须是**普通收件人**。

准备 3–4 个你自己控制的普通邮箱：QQ、163、Gmail、Outlook 各一个。

对每个邮箱发一封测试，记录：

| 收件邮箱类型 | 发件子域 | messageId | 反馈 Queue 是否收到事件 | 事件类型序列 | 收件服务器接受 | 进收件箱/垃圾箱 |
| --- | --- | --- | --- | --- | --- | --- |
| QQ |  |  |  |  |  |  |
| 163 |  |  |  |  |  |  |
| Gmail |  |  |  |  |  |  |
| Outlook |  |  |  |  |  |  |

关键是**第四、五列**：Event Subscriptions 要真的把事件投进 Queue，并且 `messageId` 能和发送时记下的对上。
这条链路不通，P4-07 的反馈消费就没有依据，`accepted / deferred / bounced / complained` 全是猜的。

⚠ **不要用真实用户群发做压测**（§10.3）。

## 4. 退订头与 DKIM

在收到的测试邮件里查看原始邮件头，确认：

- ☐ `List-Unsubscribe` 存在
- ☐ `List-Unsubscribe-Post: List-Unsubscribe=One-Click` 存在
- ☐ **DKIM 签名覆盖了上面这两个头**（[R12] 的条件；不覆盖的话 one-click 不可信）

如果平台不允许自定义这两个头，记下来——这直接影响 P4-06 能不能实现，属于要写 ADR 的事。

## 5. 抑制行为

不需要主动制造投诉。只要在控制台确认：

- ☐ 抑制列表在哪看
- ☐ 记录是否带 `read_only` 字段
- ☐ 抑制的作用范围（§7.7：Cloudflare 的抑制作用于**同账户所有发件域**）

> 不要为了测试去触发真实投诉。这会污染账户信誉，且投诉记录通常无到期。

## 6. Beta 故障预案确认

§2.3 要求在发送不可用时**暂停新验证码发送**，而不是先生成一个即将过期的验证码。确认你知道：

- ☐ 发送不可用时控制台在哪能看出来
- ☐ 账户配额被降低时会不会有通知

## 7. 完成判定

G-P0-MAIL 开的条件：**第 1 节表格填满** + **第 3 节至少两种不同邮箱服务商拿到 messageId 与 Queue 事件关联**。

任何一项拿不到就写"未取得"，**不写"应该没问题"**。P0-06 的结论表不接受空格。

## 8. 如果拿不到 Email Sending 资格

不是死路，但要立刻知道后果：

- 认证靠邮箱验证码，**没有邮件就没有登录**。§9.2 的"恢复入口不依赖发信预算"救的是已有码的老用户，救不了新注册。
- 按 §2.3，替代 Provider 需要实现既有发送结果、反馈、抑制合同，并在切换前验证测试收件人、幂等边界、
  退订头、反馈映射和费用。**这要写 ADR 并经你批准**，不是 Agent 能自行决定的。
- 在拿到结论之前，**P4 的真实外发一律不开**；P4 的逻辑实现可以用测试替身继续。

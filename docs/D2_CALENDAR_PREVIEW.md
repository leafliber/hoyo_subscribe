## 0. 结论速览

1. 预览只有一套算法：contracts 里个人 Feed 用的投影函数 `personalCalendarNodes`，加上 §4 的解释函数。
   浏览器和服务端跑的是同一份代码。
2. 新增公开接口 `GET /api/v2/calendar/nodes`。它返回当前完整发布代次里、此刻可能进入任何人日历的全部节点，以及解释 `unknownTime` 所需的非墓碑待定节点（§2.2），
   不按任何人的设置筛选。公开、可缓存，不含账号信息。（所有者决定 1）
3. 编辑草稿时，游客与已登录用户一样：浏览器拿这份数据，按草稿即时算出预览。游客看到的是真实数据，不再是样例。
4. 已登录用户启用日历前，看服务端按**已保存设置**算的预览 `GET /api/v2/me/calendar/preview`。
   它是启用确认的唯一依据，并额外核对浏览器核对不了的输出字节上限。
5. 每一条都说明三件事：
   - 为什么在日历里：基础显示，还是为哪条提醒保留、被哪项筛选隐藏；
   - 有没有闹钟，没有的话原因是什么；
   - 是不是更正条目，事实原因是什么。
6. 启用请求带上预览所用的**订阅版本号与发布代次**，任一变了就返回 409，页面重新展示、请用户再确认。（所有者决定 2）
   时间推移不核对，页面也不承诺"订阅后看到的就是预览这样"。
7. 首页"近期重要变更"已由 P3-14 的公共接口提供，不另建。

## 1. 预览是什么

### 1.1 唯一算法

- **条目**：`personalCalendarNodes(config, 当前完整发布代次的快照节点, asOf)` 的结果，加上 §4 的解释字段。
  - 与 Feed 读路径（主方案 §6.6）用同一个函数。服务端读代次也用同一套（`calendar/feed/public-read.ts` 的 `FeedPublicCache`）。
  - 解释字段由 contracts 里的一个纯函数从同一次投影结果里取，浏览器与服务端共用。
    不另写窗口、更正、闹钟的判定（AGENTS 硬规则 3），也不在浏览器里另写一份。
- **上限与新鲜度**：与 Feed 同一套判定。
  - 条目上限用 `feedNodeLimit`（`FEED_BASE_NODE_MAX`、`FEED_PATCH_NODE_MAX`），浏览器与服务端都算。
  - 新鲜度用 `feedSourcesFresh`。所需来源的选取规则（现为 Worker 里的 `requiredFeedSources`）搬进 contracts，浏览器用同一条规则（§9 P3-15）。
  - 字节上限 `FEED_RESPONSE_MAX_BYTES` 要用 Feed 的 ICS 序列化器才能算，只在服务端核对（§3）。
- **不含缩水守卫**：守卫比较的是同一个 Feed 前后两次成功输出（§6.5），预览没有这个前后关系。
  已启用 Feed 是否被守卫拦截，看 `GET /api/v2/me/calendar`（D3 §2.6）。

### 1.2 预览与实际 Feed 只差这些，页面要照实说

| 差别 | 原因 | 页面怎么说 |
| --- | --- | --- |
| 没有 UID、SEQUENCE、DTSTAMP | 它们属于具体的 Feed（namespace、`view_revision`），启用前还不存在 | 不展示 |
| 按 `asOf` 时刻计算 | 窗口按 UTC 日推移、更正到期、预计时间被确认，都随时间变化 | 标明"按某时的数据预览" |
| 之后会有新代次 | 官方新增、改期、取消都会进入新的发布代次 | "订阅后，日历会随官方更新自动变化"；不承诺订阅后所见与预览相同（前端 §13.2） |
| 浏览器即时预览不核对字节上限 | 字节数要用 Feed 的序列化器算，只在服务端做 | "启用前会再核对一次"；启用以 §3 的结果为准 |
| 外部客户端是否应用、何时刷新 | 服务端决定不了（§6.2、§6.6 末段） | 按 D3 §2.1 的实测资料说明，未测的保持未知 |

## 2. 公开节点数据：`GET /api/v2/calendar/nodes`

### 2.1 请求

- 公开，不需要登录，只读。响应外壳与 P3-14 的公共读相同：带 `cache` 字段，`cache-control: public, max-age=PUBLIC_CACHE_FRESH`。
- 参数只有 `cursor`，查询串按 P3-14 的白名单与 `queryBytes` 校验。
- **不接受任何筛选参数**：同一时刻所有人拿到同一份数据，筛选全部在浏览器里做（所有者决定 1）。
- 带不带会话 Cookie，响应都一样，不含任何账号信息。

### 2.2 响应

| 字段 | 含义 |
| --- | --- |
| `publication` | `{ generation, publishedAt }`：当前完整发布代次及其发布时间 |
| `asOf` | 算候选集合所用的时刻（UTC 毫秒）。续页沿用第一页的值（§2.3） |
| `window` | `feedWindow(asOf)` 的 `{ start, end }` |
| `sources` | 内容来源逐行 `{ sourceId, game, region, lastSuccessAt }`。范围与 `requiredFeedSources` 的取数范围相同：已登记、正文通道未停用的来源。浏览器按草稿选出所需来源，再用 `feedSourcesFresh` 判断 |
| `totals` | `{ nodes }`：整个候选集合的节点数，不随分页变化 |
| `nodes` | 本页节点。取公共快照节点的公开字段：`game`、`region`、`projection`（`event_id`、`milestone_id`、`event`、`milestone`）、`patch`、`tombstone`。不含 `source_projection_json` 等内部字段，也不含 UID |
| `nextCursor` | 续页游标；`null` 表示已全部给出 |

**候选集合（2026-10-02 验收解释补齐）**：由以下两部分按同一 Milestone 身份取并集：

1. 把所有游戏、区服、事件类型、节点类型都选上，在 `asOf` 时刻跑 `personalCalendarNodes(全选配置, 整代, asOf)`，取它用到的节点；这部分仍是日历条目的候选。
2. 额外保留当前完整代次中、**非墓碑且有效展示时间仍为 `unknown`** 的节点，只为 §4 的 `omitted.unknownTime` 提供输入。有效展示时间与 Feed 相同：`retain_until > asOf` 的有效更正存在时用 `patch.display_time`，否则用节点当前时间。当前时间未知但有效更正仍给出日期/时刻的，不属于这个补集；已经由 Feed 输出为更正/取消条目的，也不再计为 omitted。

- 两部分使用与 `effectivePublicSnapshotNodes` 相同的去重结果与代表节点，**先确定代表，再判断是否保留**；不能先筛去墓碑或已知时间记录，再把同一 Milestone 的旧未知记录复活。原投影需要的有效更正墓碑仍可由第 1 部分进入；第 2 部分不额外引入墓碑。
- 具体配置的日历条目仍是全选投影结果的子集。补集节点再由 §4 的同一解释函数按该配置的 scope、基础筛选及提醒关联规则决定是否计数，不是把全部未知节点直接记到每个用户名下。
- 浏览器对完整候选集合与服务端对整代运行解释函数，`items`、`totals`、`omitted` 及条目上限结论都须相同；§8 的等价性用例必须包含未知时间，不能只比较实际输出条目。
- 公开响应的 `totals.nodes` 包含补集节点，并按整个候选集合分页；预览的 `totals.items`、`feedNodeLimit` 与 ICS 字节判定只看实际投影条目。补集不变成 VEVENT/VALARM，不占 Feed 基础或更正条目上限。
- 服务端过滤只为控制下载量，不按人筛选。补集只限上述 unknown 节点，不扩为保留所有非墓碑或全部窗口外历史；不为未知时间虚构日期或窗口归属。
- 候选集合与解释函数仍只定义在 contracts；实际条目调用 `personalCalendarNodes`，复用已有筛选/去重规则，不另写窗口、更正或提醒投影。Feed 的函数行为与序列化输出不改，也不新增参数、接口或诊断枚举。

此前“它用到的节点就是候选集合”漏掉了已有 `unknownTime` 诊断所需的输入。本次只补齐 §4 与 §8 的一致性，不改变个人日历投影语义。

### 2.3 分页与一致性

- 页大小按字节自适应，单页与单节点的字节上限复用 `PUBLIC_READ_LIMITS.responseBytes` 与 `nodeBytes`（P3-14）。
  单个节点超限时整次返回 503，不截断（与 P3-14 相同）。
- 游标绑定 `generation` 与 `asOf`。续页按游标里的 `asOf` 算候选集合，不按新的时刻：
  一次下载的所有页属于同一代次、同一时刻，不跨代拼接。
- 代次已变：续页返回 409 conflict，原因 `preview_outdated`。浏览器丢掉已下载的页，绕过缓存从第一页重取。
- 游标的 `asOf` 晚于服务端当前时刻，或早于该代次的发布时间：400 validation（伪造或损坏的游标）。
- **下载完整**：`nextCursor = null`，并且收到的节点数等于 `totals.nodes`。

### 2.4 成本

- 只读，查询数有上界：
  - 读一次当前代次头；整代读取走 `FeedPublicCache`，与 Feed 共用 isolate 内缓存；
  - 读一次来源水位。
- 进 `storage/schema.test.ts` 的 rows_read 基准，并用"塞入大量历史后读数不涨"钉住（ENGINEERING §5.4）。
- 每次请求在内存里过滤一遍整代。响应可在浏览器缓存 `PUBLIC_CACHE_FRESH` 秒；浏览器改草稿时本地重算，不再请求。
- 与 P3-14 的公共读一样，不另设限速，不新增参数。

## 3. 已保存设置的权威预览：`GET /api/v2/me/calendar/preview`

### 3.1 请求

- 普通用户会话（active）可以访问，受限恢复会话也可以读；不接受 pending 会话。
- 只读：不写库，不创建 Feed 行，不记活动水位；不续会话（§4.5：被动 GET 不续期）；响应 `cache-control: private, no-store`。
- 参数只有 `cursor`（§3.3）。预览的一律是云端已保存的设置，服务端自己读 `user_subscriptions`。
- 订阅未初始化：400 validation，原因 `subscription_uninitialized`（D3 §1.2 的同名受阻原因），页面显示"先保存一次订阅内容"。
- 变更消息的四个开关不影响日历（`changesCalendarView` 的口径），不参与预览。

### 3.2 响应

| 字段 | 含义 |
| --- | --- |
| `subscription` | `{ revision }`：本次预览用的已保存版本 |
| `config` | 服务端规范化（去重排序）后的日历相关配置回显 |
| `publication` | `{ generation, publishedAt }`：本次使用的当前完整发布代次 |
| `asOf` | 计算所用时刻（UTC 毫秒）。窗口、更正到期都按它算 |
| `window` | `feedWindow(asOf)` 的 `{ start, end }` |
| `sources` | `{ fresh, verifiedAt }`。`fresh` 表示所需来源是否都在 `FEED_MAX_STALE` 内核验成功；`verifiedAt` 取所需来源中最旧的一次成功核验，任一来源没有成功记录时为 `null` |
| `outcome` | `ok`：按已保存设置与当前公共数据，能生成完整内容。`blocked` 加 `diagnostic`：Feed 此刻会拒绝输出，诊断码取 `FEED_DIAGNOSTICS` 里的 `base_node_limit`、`patch_node_limit`、`response_byte_limit`、`source_stale` 之一。blocked 时条目照常返回，供用户判断怎么缩小范围 |
| `totals`、`omitted`、`items` | 见 §4 |
| `nextCursor` | 续页游标；`null` 表示本次预览已全部给出 |

- 字节上限用 Feed 同一个序列化器判定。UID 用与真实 namespace 等长的占位，SEQUENCE 取当前 `view_revision`
  （还没有 Feed 行时取 0），与真实输出只差几个字节。实现卡在报告里写明误差。
- `totals.items = 0` 且 `outcome = ok`，才表示"真实没有匹配节点"，页面才可以显示空日历（§6.5：只有真实无匹配才是成功的空日历）。

### 3.3 分页与一致性

- 页大小与单条目上限同 §2.3。
- 游标绑定 `revision`、`generation` 与 `asOf`。续页一律按第一页的 `asOf` 计算，不跨代拼接。
- 以下情况续页返回 409 `preview_outdated`，页面清空后从第一页重取：
  - 发布代次已变；
  - 已保存版本已变；
  - `asOf` 早于当前时刻超过 `PUBLIC_CACHE_FRESH`。这个接口不进缓存，这里沿用 P3-14 裁定的"一份响应副本的新鲜期"。
- **完整**：`nextCursor = null` 且 `outcome = ok`，页面才能说"这就是按已保存设置，日历此刻的完整内容"。
  分页没加载完，或 `outcome = blocked`，都不能说完整（前端 §6.5"分页结果不能声称全量"）。

### 3.4 错误

| 情况 | 响应 |
| --- | --- |
| 未登录、会话待激活或已过期 | 401，`UnauthorizedReason` 照常 |
| 订阅未初始化 | 400 validation，原因 `subscription_uninitialized` |
| 续页或启用时，核对的版本或代次已变 | 409 conflict，原因 `preview_outdated`（contracts 新增的闭合枚举值；§2.3 的公开接口共用） |
| 没有当前完整发布代次，或读取失败 | 503 temporarily_unavailable，`calendar.reason = snapshot_unavailable`（沿用 Feed 的诊断体） |
| 请求过于频繁 | 429 rate_limited |
| Feed 此刻会拒绝输出（超限、来源过期） | **200**，`outcome = blocked` 加诊断码。预览本身成功了，它如实报告 Feed 会怎样 |

### 3.5 成本

- 只读，查询数有上界：会话校验沿用外壳；读一次订阅；读一次代次头（isolate 内缓存命中时不读整代）；读一次来源水位。
- 进 rows_read 基准，塞入大量历史后读数不涨。冷 isolate 读整代的代价与 Feed 相同。
- 只在启用确认时调用（§5.1），调用量很小。按会话近似限速（P1-07 原语）；不是写操作，不计入 `USER_MUTATIONS_DAY`。
  **2026-10-02 所有者已定值**：见 [ADR-0006](adr/0006-private-calendar-preview-rate-limit.md) 的 `CALENDAR_PREVIEW_RATE_WINDOW` / `CALENDAR_PREVIEW_RATE_LIMIT`；每会话、每 isolate 首屏与续页共用限额，超限 429。先注册参数再实现，最大分页与恢复成本仍须实测。本批准不代表代码已通过。

## 4. 条目与解释（浏览器与服务端共用）

contracts 提供一个纯函数，输入配置、节点、`asOf`，输出条目、`totals`、`omitted` 与条目上限结论。
§3 的接口在它之外加上来源新鲜度、字节上限与分页；浏览器在它之外加上来源新鲜度（用 §2 的 `sources`）。

**`totals`**：全集计数，不随分页变化：条目总数、基础窗口内、更正层、提醒关联、带闹钟、已取消。

**`omitted`**：符合筛选、却不会进日历的节点数：
- `unknownTime`：按同一筛选/去重规则命中、非墓碑且有效展示时间仍未知、没有实际投影条目的节点；更正展示时间按 §2.2，不只看原始 milestone.time；
- `reminderNotExact`：为提醒保留、但只有日期或预计时刻，Feed 不输出。只计窗口内或更正层延长的。

**条目字段**：

| 字段 | 含义 |
| --- | --- |
| `milestoneId`、`eventId` | 身份。同一 Milestone 只出现一次：基础筛选与提醒同时命中也只算一条（§5.2） |
| `game`、`region`、`eventType`、`nodeType`、`eventTitle`、`milestoneTitle` | 与 Feed 的 SUMMARY 同源 |
| `time` | 日历实际输出的时间：有更正时取更正层的展示时间，否则取节点当前时间。只有 `datetime` 与 `date` 两种；时间未知的节点不进日历，计入 `omitted` |
| `status` | 事件状态 |
| `cancelled` | Feed 里是否输出为 CANCELLED：官方取消、本站撤回、节点删除、延期待定 |
| `inBaseWindow` | 是否在基础窗口内。为 false 时，它靠更正层留在日历里，例如改期越过窗口未来端（§6.3） |
| `inclusion` | 为什么在日历里：`{ kind: "base" }`，或 `{ kind: "reminder_associated", ruleIds, hiddenBy }`。`ruleIds` 是引入它的所选规则；`hiddenBy` 是隐藏它的基础筛选：`event_type`、`node_type`，可以两者都有。前端 §6.5 要求这两种隐藏都要说清楚，不能只处理"隐藏结束节点" |
| `patch` | 更正层条目：`{ kind, factReason, oldTime, retainUntil }`，`kind` 取 `CALENDAR_PATCH_KIND`；不是更正条目时为 `null`。删除（`deleted`）、官方取消（`cancelled`）、本站撤回（`retracted`）分开表现 |
| `alarm` | 这个节点与所选提醒规则的关系。没有任何所选规则匹配时为 `null`，否则是 `{ ruleIds, leadSeconds, blocked }`：`leadSeconds` 是 Feed 实际嵌入的 DISPLAY VALARM 提前量（去重、升序）；为空时 `blocked` 给出原因 |

`alarm.blocked` 的取值（闭合枚举）：

| 值 | 含义 | 依据 |
| --- | --- | --- |
| `alarms_disabled` | 日历提醒未开启；开启后这里会按 `ruleIds` 提醒 | §5.2、前端 §6.3 |
| `cancelled` | 已取消、撤回、删除或延期待定的条目不设闹钟 | §5.2 |
| `date_only` | 只有日期，不能生成精确闹钟 | §5.2、前端 §6.5 |
| `estimated` | 有时刻，但时间依据是官方预计或未确定，不能生成精确闹钟 | §5.2 |

多个原因同时成立时，取表中靠前的一个。

- 前端 §6.5 的"同时命中基础显示的条目不标成额外条目，但仍可显示其提醒信息"，就是 `inclusion.kind = base` 且 `alarm` 不为 null 的条目。
- 顺序由 contracts 定义一次：按北京时间日期分组的时间顺序；同一天内精确时刻在前、纯日期在后（前端 §4.3 的"具体时刻未公布"区域），
  再按 Milestone 身份。页面直接按这个顺序分组显示，不另排。

## 5. 版本核对，以及确认之后配置又变了怎么办

### 5.1 启用时核对

- 首次启用，以及停用后再次启用之前，页面先取 §3 的预览并展示，由用户确认
  （主方案 §5.2"首次启用日历展示提醒预览并由用户确认"；前端 §9.1）。浏览器算的即时预览不能代替这一步。
- 启用请求（P3-07 的 `POST /api/v2/me/calendar/enable`）的请求体在 P3-07 现有字段之外再带两个：
  - `expected_revision` = 预览响应的 `subscription.revision`；
  - `publication_generation` = 预览响应的 `publication.generation`。
  - 注意与 P3-07 已有的 `expected_generation` 区分：那是日历地址（token）的代次，防并发启用与重置；这里是公共数据的发布代次。
- 服务端在启用的**同一个条件提交**里核对：订阅仍为 initialized 且 `revision` 相等；当前完整发布代次仍是该代次。
  任一不符 → 409 `preview_outdated`，不启用。页面重取预览、重新请用户确认，**不自动重试启用**。
- 为什么两样都核对（所有者决定 2；前端 §13.2 原文"若返回预览版本，必须说明它绑定的是哪份配置与哪一代公共数据。启用前发现变化需重新展示"）：
  - 配置变了，用户确认的就不是将要生效的内容；
  - 代次变了，页面上展示的就不是最新事实。发布代次只在内容变化时重建，确认通常只要几十秒，很少撞上；撞上的代价只是多确认一次。
- 重置地址不需要预览：内容不变，只换 token（§6.1）。
- `outcome = blocked` 时页面不提供启用按钮，先显示诊断与下一步（缩小范围；来源过期时说明稍后再试）。
  服务端不为此另设检查：即使启用了，Feed 也会按同一判定返回 503 诊断。

### 5.2 启用之后再改设置

- 保存订阅照常走 P2-06（`expected_revision`，冲突时 409 比较）。ICS 语义变化会递增 `view_revision`，下次拉取生效，地址不变。
- 订阅页的预览区一律由浏览器算（§6）：编辑中按草稿算，保存后按已保存设置算，并标明是哪一种（前端 §6.5）。
- 启用后改设置**不需要**再走一次启用确认，也不做核对。
- 保存成功文案写"地址保持不变；外部日历何时更新由客户端决定"（F3-04 卡的 F2-03 交接），不写"日历已更新"。

### 5.3 不核对、也不承诺的

- 时间推移：窗口按 UTC 日推进、更正到期、预计时间被官方确认，都会让之后的输出与预览不同。
- 预览之后、客户端第一次拉取之前出现的新代次。
- 外部客户端是否应用、何时刷新。

页面不得写"订阅后日历将与预览一致"之类的保证（前端 §13.2："若接口不能提供原子绑定，不承诺确认时所见永远等于稍后拉取结果"）。

## 6. 浏览器里的预览

| 浏览器要做 | 浏览器不可以做 |
| --- | --- |
| 下载 §2 的全部页，按草稿或已保存设置跑 contracts 的同一组函数：投影、解释、排序、条目上限、来源新鲜度 | 用 `/api/v2/events` 等浏览接口的数据拼日历条目：窗口、更正层、时间依据都与 Feed 不同，等于另写一套投影（AGENTS 硬规则 3） |
| 标明四件事：预览的是"未保存草稿"还是"已保存设置"；数据时间 `asOf`；窗口；是否完整 | 把浏览器算的结果当作启用确认的依据；启用只认 §3 |
| 草稿变化后在本地重算，不再请求服务端；数据过了 `PUBLIC_CACHE_FRESH` 再刷新 | 把不同代次或不同 `asOf` 的页混在一起算 |
| §2 取不到（503、断网）时显示样例预览：合成夹具跑同一组函数，标"样例"，并说明真实数据暂时取不到 | 把样例当实际预览，或在取不到数据时显示空日历 |

- **完整**的说法：§2 的数据已下载完整（§2.3）、条目未超限、所需来源新鲜，才能说"按这份设置，日历此刻会包含这些条目"，
  并注明"输出大小启用前再核对一次"。任一条件不满足，照实显示不完整或诊断。
- 游客与已登录用户规则相同；游客的草稿在本机（F2-04），已登录用户的已保存设置取自 `GET /api/v2/me/subscription`。
- 时序：新数据（新代次、新 `asOf`）到了就整份替换并重算；替换期间旧结果标"正在更新"，不与新结果混排
  （前端 §6.5"新配置到来后丢弃旧异步请求结果"）。

## 7. 列表的重要变更数据（已由 P3-14 提供）

- 前端 §4.4 的"近期重要变更"由 P3-14 的 `GET /api/v2/events` 第一页的 `recentChanges` 提供：
  - 取共享更正层仍在保留期内的节点；
  - 只按游戏筛选，不随浏览窗口隐藏；
  - 条数上限 `PUBLIC_READ_LIMITS.recentChanges`，超出时 `recentChangesTruncated = true`。
- 详情页的变更说明用详情接口的 `changes`。
- 数据来自已发布事实与现有共享更正层，不建用户级变更历史，也不另建第二套更正业务（前端 §13.2 末段）。F1-06 按 P3-14 的交接消费。

## 8. 验收要点（A-P3-PREVIEW，已写入 ACCEPTANCE）

- **浏览器与服务端等价**：对一组配置（事件类型被隐藏、节点类型被隐藏、两者都隐藏的提醒关联节点；日历提醒开关；多条规则），
  "候选集合上跑解释函数"与"整代上跑解释函数"的结果逐项相同。夹具里要有窗口外的历史节点、同一 Milestone 的重复节点、
  没有未到期更正的墓碑，证明候选过滤只去掉了任何配置都用不到的节点。未知时间补充夹具必须覆盖：无更正的未知时间、有效更正给出旧日期/时刻、到期边界 `retain_until = asOf`、未知墓碑、同一身份新旧记录冲突，以及 scope/基础筛选/提醒关联命中与不命中。逐项比较 `omitted.unknownTime`，并确认同一身份只计一次、已经输出的取消条目不重复计入 omitted。
- **与 Feed 一致**：同一配置、同一代次、同一 `asOf` 下，预览条目（milestone、`time`、`cancelled`、`leadSeconds`）与 Feed 输出的 VEVENT 逐项一致。至少覆盖：
  - 改期越过窗口未来端；取消、撤回、删除、延期待定；
  - 纯日期与预计时刻的提醒关联节点被省略并计入 `omitted`；
  - 关闭日历提醒后，提醒关联节点与闹钟消失，基础节点保留。
- Feed 输出逐字节不变，现有 Feed 用例全过。
- **公开接口**：带会话 Cookie 与不带时响应体相同，不含账号信息；任何筛选参数都拒绝；`cache-control` 与 P3-14 相同；
  代次变化 → 409 `preview_outdated`；游标 `asOf` 在未来或早于代次发布时间 → 400；单节点超限 → 503 不截断。
- **已保存预览**：不写库（前后比对 `calendar_feeds`、`sessions`、`user_subscriptions` 等表没有变化，不创建 Feed 行）；
  超限、来源过期返回 200 加 blocked 诊断，诊断码与 Feed 在同一配置下的 503 一致；
  续页时代次变化、已保存版本变化、`asOf` 过旧 → 409 `preview_outdated`；401、400 按 §3.4。
- **启用核对**：配置版本或发布代次变了 → 409 `preview_outdated`，Feed 仍未启用；两者都一致才启用。
- 两个接口的查询数与 rows_read 有上界，塞入大量历史后读数不涨。
- 建议变异：候选过滤另写一份窗口判断；候选过滤漏掉"更正延长窗口"的节点；`hiddenBy` 漏掉 `event_type`；
  把预计时刻当精确时刻给闹钟；候选集合漏未知时间补集；忽略有效更正的展示时间；先筛后去重导致旧未知节点复活；启用不核代次；启用不核订阅版本；续页不核代次。

## 10. 所有者决定（2026-09-30）

1. **游客可以看到没有经过筛选的真实日历数据，在网页前端自行筛选。**落在 §2（公开、不筛选、可缓存）与 §6（浏览器按草稿计算）。
   草案原先建议游客只看样例，已按此改掉。
2. **启用时对上数据版本。**落在 §5.1：订阅版本与发布代次都核对。
3. **其余按推荐方案执行。**新接口与字段、409 原因码、复用 P3-14 的字节保护值、新立 P3-15。

同日所有者审定 D3 时定下一条原则："尽可能减少服务端计算，能在浏览器算的就在浏览器算"。验收方据此把一处落到本文：
已登录用户编辑草稿时，预览也由浏览器用同一份代码、同一份公开数据计算。服务端预览只保留"已保存设置"一种，用于启用确认。
草案里服务端的草稿预览（`source=draft`）因此取消；以后若需要，可以在不改条目形状的前提下加回。

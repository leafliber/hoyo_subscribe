## 0. 结论速览

1. 预览由服务端算，用的是个人 Feed 的**同一个投影函数、同一份当前完整发布代次**。只读：不写库、不建 Feed、不续会话。
2. 新增一个只读接口 `GET /api/v2/me/calendar/preview`：`source=saved` 看已保存设置，`source=draft` 带上草稿配置看草稿效果。需要登录。
3. 每一条都说明：为什么在日历里（基础显示，还是为哪条提醒保留、被哪项筛选隐藏），有没有闹钟、没有的原因，是不是更正条目及其事实原因。
4. 启用日历时，请求带上预览所用的**订阅版本号与发布代次**。任一变了就返回 409，页面重新展示预览、让用户再确认一次。
   时间推移不绑定，页面也不承诺"订阅后看到的就是预览这样"。
5. 端侧只做类别层面的即时说明；具体条目只采用服务端结果。游客看标注为样例的预览。
6. 首页"近期重要变更"已由 P3-14 的公共接口提供，不另建。
7. 需要所有者定两件事，见 §8。

## 1. 预览是什么

### 1.1 权威来源

- **条目**：`personalCalendarNodes(config, 当前完整发布代次的快照节点, asOf)` 的结果，加上 §2.3 的解释字段。
  - 与 Feed 读路径（主方案 §6.6）用同一个函数，读代次也用同一套（`calendar/feed/public-read.ts` 的 `FeedPublicCache`）。
  - 不另写窗口、更正、闹钟的判定（AGENTS 硬规则 3）。解释字段也从同一次计算里取，不在预览里重算一遍。
- **上限与新鲜度**：与 Feed 同一套判定。
  - 条目上限用 `feedNodeLimit`（`FEED_BASE_NODE_MAX`、`FEED_PATCH_NODE_MAX`），字节上限用 `FEED_RESPONSE_MAX_BYTES`。
  - 新鲜度用 `feedSourcesFresh`，所需来源由 `requiredFeedSources(config)` 决定。
- **不含缩水守卫**：守卫比较的是同一个 Feed 前后两次成功输出（§6.5），预览没有这个前后关系。
  已启用 Feed 是否被守卫拦截，看 `GET /api/v2/me/calendar`（D3 §2.6）。

### 1.2 预览与实际 Feed 只差这些，页面要照实说

| 差别 | 原因 | 页面怎么说 |
| --- | --- | --- |
| 没有 UID、SEQUENCE、DTSTAMP | 它们属于具体的 Feed（namespace、`view_revision`），启用前还不存在 | 不展示 |
| 按 `asOf` 时刻计算 | 窗口按 UTC 日推移、更正到期、预计时间被确认，都随时间变化 | 标明"按某时的数据预览" |
| 之后会有新代次 | 官方新增、改期、取消都会进入新的发布代次 | "订阅后，日历会随官方更新自动变化"；不承诺订阅后所见与预览相同（前端 §13.2） |
| 外部客户端是否应用、何时刷新 | 服务端决定不了（§6.2、§6.6 末段） | 按 D3 §2.1 的实测资料说明，未测的保持未知 |

## 2. 接口：`GET /api/v2/me/calendar/preview`

### 2.1 请求

普通用户会话（active）即可访问，受限恢复会话也可以读。不接受 pending 会话。只读：
- 不写库，不创建 Feed 行，不记活动水位；
- 不续会话（§4.5：被动 GET 不续期）；
- 响应 `cache-control: private, no-store`。

| 参数 | 含义 |
| --- | --- |
| `source=saved` | 预览云端已保存的设置，服务端自己读 `user_subscriptions`。订阅未初始化时返回 validation，原因 `subscription_uninitialized`（D3 §1.2 同名受阻原因），页面显示"先保存一次订阅内容" |
| `source=draft` 加配置 | 预览草稿。配置只收影响日历的六项：`games`、`regions`、`event_types`、`node_types`（逗号分隔的枚举值），`alarms`（true / false），`rule_ids`（可为空）。按 initialized 的同一套校验（contracts 的枚举与非空约束；未知值、重复值、缺参数都拒绝），字段原因与保存订阅时相同。账号未初始化也可以预览草稿——首次保存前就要看得到效果 |
| `cursor` | 续页，见 §2.4 |

- 变更消息的四个开关不影响日历（`changesCalendarView` 的口径），草稿不收这四项。
- 用 GET 的理由：预览是读取；配置全是有限枚举，查询串有上界（P3-14 的 `queryBytes` 保护值）；
  不需要 CSRF，受限恢复会话也能看。订阅偏好不在 AGENTS 硬规则 7 的秘密清单里，但请求 URL 照样只按外壳白名单记日志。

### 2.2 响应

| 字段 | 含义 |
| --- | --- |
| `source` | `saved` 或 `draft` |
| `subscription` | saved：`{ revision }`，即本次预览用的已保存版本；draft：`null` |
| `config` | 服务端规范化（去重排序）后的配置回显。页面据此核对响应是否属于当前草稿（§4） |
| `publication` | `{ generation, publishedAt }`：本次使用的当前完整发布代次及其发布时间 |
| `asOf` | 计算所用时刻（UTC 毫秒）。窗口、更正到期都按它算 |
| `window` | `feedWindow(asOf)` 的 `{ start, end }` |
| `sources` | `{ fresh, verifiedAt }`。`fresh` 表示所需来源是否都在 `FEED_MAX_STALE` 内核验成功；`verifiedAt` 取所需来源中最旧的一次成功核验，任一来源没有成功记录时为 `null` |
| `outcome` | `ok`：按当前设置与公共数据，能生成完整内容。`blocked` 加 `diagnostic`：Feed 此刻会拒绝输出，诊断码取 `FEED_DIAGNOSTICS` 里的 `base_node_limit`、`patch_node_limit`、`response_byte_limit`、`source_stale` 之一。blocked 时条目照常返回，供用户判断怎么缩小范围 |
| `totals` | 全集计数，不随分页变化：条目总数、基础窗口内、更正层、提醒关联、带闹钟、已取消 |
| `omitted` | 符合筛选、却不会进日历的节点数：`unknownTime`（时间待定）；`reminderNotExact`（为提醒保留、但只有日期或预计时刻，Feed 不输出；只计窗口内或更正层延长的） |
| `items` | 本页条目，见 §2.3 |
| `nextCursor` | 续页游标；`null` 表示本次预览已全部给出 |

- 字节上限的判定用 Feed 同一个序列化器。UID 用与真实 namespace 等长的占位，SEQUENCE 取当前 `view_revision`
  （还没有 Feed 行时取 0），与真实输出只差几个字节。实现卡在报告里写明误差。
- `totals.items = 0` 且 `outcome = ok` 才表示"真实没有匹配节点"，页面才可以显示空日历（§6.5：只有真实无匹配才是成功的空日历）。

### 2.3 条目

| 字段 | 含义 |
| --- | --- |
| `milestoneId`、`eventId` | 身份。同一 Milestone 只出现一次：基础筛选与提醒同时命中也只算一条（§5.2） |
| `game`、`region`、`eventType`、`nodeType`、`eventTitle`、`milestoneTitle` | 与 Feed 的 SUMMARY 同源 |
| `time` | 日历实际输出的时间：有更正时取更正层的展示时间，否则取节点当前时间。只有 `datetime` 与 `date` 两种；时间未知的节点不进日历，计入 `omitted` |
| `status` | 事件状态 |
| `cancelled` | Feed 里是否输出为 CANCELLED：官方取消、本站撤回、节点删除、延期待定 |
| `inBaseWindow` | 是否在基础窗口内。为 false 时，它靠更正层留在日历里，例如改期越过窗口未来端（§6.3） |
| `inclusion` | 为什么在日历里：`{ kind: "base" }`，或 `{ kind: "reminder_associated", ruleIds, hiddenBy }`。`ruleIds` 是引入它的所选规则；`hiddenBy` 是隐藏它的基础筛选：`event_type`、`node_type`，可以两者都有。前端 §6.5 要求这两种隐藏都要说清楚，不能只处理"隐藏结束节点" |
| `patch` | 更正层条目：`{ kind, factReason, oldTime, retainUntil }`，`kind` 取 `CALENDAR_PATCH_KIND`；不是更正条目时为 `null`。删除（`deleted`）、官方取消（`cancelled`）、本站撤回（`retracted`）分开表现 |
| `alarm` | 这个节点与所选提醒规则的关系。没有任何所选规则匹配时为 `null`，否则是 `{ ruleIds, leadSeconds, blocked }`：`leadSeconds` 是 Feed 实际嵌入的 DISPLAY VALARM 提前量（去重、升序）；为空时 `blocked` 给出原因 |

`alarm.blocked` 的取值（闭合枚举）：

| 值 | 含义 | 依据 |
| --- | --- | --- |
| `alarms_disabled` | 日历提醒未开启；开启后这里会按 `ruleIds` 提醒 | §5.2、前端 §6.3 |
| `cancelled` | 已取消、撤回、删除或延期待定的条目不设闹钟 | §5.2 |
| `date_only` | 只有日期，不能生成精确闹钟 | §5.2、前端 §6.5 |
| `estimated` | 有时刻，但时间依据是官方预计或未确定，不能生成精确闹钟 | §5.2 |

多个原因同时成立时，取表中靠前的一个。

- 前端 §6.5 的"同时命中基础显示的条目不标成额外条目，但仍可显示其提醒信息"，就是 `inclusion.kind = base` 且 `alarm` 不为 null 的条目。
- 顺序由 contracts 定义一次：按北京时间日期分组的时间顺序；同一天内精确时刻在前、纯日期在后（前端 §4.3 的"具体时刻未公布"区域），
  再按 Milestone 身份。页面直接按这个顺序分组显示，不另排。

### 2.4 分页与一致性

- 页大小按字节自适应。单页与单条目的字节上限复用 P3-14 合入后的 `PUBLIC_READ_LIMITS.responseBytes` 与 `nodeBytes`：
  预览只含公共数据，保护的是同一件事，不新增参数。单个条目超限时整次预览返回 503，不截断（与 P3-14 相同）。
- 游标绑定 `source`、配置（草稿为规范化配置的摘要，已保存为 `revision`）、`generation` 与 `asOf`。
  续页一律按第一页的 `asOf` 计算，整次预览是同一时刻、同一代次、同一配置的结果，不跨代拼接。
- 以下情况续页返回 409 `preview_outdated`，页面清空后从第一页重取：
  - 发布代次已变；
  - 已保存版本已变；
  - `asOf` 早于当前时刻超过 `PUBLIC_CACHE_FRESH`（沿用 P3-14 裁定的"一份响应副本的新鲜期"）。
- **完整**的判定：`nextCursor = null` 且 `outcome = ok`，页面才能说"这就是按当前设置，日历此刻的完整内容"。
  分页没加载完，或 `outcome = blocked`，都不能说完整（前端 §6.5"分页结果不能声称全量"）。

### 2.5 错误

| 情况 | 响应 |
| --- | --- |
| 未登录、会话待激活或已过期 | 401，`UnauthorizedReason` 照常 |
| 草稿配置不合法 | 400 validation，字段原因与保存订阅相同 |
| 已保存预览，但订阅未初始化 | 400 validation，原因 `subscription_uninitialized` |
| 续页或启用时，绑定的版本或代次已变 | 409 conflict，原因 `preview_outdated`（contracts 新增的闭合枚举值） |
| 没有当前完整发布代次，或读取失败 | 503 temporarily_unavailable，`calendar.reason = snapshot_unavailable`（沿用 Feed 的诊断体） |
| 请求过于频繁 | 429 rate_limited |
| Feed 此刻会拒绝输出（超限、来源过期） | **200**，`outcome = blocked` 加诊断码。预览本身成功了，它如实报告 Feed 会怎样 |

### 2.6 成本

- 只读，热路径的查询数有上界：
  - 会话校验沿用外壳；
  - 已保存模式读一次订阅；
  - 读一次代次头（isolate 内缓存命中时不读整代）；
  - 读一次来源水位。
- 进 `storage/schema.test.ts` 的 rows_read 基准，并用"塞入大量历史后读数不涨"钉住（ENGINEERING §5.4）。
- 冷 isolate 读整代的代价与 Feed 相同，P3-13 之后按活跃集合封顶。
- 限速：按会话的近似限速（P1-07 原语）。预览不是写操作，不计入 `USER_MUTATIONS_DAY`。阈值若需要新参数，按硬规则 2 先进注册表。

## 3. 版本绑定，以及确认之后配置又变了怎么办

### 3.1 启用时绑定

- 首次启用，以及停用后再次启用之前，页面先取 `source=saved` 的预览并展示，由用户确认
  （主方案 §5.2"首次启用日历展示提醒预览并由用户确认"；前端 §9.1）。
- 启用请求（P3-07 的 enable，路径以 P3-07 的实现为准）的请求体带两个字段：
  - `expected_revision` = 预览响应的 `subscription.revision`；
  - `preview_generation` = 预览响应的 `publication.generation`。
- 服务端在启用的**同一个条件提交**里核对：订阅仍为 initialized 且 `revision` 相等；当前完整发布代次仍是该代次。
  任一不符 → 409 `preview_outdated`，不启用。页面重取预览、重新请用户确认，**不自动重试启用**。
- 为什么两样都绑：前端 §13.2 原文是"若返回预览版本，必须说明它绑定的是哪份配置与哪一代公共数据。启用前发现变化需重新展示"。
  - 配置变了，用户确认的就不是将要生效的内容。
  - 代次变了，页面上展示的就不是最新事实。发布代次只在内容变化时重建，确认通常只要几十秒，很少撞上；撞上的代价只是多确认一次。
- 重置地址不需要预览：内容不变，只换 token（§6.1）。
- `outcome = blocked` 时页面不提供启用按钮，先显示诊断与下一步（缩小范围；来源过期时说明稍后再试）。
  服务端不为此另设检查：即使启用了，Feed 也会按同一判定返回 503 诊断。

### 3.2 启用之后再改设置

- 保存订阅照常走 P2-06（`expected_revision`，冲突时 409 比较）。ICS 语义变化会递增 `view_revision`，下次拉取生效，地址不变。
- 订阅页的预览区：编辑中显示 `source=draft` 的结果，保存后显示 `source=saved`，并标明是哪一种（前端 §6.5）。
- 启用后改设置**不需要**再走一次启用确认，也不做绑定。
- 保存成功文案写"地址保持不变；外部日历何时更新由客户端决定"（F3-04 卡的 F2-03 交接），不写"日历已更新"。

### 3.3 不绑定、也不承诺的

- 时间推移：窗口按 UTC 日推进、更正到期、预计时间被官方确认，都会让之后的输出与预览不同。
- 预览之后、客户端第一次拉取之前出现的新代次。
- 外部客户端是否应用、何时刷新。

页面不得写"订阅后日历将与预览一致"之类的保证（前端 §13.2："若接口不能提供原子绑定，不承诺确认时所见永远等于稍后拉取结果"）。

## 4. 端侧即时预览的边界

| 端侧可以算（只用 contracts 的纯函数） | 端侧不可以算 |
| --- | --- |
| **类别说明**：对 catalog 给出的"事件类型 × 节点类型"有限组合跑 `effectiveCalendarNodes`，即时显示哪些类别会进日历、哪些是为哪条提醒保留的 | **具体条目**：有哪些节点、什么时间、有没有取消，只采用服务端响应 |
| **闹钟规则说明**：规则注册表的提前量，以及"纯日期、预计、未知不设精确闹钟"这条固定规则 | 用公共浏览接口（`/api/v2/events`）的数据自己拼日历条目：窗口、更正层、时间依据都与 Feed 不同，等于另写一套投影（AGENTS 硬规则 3） |
| **变更消息范围**：`changeNotificationScope`（前端 §6.4） | 把旧响应的条目按新草稿增删后当作结果展示 |
| **样例预览**：合成夹具跑同一组函数，标"样例 · synthetic"；游客、或服务端预览不可用时使用 | 把样例当作启用确认的依据 |

请求时序：
- 草稿变化后防抖再请求。新请求发出后，旧结果标"正在按新设置更新"，不与新结果混排。
- 响应回来先核对：草稿看回显的 `config`，已保存看 `subscription.revision`，不是当前的就丢弃（前端 §6.5"新配置到来后丢弃旧异步请求结果"）。

## 5. 列表的重要变更数据（已由 P3-14 提供）

- 前端 §4.4 的"近期重要变更"由 P3-14 的 `GET /api/v2/events` 第一页的 `recentChanges` 提供：
  - 取共享更正层仍在保留期内的节点；
  - 只按游戏筛选，不随浏览窗口隐藏；
  - 条数上限 `PUBLIC_READ_LIMITS.recentChanges`，超出时 `recentChangesTruncated = true`。
- 详情页的变更说明用详情接口的 `changes`。
- 数据来自已发布事实与现有共享更正层，不建用户级变更历史，也不另建第二套更正业务（前端 §13.2 末段）。F1-06 按 P3-14 的交接消费。

## 6. 验收要点（审定后作为 A-P3-PREVIEW 进 ACCEPTANCE）

- **与 Feed 一致**：同一配置、同一代次、同一 `asOf` 下，预览条目（milestone、`time`、`cancelled`、`leadSeconds`）与 Feed 输出的 VEVENT 逐项一致。用例至少覆盖：
  - 事件类型被隐藏、节点类型被隐藏、两者都被隐藏的提醒关联节点；
  - 改期越过窗口未来端；取消、撤回、删除、延期待定；
  - 纯日期与预计时刻的提醒关联节点被省略并计入 `omitted`；
  - 关闭日历提醒后，提醒关联节点与闹钟消失，基础节点保留。
- Feed 输出逐字节不变，现有 Feed 用例全过。
- 预览不写库：前后比对 `calendar_feeds`、`sessions`、`user_subscriptions` 等表没有变化，不创建 Feed 行。
- 超限、来源过期返回 200 加 blocked 诊断，诊断码与 Feed 在同一配置下的 503 一致。
- 续页时代次变化、已保存版本变化、`asOf` 过旧 → 409 `preview_outdated`；不跨代拼接。
- 启用绑定：配置版本或代次变了 → 409 `preview_outdated`，Feed 仍未启用；两者都一致才启用。
- 查询数与 rows_read 有上界，塞入大量历史后读数不涨。
- 401、400 按 §2.5；草稿不合法时的字段原因与保存订阅相同。
- 建议变异：预览另写一份窗口判断；`hiddenBy` 漏掉 `event_type`；把预计时刻当精确时刻给闹钟；启用不核代次；续页不核 `asOf`。

## 8. 请所有者确认

1. **游客能不能看实际预览。**本文按"只给已登录用户"写：
   - 唯一依赖预览的决定是启用日历，这本来就要登录；
   - 公开接口保持主方案 §8.2 的三个（catalog、events、status）。
   - 游客看样例预览，并提示"登录后可以看按实际数据生成的预览"。

   另一种做法：再加一个公开的 `GET /api/v2/calendar/preview`，只收草稿配置，响应形状相同但没有 `subscription`，可按 `PUBLIC_CACHE_FRESH` 进公共缓存。
   游客也能看实际预览；代价是多一个公开的计算端点，靠边缘限速兜底。以后再加也不改响应形状。
2. **启用时是否连发布代次一起绑定。**本文按"订阅版本与发布代次都绑"写，这是前端 §13.2 的原文要求。
   只绑订阅版本也说得通：代次变化只是事实更新，不改变用户确认的是什么；代价是启用那一刻展示的可能不是最新事实。
3. 其余各项如无异议，按本文执行：新接口与字段、409 原因码、复用 P3-14 的字节保护值、新立 P3-15。

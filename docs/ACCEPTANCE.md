## 1. 验收 ID 约定

- 后端/管线：`A-<阶段>-<域>`，例如 `A-P2-SESSION`。
- 前端：直接用前端文档的 `U01`…`U29`、`U09a` 等编号。
- 测试标题必须包含验收 ID，可被 `grep -r "A-P2-SESSION" --include="*.test.ts"` 找到（见 `ENGINEERING.md` §7）。

## 2. 证据的三个等级

| 等级 | 含义 | 可用于 |
| --- | --- | --- |
| **E1 自动化** | 仓库内测试，重跑可复现 | 绝大多数验收项 |
| **E2 受控观测** | 隔离环境的实际运行截图/日志，含时间与环境标识 | 前端交互、客户端行为、性能 |
| **E3 外部事实** | 真实账户、真实收件人、真实客户端、真实账单产生的证据 | 仅 P0 与 P5 的放行项 |

**E3 不能由 E1/E2 替代。**模拟登录、模拟已投递、模拟兼容性不得进入生产判定（前端 §14.3）。合成样本必须显式标记 `synthetic`，不得当作官方证据。

### 2.1 验收方的必做动作：变异测试

报告里写"已做反向验证"不等于反向验证有效。验收时**亲手破坏实现，确认测试真的失败**：

```text
1. 改实现（拆掉守卫谓词 / 放宽品牌类型 / 退化成 COUNT→INSERT）
2. ★ 先确认变异落地 —— 输出 grep -c 替换数或 git diff --stat，非零才继续
3. 跑测试，期望 FAIL，并核对失败的是不是该失败的那几条
4. 还原，复跑确认恢复绿（证明失败来自变异而非环境）
```

**第 2 步不能省。**`sed` 模式没匹配上时文件原封未动，测试照常通过，

## 1. 产品范围与关键取舍

### 1.1 首版交付

| 领域 | 范围 |
| --- | --- |
| 内容 | 原神、崩坏：星穹铁道、绝区零；CN、简体中文；仅开放官方来源验证通过的类别 |
| 日程 | 前瞻、维护、限时活动、卡池；开始、结束、阶段解锁、奖励截止；预计与实际时间分开 |
| 账号 | 邮箱 OTP、可撤销长会话、离线恢复码、换邮箱、删除；没有用户设置的密码 |
| 配置 | 每账号一份云端订阅；本地保留临时筛选、草稿、缓存和界面设置 |
| 日历 | 固定只读 URL；保存筛选无需换地址；可启用 VALARM；明示客户端兼容范围 |
| 通知 | 邮件需单独同意且受预算约束；Web Push 按浏览器授权，不自动跟随登录开启 |
| 运营 | 来源与候选审核、用量、降级状态、退订、设备管理、备份和恢复 |

游客可以查看全部公开日程，不因访问而创建 User。账号的主要价值是**跨设备维护同一份日历及提醒规则、长期地址和撤销控制**；邮件是限额补充，不再作为全部账号获得提醒价值的前提。

不做玩家米哈游账号登录、私人游戏数据、任意抓取地址、任意规则脚本、逐用户 LLM、短信、营销代发、全量视频转录、自建 SMTP。首版不同时增加密码、Magic Link、OAuth 和 Passkey。

### 1.2 本版明确改变的合同

| 决策 | 实现边界 |
| --- | --- |
| 日历优先 | 所有账号均可使用个人 ICS 与日历提醒设置；邮件名额独立、可回收 |
| 完整快照替换 | 个人筛选移除和普通窗口退出以完整快照为准；不再保留 `feed_retirements` |
| 真实更正不靠静默消失 | 取消、未知日期延期及跨窗口改期，通过共享更正投影表达 |
| 独立日历版本 | 删除全局 `calendar_change_no`；使用节点版本与逻辑 Feed 版本组合 |
| 免密码但有离线恢复 | OTP 为常规登录；高熵单次恢复码用于邮箱不可达时重新取得控制 |
| 可持续邮件预算 | 月预算拆分、每日平滑分配、用户限频与公平调度共同生效 |
| 设置解耦 | 日历可见性与提醒资格分别定义，提醒不再隐式依赖日历节点筛选；变更通知也不再挂在 `rule_ids` 上，规则可以为空 |
| 邮件是补充而非主通道 | 常规提前提醒默认由 VALARM 承担，邮件默认只发取消/更正/晚发现；预算与名额随之向紧急池和认证池倾斜 |
| 通知按批合并 | 同一用户同批次同优先级的多条提醒合并为一封，只允许提前、不允许推迟，避免每日一封的额度把同刻多节点砍成一条 |
| 账号先空后填 | 新账号以 `uninitialized` 建立，服务端不替用户写默认订阅；未完成首次保存不能开通任何通道 |
| 删除等于删除 | 完整快照下缺席即删除，因此输出前加一道无法解释的收缩守卫，宁可 503 也不下达疑似错误的删除指令 |

**不承诺任意日历客户端都能正确处理完整快照或 VALARM。** 至少一个目标客户端通过删除、恢复、改期及提醒测试后，才能开放“日历提醒可用”的账号版本；未通过的客户端明确标为未支持或功能受限。不能一边删掉撤销状态，一边沿用“所有客户端都自动正确更新”的承诺。

### 1.3 凭证与操作边界

登录会话管理本人资源；Feed token 只读日历；退订 token 只关闭对应地址的业务邮件；Push receipt token 只确认本浏览器接收；恢复码只进入受限的恢复流程。它们不复用密钥或授权范围。

退出本机、关闭邮件、暂停浏览器通知、停用日历和删除账号是不同操作。退出对话框提供“仅退出”和“退出并暂停本浏览器通知”两个明确按钮，不用预勾选项替用户作决定；无论选择哪项，都不自动关闭邮件或外部日历。

## 2. 平台、部署与依赖预案

### 2.1 最小架构

```text
官方来源 → PipelineDO → D1：正文版本 / 候选 / 事件 / 节点 / 证据 / 公共快照
                               │                           │
Astro 静态 Web → Worker API → 用户 / 会话 / 云端订阅       outbox
                               │                           ↓
                         个人 Feed 鉴权                DeliveryDO
                               │                       ├─ MailProvider → Cloudflare Email
                         共享数据 → ICS                └─ 可选 Web Push

Email Event Subscriptions → 反馈 Queue → Worker queue() → D1；失败进入 DLQ
Cron → 修复两个固定 DO 的唤醒、租约、清理与用量对账
```

一个 TypeScript 仓库、一个 Worker 项目、一个 D1、两个固定 SQLite-backed DO：`PipelineDO/main` 与 `DeliveryDO/main`。DO 不按账号或文章创建，D1 是正式状态源；Queue 只承接邮件反馈，不保存数月后的提醒。

前端使用 Astro 静态页面和小型 TypeScript 模块，API 可用 Hono。静态资源直达；账号 API、Feed、退订等动态路径进入 Worker。浏览器只缓存白名单公开内容，私人 API 不进入 Service Worker 缓存。不新增 VPS、Redis、PostgreSQL、向量库或通用 Agent 框架。

### 2.2 Cloudflare 邮件前提

当前 Email Sending 标为 Beta；面向任意普通收件人的发送需要 Workers Paid。账户基础费最低 US$5/月，邮件每账单周期含 3,000 封，超出 US$0.35/1,000 封；账户其他应用共享额度。实际日发送权限随账户情况变化，不能从月包含量推导出来。[R01][R02][R03]

Email Routing 只是可选入站转发，不负责本站用户认证，也不能用 Cloudflare 手动验证的 routing destination 代替面向普通用户的发送验证。

站点采用一个稳定 HTTPS origin；认证和业务使用不同发件子域，DNS 按实际控制台生成的记录配置，不覆盖已有收信系统。关闭认证域的 Email preview；两个用途均关闭“静默丢弃受抑制收件人”，确保发送被阻止时得到明确错误。[R04]

原生 `send_email` binding 是唯一首版发送路径；MailProvider 接口返回 `accepted(messageId) / rejected / unknown`，不得只返回 boolean。发件人、收件引用与模板来自服务端，不能接收用户任意 `to/from/html`。[R05]

### 2.3 Beta 故障与替换

| 故障 | 立即行为 | 恢复路径 |
| --- | --- | --- |
| 邮件发送不可用或账户配额降低 | 暂停新验证码发送和业务外发；不先生成即将过期的验证码；公开状态提示 |
| 邮箱被供应商抑制 | 冻结适用邮件，登录后的账号页突出显示；不冻结已有会话或公开数据 |
| 邮箱不可达且会话过期 | 用户可使用离线恢复码进入账号，停用 Feed、导出或准备换邮箱 |
| Beta 接口撤销或长期不适用 | 保持公共查询、已有会话、恢复入口和 ICS；由所有者批准替代 Provider 后迁移 |

替代 Provider 只需实现既有发送结果、反馈和抑制合同，不重做用户表。切换前必须验证测试收件人、幂等边界、退订头、反馈映射和费用，迁移现有退订及抑制状态；**不自动开通新服务，不借换域或换供应商绕过投诉/政策抑制**。整个 Cloudflare 平台故障不属于这一邮件单点预案的可恢复范围。

### 2.4 P0 必须得到的真实证据

记录实际 Paid/Beta 资格、站点与发件域、账单周期起止、账户日发信权限、其他应用额度占用；测试普通收件人的 messageId 与反馈 Queue 关联。仅给 routing verified destination 发成功，不能证明 Email Sending 生命周期反馈链成立。[R06]

同时验证目标 Cloudflare 环境访问官方来源、D1 条件事务、DO 发送位置、模型真实计费输出，以及至少一个客户端的完整快照与 VALARM 行为。未获收费或生产权限时只交付探测代码和缺口，不擅自开通资源。

## 3. 官方事实、时间与抽取管线

### 3.1 来源适配

保留原稿的候选路径如下。它们是**继承的实现线索，不是本轮连通性证明**；参数、发布者 UID、栏目、区域与分页由 P0 保存真实样本后登记。

| 来源 | 原稿线索 |
| --- | --- |
| 米游社官方资讯 | `post/wapi/getNewsList`；生产主机与官方发布者身份另行核验 |
| 原神公告 | `hk4e-ann-api.mihoyo.com/common/hk4e_cn/announcement/api/` |
| 星铁公告 | `hkrpg-ann-api.mihoyo.com/common/hkrpg_cn/announcement/api/` |
| 绝区零公告 | `announcement-api.mihoyo.com/common/nap_cn/announcement/api/` |

后三项的列表/正文方法为 `getAnnList/getAnnContent`，不得把列表展示时间当成活动时间。

来源注册项包含 `source_id、game、region、adapter、approved_hosts、verified_publishers、cursor、poll_policy、last_success_at、verification_state`。上游 ID 存字符串；生产只访问经审核的官方地址。第三方代码可以用于定位接口，第三方聚合后端不能冒充官方来源。遇到鉴权、验证码或访问限制，停用并提示维护，不实施绕过。

适配器提供 `list(cursor, limit) → items/next_cursor/complete` 与 `fetchArticle(stub)`。`complete` 表示扫描范围真的完成；HTTP 成功不等于正文完整。请求限制域名、重定向、超时、大小和类型，不提供公开通用抓取代理。

### 3.2 采集与版本

普通轮询保留重叠窗口，不能仅按最大 ID 推进水位；近期公告复查正文，仍关联活跃节点的公告继续跟踪。分页、补漏和重试保存游标，每批有上限，全部用户共用采集结果。

`(source_id, external_id)` 标识文章；语义内容变化新增不可变 ArticleVersion，保存正文块、内容 hash、官方 URL、发布时间、抓取时间、媒体引用及 `completeness`。去掉阅读量等噪声，但不能去掉时间和阶段文本。引用图片只有 URL 没有内容验证时，不声称可以发现同 URL 换图。

正文截断、图片承载关键日期或来源暂空进入缺口/审核状态；不转成“无活动”。没有官方取消证据时，抓取失败、文章删除或列表为空都不能自动取消事件。首版不做全量视频转录，必要图片日期由人工核验或另行批准的视觉流程处理。

### 3.3 Event / Milestone 合同

| 维度 | 合同 |
| --- | --- |
| 事件类型 | `livestream / maintenance / limited_event / gacha` |
| 节点类型 | `start / end / phase_unlock / reward_deadline / expected_end / actual_end`；同类阶段用稳定 milestone_key 区分 |
| 审核状态 | `pending / approved / rejected` |
| 事件状态 | `scheduled / postponed / cancelled / retracted`；最后一项表示系统纠错，不是官方取消 |
| 时间依据 | `official_explicit / deterministic_derived / official_estimate / unresolved` |
| 时间精度 | `datetime / date / unknown` |

精确时间存 UTC 毫秒，日期存 `YYYY-MM-DD`，保留源时区、原始表达和证据。只有日期不补成精确午夜；“预计维护五小时”不是实际开服；“更新后开放”不能猜固定时刻。跨年、省略年份和结束包含性无法唯一确定时进入审核。

提醒只使用精确、证据通过的明确时间或确定性推导。预计与未知时间可在 Web 标注，但不冒充精确提醒。一个 Event 可有多个 Milestone，奖励截止与玩法结束分别保存；身份不含日期，改期不换 ID。

### 3.4 规则、模型与人工三条发布路径

```text
完整官方版本 → 规则分类
               ├─ 已通过测试的结构化字段/明确日期模板 → 确定性候选
               ├─ 需要语义理解 → 批准的模型 profile → 结构化候选
               └─ 图片、矛盾、超预算或无可用模型 → 人工审核队列
候选 → 统一来源/证据/时间校验 → 原子发布
```

规则兜底不是宽泛正则猜日期：只有明确事件类别、完整时间和区域均有证据的白名单模式可自动发布，模板不匹配就审核。人工可以直接依据保存的官方材料创建/修正候选，**不依赖先取得一次模型结果**。

模型一次提交分类、多个事件、节点、变更关系、证据块引用及歧义。Schema 限定类型、枚举、长度、数组、空值和未知字段；来源身份由服务器注入。模型不获得用户数据、秘密、网络工具或写库权限；自报置信度不能代替证据校验。

同一 `article_version + extractor/prompt/schema/model_profile` 成功结果可重放，结构修复和网络重试分别有界。保留主 profile；经济 profile 只有 P0 同时通过质量与费用测试后才可配置，否则为未启用，不能临时换陌生模型。

### 3.5 模型预算与降级

原候选 `@cf/qwen/qwen3-30b-a3b-fp8` 保留为测试对象，不承诺已适合本项目。P0 记录输入、全部计费输出、可见 JSON、推理相关 usage、截断率、修复率、延迟和单篇费用的分布；不能用“可见 JSON 大小”代替供应商计费输出，也不猜测部署支持关闭思考参数。[R07]

```text
单次最大预留 = 输入保护值 × 输入费率 + 最大计费输出 × 输出费率
实际结算     = 供应商 usage 对应费用 + 已发生的修复/重试费用
可处理量     = 可用日预算 / 实测每篇费用（分别报告中位数与高分位）
```

达到软线：优先前瞻、维护、截止和关键更正，停低价值回填；达到硬线或模型故障：确定性规则与人工仍可发布，其他内容排队并在状态页显示缺口。经济 profile 也受同一总账本约束；达到硬线不能靠切便宜模型继续越额。恢复后按仍有时效价值排序，不用陈旧积压耗尽新一天预算。

### 3.6 发布一致性

去重分为文章身份、抽取版本和业务事件关联三层。不同公告可能描述同一活动，标题相似不足以自动合并；人工保护字段只能通过带理由的操作修改，迟到旧模型结果只能留历史。

一次条件提交更新 Event、Milestone、证据关联、不可变修订、必要日历投影、outbox 与快照待更新状态。D1 batch 的 SQL 失败回滚不等于 CAS 更新零行会自动失败；实现必须用统一条件守卫或约束让整批相关写入一起成立或一起失败。[R08]

`event_revision` 描述事件修订，`schedule_revision` 只在时刻/提醒语义变化时增加，`public_ical_revision` 对影响该节点日历表现的变更增加。完整快照先构建后切换可见代次，禁止跨代拼接；旧文章版本、旧租约和旧配置不能覆盖新状态。

## 4. 用户、认证与离线恢复

### 4.1 邮箱身份规范

去除两端空白，规范域名并小写；首版支持 ASCII 本地部分。本地部分也折叠小写用于**本站账号身份键**，不删除点号、加号或标签，不做供应商特例合并。页面说明这是产品的身份约定，不声称所有邮件服务器天然大小写不敏感。

保存 `email_key = HMAC(lookup_key, canonical_email)` 和加密的已验证实际投递地址。已有身份再次请求登录时，验证码只发到数据库中已验证的实际地址，**不按请求中不同大小写的地址改投**，防止极少数大小写确实不同的邮箱被错误授权。

新地址挑战绑定实际投递串与注册预占；消费时检查身份/地址版本。若并发期间同规范键已被另一个实际地址建立，不能把验证码成功直接转成该账号登录，须重新走向已验证地址发送的流程。首次绑定后，任何实际投递地址改变都属于换邮箱。

### 4.2 申请验证码前的准入

认证检查顺序：请求结构与尺寸 → 同源/CSRF → 近似限速 → Turnstile 服务端校验 → 邮箱与全局配额 → 原子预占 → 创建挑战及发信任务。Turnstile 是单次验证，不替代会话或配额。[R09]

`/status` 公布全局 `registration_open`，不提供按邮箱查询是否注册的接口。存在账号时按登录路径处理；新身份只有注册开放、容量和注册邮件预算均可预占时才发码。满额或关闭注册时，未知邮箱不生成实际发信任务；公开响应仍与普通申请同形，说明“符合条件的请求将发送验证码”。不能回显“该邮箱不存在”。

注册槽在验证码有效期间保留，验证成功转成账号存量，过期释放；同一规范邮箱共享有限预占，防止并发超卖。已有用户登录不占新注册槽。攻击下可以全局关闭注册或切为受控邀请开放，但不承诺邮箱、IP 或 Turnstile 能证明真人唯一性。

### 4.3 OTP 与预认证 Cookie

首次同源 POST 生成 `__Host-preauth`，Secure、HttpOnly、SameSite=Lax、Path=/，不设置 Domain；预认证 CSRF 与该 Cookie 绑定，并携带服务端认证的签发/截止信息，用于检查一次性凭证消费前的交付余量。不同标签页复用同一个未失效随机值，不把它升级为正式会话。

创建有效挑战时续期**同一个 Cookie 值**，确保浏览器保留期限覆盖该上下文所有未过期挑战的最晚结束时间，再加 `AUTH_COMPLETION_TTL + PREAUTH_MARGIN`。活动 Cookie 临近到期不影响新验证码；返回响应丢失或用户清 Cookie 仍可能失败，须提供重新申请提示，不能把它误报为验证码错误。

验证码均匀随机生成，验证表保存带独立 pepper 的 MAC，绑定用途、challenge_id、email_key、地址版本、generation 和验证码。验证码原值只存在短期加密发信载荷中，在接受、消费、过期或终止后清除；服务器能在发送阶段解密，不宣传不可读取。

重发只旋转本挑战的 generation，不重置累计失败次数、不延长挑战最初截止、不废掉其他浏览器挑战。网络重试沿用绑定预认证上下文的 idempotency_key；明确重发才创建新发送意图。错误尝试必须持久扣减，不能被返回错误的事务回滚抵消。

### 4.4 原子消费与响应丢失

正确验证后，挑战消费、可能的新账号、注册容量转换及 pending Session 一致提交。多次并发最多一次成功消费，不能出现“会话已创建但挑战仍可用”。

新建账号写入的订阅行状态为 `uninitialized`，**不写入任何代替用户选择的游戏、事件或节点默认值**。附录 A 的 `DEFAULT_*` 只是界面预选建议，用户首次保存时才成为正式配置并转为 `initialized`。`uninitialized` 账号可以浏览、登录、管理会话和删除账号，但不能启用个人 Feed、邮件或 Push，也不产生任何通知发生项匹配；界面据此引导先完成一次保存。

为避免提交成功但 Cookie 响应丢失迫使用户再次收码，保留一个短期**认证完成回执**：绑定原 preauth、操作幂等键及目标 pending Session，保存加密的待交付 Cookie 值。客户端可通过同源完成接口重新取得同一待激活会话；这不是重新开放验证码，也不能凭 challenge_id 单独领取。

消费一次性凭证前，预认证上下文必须已成功建立并具备完成交付所需的剩余期限；不足则先要求续期，不能先消费恢复码。回执仅在 `AUTH_COMPLETION_TTL` 内、pending 状态且原浏览器上下文匹配时可取。客户端携带收到的 Cookie 完成激活后立即清除可恢复值；到期由清理任务兜底。因此“会话常态只存 hash”有明确的短期交付例外，不保留长期可重放的登录结果。

### 4.5 长会话与孤儿会话

正式 Cookie 为 `__Host-session`，与预认证分离，属性遵守上一节的安全边界；会话 token 使用 `SECRET_BITS` 随机强度，常态只存 hash，不放 URL、localStorage 或配置导出。[R10]

```text
pending --浏览器带新 Cookie 确认--> active --到期/撤销--> revoked
   └─超时清理，不计入 active 会话名额
```

pending 只允许查看脱敏设备列表及完成激活。active 名额已满时，由用户明确选择撤销哪个旧会话再原子激活；**不自动淘汰最早创建的会话**。未拿到 Cookie 的孤儿不会把正常设备挤下线。

用户要在这里做出“撤销哪一个”的决定，因此会话列表必须给出可判断的信息：激活时用户可自填设备名称，缺省标签由创建时间加粗粒度平台类别（桌面/移动/未知）组成，并同时展示 `created_at` 与 `renewed_at`，且说明 `renewed_at` 的精度受 `SESSION_RENEW_INTERVAL` 限制、最多滞后一个续期间隔。**设备标签只是用户显示信息，IP/UA 指纹不参与鉴权，也不据此推断真人身份。**

有效期同时受绝对期限和不活跃期限限制。绝对期限在**创建会话时**取 `SESSION_ABSOLUTE_TTL ± SESSION_ABSOLUTE_JITTER` 内的随机值并固定写入，避免上线期集中注册的账号在同一窗口集中到期，把周期性重新认证压成一次发信洪峰。

“真实前台操作”有明确定义，不留给实现解释：**用户在本会话中完成一次显式的状态变更或账号管理请求**（保存订阅、启用/停用通道、管理会话或设备、换邮箱、轮换恢复码、导出数据）之后，前端可发起一次续期 POST。页面加载、被动 GET、预取、后台标签页、Service Worker、外部日历拉取和收到邮件都**不算**。每个会话最多按 `SESSION_RENEW_INTERVAL` 更新一次活动与到期时间，且 `expires_at ≤ created_at + 本会话抖动后的绝对期限`。

因此只用外部日历、长期不回网页的用户，其会话按 `SESSION_IDLE_TTL` 到期并需要重新认证；这是有意的安全取舍，但**认证预算必须按 `SESSION_IDLE_TTL` 而不是绝对期限估算**（见 §9.3）。账号本身不因此被回收，回收另按 §9.4 的活动信号判断。

私人操作从主状态核对 Session、账号状态、auth_epoch、恢复 epoch 和到期；Cookie 写操作同时做 Origin、CSRF 和所有权检查。临近到期在网页提示重新验证；不能靠一封可能同样被抑制的提醒邮件保障恢复。

### 4.6 离线恢复码

首次登录后，用户保存一份 `recovery_id + 高熵随机秘密`，服务端只存 hash。首次开启长期 Feed、邮件或 Push 前要求完成保存确认；普通偏好导出、日志和邮箱通知不得包含恢复码。重新显示旧码不可行，轮换必须有最近认证证明。

恢复码可用于两项明确动作：

- **紧急停用：**无邮件、无既有会话也能凭该码执行，撤销所有会话与 Feed、关闭业务邮件、暂停 Push；不返回任何私人数据。**该动作不消费恢复码**：它是纯防御操作，持码者本来就能直接走恢复登录，消费它只会让合法用户在停用之后失去唯一的回账路径。重复停用幂等，另受 `RECOVERY_ATTEMPTS_HOUR / RECOVERY_ATTEMPTS_DAY` 限制。
- **恢复登录：**消费该码，执行同样的安全暂停，创建 pending 恢复会话；激活后可查看、导出、删除或更换邮箱。**恢复会话激活后立即交付新恢复码，在用户完成保存确认前只允许查看、导出、保存新码和删除账号**，不得启用任何通道或更换邮箱——否则一次中断就会让账号既无旧码也无新码。重新启用各通道必须由用户逐项确认。

恢复流程沿用预认证绑定、限速、用途限定、一次消费与短期完成回执，避免响应丢失把用户唯一的码消耗掉。恢复权限是新的认证入口，必须视为高价值凭证，**不是“没有增加恢复攻击面”**。

恢复入口有自己的闸门，不沿用验证码那一套参数：按 `recovery_id` 与来源分别限制 `RECOVERY_ATTEMPTS_HOUR / RECOVERY_ATTEMPTS_DAY`，超出返回统一的稍后重试；`recovery_id` 与秘密一起校验，单独提交 `recovery_id` 不得产生存在性差异。高熵秘密使暴力猜测不可行，这些限制针对的是枚举与刷量，不是猜中概率。

恢复码不证明某个新邮箱的所有权。换邮箱仍须验证新邮箱；发送平台整体故障时，可先停止旧服务和导出，但不能假装新邮箱已验证。旧邮箱、会话和恢复码全部丢失时，不允许管理员仅凭一封自述邮件接管账号。

### 4.7 最近验证、换邮箱和危险操作

最近认证证明来自本次实际成功的 OTP 或恢复码校验，绑定 Session、用途、目标摘要和有效期；消费后失效，不能由客户端提交时间戳冒充。

换邮箱要求“当前邮箱 OTP 或恢复码证明”再加“新邮箱 OTP”；原子更新实际地址、email_key、email_version、auth_epoch，撤销旧会话和未完成挑战，停止旧地址待发任务，为当前操作交付新会话。新邮箱业务邮件默认关闭，user_id 与订阅保持不变。

删除账号、轮换恢复码需要最近认证；**Feed 停用、启用、重置统一只需有效会话、CSRF、显式确认和限速，不要求额外 OTP**。重置与 disable→enable 权限等价，邮箱失联时也能撤销只读地址。已进入恢复登录的 Feed 地址被撤销后，重新启用必须替换外部订阅 URL。

## 5. 云端订阅、提醒规则与前端

### 5.1 唯一配置模型

```json
{
  "schema_version": 3,
  "revision": 1,
  "scope": {"games": ["genshin", "hsr"], "regions": ["CN"]},
  "calendar": {
    "event_types": ["livestream", "maintenance", "limited_event"],
    "node_types": ["start", "end", "reward_deadline"],
    "alarms_enabled": true
  },
  "notifications": {
    "rule_ids": ["livestream_start_1h", "limited_end_1d"],
    "new_event": false,
    "important_change": true,
    "cancelled_or_retracted": true,
    "late_discovery": true
  }
}
```

此例只表示结构，初值见附录 A。数组为有限枚举，去重排序，拒绝未知键和额外层级。邮件 enabled、设备权限、Feed 状态是独立服务状态，不以 JSON 中一个布尔值冒充实际开通或用户同意。

订阅行另有 `state ∈ {uninitialized, initialized}`。`scope` 与 `calendar.event_types` **不得为空**这一约束只适用于 `initialized`；`uninitialized` 表示用户尚未做过任何选择，此时不允许启用 Feed、邮件或 Push，也不参与任何通知匹配（见 §4.4）。首次成功保存一份合法配置即转为 `initialized`，且不可退回。`notifications.rule_ids` **可以为空**：只要变更消息而不要任何提前提醒是合法配置（见 §5.3）。

`scope` 同时限制日历与通知的游戏/区域；`calendar.event_types/node_types` 仅控制基础可见节点；`notifications.rule_ids` 是精确提前提醒的唯一业务选择源。规则注册表自身给出事件、节点和提前量，**发送资格不再与 calendar.node_types 隐式相交**。

### 5.2 VALARM 与独立可见性的协调

日历提醒启用后，实际输出节点为：

```text
有效日历节点 = 基础可见节点 ∪ 当前提醒规则需要的节点
              （均受 scope、时间依据及第 6 章窗口合同约束）
```

提醒所需而被基础筛选隐藏的节点作为“提醒关联节点”显示在配置预览中，沿用同一个 Milestone/UID，不另造重复事件。用户可以取消对应规则或关闭日历提醒，不能默默勾选提醒却输出不承载提醒的日历。

邮件与 Push 不受日历可见性影响；关闭 VALARM 也不关闭它们。只对合法精确节点嵌入 DISPLAY VALARM，触发量来自规则；同节点相同提前量去重。预计和未知节点不生成精确闹钟。首次启用日历展示提醒预览并由用户确认，兼容未验证时不能标为“提醒已可靠启用”。[R11]

### 5.3 规则注册与变更开关

固定 rule_id 及定义只列于附录 A，不接受任意脚本或自然语言表达式。规则标识一旦发布不得改成另一种提前量；新增语义用新 ID。

更正、取消、公布和晚发现不是“提前零分钟”规则，**范围也不再挂在 `rule_ids` 上**。它们的范围是：

```text
变更通知范围 = scope ∩ ( calendar.event_types ∪ rule_ids 所涉及的事件类型 )
```

取并集有两个原因：用户在日历里看得见的事件，出了变化就该被告知；只选了提醒规则、没把对应类型放进日历显示的用户，也不应因此漏掉取消。由此，**`rule_ids` 为空是合法配置**——“我不要任何提前提醒，但活动取消了要通知我”是常见且正当的需求，界面不得禁用这些开关，API 不得以“规则为空”为由拒绝。

重要更正核对受影响事件是否落在上述范围内；事件整体取消适用于该事件在范围内的节点。日历基础可见性参与范围计算，但不决定是否发送，也不改变提前提醒资格。

服务端记录每个兴趣 `(game, region, rule_id/变更开关)` 的启用时间。新增或重新启用只影响该兴趣，未变化的规则不因一次保存全部重新计时。该元数据规模受有限枚举约束，不生成用户×未来事件任务。

### 5.4 保存、跨设备与离线

网页临时筛选立即本地响应；点击保存才提交完整规范配置和 expected_revision。无变化保存幂等；并发冲突返回 409，展示云端与草稿差异，不静默覆盖。ICS 语义变化才增加 Feed view_revision，单改邮件启用、主题等不增加。

其他设备在登录、返回前台或主动刷新时获取最新云配置，不维护常驻 WebSocket。IndexedDB 按 user_id 隔离草稿与私人缓存，切账号不跨用户补提交。离线内容标注实际数据时间；导入只形成草稿，保存后才生效，永不自动开启邮件或请求浏览器权限。

配置分享仅导出白名单偏好，不含邮箱、账号 ID、会话、恢复码、Feed/退订 URL、Push 密钥或通道同意。账号中心分别展示云端保存、日历兼容、邮箱可投递和浏览器权限状态，不能合并成一个含糊的“同步成功”。

## 6. 固定个人 ICS 与完整快照合同

### 6.1 地址与授权

用户主动启用后创建一个逻辑 Feed，以安全随机 token 提供 `/feeds/u/{token}.ics`。日历客户端无需 Cookie、JavaScript 或交互验证码。token hash 用于校验，另存认证密文供所有者再次复制同一地址；这是长期凭证“只存 hash”原则的明确例外，其可恢复性依赖字段密钥保护。

修改筛选、退出或换设备不改变 URL。停用永久撤销当前 token；再次启用或重置生成新 token，但保留逻辑 Feed 的 namespace 和版本。所有者可随时撤销，不要求邮箱重新可达。外部客户端需替换重置后的地址，服务端不能擦除已经下载的文件或客户端副本。

### 6.2 采用完整快照，不保留个人撤销池

正常响应是一份完整的当前订阅集合。用户移除游戏/节点、关闭提醒关联节点，以及条目正常滑出窗口时，响应中不再包含该条目；**支持的客户端必须将缺席条目从这份订阅中移除**。这属于项目兼容合同，不是 RFC 5545 对所有 HTTP 订阅客户端的保证。

删除 `feed_retirements`、私人撤销全局池、筛选差集暂存和逐用户取消记录。保存配置只更新有限配置与 Feed view_revision，不遍历并写入全部被移除节点。因此一个用户反复改筛选不再消耗其他用户的撤销名额。

未通过完整快照删除/重新加入测试的客户端，不提供自动筛选同步承诺；页面要求移除后重新订阅，或使用验证通过的客户端。若目标用户环境没有任何合适客户端，P0 必须重新评估日历主通道，不能偷偷恢复一套没有容量论证的个人撤销系统。

不采用“某次 GET/304 成功后就清理撤销记录”：一个 URL 可以被多台客户端拉取，HTTP 成功既不证明已应用，也不证明所有客户端都已更新。

### 6.3 公共更正与窗口边界

基础窗口由 `FEED_PAST_DAYS / FEED_FUTURE_DAYS` 定义，按固定 UTC 日桶计算；纯日期节点按保存的日期语义判断。另加一份**共享更正层**，按 Milestone 保存当前需要补偿的投影，不按用户复制：

| 变化 | 当前响应 |
| --- | --- |
| 有明确新时间的改期 | 同 UID 输出真实新时间和更高公共版本 |
| 改期越过基础窗口未来端 | 在更正保留期内仍通过共享层输出真实新时间，不因新时间在窗口外而直接消失 |
| 官方取消、系统撤回、节点删除、延期但新时间未知 | 使用最近已发布时间输出 CANCELLED，并分别说明事实原因；不虚构新日期 |
| 分类/归属纠正 | 当前匹配的新分类显示正确节点；旧分类按完整快照删除语义移除 |
| 纯自然窗口退出或用户隐藏 | 从完整快照移除，不把它伪称为官方取消 |

例如节点从未来第 170 天改到第 200 天：新日期通过共享更正层继续输出，旧日期不作为当前安排保留。恢复确定日期时仍用原身份和更高公共版本；同一 Feed 同一 UID 最多一条。

**更正层条目与基础节点走同一套用户筛选**：组装某个 Feed 时，只输出按该用户**当前** `scope`、`calendar.event_types/node_types` 及提醒关联节点仍然匹配的更正条目。更正层是共享存储，不是绕过筛选的旁路。否则会出现最坏的一种结果——用户隐藏了某类节点，却凭空收到一条“某活动已取消”的 VEVENT，而他从未在自己的日历里见过这个活动。用户改筛选后不再匹配的更正条目，按完整快照语义自然缺席即可，不需要为它再补一条取消。

更正保留截止取 `max(最后更正时间 + CAL_PATCH_MIN_DAYS, 仍需覆盖的旧节点最晚时间 + CAL_PATCH_TAIL_DAYS)`。连续改期累计旧时间保留水位，不因只保留最新更正而缩短此前需要的期限。保留期结束后重新服从完整快照窗口；离线超过该期限的客户端不享受无限历史补偿承诺。

共享层受独立容量和字节保护；提前告警、归档已可回收记录，必要时暂停新非关键发布，不丢未到期补偿。它随公共事实变化增长，不随用户保存筛选增长。容量故障不能导致无关用户配置无法保存，也不能以成功空日历掩盖。

### 6.4 身份与序列：两个独立单调量

新部署为每个逻辑 Feed 分配不含用户身份的随机公开 namespace：

```text
UID      = feed_namespace + milestone_id + 固定日历命名空间
SEQUENCE = public_ical_revision(milestone) + view_revision(feed)
```

节点公共版本跨正常、取消、延期和恢复状态单调，不删除后从零重建；Feed 版本只在影响 ICS 的设置改变时递增。二者均不减少，因此同 UID 的内容变化或取消选择后重新加入会取得更高序列，普通读取不取号。这里的加法成立，前提是**本版已取消私人撤销记录的第三套序号**；不能把旧版 removal_change_no 混入后继续沿用公式。

DTSTAMP/LAST-MODIFIED 取参与投影的实际公共/Feed 变更时间，不每次设为 now。时间窗口自然推进本身不改公共版本，客户端必须支持完整集合中的自然出现/缺席；相同内容重新进入集合不意味着一条新的官方修订。

Feed token 轮换、停用后再启用、部署和会话变化均不重置 namespace/view_revision。既有系统有真实用户时保留其已发 UID，按历史高水位初始化新计数，不能直接套用新 namespace。SEQUENCE 按协议非负整数范围校验，接近上限必须停下并迁移，不回绕。[R11]

### 6.5 格式、提醒与完整性

精确时间输出 UTC `Z`，纯日期用 DATE；一个节点一个 VEVENT，不凭空补结束时刻。按 RFC 5545 处理 CRLF、转义、UTF-8 安全折行、非包含 DTEND、稳定 UID 和 DISPLAY VALARM；默认 TRANSPARENT，订阅文件不整体使用 METHOD:CANCEL。[R11]

当前节点与共享更正去重后检查条目及响应大小；超限返回明确错误和设置页诊断，不能截断。只有真实无匹配节点时才返回成功空 VCALENDAR。

完整快照语义有一个必须正视的代价：**v2.0 里一个导致条目缺失的 bug 只是“少显示”，本版等于向客户端下达删除指令。**因此除构造期校验外，还要有一道输出前的运行时闸门：`calendar_feeds` 保存上次成功返回的条目数及当时的 `view_revision` 与公共发布代次；本次组装结果的条目数比上次下降超过 `FEED_SHRINK_GUARD_RATIO`，而 `view_revision` 未变、公共代次也没有对应的取消/删除/窗口推移证据时，**拒绝返回该响应**（返回 503 并告警），不把疑似残缺的结果当成权威删除。条目数低于 `FEED_SHRINK_GUARD_MIN` 的小日历不触发该守卫，避免正常的小幅波动误报。日历客户端对 5xx 的常规行为是保留上一次成功结果，正是这里需要的兜底。守卫只拦截无法解释的收缩，用户自己缩小筛选（`view_revision` 变化）或事实确实取消（公共代次有证据）都照常输出。来源暂时失效时可继续输出未超过 `FEED_MAX_STALE` 的当前完整发布代次；新鲜度基于所需来源的成功核验水位，不因重新组装或写缓存而续命。私人 Feed 不回退到更旧发布代次。公共浏览可以另行展示带陈旧标记的旧缓存，不能把这一退路直接用于私人日历。

### 6.6 读路径与缓存

```text
校验方法/长度/token规范编码
  → 主状态验证 Feed + User + token代次 + 恢复epoch
  → 主状态取得云配置、view_revision、当前完整发布代次
  → 仅读取该代次的公共快照与更正层（缓存代次不符则回源）
  → 计算基础节点/提醒关联节点、按同一筛选取更正层，组装完整ICS
  → 再核对授权代次、配置版本与公共数据代次；变化则有界重试
  → 缩水守卫：无法解释的条目数骤降 → 503 并告警，不返回该响应
  → 授权后处理 HEAD / ETag / If-None-Match
  → Cache-Control: private, no-store
```

公开快照和无私人内容的模板可以共享缓存；个人响应不放公共 CDN，不用执行前缓存绕过权限。授权数据库不可用时返回 503，即使有旧内容也不放行。Feed 路由排除登录墙和交互挑战，但保留协议校验和适合日历服务共享出口的限速。

ETag 来自实际内容与版本，不用事件数量或请求时间；304/HEAD 同样验证权限。最终版本检查只能限制服务端竞态，不能撤回已经在途的响应，旧响应乱序到达也列入客户端测试。

Feed 使用情况只作低频合并的 `last_feed_poll_at` 活动水位，随授权查询在同一条 D1 条件更新里完成，每 `FEED_ACTIVITY_WRITE_INTERVAL` 最多写一次；不创建逐请求记录，不续登录会话、不修改配置。**写入失败不改变本次日历内容，但必须计入 `activity_write_failures` 指标。**

这一点不能含糊：该字段是 §9.4 判断账号是否可回收的依据之一，一个被设计成可以静默失败的写入，不能单独决定删不删用户的账号。因此指标异常、或最近一次成功写入早于 `RECLAIM_TELEMETRY_STALE_HOURS` 时，**全局暂停账号与席位回收**，直到水位恢复可信。外部日历刷新频率由客户端决定，提供 URL 不等于提醒必达。

## 7. 通知调度、邮件与 Web Push

### 7.1 事件级计划与生效时间

长期计划是 `NotificationOccurrence(event/milestone, schedule_revision, rule/kind, due_at, expires_at)`，不含用户或设备。新账号和改偏好不预建其全部未来任务。到期才匹配当前兴趣，邮件目标为 user_id，Push 目标为 binding_id。

每个兴趣和通道有生效时间。正常提前提醒要求规则与通道在 due_at 前已生效；公布/晚发现要求在对应发布时已生效。未变兴趣继续原生效时间，新增兴趣不追溯补发过去通知。发送前再次检查用户状态、最新兴趣、通道、邮箱版本、节点计划版本及有效期。

官方改期增加 schedule_revision，旧发生项与未发 Delivery 失效；标题错字只改日历内容，不重发提前提醒。已进入外部服务的旧消息不能保证撤回，消息链接始终指向最新事件详情。

### 7.2 晚发现事件的专门规则

`late_discovery` 是推荐开启的独立开关，不依赖 new_event 开关。首次正式发布或首次解析出有效时间时，发现所选规则的提前时点已经错过，按下表处理：

| 情况 | 行为 |
| --- | --- |
| 节点尚未发生，提前提醒窗口已过 | 创建立即到期的 late_discovery，最晚不超过节点时间及自身有效期 |
| 开始节点刚过去，仍在补报窗口且没有已确认结束事实 | 可补报“刚收录的安排已到计划开始时间”，不声称正在进行或尚未结束 |
| 截止节点已过、已确认结束、陈旧回填 | 不补发“即将开始/结束”类通知 |
| 普通提前提醒仍在有效窗口 | 继续原发生项，不再生成一份晚发现提醒 |

正常提前提醒与晚发现共享 `(node, schedule_revision, rule_id, channel, target)` 去重族，同一逻辑提醒不因换一种名称重复发送。与公布/更正同时适用时按关键更正、晚发现、普通公布的优先级合并同一节点的本轮意图。首次历史导入标记 backfill，不伪装成新发现群发。

晚发现走**紧急池**而不是基础池。理由很直接：按定义，这类通知不发出去用户就什么都收不到，而普通提前提醒在启用了日历提醒的用户那里已经有 VALARM 兜底。它仍受用户关闭、抑制、通道权限和 `MAIL_URGENT_FLOOR` 约束。

该规则修补“公告晚于提前点才入库”的盲区，不绕过用户关闭、预算、抑制或通道权限，也不能保证预算不足时全部补报。

### 7.3 到期展开与公平调度

发生项冻结本轮受众 order 上界，按 keyset 分页匹配；每页 Delivery 与扫描游标同事务提交。order 只服务于完整扫描，不代表优先发送；不能遍历到预算耗尽就停止，把后注册用户永久留在后面。

邮件先完成本次有限受众的候选展开，再进入发送池。优先级阶梯固定且唯一，不由实现临时解释：

```text
取消/撤回 > 重要更正 > 晚发现 > 常规提前提醒 > 新事件公布
前三档取紧急池，后两档取基础池（见 §9.1）
```

调度按上述优先级分组，组内使用持久 round-robin 用户游标。**同一用户在同一批次中的多条候选合并为一封邮件**，而不是丢掉其余的：

- 合并范围是该用户本批次内所有已到期、未过期、同一优先级组的候选，外加 `due_at` 落在 `MAIL_DIGEST_WINDOW` 之内的即将到期候选。
- **合并只允许提前发送，不允许推迟任何一条**，因此不会与 `REMINDER_GRACE` 冲突，也不引入新的过期风险。
- 合并后计为**一次**发送机会、一个 MailOutbox 意图；其中每条 Delivery 各自保留 `(node, schedule_revision, rule_id, channel, target)` 去重键，并记录共享的 mail_outbox 引用。

这条很重要：版本更新日常常有维护开始、多个卡池开始、上版活动结束挤在同一时刻，不合并的话 `MAIL_USER_BASE_DAY = 1` 意味着用户只能收到其中一条，其余全部标 expired——同样的额度，合并后能送达全部内容。跨优先级不合并，取消不会被塞进一封普通提醒里。预算池和日限频见第 9 章。

游标在**批准一次发送尝试**时推进，unknown/失败也算已获得本轮机会，不让持续失败邮箱反复占队首；明确失去资格则跳过，不扣发送机会。每个优先级/预算池单独保存游标，不能每天或每个发生项重置为注册顺序起点。过期候选留下 skipped/expired 原因，不次月追发。

公平只保证不因固定身份顺序长期偏置，不意味着有限额度下每次事件都能通知所有用户；不同优先级的策略性差异在页面说明。

### 7.4 可靠后台与发送状态

任务领取带 lease_version；D1 保存待办和预算，DO 保存短期协调信息。每批有限数量和墙钟，结束后休眠。提交后尽力唤醒，Cron 修复缺失 alarm 和过期租约；`waitUntil` 不能成为唯一持久保障。慢模型只在 PipelineDO，不占认证发送链。

认证邮件最高优先，可在 HTTP 快速路径领取同一 MailOutbox 租约尝试发送，不能与后台重复外发。业务 Delivery 记录“通知谁”，MailOutbox 记录“实际哪封信”；两者均有唯一键和保留期限。

```text
pending → leased → calling_provider → accepted(messageId)
                      ├─ 明确未接受且可重试 → retry_wait
                      └─ 是否接受不明 → unknown，保留预算，不自动盲重发

accepted → 收件服务器接受 / deferred / bounced / failed / complained / rejected
发送前失效 → skipped / superseded / expired
```

不假定供应商支持项目自定义幂等键。外部已接受但本地尚未记账的崩溃无法靠唯一索引实现端到端严格一次；unknown 优先等反馈/对账，不能证明未发送时默认不补发。deferred 表示供应商仍在处理，应用不得再提交同一封。[R05][R06]

### 7.5 邮件同意、正文与反馈

业务邮件默认关闭，登录成功、导入偏好、恢复会话不构成同意。用户确认内容范围、日限频、邮件名额租期和预算降级说明后启用，保存同意版本；换新邮箱重新同意。

邮件通道分两层，因为它们的价值差得很远：

| 层 | 内容 | 默认 | 名额 |
| --- | --- | --- | --- |
| 邮件席位（`email_channels.enabled`） | 取消/撤回、重要更正、晚发现 | 用户同意后开启 | `MAIL_SEATS_MAX` |
| 常规提醒邮件（`email_channels.routine_enabled`） | 常规提前提醒、新事件公布 | **关闭** | `MAIL_ROUTINE_SEATS_MAX`，席位的子集 |

两层划分与 §9.1 的池划分严格对应：第一层取紧急池，第二层取基础池。默认关闭第二层不是节省，而是避免重复：`CALENDAR_ALARMS_DEFAULT = true`，启用了个人日历的用户本地已经会收到同一条提醒，新事件也会直接出现在日历里，再发一封邮件只是把最紧张的预算花在重复通知上。邮件真正不可替代的是取消、更正和晚发现——那正是第一层。用户可以显式开启第二层（例如日历客户端不支持 VALARM，或根本不用外部日历），受子名额与基础池约束。`routine_enabled` 属于通道状态，不进订阅 JSON，另计同意记录。

每封只投一个已验证收件人，固定 HTML/纯文本模板，包含准确节点、源时区、时间依据、变化原因、官方及本站详情链接、退订入口；不用跟踪像素、任意附件或用户 HTML。认证邮件不附业务退订头，不夹带日程推广。

反馈只通过受控 Queue 消费，校验预期账户、发送域、订阅 ID、schema 和大小；provider eventId 去重、messageId 关联。先于结果到达的反馈有限保留，不能靠相同标题猜关联。投诉/硬退信优先于晚到成功；旧邮箱消息只更新旧地址状态。提交后才 ack，异常重试，最终进入 DLQ。[R06]

运营状态区分“已提交平台”“收件服务器已接受”“延期”“退信”“投诉”“未知”；不把 delivered 当已读。反馈正文、完整地址和验证码不写公共日志。

### 7.6 旧邮件也能退订当前业务

每个当前邮箱绑定和业务列表使用稳定退订能力，不因取消后重新订阅而换同意代次使旧链接空转。实现采用带 key_id 的高熵 MAC token，绑定不可变 email_binding_id 与 list_scope；不用逐邮件存 token 行，也不在 token 中放邮箱明文。

```text
GET  /unsubscribe/{token}       → 只展示确认页，无状态变更
POST /unsubscribe/{token}       → 正文入口确认退订
POST /email/one-click/{token}   → 有效标准请求立即关闭对应业务列表
```

同一邮箱绑定仍为当前绑定时，旧邮件中的有效 token 必须关闭**当前**业务邮件，即使用户中途重新同意。已关闭则幂等成功；已换到另一邮箱时，旧链接不具有新地址权限，返回旧绑定已失效，不影响新地址。旧绑定注销、MAC 无效或不再支持的 token 返回明确失效响应，不以成功冒充当前退订。

标准 one-click POST 不要求登录、Cookie、CSRF 或额外交互，不重定向；支持 RFC 指定的表单编码。发送头包含 List-Unsubscribe 与 List-Unsubscribe-Post，并验证收到的邮件 DKIM 覆盖相应头。[R12][R13]

这里“跨重新订阅仍有效”是项目的产品合同，不把它说成 RFC 强制所有链接永久有效。正常密钥轮换保留验证能力；灾难性密钥撤销须明确失效，不能静默返回成功。安全扫描器 GET 不退订；有效授权 POST 会生效，不为避免可能的旧 POST 而让真实用户无法退订。

### 7.7 退订、投诉与抑制

应用普通退订只关闭业务通道，不主动加入供应商全账户抑制。Cloudflare 的抑制作用于同账户所有发件域；投诉通常无到期，但能否修改应检查 `read_only`，不能笼统说所有投诉记录都永久不可解除。[R14]

收到投诉或适用硬退信后冻结该地址业务发送和其他被平台禁止的发送，在网页提示恢复码/换邮箱路径。只读抑制不能由应用解除；可变抑制也不自动删除，须有用户重新明确请求及受控核验。后来的 delivered 不恢复同意，不靠换发件域反复试发。

### 7.8 可选 Web Push

用户主动授权当前浏览器后，由会话/CSRF 校验创建归属账号的 pending 绑定，验证精确 HTTPS 推送服务域名、端点与加密密钥，再发送可见激活通知。Service Worker 使用狭窄 receipt token 与随机 challenge 确认后 active；管理和改偏好仍必须账号会话。[R15]

同 endpoint、同 owner 可幂等；不同 owner 冲突，不 UPSERT 抢占。receipt token 不能获取邮箱、修改账号或管理其他设备。测试、激活、重试均计入 Push 预算，接口不得成为任意 Webhook/SSRF 入口。

绑定有激活期限、服务租期和宽限期。真实业务处理确认或账号操作可续期，平台接受不是客户端存活证明，不发静默心跳。明确 404/410 停用端点；401/403 先检查 VAPID/配置，不批量删除用户；临时错误退避。

桌面、Android、iOS 主屏幕 Web App 及目标网络分别验收。邮件、日历、Push 同时开启可能产生跨通道重复提醒，不能声称能控制外部日历去重；Web Push 未通过时可不开放，但不能借此掩盖尚未验收的日历主通道。

### 8.3 安全、秘密与日志

OTP MAC、邮箱 lookup、字段加密、退订 MAC、CSRF、VAPID、管理员与恢复 epoch 用途隔离；认证加密使用唯一 nonce 和记录类型/ID 的认证数据。纯验证秘密存 hash/MAC，需要发信或再次复制的值采用受控密文，短期完成回执严格到期清除。

公开 ID、邮箱、endpoint、UA/IP 和 device_id 都不是授权。近似 IP/边缘限速只挡突发，精确预算/存量使用数据库账本；异常请求日志采样，不能把每次攻击变成一条持久审计记录。[R16]

应用日志与平台 invocation 配置均排查 Cookie、OTP、恢复码、完整邮箱、Feed/退订 URL、Push endpoint 和密钥泄漏。使用 CSP、no-referrer、严格同源 CORS；认证和退订页面不加载第三方追踪代码。公告 HTML、邮件模板与 ICS 均按数据转义，LLM 无指令升级权。

普通用户与管理员会话分离。管理员高强度引导秘密只经受限 HTTPS POST 换短期会话；后续使用 Access 必须验证完整 JWT 合同，不能只认一个请求头，也不能把个人 Feed 放到交互登录墙后。

## 9. 预算、容量与生命周期

### 9.1 唯一预算口径

参数初值集中在附录 A。应用日限额按 UTC；邮件月预算按真实账单周期，不能假定自然月。`settled + reserved + uncertain` 均占可用预算，所有测试、重发和明确失败后的新调用也纳入各自用途预算。

月邮件总池分为四份：既有账号认证/安全、新注册认证、基础业务、紧急业务。**基础池**只发常规提前提醒与新事件公布（按 §7.5 默认关闭，需显式开启）；**紧急池**发取消/撤回、重要更正和晚发现，不被公布或普通测试借走。每用户基础日机会与紧急日机会分别限频，界面展示实际可获得的服务，而不是“最多数封”却没有分配机制。

额度分配向紧急池和认证池倾斜，是因为 `CALENDAR_ALARMS_DEFAULT = true` 之后，常规提前提醒对启用了个人日历的用户已由 VALARM 覆盖，基础池买到的多半是重复通知；而取消、更正、晚发现和登录验证码没有任何替代通道。

日硬上限用于防突发，**不是每天都能消耗的额度**。扩大邮件名额必须同时通过月预算、日平滑分配、平台动态限额和投递质量检查，不能只改 seats 数。

### 9.2 按月剩余自动平滑

三类池的节流方式不同，不能一刀切：**基础业务池**用 envelope 平滑（常规提醒价值低、可排队可丢弃）；**紧急业务池**和**认证池**不平滑（取消通知和登录都不能等到明天），改用底线储备保护。

基础业务池在每个“UTC 日与账单周期交集”的起点生成配额 envelope。建立前撤回尚未调用的旧日预留并重排，保留发送意图；已调用或 unknown 的不释放：

```text
R     = max(0, 该池月上限 - 已结算 - 未决预留 - 不确定占用)（建立本片段前）
D     = 本周期尚余的 UTC 日片段数，含当前片段
carry = 上一片段未发放的小数余额（同池持久保存，初值 0）

E_raw = R / D + carry
E     = min(该池日硬上限, floor(E_raw))
carry = E_raw - E；仅在未被日硬上限截断时累积，被截断的部分留在 R 里
若 R > 0 且 E = 0，则 E = 1

片段可批准 = E - 本片段已批准且未释放的占用
实际可批准 = min(片段可批准, UTC日各级剩余额度, 平台可用额度)
```

`carry` 与 `E = 1` 兜底是必需项而不是优化：单纯 `floor(R / D)` 在池子见底时会直接归零——R=20、D=25 时算出 0，于是剩下 25 天一封都发不出，池里那 20 封被 floor 永久吞掉。正确行为是随额度减少平滑降频，不是提前静默停发。

E 建立后不会因每封发送重新计算而二次扣减；新增明确外部占用只减少后续可批准量，不抹掉已发生使用。UTC 日硬计数与每用户日限频在账单月界不重置。未用额度经 `carry` 留到以后片段。月末半日同样作为片段，避免账单起点不在 UTC 零点时少算一天；平台限额更低时，业务额度再压缩，并优先留出认证与紧急份额。

**紧急池不做 envelope。**一次官方取消需要当天覆盖全部席位，按 `floor(R / D)` 摊开会变成“第一天只通知得了二十几个人”。它直接按月池消耗，`MAIL_URGENT_DAY` 足以覆盖 `MAIL_SEATS_MAX` 一次全量取消；月池剩余跌破 `MAIL_URGENT_FLOOR` 后收紧为只发取消/撤回这一最高档，把储备留给真正不可替代的消息。

**认证池同样不排队**，但必须有下限保护。可立即取得认证预算就创建挑战，否则直接给出稍后重试；日硬上限只防突发，挡不住持续消耗——`MAIL_EXISTING_AUTH_MONTH ÷ MAIL_AUTH_DAY` 的可撑天数远短于一个账单周期，没有下限的话几天就能把整月的登录能力烧光，而登录不可用的后果远重于收不到提醒。规则是：

```text
软线 S = 该池剩余月额 / 本周期尚余片段数

本片段认证已用量 > S 时：
  → 同一规范邮箱当日第二次及以后的发送意图降级：返回稍后重试并延长冷却
  → 剩余额度优先留给本片段尚未取得任何验证码的邮箱

剩余月额 < MAIL_AUTH_FLOOR 时：
  → 只接受既有账号的首次登录意图
  → 暂停新注册发信与全部重发，页面明确标示处于认证降级
```

旧账号认证有独立月池，新注册不能消耗它；新注册认证也按剩余预算节流，避免推广流量先烧完全部登录费用。合法需求仍可能超额，**恢复入口不依赖发信预算**——这是认证降级期间用户仍能取回控制权的唯一保障。

任务尚未外发就跨日/跨账单周期时，先原子释放旧的未使用预留并按实际发送周期重新预占；已经调用或 unknown 的不能假装未调用释放。平台按其真实接受时间计费，跨界差异及共享账户消耗要对账并留余量，不承诺应用账本等于绝对账单封顶。

### 9.3 初值的数量关系

附录 A 的基础池覆盖 `MAIL_ROUTINE_SEATS_MAX` 个常规提醒名额在一个常规月账单周期内每日各一个发送机会的数量级；紧急池按“每席位每月数次官方取消/更正/晚发现”估算，并额外留出 `MAIL_URGENT_FLOOR`。平台日权限不足时缩小开放名额或明确降低能力，不先承诺后停发。

认证需求估算采用：

```text
会话有效寿命       = min(会话抖动后绝对期限, SESSION_IDLE_TTL)
成熟用户重新认证量 ≈ 活跃用户数 × 活跃设备均值 × 周期天数 / 会话有效寿命
认证总量           = 上式 + 新设备登录 + 新注册/重发 + 安全动作
```

**分母取 `min` 而不是绝对期限**，这一点不能省。§4.5 规定只有真实前台操作才续期，而本产品的主用户画像恰恰是“设置一次后只用外部日历、不再回网页”——对他们生效的是 `SESSION_IDLE_TTL = 90 天`，不是 `SESSION_ABSOLUTE_TTL = 180 天`。用附录初值、平均两个持续活跃设备估算得 `500 × 2 × 30 / 90 ≈ 333 封/三十天`，而按绝对期限算只有 167 封，低估一倍。`MAIL_EXISTING_AUTH_MONTH = 1,000` 为重发、新设备、安全动作和估算误差留出余量。

另一项必须计入的是**集中到期**：绝对期限自 `created_at` 起算且续期突破不了，上线期按 `REGISTRATIONS_DAY` 灌满账号容量之后，这批会话会在一个绝对期限之后落进同样宽的窗口里集中到期。这是确定会发生的事，不是尾部风险；`SESSION_ABSOLUTE_JITTER` 就是用来把这个队列摊平的。以上算例仍不含丢 Cookie、休眠到期和攻击，不能代替认证硬预算或真实 usage。

邮件边际费用按 `max(账户计费邮件量 - 平台包含量, 0) × 单封超额费率` 计算，再加账户基础费和其他产品用量；不再把远超本版开放规模的大量邮件算例混在初期预算旁。Workers Paid、AI、D1、DO、Queue 仍各有计量，具体账单从平台对账，不按邮件量代表全部费用。[R01][R03]

### 9.4 存量、日额度与回收分开

| 对象 | 回收信号与行为 |
| --- | --- |
| 注册预占、验证码、完成回执 | 到期清理；预占释放，不创建永久“候补用户” |
| pending Session | 未被浏览器确认就到期释放，不挤占 active 名额 |
| 正式会话 | 绝对/不活跃到期或用户撤销；低频续期保存活动 |
| 邮件名额 | 有服务租期，但**有任何账号活动信号即自动续租**；只有连同账号一起进入沉睡判定时才释放，不自动删除账号 |
| Push | 有效接收确认/账号操作续期，过期暂停，宽限后清理 |
| 账号 | 按真实交互、有效 Feed 拉取或客户端处理信号判断活动；长期无任何信号进入回收宽限，再清理 |

账号活动 `max(last_interactive_at, last_feed_poll_at, last_push_processed_at)` 用低频合并写入，不每 GET 写 last_seen。持续使用外部日历但不访问网页的用户不会仅因缺少网页登录被清理；邮件服务商接受、邮件扫描器访问退订页不算用户活跃。

邮件席位是有限服务租约，但续租**不要求用户专门回网页点一次**。早期设计里“用户主动续订，到期释放”会产生一个正好相反的结果：最先丢掉席位的恰恰是配置好、一直正常使用、从不出问题的那批人，而反复折腾设置的人保得住——因为主用户画像本来就不回网页。既然 §9.4 已经有了 `max(last_interactive_at, last_feed_poll_at, last_push_processed_at)` 这个活动水位，席位就用同一个信号自动续租：有活动即续，只有账号本身进入沉睡判定时才连带释放席位。“发过邮件”本身不算活动信号，投递成功也不算。

到期和账号回收在设置页提前告知；未退订、未被抑制且预算允许时可从认证/安全池发一次提示（不占业务额度），但清理逻辑不假定该提示一定送达。**回收前还需要一次维护者可见的待回收清单复核，不在无人确认的情况下直接清理**；活动水位不可信时按 §6.6 全局暂停回收。账号回收宽限期间仍可通过原账号证明恢复使用；无活动清理规则从注册时明确展示，不能事后无提示缩短。

**删除/清理释放实际存量；已经消耗的日创建、尝试和发送额度不退款。** v2.0 原本已区分这两者，本版补的是活动信号和可执行回收，不把原稿误写成“删除永不释放账号槽”。恶意持续使用者仍可能占满容量，届时暂停注册并由维护者处理，不能承诺自动识别所有僵尸或攻击者。

### 9.5 操作限额与终止能力

`USER_MUTATIONS_DAY` 是每账号上限，`GLOBAL_MUTATIONS_DAY` 是全站上限；范围为普通订阅保存、日历启用/重置和设备管理等状态变更。认证、发信、后台执行、低频活动合并另有自己的预算，不把业务动作数称作 D1 实际写入行数。

邮件退订、Feed 停用、会话撤销、恢复码紧急停用和删除入口不被普通修改日额阻断；采用轻量幂等状态转换与防突发保护。已经停止的对象再次停止不重复写库。平台整体不可用时返回真实错误，不能伪称已经停用。

### 9.6 删除账号

最近认证后，先原子标记 deleting、增加 auth_epoch、撤销 Feed 和会话、关闭邮件及 Push，立即阻止新的私人读取和发送。之后分页清理邮箱密文、偏好、设备秘密、认证载荷等，清理完成才释放相应存量；最小撤销审计不保留可继续发送的材料。

用户可删除本站数据，但不能即时抹除已经送达的邮件、客户端日历副本或未到期备份。必要同意/抑制/撤销记录保留理由和期限；HMAC 邮箱键仍是可能关联的个人数据，不宣传匿名化或自动满足所有地区法规。

## 10. 运维、验收与实施合同

### 10.1 观测与开关

公开页按游戏显示来源最新成功、数据代次和待审核缺口。后台看认证排队、账户/席位存量、预算剩余与当日 envelope、各优先级等待时间/跳过原因、退订延迟、邮件 unknown/抑制、Queue DLQ、Feed 完整性以及真实 CPU/读写/存储。

本轮新增的几个指标不是锦上添花，它们各自对应一个会静默发生的故障：

| 指标 | 它在盯什么 |
| --- | --- |
| 认证池软线状态、剩余月额、是否跌破 `MAIL_AUTH_FLOOR` | 登录能力提前几周耗尽，而表面上每天都没超日限 |
| 基础池 `carry` 与当日 `E` | envelope 归零导致的静默停发 |
| 缩水守卫命中次数与被拦响应 | 构造 bug 正在向客户端下达错误的删除指令 |
| 活动水位写入失败数、回收是否处于暂停 | 遥测坏了却仍在回收活跃用户的账号与席位 |
| 邮件合并率（每封平均承载的 Delivery 数） | 每日一封的额度是否真的送出了当天全部内容 |
| 席位自动续租与实际释放的比例 | 是否在摘掉“只用外部日历”的正常用户 |

独立开关覆盖注册、新邮件名额、常规提醒邮件层、业务邮件、全部外发、Push、模型、自动发布、单来源、账号与席位回收及只读维护。达到预算先停止低价值扩大，不用假空数据和假成功遮蔽。账单告警只是监控，不是平台收费绝对封顶。

### 10.2 保留与备份

按附录 A 的期限清理，但正式证据、未过有效期的更正、未完成发送和合法退订依赖优先于机械 TTL。短期表同时有行数/字节上限；到期任务不能因为删除 Delivery 就重新展开。正文和日志不保存媒体二进制或无限响应全文。

独立加密备份包含正式事件、证据、UID/版本、用户同意与撤销、必要运行状态；字段密钥、退订验证密钥、VAPID 和恢复 epoch 分开保管。Time Travel 不是独立备份；导出阻塞和恢复时间必须在目标环境验证。[R17]

恢复顺序：隔离环境关外发 → 校验 Schema/密文/证据 → 使用旧快照之外的当前恢复 epoch 废止旧会话与认证结果 → 对账撤销和版本 → 恢复公开读及账号控制 → 最后恢复发送。

没有可信的新近撤销清单时，恢复的邮件/Push 默认暂停，旧 Feed token 默认撤销；恢复码的已消费状态不确定也不能直接恢复使用。禁止向可能已退订的地址群发重新确认。能够证明高水位时保留 UID 并抬高版本；无法证明时暂停受影响 Feed，进行明确的新订阅迁移，不承诺无损透明回滚。

### 10.5 仓库、配置与迁移

保持 `apps/web、apps/worker、packages/contracts、migrations、fixtures、tests、scripts、docs` 的单仓库。Worker 内按 auth、accounts、sources、extraction、publishing、calendar、mail、push、executors、storage 分职责，不把每个目录变成部署服务。

部署配置记录 origin、资源绑定、发件域、账单周期和实际平台权限；运行配置来自附录 A 的注册表；秘密不进入前端/仓库。固定锁文件、Wrangler 及兼容日期，开发/预览不连接生产用户发送链。自动化备份使用最小权限，代码回滚不等于数据库回滚。

尚未上线则直接采用本版，不开发无真实对象的兼容层。已有用户时先盘点公开/私人 URL、UID/序列、同意与发送水位；保留旧身份并完成有界迁移，不能 DROP 表或直接改已发布 URL 语义。原匿名 Push 只能凭旧权限和新账号验证认领，不能凭 endpoint 接管。

`docs/INDEX.md` 和 `AGENTS.md` 只指向本版。实现不得恢复个人撤销池、全局日历取号、隐式三重筛选、未确认会话自动挤占或旧退订成功空转；**也不得把变更通知重新挂回 `rule_ids`、让紧急停用消费恢复码、用 `floor(R/D)` 取代带 carry 的 envelope、给新账号写入用户没选过的默认配置、去掉完整快照的缩水守卫，或要求用户专门回网页才能续邮件席位**。改变这些合同须先提交说明价值、成本、安全和回退的 ADR。未经所有者批准，不升级收费计划、不新增供应商、不扩大权限或绕过官方访问控制。

启动与修改配置时必须验证下列等式，任一不成立则拒绝启动：

```text
# 邮件池划分
MAIL_TOTAL_MONTH = MAIL_EXISTING_AUTH_MONTH + MAIL_SIGNUP_AUTH_MONTH
                 + MAIL_BASE_MONTH + MAIL_URGENT_MONTH
MAIL_TOTAL_DAY   = MAIL_AUTH_DAY + MAIL_BASE_DAY + MAIL_URGENT_DAY
MAIL_SIGNUP_AUTH_DAY <= MAIL_AUTH_DAY
MAIL_AUTH_FLOOR   < MAIL_EXISTING_AUTH_MONTH
MAIL_URGENT_FLOOR < MAIL_URGENT_MONTH

# 池容量要对得起承诺的名额
MAIL_ROUTINE_SEATS_MAX <= MAIL_SEATS_MAX
MAIL_BASE_MONTH >= MAIL_ROUTINE_SEATS_MAX × 本账单周期相交UTC日期数 × MAIL_USER_BASE_DAY
MAIL_URGENT_DAY >= MAIL_SEATS_MAX × 1        # 一次官方取消要能当天覆盖全部席位

# 合并不得制造新的过期风险
MAIL_DIGEST_WINDOW 只用于提前发送；合并后任一条的实际发送时间不得晚于其自身 expires_at

# 认证时序：下限本身即安全，不依赖实现另行加算
PREAUTH_MIN_TTL >= OTP_TTL + AUTH_COMPLETION_TTL + PREAUTH_MARGIN
OTP绑定Cookie截止 >= 最晚挑战截止 + AUTH_COMPLETION_TTL + PREAUTH_MARGIN

# 会话时序：抖动下界仍须显著大于不活跃期限
SESSION_ABSOLUTE_TTL - SESSION_ABSOLUTE_JITTER > SESSION_IDLE_TTL > SESSION_RENEW_INTERVAL
SESSION_IDLE_TTL > SESSION_EXPIRY_NOTICE

# 其余
DELIVERY_DEDUPE_TTL > 业务发生项最大有效期 + 最大重试余量
0 < FEED_SHRINK_GUARD_RATIO < 1
各预留包含于对应总量；pending <= total；价格/usage单位一致
```

实际计费周期不同、突发测试量增加或其他应用占用共享额度时，重新计算而非假定上述初值继续成立。绝不能靠提高字面上限而掩盖 P0 尚未测得的发送资格、模型输出或客户端行为。

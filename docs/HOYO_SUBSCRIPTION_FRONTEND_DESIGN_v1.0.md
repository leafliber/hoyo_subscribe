> 版本：v1.0（修订 r2）｜日期：2026-09-21  
> 依据：《米哈游官方日程订阅服务：免密码账号与日历优先方案》v2.1（修订 r2），以及两轮体验与设计评审。
> 
> **r2 同步内容：**变更消息不再要求先选提醒规则（§3.2、§6.2、§6.4、U10）；紧急停用不消费恢复码、恢复登录强制先保存新码（§7.4、U15/U25）；邮件改为两层并补齐名额不足的完整交互（§9.2、U22）；新账号 `uninitialized` 与 `DEFAULT_*` 预选定案，D1 关闭（§7.1、§13）；会话续期触发条件与会话列表字段写入合同（§12.2、§13.3、U14）；日历输出加入缩水守卫的前端表现（§9.1、U21）。

## 1. 文档边界与体验目标

### 1.1 与主方案的关系

主方案 v2.1 定义业务、数据、安全、预算和上线条件；本文定义页面组织、交互、反馈与前端验收，不替代主方案。

- **继承约束：**凡涉及账号权限、配置语义、时间事实、通道开通、配额及生命周期，遵守主方案。相关章节在本文对应位置注明。
- **前端设计决定：**本文的页面路径、布局、按钮文案、呈现顺序、组件拆分及视觉规格，是根据前述分析拟定的设计，不冒充主方案已有合同。
- **待确认项：**预览接口与部分状态字段的具体形状仍未定义，集中列于第 13 章；不得用演示实现代替正式约定。账号初始化与业务默认值（原 D1）已在主方案 §4.4、§5.1 与附录 A.1 定案。

发生冲突时，停止受影响部分的实现并记录差异，不由前端自行修改业务含义。新视觉想法不得顺带扩展订阅模型或修改安全权限。

### 1.2 产品体验定位

**打开就能查看重要日程，设置一次后通过外部日历长期使用，必要时回来修改。**

用户无需理解 ICS、VALARM、Feed、配置版本或调度预算，也应能回答：接下来发生什么、自己关注什么、设置已保存在哪里、哪些接收方式真正开启。

首版优先解决三类任务：

| 核心任务 | 完成条件 |
| --- | --- |
| 查询时间 | 不登录即可找到对应游戏的具体节点，分清玩法结束、奖励截止、预计时间和改期 |
| 设置订阅 | 选择游戏与提醒，看懂实际日历预览，显式保存，取得个人日历地址 |
| 维护服务 | 能独立调整内容、关闭某一通道或管理账号，不误停其他服务 |

### 1.3 首版范围

继承原神、崩坏：星穹铁道、绝区零，CN、简体中文的范围；仅展示经验证开放的内容类别。每账号一份云端订阅，邮件独立同意，Push 为后期可选能力。

本文不设计玩家账号接入、单活动收藏订阅、每游戏独立提醒配置、任意提前量、任意规则表达式、营销首页或完整管理后台。月历格子、深色主题和装饰动效不作为首版前置条件。管理员页面由独立权限域和后续管理端设计覆盖，不混入普通导航。

依据：主方案 §1、§5、§10.4。

## 2. 信息架构与导航

### 2.1 页面清单

主导航仅保留 **日程 / 我的订阅**。右上角显示登录入口或账号菜单；帮助与服务状态置于页脚，相关异常处提供直达链接。

| 页面 | 建议路径 | 访问条件与责任 |
| --- | --- | --- |
| 日程 | `/` | 游客可用；查看、筛选公开日程，不创建用户 |
| 事件详情 | `/events/{event_id}` | 游客可用；显示最新安排、时间线、变化及官方依据 |
| 我的订阅 | `/subscription` | 游客编辑本机草稿；登录后读取、保存云配置和管理接收方式 |
| 邮箱登录 | `/login` | 统一处理邮箱验证码登录及符合准入条件的注册，不分两套表单 |
| 账号恢复 | `/recover` | 提供恢复登录与紧急停用两个明确流程 |
| 账号与设备 | `/account` | 账号、安全、登录会话、浏览器绑定及导出；权限以实际会话状态为准 |
| 使用帮助 | `/help` | 日历接入指引、实测兼容性、时间说明和限制 |
| 服务状态 | `/status` | 展示公开来源状态、服务开放及降级信息 |
| 邮件退订 | `/unsubscribe/{token}` | 由 Worker 处理；GET 仅展示，确认 POST 才退订，不要求登录 |

页面路径是本文件的设计选择；已有 `/api/v2/*`、Feed、退订和 receipt 路径合同不因此改变。能力型 URL 不进入站内普通导航、公共缓存或偏好分享。

### 2.2 导航行为

日程是默认首页，不先展示大幅宣传、登录弹窗或通知授权。用户点击事件进入独立详情页；返回列表恢复原筛选与合理的滚动位置。邮件和 Push 中的本站链接进入同一详情页，展示当前事实，而非旧通知的静态副本。

游客进入“我的订阅”仍能配置草稿与查看说明，直到保存云端或开启长期通道时才要求登录。登录后回到发起操作的页面；返回地址仅允许站内白名单路径。

手机端保留两个可见主入口，不为了形式完整增加多个底部标签。账号的低频操作集中在账号页，不与日程筛选竞争位置。

## 3. 状态归属与操作边界

### 3.1 五类状态必须分开

| 状态 | 归属与存放 | 如何生效 |
| --- | --- | --- |
| 公开日程与来源状态 | 服务端发布；浏览器只缓存允许的公开数据 | 按完整发布代次读取；标注真实数据时间 |
| 浏览筛选、界面偏好 | 本浏览器；不属于云端订阅 | 改动立即影响当前页面；不自动写云端 |
| 订阅编辑草稿 | 本浏览器；游客草稿与各 `user_id` 草稿隔离 | 仅是未提交内容；导入也只生成草稿 |
| 已保存订阅 | 每账号一份；服务端 `revision` 为准 | 提交完整配置与 `expected_revision`，成功后才标为云端已保存 |
| 接收方式与权限 | Feed、邮件同意/投递、Push 绑定、浏览器权限分别管理 | 通过各自接口与确认流程生效，不由订阅 JSON 或本地开关冒充 |

不得用一个 `subscribed` 或“同步成功”描述以上全部状态。

### 3.2 四种设置的用户语义

| 界面名称 | 实际影响 | 不应产生的影响 |
| --- | --- | --- |
| 浏览筛选 | 当前看到的游戏、节点及时间范围 | 不修改已保存订阅 |
| 关注的游戏 | 云配置 `scope`，同时约束日历与通知 | 不代表所有通道已开启 |
| 提醒规则 | `notifications.rule_ids`，决定事件、节点与提前量；**可以为空** | 不依赖日历基础可见性；不决定变更消息是否可开；不请求浏览器权限 |
| 变更消息 | `new_event` 等四个开关；范围为 `scope ∩ (calendar.event_types ∪ 规则所涉事件类型)` | 不要求先选任何提醒规则；不跟随日历基础可见性决定是否发送 |
| 日历显示内容 | `calendar.event_types/node_types`，决定基础可见节点 | 不关闭邮件或 Push 的对应提醒 |

`calendar.alarms_enabled` 只控制日历中的提醒。邮件 enabled、Feed 状态、Push 绑定和设备权限仍是独立服务状态。

规则、枚举、规范化与参数来自共享 contracts 和主方案配置注册表；不得在前端另设一套业务默认值。草稿可以暂时不完整，但保存时必须通过完整校验；尤其是 `scope` 不得为空。

依据：主方案 §5.1—§5.4。

## 4. 日程首页

### 4.1 页面骨架

```text
站点名称                       日程  我的订阅  账号

日程                          CN · 简体中文 · 北京时间 UTC+8
游戏选择    时间范围    临近截止    更多筛选
当前筛选摘要                                      清除筛选

近期重要变更（有相关内容时出现）
数据受影响提示（仅异常时突出）

日期分组
  时刻 / 时间说明   节点动作
                    活动名称 · 游戏 · 必要状态

继续加载 / 已显示完当前范围
来源核验时间、帮助、服务状态
```

默认采用按时间排列的列表，而不是月历格子。首屏优先展示日程；筛选区域不铺成管理后台式的多列表单。

### 4.2 筛选

游戏以有限多选项呈现；CN、简体中文直接标注，不做单选项下拉框。时间范围使用有限预设，不允许前端发起无限历史查询；具体预设和默认范围见第 13 章。

“临近截止”是当前浏览范围内的任务快捷筛选，优先定位限时活动/卡池结束及奖励截止；不改变云端提醒规则。事件类型、节点类型等低频筛选放入“更多筛选”，折叠后仍显示已选摘要。

修改公开筛选后立即更新本地展示；需要加载远端数据时明确显示加载状态。清除筛选只恢复浏览选择，不重置订阅。允许把公开浏览条件写入可分享 URL，但不得附带账号、草稿、日历地址或任何秘密。

可提供“将当前游戏选择用于订阅”，仅由用户主动触发，复制后进入订阅草稿。浏览时间范围等其他条件不随之隐式写入。

### 4.3 条目与排序

每个列表条目表达一个 Milestone，视觉顺序为 **时间 → 节点动作 → 活动名称 → 游戏 → 必要状态**。同一 Event 的不同节点可出现在不同日期，点击进入同一事件详情。

精确节点按时间排序，同时间使用稳定身份作确定性排序。纯日期节点放在对应日期的“具体时刻未公布”区域，不伪造午夜时间参加精确排序。未知日期节点放在独立的待定/变更区域，不编造排序日期。

正文使用“玩法结束”“奖励领取截止”“阶段解锁”等具体动作，不统一压成“截止”。长标题允许换行，完整时间和节点动作不能被省略号遮住。游戏标识使用文字即可，不依赖大图背景和品牌色区分内容。

### 4.4 时间与状态呈现

| 源事实 | 页面表达 | 禁止行为 |
| --- | --- | --- |
| 精确、已核验时间 | 日期、时刻、展示时区；倒计时只能作为补充 | 只显示倒计时，不给绝对时间 |
| 只有日期 | “某月某日，具体时间未公布” | 补成 00:00，或按设备时区移动日期 |
| 官方预计 | “预计……”并注明依据 | 显示为已确定结束或实际开服 |
| 确定性推导 | 显示结果，详情提供原始表述与推导依据 | 伪称官方直接公布了该精确时刻 |
| 延期、无新时间 | “已延期，新时间待公布” | 保留旧时间为当前安排，或显示为官方取消 |
| 官方取消 | “官方已取消”，可查看依据 | 与系统收录纠错混为一谈 |
| 系统撤回 | “本站撤回：此前收录有误”及可公开原因 | 写成“官方取消” |
| 计划开始时间已经过去 | “已到计划开始时间”等与证据一致的描述 | 仅凭时钟断言活动实际进行中或已经结束 |

首版统一显示北京时间 UTC+8，并在页面和详情中明确。未来的设备时区切换只属于展示偏好，不改变 CN 区域、源事实或提醒提前量；本版不以此增加额外开发范围。

“近期重要变更”覆盖有公开依据的改期、取消、撤回和待定安排，包括无法自然进入当前未来列表的变化。只展示与当前游戏相关的有限公开结果；期限、数量及数据形状由公共接口合同确定，不建立用户级变更历史库。与主列表重复的节点使用一致状态，不展示相互冲突的两份安排。

### 4.5 数据状态与空结果

正常时显示来源核验时间和状态入口；来源异常时在受影响游戏范围内提示。来源成功核验时间、公告发布时间、发布代次时间是不同字段，不用“页面刚刷新”替代数据新鲜度。

“当前范围没有已发布日程”“筛选没有匹配项”“来源暂不可用”“仍有待审核缺口”分别表达。未审核候选不以事实条目展示；只有聚合缺口信息可公开。

公共旧缓存可以继续展示，但必须标明离线/陈旧及实际时间。不得把公共浏览可展示旧缓存的策略移植为私人 Feed 的成功兜底。分页或加载失败保留已有条目并提供重试，不显示为“全部加载完成”。

依据：主方案 §3.2—§3.3、§6.3、§6.5、§10.1。

## 5. 事件详情

详情顺序固定为 **当前重要安排 → 完整节点时间线 → 变更说明 → 官方依据**。

页首展示事件名称、游戏、状态和当前最重要节点。时间线只呈现实际存在的节点；玩法结束与奖励截止分开，不补齐不存在的节点。改期时并排说明原时间和当前时间，旧时间明确标为历史，不继续作为当前安排。

官方链接易于找到；原始时间表述、证据片段、源时区和更新时间可逐级展开。正文先使用受控文本结构；需要展示公告内容时按数据转义，不直接执行公告 HTML。

主要操作为“返回日程”“查看官方公告”“设置订阅”。“设置订阅”只能进入或调整整份订阅草稿，不叫“订阅这个活动”，不自动增加新游戏或覆盖现有规则。

从旧通知进入时显示最新事实；若原通知已经过时，在当前事实可确认的情况下提示变化。不得因为详情页内容更新就宣称已撤回旧邮件、Push 或客户端日历副本。

依据：主方案 §3.3、§3.6、§7.1、§8.3。

## 6. 我的订阅：内容配置与结果预览

### 6.1 页面结构

```text
我的订阅
云端保存状态 / 本机草稿状态
已保存摘要：关注游戏、已选提醒；各接收方式另列

① 关注的游戏
② 提前提醒：推荐规则 / 更多提醒
③ 日历显示：当前摘要 / 调整内容 / 日历提醒设置
④ 变更消息：当前摘要 / 展开调整
⑤ 实际日历预览

未保存修改提示                   放弃修改  保存订阅

接收方式
  日历订阅
  邮件提醒
  本浏览器通知（仅能力开放时显示）
```

桌面可采用左侧配置、右侧预览；手机按内容顺序纵向排列，预览有明确入口。保存栏可固定，但不能遮挡最后一项、焦点或错误提示。当前主要任务只有一个主按钮，通道管理不与内容保存合并。

### 6.2 关注游戏与固定规则

游戏选择作用于全部日历和通知。规则适用于所选游戏，不提供每游戏一套配置、每通道不同提前量或自由输入分钟数。

规则来自同一份注册表；以下是用户文案映射，不是第二份业务定义：

| rule_id | 用户文案 |
| --- | --- |
| `livestream_start_1h` | 前瞻开始前 1 小时 |
| `maintenance_start_1h` | 维护开始前 1 小时 |
| `limited_start_1h` | 限时活动开始前 1 小时 |
| `limited_end_1d` | 限时活动结束前 1 天 |
| `gacha_start_1h` | 卡池开始前 1 小时 |
| `gacha_end_1d` | 卡池结束前 1 天 |
| `phase_unlock_1h` | 活动阶段解锁前 1 小时 |
| `reward_deadline_1d` | 奖励领取截止前 1 天 |

推荐项由 `DEFAULT_RULE_IDS` 决定，其他项放入“更多提醒”。文案中的“前 1 天”沿用注册表的固定提前量，不改成前一日零点。默认值仅用于新用户推荐，不覆盖已保存配置；新游戏不自动加入已有用户的 `scope`。

**规则可以一条都不选。**“我不要任何提前提醒，但活动取消了要告诉我”是常见且正当的配置，界面不得因此禁用变更消息开关，也不得在提交时被 API 拒绝（主方案 §5.3）。取消最后一条规则时，只需说明“将不再收到提前提醒，变更消息仍按所选游戏与日历显示范围发送”，不制造连带关闭的确认步骤。

### 6.3 日历显示内容

`calendar.event_types` 与 `calendar.node_types` 控制基础可见节点；选择项由目录能力和有限枚举生成。折叠标题展示当前选择摘要，不使用没有说明的“高级设置”。初始预选取 `DEFAULT_CALENDAR_EVENT_TYPES / DEFAULT_CALENDAR_NODE_TYPES`（附录 A.1），仍**只是预选**：服务端不写入未保存的配置，界面也不得把预选显示成“已保存”。示例 JSON 永远不是默认值来源。

日历提醒开关对应 `calendar.alarms_enabled`，本身属于待保存配置。未启用 Feed 时可以配置它，但只能显示“已选择日历提醒”，不能显示“已在外部日历开启”。

关闭日历提醒不清空已选规则、不关闭邮件或 Push；只移除提醒所引入的额外节点和闹钟，基础显示仍按配置保留。

### 6.4 变更消息

单独分组显示 `new_event`、`important_change`、`cancelled_or_retracted`、`late_discovery`，默认由 `CHANGE_DEFAULTS` 提供。它们不是“提前零分钟”的另一种写法。

范围是 `scope ∩ ( calendar.event_types ∪ 已选规则涉及的事件类型 )`，界面用一句话讲清楚：**日历里看得见的、或设了提醒的事件，出了变化就会通知**。取并集的好处是两类用户都不漏——只看日历的人不会因为没设提醒而漏掉取消，只设提醒的人也不会因为把该类型从日历里藏起来而漏掉。

折叠时展示已开启项目；没有可接收的服务端通道时说明“变更消息已配置，邮件/浏览器通知尚未开启”。不要写成“规则已配置”——变更消息不依赖提醒规则。

“晚收录补充提醒”说明为：本站收录或确认时间较晚、常规提前点已经过去时，按适用条件尝试补充通知；不承诺补发所有历史消息或已过截止的提醒。新增/重新开启的兴趣不追溯补发过去通知。

### 6.5 实际日历预览

预览须遵守同一投影语义：

```text
日历提醒关闭：基础可见节点
日历提醒开启：基础可见节点 ∪ 当前提醒规则所需节点
两者均受 scope、时间依据、窗口、更正和完整性约束
```

以 Milestone 身份去重，不因基础筛选与提醒同时匹配而出现两条。额外节点标注 **“提醒关联节点”**，并说明由哪个规则引入；事件类型被隐藏与节点类型被隐藏都需要正确处理。不能只处理“隐藏结束节点”这一种例子。

例如：用户隐藏活动结束节点，但选了“限时活动结束前 1 天”且开启日历提醒，预览仍显示该结束节点，并说明“为所选提醒保留”。同时命中基础显示的条目不标成额外条目，但仍可显示其提醒信息。

纯日期、预计和未知节点不能产生精确闹钟。取消、未知延期等更正条目保留事实原因，不以普通即将发生条目的样式展示。

预览还必须做到：

- 明确标记正在预览“未保存草稿”或“已保存设置”，以及数据时间、窗口和是否完整。
- 首次启用 Feed 前提供实际结果与提醒说明；超限、缺数据或无法校验时显示诊断，不伪造空日历。
- 新配置到来后丢弃旧异步请求结果，防止旧预览覆盖新草稿。
- 样例预览标为样例；分页结果不能声称全量，实际 Feed 不得沿用界面分页而静默截断。

服务端权威预览与端侧即时预览的分工、返回字段及校验方式仍需按第 13 章确认。未完成前，模拟预览仅供体验验证，不充当正式启用证据。

依据：主方案 §5、§6.3—§6.5、§7.1—§7.2、附录 A.1/A.6。

## 7. 首次使用、登录与恢复

### 7.1 主流程

```text
公开浏览 → 编辑本机订阅草稿 → 申请邮箱验证码 → 完成并激活会话
       → 读取云配置，确认草稿处理方式 → 保存订阅
       → 保存恢复码并确认 → 确认日历预览与限制 → 主动启用日历
       → 复制地址，按目标客户端指引订阅
```

邮件与 Push 不附带开启。用户可中途退出，已保存云配置不回滚；恢复码的秘密不得当普通草稿保存。

登录成功仅恢复身份，不代表保存、Feed 开通或外部客户端设置成功。已有云配置时展示与游客草稿的差异，由用户选择采用云端或继续编辑草稿。

新账号在服务端以 `uninitialized` 建立，**服务端不替用户写入任何默认订阅**（主方案 §4.4）。界面据此承担两件事：按 `DEFAULT_SCOPE_GAMES / DEFAULT_CALENDAR_EVENT_TYPES / DEFAULT_CALENDAR_NODE_TYPES / DEFAULT_RULE_IDS` 做**预选**，让用户一眼看到推荐组合；并在用户完成第一次保存之前，把日历、邮件、Push 的启用入口显示为“先保存一次订阅内容”，而不是让它们看起来可点却在提交时报错。预选不是已保存，两者的视觉区分沿用 §8.1 的保存状态机。

### 7.2 邮箱验证码页面

表单包含邮箱、申请验证码、一个可整段粘贴的验证码输入框及确认按钮。验证码位数、重发间隔、有效期来自主方案注册表及服务端真实挑战状态，不在页面另写常量。

邮箱输入说明遵守本站身份规范：不删除点号、加号或标签，不猜测用户想登录另一个地址，不把登录输入当换邮箱。必要说明以帮助文字提供，不把内部 HMAC 等实现细节放入主流程。

挑战处理要求：

| 情况 | 交互要求 |
| --- | --- |
| 申请验证码 | 使用不泄露账号存在性的统一响应；不无条件写“邮件已送达” |
| 暂停注册 | 展示全局注册状态与已有账号登录说明，不按邮箱显示“账号不存在” |
| 邮件平台/全局额度故障 | 显示真实全局不可用状态和恢复入口，不模拟发码成功 |
| 明确重发 | 更新对应挑战，不重置最初有效期限或累计错误次数 |
| 请求超时重试 | 复用同一操作的幂等上下文，不自动变成一次新的发信意图 |
| preauth 丢失或过期 | 提示重新建立认证流程，不统一归咎于验证码错误 |
| 验证完成响应丢失 | 按完成回执合同确认结果，不盲目重用已消费验证码 |
| active 会话名额已满 | 展示脱敏设备，由用户选择撤销后激活；不自动踢出旧设备 |

页面等待状态分别说明“正在申请”“正在验证”“正在完成登录”，提交期间避免重复点击。进入 pending 不等于普通账号权限已经可用。

### 7.3 首次保存恢复码

首次启用 Feed、邮件或 Push 前，要求用户保存当前恢复码并明确确认。提供单独复制或下载操作，不将其放入普通偏好导出、URL、本机长期缓存或遥测。

界面说明：它用于邮箱无法使用时恢复控制或紧急停用；仅当前授权交付时展示，旧码不能再次取回；消费或轮换后失效。用户确认保存不代表网站已经验证其外部备份可靠。

刷新、离开或响应丢失后无法再显示旧码时，按最近认证和轮换合同恢复操作，不假装服务器仍能展示旧码。恢复码首次交付、保存确认和轮换的具体响应状态需要纳入第 13 章接口确认。

### 7.4 恢复入口

先让用户选择目的，再输入恢复码：

| 目的 | 操作前必须说明 | 成功后界面 |
| --- | --- | --- |
| 紧急停用 | 撤销所有会话和日历地址、关闭业务邮件、暂停 Push；**本次不会消耗恢复码，之后仍可用它恢复登录** | 仅显示停用结果，不展示私人数据；明确告知恢复码仍然有效 |
| 恢复登录 | 先执行同样的安全暂停，再进入受控恢复会话；**本次会消耗当前恢复码** | 激活后立即显示新恢复码并要求保存确认；在确认前只提供查看、导出、保存新码和删除账号，启用通道与换邮箱一律置灰并说明原因 |

紧急停用不消耗恢复码这件事必须写在按钮旁边，而不是藏进帮助页。反过来说，恢复登录消耗掉唯一的码，因此“保存新码”不是一个可以跳过的提示步骤，而是恢复会话的准入条件——刷新、断网或关掉标签页都不能让用户落到既无旧码也无新码的状态。

恢复后明确说明原日历地址已失效、邮件与 Push 已暂停，不能把暂停显示为订阅内容丢失。新邮箱仍须验证；邮件发送整体故障时提供现有权限允许的查看、导出、停用或删除，不伪造新邮箱验证。

一次性凭证的结果不确定时，使用原浏览器上下文和完成回执核对，不重新消费。所有账号证明均丢失时不提供“仅凭说明邮件接管”的界面承诺。

依据：主方案 §4、§8.2、附录 A.2。

## 8. 保存、离线和跨设备

### 8.1 保存状态机

```text
已保存 → 本机修改 → 正在保存 → 已保存
                    ├─ 字段错误：保留草稿并定位字段
                    ├─ 版本冲突：比较云端与草稿
                    ├─ 会话失效：保留草稿并重新验证
                    └─ 结果不确定：重新读取云端核对
```

内容编辑使用显式“保存订阅”，不在每次勾选后调用写接口。先规范化有限数组，再判断有无实际变化；无变化时不产生多余写请求。

每次请求保存独立的提交快照和 `expected_revision`。同一时间只发起一次保存；请求后继续产生的新草稿不能被旧成功响应清空。服务端返回的规范配置与版本用于更新已保存快照，不把本机推测状态当权威。

结果不确定时保留提交快照和当前草稿，重新读取云端：内容一致可确认该配置已在云端；内容不一致或已经发生后续修改则进入比较流程，不自动覆盖。普通重试不跳过版本检查。

推荐成功文案：

> 云端设置已保存。若日历地址已启用，地址保持不变；外部日历的更新时间由客户端决定。

日历关闭时不显示“地址保持不变”等不适用句子。关键结果以页面状态持久呈现，短暂提示条仅作补充。

### 8.2 两设备冲突

返回 409 后停止自动保存，按游戏、提醒、日历显示、变更消息分组展示云端与草稿差异；可利用原读取快照帮助解释差异，但不默认自动合并。

提供两个清晰选项：“采用云端设置”和“保留草稿，返回编辑”。丢弃本机改动前确认；保留草稿后以最新版本为比较基线，再经用户显式保存。不得把“强制覆盖”作为默认按钮或自动反复重试。

返回前台或主动刷新时读取最新云配置：没有未保存改动可更新显示；已有草稿则保留并提示云端变化。无需常驻 WebSocket。

### 8.3 离线、导入和账号切换

离线时公开数据显示实际缓存时间；订阅改动标记“仅保存在本机，尚未同步”。联网后提示有待保存草稿，不自动补提交或开启任何通道。

IndexedDB 中的草稿和允许的私人缓存按 `user_id` 隔离；游客使用独立空间。退出或换账号后清除当前内存视图，旧请求结果不得写入新账号页面；未重新确认对应身份时，不展示其私人缓存或自动提交。

偏好导出仅包含白名单配置，不含邮箱、账号 ID、会话、恢复码、Feed/退订地址、Push 秘密和通道同意。导入先校验，再生成可比较草稿；不覆盖云端，也不触发权限弹窗。账号必要数据导出是另一项受认证操作，不与可分享偏好混同。

### 8.4 未保存内容与通道操作

开启或续订通道时，展示其将使用的已保存配置摘要。有本机改动则先处理“保存后继续”或“使用已保存设置”，不让用户以为尚未保存的规则已生效。

关闭邮件、停用 Feed、撤销会话、紧急停用和删除，不被未保存草稿或普通修改额度挡住；仍遵守各自认证、防突发和确认要求。停用请求失败或结果未知时，不提前显示“已关闭”。

依据：主方案 §5.4、§8.2、§9.5。

## 9. 接收方式

接收方式采用三个独立区域，逐项展示 **当前状态、内容范围、服务限制、可执行操作**。未开放的 Push 不占据主流程；已开通但暂时故障的能力不能因功能开关而隐藏其状态和必要停用入口。

### 9.1 日历订阅

区分四种信息，不合并成一个绿色开关：

| 维度 | 显示要求 |
| --- | --- |
| 地址状态 | 未启用、有效、已停用等真实状态 |
| 配置状态 | 保存版本及是否启用了日历提醒；不等于客户端已应用 |
| 输出状态 | 当前完整内容可生成，或存在陈旧、超限、服务不可用、**被完整性守卫拦截**等诊断 |
| 客户端情况 | 依据实测资料展示完整替换、VALARM 和刷新行为；未知保持未知 |

首次启用时展示实际预览、提醒关联节点、客户端限制及只读地址的用途，由用户确认。主方案要求的客户端门槛未通过时，不开放声称“日历提醒可用”的正式版本。

取得地址后显示“日历订阅地址已创建”，提供“复制地址”和“查看订阅步骤”。说明需要在目标日历客户端中订阅该地址；不要把单次下载导入宣传为持续订阅。客户端快捷接入按钮仅在对应方式实测后提供。

地址通过专用所有者接口按需读取，不混入普通账号摘要或本地偏好。完整地址是只读凭证：不写入分析日志、错误追踪、公开截图或配置分享；复制成功也不等于外部客户端已添加。

低频危险操作放入“管理日历地址”：

| 操作 | 交互和后果 |
| --- | --- |
| 关闭日历提醒 | 修改配置；不关闭日历地址、邮件或 Push |
| 停用日历地址 | 确认后撤销当前地址；再次启用将获得新地址 |
| 重置日历地址 | 明确说明旧地址失效，所有使用它的客户端需要替换 |
| 再次启用 | 新地址需重新配置到外部客户端；不声称旧地址恢复 |

启用、停用、重置遵守有效会话、CSRF、显式确认和限速，不额外要求 OTP。重置结果不确定时核对现有状态/地址，不反复发起新的重置。普通保存、退出和换设备不改变地址。

可显示服务端记录的最近拉取时间，但必须标为“客户端曾请求地址”，并说明**该时间按天合并记录、最多滞后一个记录间隔**，不能据此显示“所有设备已同步”或“提醒已送达”。停用也不能擦除已经下载的副本。

主方案 §6.5 的缩水守卫会在条目数无法解释地骤降时返回 503，让客户端保留上一次成功结果。这对用户是“日历暂时没更新”，不是“日历被清空”，页面必须这样解释：显示“本次输出未通过完整性检查，已暂停更新以保护你现有的日历内容”，给出上次成功输出的时间与条目数，并提供重试与联系入口。**不得把它显示成普通的网络错误，更不能建议用户重置地址或重新订阅**——那恰好会把守卫保住的旧内容丢掉。

### 9.2 邮件提醒

邮件是**两层**，界面必须按两层呈现，不能并成一个开关（主方案 §7.5）：

| 层 | 内容 | 默认 | 用户文案 |
| --- | --- | --- | --- |
| 邮件提醒（席位） | 取消/撤回、重要更正、晚收录补充 | 关闭 | “活动取消或时间变了，用邮件通知我” |
| 常规提醒邮件（子名额） | 常规提前提醒、新事件公布 | **关闭** | “常规提醒和新活动也发一份邮件”（附说明：已启用日历提醒的话，日历本身会提醒、新活动也会直接出现，这一项通常不需要） |

第二层默认关闭要讲清楚原因，否则用户会以为功能缺失：**日历提醒已经在本地提醒过一次了，再发一封邮件是重复。**邮件真正不可替代的是取消、更正和晚收录，也就是第一层。不用外部日历、或日历客户端不支持提醒的用户，可以显式打开第二层。

启用前展示当前已验证邮箱、已保存内容范围、日限频、租期及预算降级说明，并分别记录两层的同意。数值读取实际服务参数，不在前端复制 `MAIL_SEAT_LEASE`、`MAIL_USER_BASE_DAY`、`MAIL_USER_URGENT_DAY` 等的第二套值。

额度说明使用“最多发送机会，非保证每条必达”，并说明**同一时段的多条提醒会合并成一封**（主方案 §7.3），避免用户把“每天一封”理解成“每天只告诉我一件事”。日口径按主方案 UTC 解释，不按浏览器本地午夜自行重置。租期**按账号活动自动续**，界面说明“只要你还在用（包括外部日历在拉取），名额不会因为没回网页而被收走”，不把“仍能登录”当作邮件服务仍有效。

**名额不足是本产品出现频率最高的一次拒绝**，要单独设计，不能只丢一行“名额已满”。`MAIL_SEATS_MAX` 远小于账号容量，多数用户第一次点“开启邮件提醒”都会撞上它。这一页至少要给出：

- 当前状态：邮件名额已满，以及这是内测期的预算限制，不是账号有问题。
- **最重要的替代方案放在最显眼位置**：个人日历 + 日历提醒是默认可用的，不占名额，大多数提醒需求它都能满足；直接给出“去启用日历提醒”的按钮。
- 差别说明：没有邮件名额时，仍会失去的是“取消/改期的主动通知”——这一点如实写，不粉饰。
- 是否可候补、预计如何变化：有候补就说明规则，没有就直说暂不提供，**不承诺具体时间**。

以下状态需要分别呈现，可以并存：

| 状态维度 | 用户可理解的表达与操作 |
| --- | --- |
| 同意/主动关闭 | “邮件提醒未开启/已关闭”；允许符合条件时重新同意 |
| 租期/名额 | 分别展示席位与常规提醒子名额；租期按活动自动续，展示实际到期时间；名额不足时按上文给出替代方案而不是只报错 |
| 可投递性 | “当前邮箱无法投递”；提供受控处理、恢复码或换邮箱路径 |
| 全站预算/发送故障 | 说明当前发送受限；不宣称自动切换其他通道 |

拒绝、抑制或投诉不能由前端重新勾选直接解除；换邮箱后业务邮件重新同意。关闭邮件不影响日历、账号登录或浏览器通知。

首版不新增逐封用户收件箱。若展示投递记录，只按实际证据标注“已提交平台”“收件服务器已接受”“延期”“退信”“未知”等，不显示“用户已读”。

### 9.3 本浏览器通知

仅在 Push 能力开放后出现，按钮统一为 **“在当前浏览器开启通知”**。用户主动点击前，不申请系统权限、不创建 Push 绑定、不发送测试。

浏览器权限与服务端绑定分别展示：不支持、未授权、已拒绝、允许，以及等待激活、已激活、已暂停/失效等。这里是展示语义，确切后端枚举和映射按第 13 章确认。

权限允许后创建 pending 绑定，显示“正在验证本浏览器接收能力”；完成可见激活与 receipt 合同后才显示“本浏览器接收验证通过”。平台已接受请求不等于客户端激活成功。

权限拒绝时说明需要用户在浏览器设置中调整，不循环弹窗。绑定属于其他账号时解释冲突并保留当前账号边界，不通过 endpoint 自动认领或删除他人绑定。

测试、重试和续期受真实额度与状态约束；显示可重试时间，不靠无限测试或静默心跳维持“在线”。激活通过也不承诺未来每条必达。

### 9.4 跨通道说明

同时使用日历、邮件和 Push 时可能重复提醒。页面说明各通道独立，没有自动故障转移，也无法控制外部日历去重。用户关闭某一通道后，其他通道继续按原有同意和规则运行。

依据：主方案 §6、§7.5—§7.8、§9.1—§9.5、§10.3—§10.4。

## 10. 账号、设备与退订

### 10.1 账号页组织

账号页分为账号信息、登录设备、本浏览器/其他 Push 绑定、恢复与数据、危险操作。登录会话与 Push 绑定分组展示，不把“设备”当成一个万能对象，也不承诺撤销会话会自动撤销其 Push。

显示邮箱状态、会话到期提示、邮件租期，以及适用的账号回收提示。时间取服务端事实，不能因为长期不访问网页就断言账号不活跃；Feed 使用等信号按主方案处理。

换邮箱引导用户完成当前账号证明与新邮箱验证，之后提示旧会话被撤销、新邮箱业务邮件尚未开启。订阅内容保持原账号归属，不创建第二份配置。

### 10.2 退出

退出对话框提供两个独立按钮：

- **仅退出账号**：只撤销当前登录会话。
- **退出并暂停本浏览器通知**：撤销当前会话，并暂停对应的本人浏览器通知。

两者都不关闭邮件或外部日历，不使用预勾选项代替选择。若涉及多项请求，逐项核对结果；只完成退出或只完成暂停时说明实际状态，不用一条“退出成功”掩盖部分失败。具体协调方式需与现有接口合同对齐。

### 10.3 删除与安全动作

删除账号、轮换恢复码使用用途限定的最近认证；Feed 管理不混入这套额外 OTP 要求。删除确认说明将停用本站权限和通道，但不能即时擦除已送达邮件、外部日历副本或尚未到期的备份。

服务端进入 deleting 后，界面可说明权限和发送已停止、数据仍在清理；只有清理状态有证据时才显示“清理完成”。未确认成功时不先清空所有反馈并伪装删除完成。

### 10.4 邮件退订页

GET 仅展示简洁确认页和“关闭此邮箱的业务邮件”按钮，不执行状态变化、不要求登录、不夹带挽留步骤。成功后说明其他通道不受影响。

已关闭时幂等显示关闭状态；旧邮箱绑定失效时明确说明该链接不适用于当前邮箱，不能写成“当前账号邮件已退订”。标准 one-click POST 由对应接口直接处理，不借助页面增加登录、Cookie 或额外确认。

依据：主方案 §1.3、§4.5—§4.7、§7.6、§9.4—§9.6。

## 11. 统一视觉、可访问性与反馈

### 11.1 视觉方向

采用浅色、低装饰、高信息清晰度的工具界面。主要依靠文字层级、对齐、分组与留白区分信息，不以大面积渐变、背景图、重阴影或大量卡片制造层次。

以下仅是本文件新增的首轮原型视觉值，集中维护于样式变量；核心页验收后可以统一调整，不是主方案业务参数。

| 设计项 | 原型基线 |
| --- | --- |
| 字体 | 系统中文无衬线字体栈；不以下载额外字体为前置 |
| 字号层级 | 辅助文字 14px、正文 16px、分区标题 22px、页面标题 28px |
| 间距层级 | 4 / 8 / 12 / 16 / 24 / 32px |
| 内容宽度 | 页面最大 1120px；单列表单最大 760px |
| 布局断点 | 960px 以下优先单列；以上按实际内容使用配置/预览双列 |
| 触控目标 | 主要按钮、复选项及展开入口的有效点击区域至少 44px |
| 圆角与边框 | 常用组件圆角 8px；细边框，不叠加多层装饰 |
| 基础颜色 | 页面浅灰、内容白色、正文深灰；主题强调色集中为一个变量 |
| 状态颜色 | 成功、警告、错误使用语义变量，同时保留明确文字或图标说明 |

颜色最终值由核心页面预览确定并写入同一份 token 文件，不允许不同页面分别选择近似值。游戏颜色只作辅助，时间事实与服务状态不靠颜色独立表达。

### 11.2 响应式与可操作性

手机优先保证阅读顺序和点击区域，不把桌面多列表格直接缩小。日期与节点动作保持完整可见，长标题换行；复选项整行可点击，选中与展开状态清楚。

所有表单有持续可见的标签，不只用 placeholder。键盘可到达全部主要操作，焦点明显；弹窗打开、关闭后正确移动和恢复焦点，背景不可误操作。折叠区包含错误时自动展开并定位错误。

加载、保存和失败提示可被辅助技术获知；关键结果不只依赖短暂 Toast。减少非必要动效，倒计时不持续抢占读屏提示。页面缩放后不得丢失关键操作；文字与背景对比度通过测试检查，不在未测试时宣称达到某个无障碍合规等级。

### 11.3 错误与重试

| 已有错误类别 | 页面反馈与下一步 |
| --- | --- |
| `validation` | 显示具体字段原因，保留输入；聚焦首个错误，不只弹“参数错误” |
| `unauthorized` | 区分需要重新登录或完成激活；保留对应账号草稿，不继续写入 |
| `conflict` | 展示云端与草稿差异；停止自动重试 |
| `rate_limited` | 按服务端可公开的等待信息提示；不把重复点击变成连续请求 |
| `capacity_reached` | 说明当前能力无名额；公开浏览和其他已启用能力不假失败 |
| `quota_paused` | 指明受影响操作或通道；不无依据承诺某个时刻一定恢复 |
| `temporarily_unavailable` | 保留可用内容和草稿，标明未完成操作，提供受控重试 |

认证存在性敏感结果仍按主方案折叠，不能借错误文案暴露某邮箱是否注册。网络超时属于结果可能不确定，不自动等同“服务端未执行”。

复制失败时提供可手动选择的文本，不显示复制成功；加载失败不假空；关闭失败不假停；未知状态不涂成成功。全站故障横幅不得遮住恢复和必要终止入口，也不能承诺平台不可用时操作仍能完成。

### 12.1 实现组织

沿用主方案的 Astro 静态页面与小型 TypeScript 模块，不为原型引入新的部署服务或复杂 Agent 框架。

建议在既有仓库中按以下责任组织；这些是代码模块，不是新增部署单元：

| 位置/模块 | 责任 |
| --- | --- |
| `apps/web/src/pages` | 页面路由、静态骨架和按需加载入口 |
| `apps/web/src/components` | 字段、按钮、提示、对话框、日期组、节点条目等可复用呈现 |
| `apps/web/src/features/schedule` | 公共筛选、列表、详情、数据状态 |
| `apps/web/src/features/subscription` | 草稿、已保存快照、差异、预览与保存状态机 |
| `apps/web/src/features/auth` | 预认证、OTP、会话激活和恢复流程 |
| `apps/web/src/features/channels` | 日历、邮件、Push 各自状态与操作 |
| `apps/web/src/lib` | API 访问、错误映射、按账号本机存储及安全格式化 |
| `apps/web/src/styles` | 统一 token、基础排版和布局规则 |
| `packages/contracts` | 共享枚举、规则、Schema、规范化和确定性纯函数 |

不把全部行为写进一个页面脚本，也不为每个小组件建立独立全局状态。业务规则只保留一个定义源；前端复用或消费服务端导出的结果，不按中文标签反推规则。

### 12.2 对接责任

| 数据/动作 | 现有接口依据 | 前端边界 |
| --- | --- | --- |
| 目录、日程、公开状态 | `/api/v2/catalog、events、status` | 公开读取、有限范围、按代次；不创建身份 |
| 认证和恢复 | `/api/v2/auth/*` | preauth、完成回执、激活分别处理；不能越过 pending |
| 云配置 | `/api/v2/me/subscription` | 完整配置及版本校验；用户归属由服务端派生 |
| 个人日历 | `/api/v2/me/calendar` | URL 专门读取；启用/停用/重置遵循独立动作合同 |
| 邮件 | `/api/v2/me/email-channel` | 同意、续期、关闭；不以请求体任意指定收件邮箱 |
| Push 与回执 | `/api/v2/me/push-bindings` 及专用 receipt 路径 | 普通页面管理与 Service Worker 窄能力分离 |
| 账号及数据管理 | 主方案 §8.2 对应 `/me/*` 接口 | 最近认证、目标绑定和所有权不由前端自行授予 |
| 权威预览、展示状态字段 | 尚未完整定义 | 按第 13 章对齐后实现，不虚构现成端点 |

API 模块统一处理请求上下文、错误、取消和过期响应；写权限由 Worker 最终校验。返回前台可以读取最新配置，但被动 GET 不用于滑动续会话。

续期的触发条件按主方案 §4.5 的定义执行，前端不得自行放宽或收紧：**只有用户完成一次显式的状态变更或账号管理请求之后**（保存订阅、启用/停用通道、管理会话或设备、换邮箱、轮换恢复码、导出数据），才发起一次续期 POST。页面加载、路由切换、返回前台、预取、可见性事件、后台标签页轮询和 Service Worker 都**不触发**。这条边界直接决定长期只用外部日历的用户多久要重新登录一次，也直接决定认证发信预算，不能当成性能细节随手改。

### 12.3 缓存、安全与性能

静态页面只包含公开骨架，不把账号或个人 Feed 内容构建进共享 HTML。按需加载认证、配置和通道逻辑，首页不因不相关账号模块阻塞公开日程。

Service Worker 仅缓存白名单公开资源，私人 API、认证、退订和个人 Feed 不进入其缓存。IndexedDB 的账号隔离不等于加密存储，优先只保存必要草稿和允许的缓存；会话、OTP、恢复秘密和能力 URL 不作为界面偏好落盘。

公告与用户输入按数据处理；身份凭证、完整邮箱、Feed/退订 URL、Push 端点和密钥从日志、遥测、截图及错误上下文中排除。认证与退订页面不加载第三方追踪。秘密管理与 CSP、同源、CSRF 等配置沿用主方案，不由组件局部放宽。

预览和公共列表处理并发时仅采用与当前条件相符的结果。批量数据使用有限分页或分组加载，明确当前显示范围；不以分页静默改变实际日历内容。

开发/预览使用隔离环境和明确模拟数据，不连接生产用户发送链，不自动开启收费资源或扩大权限。性能验收记录实际页面加载、交互反馈和请求次数；本文件不虚构尚未测量的速度指标。

依据：主方案 §2.1、§4.5、§5.4、§8、§10.5。

### 13.1 D1 的处理原则（已定案）

原先的矛盾是：主方案要求在验证码消费的原子事务里创建默认配置，而默认组合并不完整，于是服务端不得不替用户编一份配置。现已改为**不编**——账号以 `uninitialized` 建立，`scope` 与 `calendar.event_types` 的非空约束只对 `initialized` 生效，用户首次保存才产生正式配置（主方案 §4.4、§5.1）。

前端因此承担两件确定的事：用 `DEFAULT_SCOPE_GAMES / DEFAULT_CALENDAR_EVENT_TYPES / DEFAULT_CALENDAR_NODE_TYPES / DEFAULT_RULE_IDS / CALENDAR_ALARMS_DEFAULT / CHANGE_DEFAULTS` 做预选；并在首次保存完成前，把日历、邮件、Push 的启用入口显示为“先保存一次订阅内容”。这些常量一律从附录 A.1 读取，不在本文件另选一组，也不把示例 JSON 当默认值。

遗留的 D1′ 只剩日程页的浏览范围预设——它是纯浏览态参数，既不进云端订阅也不等于 `FEED_PAST_DAYS / FEED_FUTURE_DAYS`，可以在 F1 内独立定案。

### 13.2 D2 的处理原则

本文件要求体验上可解释、结果与 Feed 一致，但不假定已经存在专用预览 API。建议以服务端权威结果为最终依据，端侧复用共享纯函数可提供即时反馈；具体方案仍由接口合同确认。

若返回预览版本，必须说明它绑定的是哪份配置与哪一代公共数据。启用前发现变化需重新展示；若接口不能提供原子绑定，不承诺“确认时所见永远等于稍后拉取结果”，也不让 UI 虚构这种保证。

预览不因查看而创建长期 Feed 或用户×事件状态。公共重要变更使用已发布事实与现有公共投影，是否需要扩展公开响应由合同明确，不自行建设第二套更正业务。

### 13.3 D3 的最小语义清单

以下是所需含义，不是已存在的字段名或要求新增的持久状态：

| 对象 | 页面需要知道什么 |
| --- | --- |
| 公开状态 | 注册/通道是否开放，来源核验时间、发布代次、缺口、降级原因及实测客户端支持信息 |
| 认证 | 挑战实际截止与可重发状态，pending/active、是否需要设备选择及可否完成回执 |
| 会话列表 | 每个会话的标签（用户自填或缺省的“创建时间 + 粗粒度平台”）、`created_at`、`renewed_at`，以及 `renewed_at` 最多滞后一个 `SESSION_RENEW_INTERVAL` 的说明——名额已满时用户要据此决定撤销哪一个，信息不足就是在让用户盲选 |
| 恢复码 | 是否已完成保存确认，本次是否可交付新码，无法再次显示时允许的下一步；**恢复会话在保存确认前被限制的具体能力集合**，以便界面准确置灰而不是逐个试错 |
| 云配置 | 服务端规范内容和版本，冲突时如何重新获取用于比较的数据 |
| 日历 | 地址状态、是否可输出完整内容、用户可执行动作和实际诊断；**完整性守卫拦截要能与普通故障区分**，并带上次成功输出的时间与条目数供页面解释；兼容未知不能映射为支持 |
| 邮件 | 席位与常规提醒子层各自的同意与可用性、租期与自动续租状态、可投递、服务暂停、两类名额分别的余量，以及名额不足时可公开的替代说明 |
| Push | 浏览器本地权限、本人绑定状态、激活/租期状态及允许的重试动作 |
| 组合/危险操作 | 哪些动作已确认完成，哪些未完成或未知，幂等重试和再次读取的合法路径 |

优先从现有事实派生展示视图，不为每种前端文案新增数据库枚举。公共页面只获得必要的安全信息，不导出整份运行配置或秘密；所有写入资格仍由服务端实时核验。

## 14. 验收与 Agent 实施顺序

### 14.1 体验与交互验收矩阵

测试数据中的合成活动、异常状态和用户必须明确标记，不作为真实官方事实、平台验证或投递证据。

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| U01 | 游客从首页查找一个游戏的节点 | 无需登录，能看到时间、动作与游戏，不创建用户 |
| U02 | 同一活动有玩法结束和奖励截止 | 两者明确区分，详情中能查看完整时间线 |
| U03 | 长标题、纯日期、预计时间和未知时间混排 | 关键时间不被裁剪，不补造精确时刻或实际进行状态 |
| U04 | 活动改期、取消或本站撤回 | 当前事实、旧时间和原因明确；无日期变更不静默消失 |
| U05 | 筛选无结果与来源故障分别发生 | 两者文案不同；故障不显示为真实无活动 |
| U06 | 改浏览筛选后切到“我的订阅” | 云配置未被改写；仅主动复制游戏才影响草稿 |
| U07 | 隐藏结束节点，同时选择结束提醒并开启日历提醒 | 预览仍有一个关联节点，注明规则来源，无重复 UID 对象 |
| U08 | 隐藏整个事件类型，但选择该类型提醒 | 与 U07 一样按有效节点并集解释，不隐式取消提醒 |
| U09 | 关闭日历提醒 | 只改变日历提醒/额外节点；邮件和 Push 状态不变 |
| U09a | 一条提醒规则都不选，但开着变更消息 | 配置可保存；变更消息范围按游戏与日历显示范围解释；不出现禁用或矛盾配置报错 |
| U10 | 取消最后一条规则，但保持变更消息开启 | 配置合法可保存；不出现连带关闭确认；服务端接受“规则为空 + 变更开启” |
| U11 | 草稿与已保存设置不同，随后启用通道 | 用户知道将使用哪份设置，不能误认草稿已生效 |
| U12 | 游客配置后登录已有账号 | 回到原任务，先比较云端与草稿，不自动覆盖 |
| U13 | OTP 重发、preauth 丢失、认证响应丢失 | 不延长挑战期限、不误报错误来源，按回执/重新建立流程处理 |
| U14 | 会话名额已满 | 用户选择旧会话后才激活，不自动淘汰；列表给出标签、创建时间与最近活动，并说明最近活动的滞后精度 |
| U14a | 只用外部日历、长期不访问网页 | 会话按不活跃期限到期并提示重新登录；账号与邮件名额不被回收，页面不出现“账号不活跃”误判 |
| U15 | 首次启用长期通道 | 先确认恢复码保存；不把码加入普通导出或本机长期缓存 |
| U15a | 新账号尚未保存过订阅 | 通道启用入口显示为“先保存一次订阅内容”，预选清楚标为未保存；不出现可点却必然失败的按钮 |
| U16 | 两设备同时保存 | 发生 409 比较，不静默覆盖；新草稿不被旧响应清空 |
| U17 | 保存响应丢失、随后重新读取 | 根据云端事实确认或比较，不无版本覆盖或无条件报失败 |
| U18 | 离线修改、恢复网络、切换账号 | 草稿标记清楚，不自动补提交，不跨账号显示或写入 |
| U19 | 导入偏好 | 只生成草稿，不开启邮件，不弹浏览器权限 |
| U20 | 日历启用、复制、重置 | 地址状态与客户端状态分开；重置说明换 URL，未知结果不重复换码 |
| U21 | 不支持/未验证的日历客户端或预览不完整 | 明确限制，未通过主通道门槛不宣传提醒可用 |
| U21a | 输出被完整性守卫拦截 | 说明“已暂停更新以保护现有日历内容”，给出上次成功时间与条目数和重试入口；**不建议重置地址或重新订阅** |
| U22 | 邮件关闭、租期到期、投递抑制、全站限额 | 显示不同原因和可执行动作，不假恢复、不保证必达 |
| U22a | 邮件名额已满（最常见的一次拒绝） | 说明是内测预算限制而非账号问题；显著给出“日历提醒”替代路径与按钮；如实说明失去的是取消/改期主动通知；不承诺开放时间 |
| U22b | 只开席位不开常规提醒邮件 | 用户能理解默认不开第二层是为了避免与日历提醒重复；开启入口可见且说明子名额限制 |
| U23 | Push 允许权限但激活未完成/失败 | 保持等待或失败状态；只有合法回执后显示验证通过 |
| U24 | 点击两种退出方式；其中一个组合动作失败 | 邮件和外部日历保持；准确说明会话与本浏览器通知的各自结果 |
| U25 | 恢复登录或紧急停用 | 旧地址和通道按合同暂停；紧急停用不暴露私人数据、**且明确告知恢复码仍然有效**；恢复登录后在保存新码前无法启用通道或换邮箱；不自动重开 |
| U26 | GET 打开旧退订链接，随后确认 | GET 不改变状态；旧绑定失效与当前业务已关闭分开表达 |
| U27 | 普通修改额度用尽后停用服务 | 终止路径仍可访问；真实服务故障不伪装成功 |
| U28 | 手机、键盘、页面缩放和读屏关键流程 | 核心操作可到达，焦点和状态可感知，固定栏不遮挡内容 |
| U29 | 账号删除进行中 | 停止权限与数据清理状态分开，不承诺抹除外部副本 |

### 14.2 分轮交付

| 前端轮次 | 本轮只完成什么 | 交付与退出条件 |
| --- | --- | --- |
| F1：查询体验 | 日程列表、事件详情、时间/来源边界状态 | 使用标注样例，桌面和手机可点击；先确认能否找到准确节点 |
| F2：订阅体验 | 游戏、规则、日历显示、变更消息、预览、保存/冲突原型 | 能解释设置影响与关联节点；D2 缺口保持可见，不伪装权威结果 |
| F3：账号与日历闭环 | 登录、恢复码、会话、真实云配置及日历接入 | 在 D2、D3 合同补齐及相应后端条件满足后，完成真实状态联调（D1 已关闭，D1′ 不阻断本轮） |
| F4：邮件及账号维护 | 同意、租期、抑制、退订、换邮箱和删除 | 实际控制结果明确；生产开放继续服从主方案 P4/P5 验收 |
| F5：可选 Push | 当前浏览器授权、激活、管理和暂停 | 主方案 P6 的浏览器/网络与 receipt 测试通过后再开放 |

F1/F2 可以在隔离原型环境开展，不改变主方案 P0—P6 的生产依赖。特别是 P0 未验证日历主通道时，不能以页面已经完成替代产品放行决策。

### 14.3 每轮交付要求

每次 Agent 任务限定一个闭环，说明允许修改的页面/模块、继承合同、对应 U 编号与不在范围的内容。交付可运行预览、桌面/手机实际截图、执行过的测试和结果、剩余问题及回退点。

核心页面验收后，先固定统一组件和 token 再扩展。反馈采用“位置 → 问题 → 期望 → 不改什么”；不接受一句“整体美化”引发跨模块重写。代码未报错不等于视觉和交互通过；截图来自实际页面，不以效果图替代实现证据。

原型代码进入正式实现前重新检查权限、缓存、错误、状态与测试。模拟登录、模拟已投递和模拟兼容性不得进入生产。未执行或仅模拟的测试必须标明，不填写“通过”。

### 14.4 用户任务验证

邀请未参与设计的人完成：找出玩法结束与领奖截止；订阅所选游戏但不启用邮件；修改已保存内容；解释预览为何多出关联节点；只关闭一个通道；从离线草稿或保存冲突中恢复。

不提前告知按钮位置，记录停顿、误点、返回和对结果的误解。先修复阻碍任务或造成错误理解的问题，再处理个人审美偏好。

**最终验收标准：用户不需要阅读主方案，也能理解页面事实、设置影响、保存结果和服务边界；简单不以隐藏这些区别为代价。**

## 1. 通用规则

### 1.1 状态值：要么是事实，要么明确未知

- 每个状态字段只有两种来源：服务端主状态的事实，或显式的 `unknown`。**缺字段等于 unknown**——前端不得把缺字段、
  `null` 或请求失败渲染成"已开启""正常""成功"（前端 §11.3"未知状态不涂成成功"）。
- 视图从现有事实派生，**不为前端文案新增数据库枚举或持久状态**（前端 §13.3 末段）。确实派生不出来的事实才落库，
  且由对应卡的迁移承担（目前只有 §2.6 的两项）。
- 时间一律毫秒时间戳（UTC，`ENGINEERING.md` §5.1）。数据时间（来源核验、发布代次、上次成功输出）与请求时间分开，
  页面不用"刚刷新"替代数据新鲜度（前端 §4.5）。
- 有滞后的时间连同滞后上界一起给：会话 `renewed_at` 最多滞后一个 `SESSION_RENEW_INTERVAL`（P2-04 已给
  `renewed_at_max_lag_ms`）；Feed 最近拉取按 `FEED_ACTIVITY_WRITE_INTERVAL` 合并记录（§2.6）。

### 1.2 可执行动作：服务端只给事实，浏览器推导置灰（2026-09-30 所有者审定时改定）

- 私人视图只返回**事实**：状态、时间戳、计数、开关，外加 `server_time`（服务端当前时刻，毫秒）。
  **不返回逐个动作算好的"能 / 不能"表。**
- "哪些事实挡住哪个动作、原因是什么"写成 contracts 里的**纯函数**：输入事实与时刻，输出
  `{ <动作码>: { allowed: boolean, reason?: <受阻原因码> } }`。浏览器调用它来置灰并说明原因，而不是逐个试错
  （前端 §13.3"恢复码"一行的原话）。动作码与原因码仍是 contracts 的**闭合枚举**（第一张需要它的卡新增，其余卡追加）。
- 随时间变化的判断，比如最近认证是否还有效、会话是否临期，也由浏览器算：先用 `server_time` 校正本机时钟偏差，
  参数取自注册表（前端打包的 contracts）。
- **服务端只做浏览器做不了的两件事**：
  1. **给事实**：有些事实只有服务端有，比如最近认证证明的到期时间、名额余量。服务端给事实本身，不给结论。
  2. **写入时校验**：写入照样实时重新校验。浏览器的推导只是展示提示，不是授权；被拒时按 §1.3 返回结构化原因码，
     取值与推导函数的受阻原因一致；页面以写入结果为准，并重新读取事实。
- 推导函数与写接口不能各说各的：每个动作都要有对表用例，同一组事实下，推导函数的结论与写接口的实际结果一致
  （放行，或返回同一个原因码）。
- 现状：P2-07 已实现的 `GET /api/v2/me` 由服务端算好 `actions`；改为只给事实、把推导搬进 contracts，由 **P2-10** 做。
  P3-07 的日历视图本来就没有动作表，不用为此改。
- 至少覆盖这些受阻原因：`pending_activation`（会话待激活）、`recovery_code_unconfirmed`（恢复会话在新码保存确认前，
  §4.6）、`recovery_code_not_saved`（首次开启长期通道前须完成恢复码保存确认，§4.6）、`subscription_uninitialized`
  （先保存一次订阅内容，前端 §7.1）、`recent_auth_required`、`capacity_full`、`quota_paused`、`feature_closed`（运行开关关闭）。

### 1.3 操作结果：四种，不许合并

| 结果 | 判定 | 前端怎么做 |
| --- | --- | --- |
| 已完成 | 2xx，响应体给出新状态 | 用响应里的服务端状态更新页面 |
| 未执行 | 七类错误码之一 | 按前端 §11.3 映射；保留草稿与输入 |
| **未知** | 超时、断网、5xx 且没有结构化错误体 | 不当作未执行，也不当作成功；按 §3 的核对路径确认 |
| 部分完成 | 组合操作只有一部分成功 | 逐项显示实际状态（前端 §10.2），不用一条"成功"盖住 |

- 错误形状只用 contracts 的七类错误码与 `UnauthorizedReason`；需要新原因时加进 contracts 的闭合枚举。
- 私人视图一律 `cache-control: no-store`；公开视图不含任何账号信息。

### 1.4 认证完成之前，不给逐挑战的事实

申请与重发验证码的响应按存在性折叠（P2-01：已注册、未注册、满额、关闭注册四条路径的 202 字节相同）。
**校验成功之前，页面能拿到的挑战信息只能由参数推导**：位数 `OTP_DIGITS`、有效期 `OTP_TTL`、重发冷却
`OTP_COOLDOWN`、尝试上限 `OTP_ATTEMPTS` 来自注册表；截止时刻由页面按"提交时刻 + `OTP_TTL`"计算，并写明
"如果验证码已发出"。逐挑战的剩余次数、是否真的发出，认证前一律不返回——否则就是按邮箱泄露账号存在性。

### 2.10 账号摘要 · `GET /api/v2/me`（本文新增的汇总入口）

账号页（前端 §10.1）与各处置灰都需要一个汇总入口。主方案 §8.2 列了 `/api/v2/me`，但**目前没有卡负责**。本文把它定为：

- `user_id`：只给本机草稿按账号分空间用（前端 §8.3；2026-09-30 F2-04 复核加入），不进偏好导出、日志与 URL；
- 邮箱状态（脱敏地址、`email_version`）、恢复码是否已保存确认、订阅 `state`、当前会话状态与临期提示、
  各通道一行摘要（有没有、什么状态；未落地的通道为 unknown）、账号回收提示（§9.4，取服务端事实）；
- §1.2 推导所需的事实：`server_time`；每个要最近认证的动作，当前会话可用证明的到期时间（没有为 null）；
  当前会话是否由恢复登录激活、激活时间。浏览器用 contracts 的推导函数，由此算出全站的置灰与原因。

提供方：**P2-07**（已合入）；按 §1.2 改为只给事实由 **P2-10** 做。其余字段取各卡已落地的事实，未落地的按 unknown。

## 3. 结果未知时怎么核对

| 操作 | 能否直接重放 | 核对方式 |
| --- | --- | --- |

| 登出、撤销会话 | 能（幂等） | `GET /api/v2/me/sessions`：401 即当前会话已撤销；目标不在列表即已撤销 |

| 紧急停用 | 能（幂等、不消费恢复码，P2-05） | 重放 |
| 恢复登录 | **不能**（一次消费） | 完成回执（沿用 P2-03 机制，P2-05） |
| 新码生成、保存确认 | 按 P2-05 的规则 | `GET /api/v2/me` 的恢复码状态 |
| Feed 启用 / 停用 / 重置 | 停用能；启用、重置**不能**（会换 token） | `GET /api/v2/me/calendar` 核对地址状态与代次（前端 §9.1） |

| Push 绑定操作 | 按 P6 合同 | `GET /api/v2/me/push-bindings` |
| 换邮箱、删除账号、轮换恢复码 | **不能** | `GET /api/v2/me`（删除后为 401，或显示 deleting） |

## 5. 所有者审定结果（2026-09-30）

1. §1.2：**改**。原草案是"服务端统一计算动作表、只作展示提示"；所有者要求尽可能减少服务端计算，能在浏览器算的就在浏览器算。
   现在的 §1.2 是改后的版本。同一原则也用在了 D2（`docs/D2_CALENDAR_PREVIEW.md` §10）。
2. §2.7 的名额余量给**精确整数**：确认。
3. §2.10 把 `GET /api/v2/me` 交给 P2-07：确认（已实现；改为只给事实由 P2-10 做）。

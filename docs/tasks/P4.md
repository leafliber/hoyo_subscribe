# P4 · 邮件通知闭环

> 唯一主要目标：**在有限且必须可持续的预算下，把取消、更正和晚发现可靠地送到用户手里。**
> 依据：主方案 §7 全章、§9.1—§9.2、§8.1、§8.2。
> 前置门禁：P3-04（发生项需要已发布事实）；**真实外发另需 G-P0-MAIL**——逻辑实现可用测试替身推进，但不得连生产发送链。

**贯穿本阶段的一句话**：邮件是补充，不是主通道。常规提前提醒默认由 VALARM 承担，邮件默认只发取消/更正/晚发现（§1.2、§7.5）。

### P4-01 · 通知发生项生成与到期展开

| 项 | 内容 |
| --- | --- |
| 前置 | P3-04 |
| 允许改动范围 | `apps/worker/src/mail/occurrences/**`、`apps/worker/src/executors/delivery/**` |
| 继承合同 | §7.1、§7.2、§7.3 前半、附录 A.3 的有效期参数 |
| 验收 ID | A-P4-OCCUR |

**交付物**

- `NotificationOccurrence(event/milestone, schedule_revision, rule/kind, due_at, expires_at)`，**不含用户或设备**。
- 生效时间：每个兴趣与通道各有生效时间。正常提前提醒要求规则与通道在 `due_at` 前已生效；公布/晚发现要求在对应发布时已生效。
- 到期展开：冻结本轮受众 order 上界，按 **keyset 分页**匹配；每页 Delivery 与扫描游标**同事务提交**。
- 发送前复核：用户状态、最新兴趣、通道、邮箱版本、节点计划版本及有效期。
- 晚发现（`late_discovery`，独立开关，**不依赖 `new_event`**）按 §7.2 四种情况实现；走**紧急池**。
- 有效期：`REMINDER_GRACE`、`NEW_EVENT_TTL`、`CHANGE_TTL`、`LATE_NOTICE_TTL`、`LATE_POST_START_WINDOW`。

**关键约束**

- 新账号和改偏好**不预建其全部未来任务**。
- **新增兴趣不追溯补发过去通知**；未变兴趣继续原生效时间。
- 官方改期增加 `schedule_revision`，旧发生项与未发 Delivery 失效；**标题错字只改日历内容，不重发提前提醒**。
- 正常提前提醒与晚发现**共享去重族** `(node, schedule_revision, rule_id, channel, target)`。
- 首次历史导入标 `backfill`，**不伪装成新发现群发**。
- 开始刚过可补报"已到计划开始时间"，**不声称正在进行或尚未结束**；截止已过/已确认结束/陈旧回填不补发。
- `order` 只服务于完整扫描，**不代表优先发送**；不能遍历到预算耗尽就停止，把后注册用户永久留在后面。
- 已进入外部服务的旧消息不能保证撤回；消息链接始终指向**最新事件详情**。

### P4-02 · 优先级阶梯、公平游标与同批次合并

| 项 | 内容 |
| --- | --- |
| 前置 | P4-01 |
| 允许改动范围 | `apps/worker/src/mail/dispatch/**` |
| 继承合同 | §7.3；`CONTRACTS_BASELINE.md` §6.1、§6.2 |
| 验收 ID | A-P4-FAIR |

**交付物**

- 固定优先级阶梯：`取消/撤回 > 重要更正 > 晚发现 > 常规提前提醒 > 新事件公布`；前三档紧急池，后两档基础池。
- 组内持久 round-robin 用户游标，**每个优先级/预算池单独保存**。
- **同批次同用户合并**：同一优先级组内所有已到期未过期候选 + `due_at` 落在 `MAIL_DIGEST_WINDOW` 内的即将到期候选，合并为一封。
- 合并后计为**一次**发送机会、一个 MailOutbox 意图；每条 Delivery 各自保留去重键并记录共享的 `mail_outbox` 引用。
- 与公布/更正同时适用时，按关键更正 → 晚发现 → 普通公布的优先级合并同一节点的本轮意图。

**关键约束（红线）**

- **合并只允许提前发送，不允许推迟任何一条**（因此不与 `REMINDER_GRACE` 冲突，也不引入新的过期风险）。
- **跨优先级不合并**——取消不会被塞进一封普通提醒里。
- 游标在**批准一次发送尝试**时推进；unknown/失败也算已获机会（不让持续失败邮箱反复占队首）；明确失去资格则跳过，**不扣发送机会**。
- 游标**不能每天或每个发生项重置为注册顺序起点**。
- 过期候选留下 `skipped`/`expired` 原因，**不次月追发**。
- 公平只保证不因固定身份顺序长期偏置，**不意味着每次事件都能通知所有用户**。

**为什么必须合并**：版本更新日常有维护开始、多个卡池开始、上版活动结束挤在同一时刻。不合并的话 `MAIL_USER_BASE_DAY = 1` 意味着用户只收到其中一条，其余全部 expired；同样的额度，合并后能送达全部内容。

### P4-03 · MailProvider 接口与 outbox 状态机

| 项 | 内容 |
| --- | --- |
| 前置 | P4-02、P1-07 |
| 允许改动范围 | `apps/worker/src/mail/provider/**`、`apps/worker/src/mail/outbox/**` |
| 继承合同 | §2.2、§2.3、§7.4、§7.5 正文部分、[R05] |
| 验收 ID | A-P4-OUTBOX |

**交付物**

- `MailProvider` 接口：返回 `accepted(messageId) / rejected / unknown`，**不得只返回 boolean**。原生 `send_email` binding 是唯一首版发送路径。
- 状态机（§7.4 全路径）：`pending → leased → calling_provider → accepted(messageId)`；`retry_wait`；`unknown`；`accepted → 收件服务器接受 / deferred / bounced / failed / complained / rejected`；发送前失效 → `skipped / superseded / expired`。
- 任务领取带 `lease_version`；每批有限数量与墙钟（`EXECUTOR_BATCH_WALL_LIMIT`），结束后休眠；提交后尽力唤醒，`WATCHDOG_INTERVAL` 的 Cron 修复缺失 alarm 与过期租约。
- 认证邮件最高优先，可在 HTTP 快速路径领取**同一 MailOutbox 租约**尝试发送。
- 邮件正文：固定 HTML/纯文本模板，含准确节点、源时区、时间依据、变化原因、官方及本站详情链接、退订入口。
- Beta 故障预案（§2.3）：发送不可用时暂停新验证码发送与业务外发，**不先生成即将过期的验证码**，公开状态提示。

**关键约束（红线）**

- **发件人、收件引用与模板来自服务端**，不接收用户任意 `to/from/html`。
- 每封只投**一个已验证收件人**。
- **不用跟踪像素、任意附件或用户 HTML。**
- **认证邮件不附业务退订头，不夹带日程推广。**
- `unknown` 优先等反馈/对账，**不能证明未发送时默认不补发**，不自动盲重发，保留预算。
- `deferred` 表示供应商仍在处理，**应用不得再提交同一封**。
- 不假定供应商支持项目自定义幂等键；外部已接受但本地未记账的崩溃**无法靠唯一索引实现端到端严格一次**——报告中不得声称严格一次。
- `waitUntil` 不能成为唯一持久保障。
- 慢模型只在 PipelineDO，**不占认证发送链**。

### P4-04 · 预算池执行

| 项 | 内容 |
| --- | --- |
| 前置 | P4-03 |
| 允许改动范围 | `apps/worker/src/mail/budget/**`（消费 P1-07 的账本原语） |
| 继承合同 | §9.1、§9.2、§9.3、附录 A.4、A.5；`CONTRACTS_BASELINE.md` §7 |
| 验收 ID | A-P4-BUDGET |

**交付物**

- 四池划分接入调度：既有账号认证 / 新注册认证 / 基础业务 / 紧急业务。
- 每个 UTC 日起点重置三个日池；重置前**撤回尚未调用的旧日预留并重排，保留发送意图**；已调用或 unknown 的不释放。
- `MAIL_URGENT_DAY = 120` 须能覆盖 `MAIL_SEATS_MAX = 100` 的一次全量取消**并在之后仍触得到** `MAIL_URGENT_FLOOR = 20`；跌破后收紧为只发取消/撤回。
- 当日认证池剩余 < `MAIL_AUTH_FLOOR` 的降级（接入 P2-01/P2-02 的发码路径）。
- 每用户日限频：`MAIL_USER_BASE_DAY`、`MAIL_USER_URGENT_DAY`，分别计。
- 月末半日作为片段；平台限额更低时业务额度再压缩，**优先留出认证与紧急份额**。

**关键约束（红线）**

- **不得恢复月度池、envelope 或 `carry`**（ADR-0003）。当日用尽即当日停发，次日自动恢复——**不得跨日借用**。
- E 建立后**不因每封发送重新计算而二次扣减**。
- UTC 日硬计数与每用户日限频**在账单月界不重置**。
- 日硬上限用于防突发，**不是每天都能消耗的额度**。
- 扩大邮件名额必须同时通过月预算、日平滑、平台动态限额与投递质量检查，**不能只改 seats 数**。
- 界面展示实际可获得的服务，而不是"最多数封"却没有分配机制。
- 应用账本 ≠ 绝对账单封顶；跨界差异与共享账户消耗要对账并留余量。

### P4-05 · 邮件通道两层同意 API

| 项 | 内容 |
| --- | --- |
| 前置 | P4-04、G-P2 |
| 允许改动范围 | `apps/worker/src/mail/channel/**` |
| 继承合同 | §7.5、§9.4、§8.2；`CONTRACTS_BASELINE.md` §6.4 |
| 验收 ID | A-P4-CONSENT |

**交付物**

- `GET|PUT /api/v2/me/email-channel`，两层独立：
  - 席位 `enabled`（取消/撤回、重要更正、晚发现；名额 `MAIL_SEATS_MAX`；紧急池）。
  - 常规提醒邮件 `routine_enabled`（常规提前提醒、新事件公布；**默认关闭**；子名额 `MAIL_ROUTINE_SEATS_MAX`；基础池）。
- 两层**各记同意版本**；`routine_enabled` 属通道状态，**不进订阅 JSON**。
- 启用前返回：当前已验证邮箱、已保存内容范围、日限频、租期、预算降级说明。
- 席位租期 `MAIL_SEAT_LEASE`，但**有任何账号活动信号即自动续租**（`max(last_interactive_at, last_feed_poll_at, last_push_processed_at)`）；只有账号本身进入沉睡判定时才连带释放。

**关键约束（红线）**

- **子名额满时只拒绝第二层**，不影响席位本身。
- **登录成功、导入偏好、恢复会话不构成同意**；换新邮箱重新同意。
- **"发过邮件"不算活动信号，投递成功也不算。**
- **不得要求用户专门回网页点一次才能续席位**——否则最先丢席位的恰恰是配置好、一直正常使用、从不回网页的那批人。
- 不能借此接口更换收件地址。

### P4-06 · 退订 token、确认页与 one-click

| 项 | 内容 |
| --- | --- |
| 前置 | P4-05 |
| 允许改动范围 | `apps/worker/src/mail/unsubscribe/**` |
| 继承合同 | §7.6、[R12]、[R13] |
| 验收 ID | A-P4-UNSUB |

**交付物**

- 带 `key_id` 的高熵 MAC token，绑定**不可变** `email_binding_id` 与 `list_scope`；**不逐邮件存 token 行，不在 token 中放邮箱明文**。
- `GET /unsubscribe/{token}` → **只展示确认页，无状态变更**。
- `POST /unsubscribe/{token}` → 正文入口确认退订。
- `POST /email/one-click/{token}` → 有效标准请求立即关闭对应业务列表：**不要求登录、Cookie、CSRF 或额外交互，不重定向**，支持 RFC 指定的表单编码。
- 发送头包含 `List-Unsubscribe` 与 `List-Unsubscribe-Post`，并验证收到的邮件 **DKIM 覆盖相应头**。

**关键约束（红线）**

- 同一邮箱绑定仍为当前绑定时，旧邮件中的有效 token 必须关闭**当前**业务邮件，**即使用户中途重新同意**。
- 已关闭则**幂等成功**；已换到另一邮箱时，旧链接返回"旧绑定已失效"，**不影响新地址**，也不得写成"当前账号邮件已退订"。
- 旧绑定注销、MAC 无效或不再支持的 token 返回**明确失效响应**，**不以成功冒充当前退订**。
- 安全扫描器 GET **不退订**；有效授权 POST **会生效**——不得为避免可能的旧 POST 而让真实用户无法退订。
- 正常密钥轮换保留验证能力；灾难性密钥撤销须**明确失效**，不得静默返回成功。
- 这条"跨重新订阅仍有效"是**项目产品合同**，报告中不得说成 RFC 强制所有链接永久有效。

### P4-07 · 反馈 Queue 消费、关联与抑制

| 项 | 内容 |
| --- | --- |
| 前置 | P4-03 |
| 允许改动范围 | `apps/worker/src/mail/feedback/**`、`apps/worker/src/mail/suppression/**` |
| 继承合同 | §7.5 后半、§7.7、附录 A.4 的 `FEEDBACK_*`、[R06]、[R14] |
| 验收 ID | A-P4-FEEDBACK |

**交付物**

- 受控 Queue 消费：校验预期账户、发送域、订阅 ID、schema 与大小；provider `eventId` 去重、`messageId` 关联；`FEEDBACK_BATCH` 小批；`FEEDBACK_MAX_RETRIES` 后进 DLQ；**提交后才 ack**。
- 先于结果到达的反馈**有限保留**（`MAIL_UNMATCHED_MAX`）。
- 抑制：收到投诉或适用硬退信后冻结该地址业务发送与其他被平台禁止的发送；在网页提示恢复码/换邮箱路径。
- 运营状态区分：已提交平台 / 收件服务器已接受 / 延期 / 退信 / 投诉 / 未知。

**关键约束（红线）**

- **不能靠相同标题猜关联。**
- **投诉/硬退信优先于晚到成功**；后来的 `delivered` **不恢复同意**。
- 旧邮箱消息**只更新旧地址状态**。
- **`accepted` 不当已读**，`delivered` 也不当已读。
- 应用普通退订**只关闭业务通道，不主动加入供应商全账户抑制**（Cloudflare 抑制作用于同账户所有发件域）。
- 只读抑制（`read_only`）**不能由应用解除**；可变抑制也不自动删除，须有用户重新明确请求及受控核验。投诉**通常**无到期，但能否修改应检查 `read_only`——**不得笼统说所有投诉记录都永久不可解除**。
- **不靠换发件域反复试发**，不借换域或换供应商绕过投诉/政策抑制。
- 反馈正文、完整地址和验证码**不写公共日志**。

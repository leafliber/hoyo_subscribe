### F3-01 · 登录与验证码页

| 项 | 内容 |
| --- | --- |
| 允许改动范围 | `apps/web/src/features/auth/**`、`apps/web/src/pages/login.astro` |
| 继承合同 | 前端 §7.1、§7.2、§13.3；主方案 §4.1—§4.5 |
| 验收 ID | U13、U14 |

**交付物**

- 表单：邮箱、申请验证码、**可整段粘贴的验证码输入框**、确认按钮。
- 验证码位数、重发间隔、有效期**来自服务端真实挑战状态与参数注册表**，页面不另写常量。
- 等待状态分别说明"正在申请""正在验证""正在完成登录"，提交期间避免重复点击。
- 会话名额已满：展示**脱敏设备列表**（标签、`created_at`、`renewed_at` + 滞后说明），由用户选择撤销后激活。
- 前端 §7.2 的八种挑战情况全部有对应交互。

**关键约束（红线）**

- **申请验证码使用不泄露账号存在性的统一响应**；不无条件写"邮件已送达"；暂停注册时展示**全局**注册状态，**不按邮箱显示"账号不存在"**。
- 邮件平台/全局额度故障时显示真实全局不可用状态，**不模拟发码成功**。
- 明确重发不重置最初有效期限或累计错误次数；请求超时重试复用同一幂等上下文，**不自动变成一次新的发信意图**。
- preauth 丢失或过期时提示重新建立认证流程，**不统一归咎于验证码错误**。
- 邮箱输入说明遵守身份规范：**不删除点号、加号或标签**，不猜测用户想登录另一个地址，不把登录输入当换邮箱。内部 HMAC 等实现细节不放入主流程。
- **进入 pending 不等于普通账号权限已经可用**；登录成功仅恢复身份，不代表保存、Feed 开通或外部客户端设置成功。
- **不自动踢出旧设备。**

**F2-04 交接（2026-09-30 晚验收登记）**：本卡接身份发布（`publishDraftIdentity`）时，给 `tests/e2e/draft.spec.ts` 的 `/me` 失败参数
补上"缺 `user_id` 字段""`user_id` 为空串"两种，断言仍是 unknown、编辑不落盘。F2-04 复核时，把合法性检查放宽成"不是 null"的变异存活了。

**P2-03 定下的接口事实（2026-09-27 验收登记，页面必须照此处理）**

- `POST /api/v2/auth/challenges/verify` **必须带 `idempotency-key` 请求头**；缺了会被拒。
- 返回 `409 {verified:false, preauth_renewal_required:true}` 并附续期 Cookie：表示预认证剩余时间不够完成交付。
  **用同一个验证码自动重试一次**，不要让用户重输，也不要显示成验证码错误。
- 校验成功但响应丢失：用**同一个** `idempotency-key` 调 `POST /api/v2/auth/complete` 取回待激活会话；
  它不接受 `challenge_id`。
- `validation / login_required`（signup 期间同一邮箱已被建号）：引导走登录流程重新收码，不是验证码错误。
- `409 conflict`：挑战在校验与消费之间被并发改变，**或当日注册完成数恰好已满**——
  后者意味着用户手里的码是对的但今天建不了号，文案要说清楚是全局名额，不按邮箱暗示账号存在与否。

**验证码邮件的"代发"提示（2026-09-28 实测登记）**：阿里企业邮会在验证码邮件上显示
"由 bounces@cf-bounce.<发件域> 代发，请谨慎处理"（验证码走认证域 `auth.hoyo.airo.cc`，届时显示 `cf-bounce.auth.hoyo.airo.cc`）。
这是 Cloudflare 发信的退信域造成的，平台不允许修改；申请验证码后的提示文案要预先说明这一点，免得用户把正常的验证码邮件当成钓鱼。

**邮件可能晚到（2026-09-29 实测登记）**：第二封测试信被阿里企业邮临时拒收 4 次，发出 43 分钟后才送达；验证码有效期
`OTP_TTL` 只有 10 分钟。申请后的提示不要承诺"马上就到"；重发入口按 P2-02 的冷却规则呈现，文案说明"没收到可以稍后重发"。
这个时延是否常见还没有定论（见 `docs/evidence/p0/platform-facts.md` §2.2），不要据此自行改动验证码有效期。

**P2-04 定下的接口事实（2026-09-28 验收登记）**

- 登录完成后浏览器拿到的是 **pending** 会话：只能调 `GET /api/v2/me/sessions` 与 `POST /api/v2/auth/activate`，
  其余 user 路由一律 `401 unauthorized / pending_activation`——按"还差激活"处理，不是登录失败。
- **会话阶段的 CSRF 从 `GET /api/v2/me/sessions` 取**（响应体 `csrf_token`，同时设置 `__Host-hoyo_csrf` Cookie），
  预认证阶段的 CSRF 在这里无效。该接口每次调用都换发新 token，**写请求前从 Cookie 现读**，不要缓存在内存里——
  多个标签页会互相覆盖。
- 激活：`POST /api/v2/auth/activate`，可选 `label`（用户自填）与 `revoke_session_ids`（**逗号分隔的会话 ID 字符串**，
  不是数组）。成功 `200 {activated:true, csrf_token}` 并重设 Cookie；当前会话已是 active（双击、响应丢失后重试）也回 200。
  `409` 且 `selection_required:true`：名额已满或所选无效，用同一响应里的 `sessions` 让用户选择后重试。
  激活途中会话失效（过期、被撤销、账号 epoch 变化）回 `401 session_expired`：引导重新登录，不要显示成名额问题。
- 设备列表：`sessions[]`（`id`、`label`、`created_at`、`renewed_at`、`is_current`、`state`；只含未过期的 pending/active），
  外加 `current_session_state`、`current_needs_reverification`（已进入 `SESSION_EXPIRY_NOTICE` 窗口，据此提示重新验证）、
  `renewed_at_max_lag_ms`。时间都是毫秒时间戳；`renewed_at_note` 是服务端说明，页面文案自己写。
- 续期：`POST /api/v2/auth/renew` 只在 CONTRACTS_BASELINE §8.3 定义的真实前台操作**之后**调；间隔内再调回
  `{renewed:false}`，不是错误。页面加载、预取、后台标签页、Service Worker 一律不得调用。
- 撤销：`DELETE /api/v2/me/sessions/{id}`，撤的若是当前会话，响应会清 Cookie；别人的与不存在的 ID 同样回
  `400 validation / not_found`。登出：`POST /api/v2/auth/logout` 只撤当前会话；**pending 会话不能登出**，
  等 `SESSION_PENDING_TTL` 到期即可。
- 标签的服务端上限借用了请求体上限（`API_BODY_MAX_BYTES` 字节），输入框自己限一个合理长度。

**F2-04 交接（2026-09-30 验收登记）**：本机草稿按 `user_id` 分空间，身份由订阅页读 `GET /api/v2/me` 确认（见 F2-04 卡末复核）。
开始登录、登录完成、换账号时，调 `apps/web/src/lib/storage/identity.ts` 的 `publishDraftIdentity({ status: "unknown" })`，
让本页和其他标签页先清空内存视图、丢弃迟到响应；不要自己发 confirmed，确认只来自 `/me`。

### F3-02 · 恢复码交付与恢复入口

| 项 | 内容 |
| --- | --- |
| 前置 | F3-01 |
| 允许改动范围 | `apps/web/src/features/auth/recovery/**`、`apps/web/src/pages/recover.astro` |
| 继承合同 | 前端 §7.3、§7.4；主方案 §4.6 |
| 验收 ID | U15、U25 |

**交付物**

- 首次启用 Feed / 邮件 / Push **之前**要求保存当前恢复码并明确确认；提供单独复制或下载。
- 恢复入口：**先让用户选择目的，再输入恢复码**，两个流程各自说明后果。
- 紧急停用：只显示停用结果，**不展示私人数据**，并**明确告知恢复码仍然有效**。
- 恢复登录：激活后**立即显示新恢复码并要求保存确认**；确认前只提供查看、导出、保存新码、删除账号，**启用通道与换邮箱一律置灰并说明原因**。

**关键约束（红线）**

- **"紧急停用不消耗恢复码"必须写在按钮旁边，不得藏进帮助页。**
- **"保存新码"不是可跳过的提示步骤，而是恢复会话的准入条件**——刷新、断网或关标签页都不能让用户落到既无旧码也无新码的状态。
- 恢复码**不进入普通偏好导出、URL、本机长期缓存或遥测**。
- 说明"旧码不能再次取回"；无法再显示旧码时按最近认证和轮换合同恢复操作，**不假装服务器仍能展示旧码**。
- 恢复后说明原日历地址已失效、邮件与 Push 已暂停，**不能把暂停显示为订阅内容丢失**。
- 新邮箱仍须验证；发送整体故障时**不伪造新邮箱验证**。
- 所有账号证明均丢失时**不提供"仅凭说明邮件接管"的界面承诺**。

**P2-05 定下的接口事实（2026-09-28 验收登记；以 #27 返工合入版本为准）**

- `POST /api/v2/auth/recovery`（public，绑预认证与 CSRF）：`{action: "emergency_stop" | "recover_login", recovery_id, secret}`。
  紧急停用成功 `{stopped: true}`，不回任何私人数据，码不消费；输给并发新登录时回 `409`，重试即可。
  恢复登录成功 `{completed: true, pending_session_id}` 并下发 pending Cookie；响应丢失按同一操作键走 `/api/v2/auth/complete`。
  只交 ID、秘密错误、码已消费、ID 不存在：一律同形 `401`。
- 恢复会话激活后先是**受限**会话：普通写路由回 `401 recovery_code_unconfirmed`，可以激活、登出、生成与确认新码、读。
- `GET /api/v2/auth/recovery/code` → `{has_current_code, saved_confirmed}`；`POST` 同路径 `{action: "generate"}` 返回
  `{recovery_id, secret, saved_confirmed: false}`（**唯一一次明文**），`{action: "confirm", recovery_id, secret}` 完成保存确认。
  返工后：生成只对受限恢复会话或刚认证（`RECENT_AUTH_TTL` 内）的会话开放，其余回 `401 recent_auth_required`——提示重新验证邮箱。
  （2026-09-29 复验通过，行为如上。）
- F1-04 给 `recovery_code_unconfirmed` 暂配了通用动作 `check_status`：本卡做出保存新码的页面后，在
  `apps/web/src/lib/errors/feedback.ts` 的动作联合里加一个专门动作并改这一条（获准的跨卡接缝），让受限会话一步回到保存新码。

### F3-03 · 账号与设备页、两种退出

| 项 | 内容 |
| --- | --- |
| 前置 | F3-01 |
| 允许改动范围 | `apps/web/src/pages/account.astro`、`apps/web/src/features/auth/sessions/**` |
| 继承合同 | 前端 §10.1—§10.3；主方案 §1.3、§4.5、§9.4 |
| 验收 ID | U14a、U24、U29 |

**交付物**

- 分区：账号信息 / 登录设备 / Push 绑定 / 恢复与数据 / 危险操作。
- 会话列表字段：标签、`created_at`、`renewed_at` 及**滞后不超过一个 `SESSION_RENEW_INTERVAL`** 的说明。
- 退出对话框**两个独立按钮**：「仅退出账号」与「退出并暂停本浏览器通知」。
- 删除账号进行中的状态展示：权限与发送已停止 / 数据仍在清理 / 清理完成（**只有有证据时才显示完成**）。

**关键约束（红线）**

- **登录会话与 Push 绑定分组展示**，不把"设备"当万能对象；**不承诺撤销会话会自动撤销其 Push**。
- 退出**不使用预勾选项代替选择**；两者都**不关闭邮件或外部日历**；只完成其中一项时说明实际状态，**不用一条"退出成功"掩盖部分失败**。
- **不能因为长期不访问网页就断言账号不活跃**（U14a）；Feed 使用等信号按主方案处理。
- 删除确认说明将停用本站权限和通道，但**不能即时擦除已送达邮件、外部日历副本或尚未到期的备份**。
- 删除账号、轮换恢复码使用用途限定的最近认证；**Feed 管理不混入这套额外 OTP 要求**。

**F2-04 交接（2026-09-30 验收登记）**：两种退出、撤销当前会话、删除账号开始时，先调 `publishDraftIdentity({ status: "unknown" })`
（`apps/web/src/lib/storage/identity.ts`），再发请求。这样本页和其他标签页会清掉该账号的内存视图，旧请求结果不会写进下一个身份的页面（前端 §8.3）。

### F3-04 · 日历订阅区域

| 项 | 内容 |
| --- | --- |
| 前置 | F3-01、P3-07、G-D2 |
| 允许改动范围 | `apps/web/src/features/channels/calendar/**` |
| 继承合同 | 前端 §9.1；主方案 §6.1、§6.5、§6.6、§4.7 |
| 验收 ID | U20、U21a |

**交付物**

- **四种信息分开显示，不合并成一个绿色开关**：地址状态 / 配置状态 / 输出状态 / 客户端情况。
- 首次启用展示实际预览、提醒关联节点、客户端限制及只读地址用途，由用户确认。
- 取得地址后显示"日历订阅地址已创建"+「复制地址」+「查看订阅步骤」。
- "管理日历地址"分组：关闭日历提醒 / 停用地址 / 重置地址 / 再次启用，四种后果各自说清。
- **缩水守卫的前端表现**：显示「本次输出未通过完整性检查，已暂停更新以保护你现有的日历内容」，给出上次成功输出的时间与条目数，并提供重试与联系入口。

**关键约束（红线）**

- **守卫拦截不得显示成普通网络错误，更不得建议用户重置地址或重新订阅**——那恰好会把守卫保住的旧内容丢掉。
- 客户端情况**依据实测资料**展示；**未知保持未知**，不得映射为支持。G-P0-CAL 未通过时，**不开放声称"日历提醒可用"的正式版本**。
- 完整地址是只读凭证：**不写入分析日志、错误追踪、公开截图或配置分享**；**复制成功不等于外部客户端已添加**。
- 地址通过**专用所有者接口按需读取**，不混入普通账号摘要或本地偏好。
- 最近拉取时间必须标为"客户端曾请求地址"，并说明**按天合并记录、最多滞后一个记录间隔**；**不得据此显示"所有设备已同步"或"提醒已送达"**。
- 启用/停用/重置**不额外要求 OTP**；重置结果不确定时核对现有状态，**不反复发起新的重置**。
- **不要把单次下载导入宣传为持续订阅**；客户端快捷接入按钮仅在对应方式实测后提供。
- 停用**不能擦除已经下载的副本**。

**P3-07 交接（2026-09-30 晚验收登记）**：
- 管理动作是 `POST /api/v2/me/calendar/{enable,disable,reset}`，请求体 `{confirmed: true, expected_generation}`，带 `Idempotency-Key`。
  结果不确定时用同一个键与同一个 `expected_generation` 重试；被后续操作替代的旧操作回 409，此时重新 GET 当前状态，**绝不再次换证**。
- `GET /api/v2/me/calendar` 按 D3 §2.6 草案返回地址状态、配置、输出状态（`unknown / normal / integrity_blocked / unavailable`）与拉取语义
  （`merge_interval_days`、`meaning: client_requested_address`）。守卫拦截显示为 `integrity_blocked`，配合上次成功输出的时间与条目数解释。
- 受限恢复会话与未保存恢复码时的拒绝原因目前还是 `no_session` 与普通 409；D3 审定后按 §1.2 的原因码对齐（见 P3-07 卡末建议）。

**D2 草案（2026-09-30 验收方起草，待所有者审定）**：`docs/D2_CALENDAR_PREVIEW.md` §3。首次启用与再次启用前先取 `source=saved` 的预览并由用户确认；
启用请求带预览所用的订阅版本与发布代次，收到 409 `preview_outdated` 就重取预览、重新确认，不自动重试；`outcome = blocked` 时不提供启用按钮。
审定后本卡另需 P3-15（日历预览 API）。

**F2-03 交接（2026-09-29 验收登记）**：保存成功文案目前只有"云端设置已保存。外部日历的更新时间由客户端决定。"——本卡有了 Feed 状态后，日历地址已启用时补上"地址保持不变"一句，未启用时不显示（F2-03 卡原文）。开启或续订日历前遇到未保存改动，走 F2-03 状态机的"保存后继续 / 使用已保存设置"，并补 U11 的真实通道用例。

### F3-05 · 真实云配置联调与首次保存引导

| 项 | 内容 |
| --- | --- |
| 前置 | F3-01、F2-03、P2-06 |
| 允许改动范围 | `apps/web/src/features/subscription/**`、`apps/web/src/features/auth/**` |
| 继承合同 | 前端 §7.1、§13.1；主方案 §4.4、§5.1 |
| 验收 ID | U12、U15a |

**交付物**

- 主流程按前端 §7.1 打通：公开浏览 → 编辑草稿 → 申请验证码 → 激活会话 → 读取云配置并确认草稿处理方式 → 保存订阅 → 保存恢复码 → 确认日历预览 → 启用日历 → 复制地址。
- 已有云配置时展示与游客草稿的**差异**，由用户选择采用云端或继续编辑。
- 新账号（`uninitialized`）：按 `DEFAULT_*` 做**预选**；在首次保存完成前，把日历、邮件、Push 的启用入口显示为**「先保存一次订阅内容」**。

**关键约束（红线）**

- **预选不是已保存**，视觉区分沿用保存状态机。
- **不出现可点却必然失败的按钮**（U15a）。
- 登录后回到发起操作的页面；**返回地址仅允许站内白名单路径**。
- 邮件与 Push **不附带开启**；用户中途退出时已保存云配置不回滚。
- 新游戏**不自动加入已有用户的 `scope`**。

## F4 · 邮件与账号维护

前置门禁：**P4-05**（两层同意 API）、**P4-06**（退订）、**G-D3**。

### F4-01 · 邮件提醒两层呈现与同意流程

| 项 | 内容 |
| --- | --- |
| 允许改动范围 | `apps/web/src/features/channels/email/**` |
| 继承合同 | 前端 §9.2、§9.4；主方案 §7.5、§9.1 |
| 验收 ID | U22、U22b |

**交付物**

- **必须按两层呈现，不能并成一个开关**：
  - 邮件提醒（席位）——「活动取消或时间变了，用邮件通知我」，默认关闭。
  - 常规提醒邮件（子名额）——「常规提醒和新活动也发一份邮件」，**默认关闭**，附说明"已启用日历提醒的话，日历本身会提醒、新活动也会直接出现，这一项通常不需要"。
- 启用前展示：当前已验证邮箱、已保存内容范围、日限频、租期、预算降级说明；**分别记录两层同意**。
- 状态四维分别呈现且可并存：同意/主动关闭、租期/名额、可投递性、全站预算/发送故障。
- 跨通道说明：各通道独立，**没有自动故障转移**，**无法控制外部日历去重**。

**关键约束（红线）**

- **数值读取实际服务参数**，前端不复制 `MAIL_SEAT_LEASE`、`MAIL_USER_BASE_DAY`、`MAIL_USER_URGENT_DAY`、`MAIL_SEATS_MAX` 的第二套值。
- 额度说明用"最多发送机会，**非保证每条必达**"，并说明**同一时段的多条提醒会合并成一封**（避免用户把"每天一封"理解成"每天只告诉我一件事"）。
- 日口径按 **UTC** 解释，**不按浏览器本地午夜自行重置**。
- 租期说明"**只要你还在用（包括外部日历在拉取），名额不会因为没回网页而被收走**"；**不把"仍能登录"当作邮件服务仍有效**。
- 第二层默认关闭**必须讲清原因**，否则用户会以为功能缺失。
- 拒绝、抑制或投诉**不能由前端重新勾选直接解除**；换邮箱后业务邮件重新同意。
- 关闭邮件**不影响日历、账号登录或浏览器通知**。
- 若展示投递记录，只按实际证据标注"已提交平台""收件服务器已接受""延期""退信""未知"；**不显示"用户已读"**。首版不新增逐封用户收件箱。

**F2-03 交接（2026-09-29 验收登记）**：开启或续订邮件前遇到未保存的订阅改动，走 F2-03 状态机的"保存后继续 / 使用已保存设置"，展示的摘要只取已保存版本，并补 U11 的真实通道用例。

### F4-02 · 名额不足体验

| 项 | 内容 |
| --- | --- |
| 前置 | F4-01 |
| 允许改动范围 | `apps/web/src/features/channels/email/**` |
| 继承合同 | 前端 §9.2 名额段落 |
| 验收 ID | U22a |

**这是本产品出现频率最高的一次拒绝**：`MAIL_SEATS_MAX = 100`（ADR-0003 已从 50 提高）仍远小于 `ACCOUNT_MAX_STORED = 500`，**五分之四的账号拿不到席位**，多数用户第一次点"开启邮件提醒"仍会撞上它。**不能只丢一行"名额已满"。**

**交付物（四项缺一不可）**

1. **当前状态**：邮件名额已满，且这是**内测期的预算限制，不是账号有问题**。
2. **替代方案放在最显眼位置**：个人日历 + 日历提醒**默认可用、不占名额**，大多数提醒需求它都能满足；直接给出「去启用日历提醒」按钮。
3. **差别说明**：没有邮件名额时，仍会失去的是「取消/改期的主动通知」——**如实写，不粉饰**。
4. **是否可候补**：有候补就说明规则，没有就直说暂不提供；**不承诺具体开放时间**。

## F5 · 可选 Push

前置门禁：**P6-03**（目标浏览器与网络验收通过）。

### F5-01 · 本浏览器通知

| 项 | 内容 |
| --- | --- |
| 允许改动范围 | `apps/web/src/features/channels/push/**`、Service Worker |
| 继承合同 | 前端 §9.3；主方案 §7.8 |
| 验收 ID | U23 |

**交付物**

- 按钮统一为 **「在当前浏览器开启通知」**，仅在 Push 能力开放后出现。
- 浏览器权限与服务端绑定**分别展示**：不支持 / 未授权 / 已拒绝 / 允许；等待激活 / 已激活 / 已暂停或失效。
- 权限允许后创建 pending 绑定，显示"正在验证本浏览器接收能力"；完成可见激活与 receipt 合同后才显示"**本浏览器接收验证通过**"。

**关键约束（红线）**

- 用户主动点击前，**不申请系统权限、不创建 Push 绑定、不发送测试**。
- **平台已接受请求不等于客户端激活成功。**
- 权限拒绝时说明需在浏览器设置中调整，**不循环弹窗**。
- 绑定属于其他账号时解释冲突并保留当前账号边界，**不通过 endpoint 自动认领或删除他人绑定**。
- 测试、重试、续期受真实额度与状态约束；显示可重试时间，**不靠无限测试或静默心跳维持"在线"**。
- **激活通过也不承诺未来每条必达。**

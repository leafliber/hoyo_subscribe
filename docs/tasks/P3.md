> 唯一主要目标：**把官方公告变成有证据、有版本、可被外部日历正确消费的事实。**
> 依据：主方案 §3 全章、§6 全章、§8.1、§10.3。
> 前置门禁：**G-P1**、**G-P0-SOURCE**（P3-01/02）、**G-P0-MODEL**（P3-03 的模型路径）、**G-P2**（P3-07）。

### P3-01 · 来源适配器与采集

| 项 | 内容 |
| --- | --- |
| 前置 | G-P1、G-P0-SOURCE |
| 允许改动范围 | `apps/worker/src/sources/**`、`apps/worker/src/executors/pipeline/**` |
| 继承合同 | §3.1、§3.2 前半、附录 A.1 的 `SOURCE_*` |
| 验收 ID | A-P3-FETCH |

**交付物**

- 适配器接口 `list(cursor, limit) → { items, next_cursor, complete }` 与 `fetchArticle(stub)`。
- 来源注册项：`source_id / game / region / adapter / approved_hosts / verified_publishers / cursor / poll_policy / last_success_at / verification_state`，从 P0-02 的登记结果导入。
- 轮询：`SOURCE_POLL` 常规 / `SOURCE_HOT_POLL` 热点；**保留重叠窗口**；每批有上限。

> **P0-02 实测推翻了原假设，采集模型必须按来源分开（证据：`docs/evidence/p0/source-params.md`）：**
> - **三个公告 API 不分页**。`page_size` 与 `page` 被服务端忽略，单请求即返回全集；`getAnnContent`
>   同样忽略 `announcement_id`，一次返回全部正文（实测约 254 KiB）。因此这三个来源是
>   **「每请求全量快照 + ann_id 差分」**，不是页码游标；`SOURCE_RECHECK_WINDOW` 的"按篇复查"
>   在这里等价于全量重拉，不要实现一个并不存在的单篇通道。
> - **米游社只有列表**。`post/wapi/getNewsList` 已 404（现行为 `painter/wapi/getNewsList`），
>   `getPostFull` 返回 403 访问控制。该来源按 `maintenance-required-list-only` 登记，
>   适配器只能贡献标题/图片级信息，**不得为了拿正文去试 UA 伪装、SSR 页面或第三方聚合后端**。
> - 公告 API 的**内容按玩家等级门控**（`level` + 登出态哑 `uid`）。该参数选择已由所有者确认，
>   适配器沿用 `fixtures/sources/registry.draft.json` 登记的参数集，不自行调整。
- 复查：`SOURCE_RECHECK_WINDOW` 内的近期公告按 `SOURCE_RECHECK_INTERVAL` 复查正文；仍关联活跃节点的公告继续跟踪。
- 请求限制：域名白名单、重定向、超时、大小与类型（`SOURCE_LIMIT_PROFILE`）。

> **已知需修正（P3-02 验收发现，2026-09-22）**：本卡把 `maxResponseBytes` 取成了
> `max_observed_content_bytes` **本身**（零余量）。修正归 **P3-08**，本卡不要重复处理，
> 也不要在别处再推导一次上限取值。

**关键约束**

- **不能仅按最大 ID 推进水位。**
- `complete` 表示扫描范围**真的完成**；HTTP 成功 ≠ 正文完整。
- 遇到鉴权、验证码或访问限制：**停用该来源并提示维护，不实施绕过**。
- 不提供公开通用抓取代理；生产只访问经审核的官方地址；第三方聚合后端不得冒充官方来源。
- 上游 ID 存字符串。

### P3-02 · 文章版本、证据与完整性状态

| 项 | 内容 |
| --- | --- |
| 前置 | P3-01 |
| 允许改动范围 | `apps/worker/src/sources/articles/**` |
| 继承合同 | §3.2 后半、§8.1 来源与正文组 |
| 验收 ID | A-P3-ARTICLE |

**交付物**

- `(source_id, external_id)` 标识文章；语义内容变化新增**不可变** ArticleVersion，保存正文块、内容 hash、官方 URL、发布时间、抓取时间、媒体引用、`completeness`。
- 去噪：去掉阅读量等噪声，**但不得去掉时间和阶段文本**。
- 缺口/审核状态：正文截断、图片承载关键日期、来源暂空。

**关键约束（红线）**

- **缺口不得转成"无活动"。**
- **没有官方取消证据时，抓取失败、文章删除或列表为空都不能自动取消事件。**
- 引用图片只有 URL 没有内容验证时，**不声称可以发现同 URL 换图**。
- 首版不做全量视频转录；必要图片日期由人工核验或另行批准的视觉流程处理。

> **待真实反例验证（验收登记，2026-09-22）**：`listClaimsContent === false → complete`
> 是全模块**唯一**能把空正文判成"已确认为空"的分支，而 P0-02 的 180 份真实样本里
> `has_content` **全是 true**，米游社是 `null`。该分支方向保守、不违红线，但没有真实
> 数据支撑其语义。P3-03 消费 `completeness` 时不得依赖它；出现 `has_content=false`
> 的真实样本后再确认语义。

> **既有缺陷（2026-09-27 验收发现，P3-02 验收时漏检）**：文章已有完整版本时，`missing-from-content-set`
> 会写一个只含标题的缺口版本；正文恢复后与原完整版本同 hash，被 `UNIQUE (article_id, content_hash)`
> 的全历史去重判为 `unchanged`，**最新版本永远停在缺口版**（场景测试已实证）。已随 P3-08 返工修复（`1579bfe`）。

### P3-03 · 三路抽取与候选审核队列

| 项 | 内容 |
| --- | --- |
| 前置 | P3-02；模型路径另需 G-P0-MODEL |
| 允许改动范围 | `apps/worker/src/extraction/**`、`apps/worker/src/executors/pipeline/**` |
| 继承合同 | §3.3、§3.4、§3.5、附录 A.3 |
| 验收 ID | A-P3-EXTRACT |

**交付物**

- 三条发布路径：确定性规则模板 → 模型 profile → 人工审核队列。
- 规则路径：**只有明确事件类别、完整时间和区域均有证据的白名单模式可自动发布**；模板不匹配就进审核。
- 模型路径：一次提交分类、多个事件、节点、变更关系、证据块引用及歧义；Schema 限定类型、枚举、长度、数组、空值和**未知字段**；**来源身份由服务器注入**。
- 可重放：同一 `article_version + extractor/prompt/schema/model_profile` 的成功结果可重放；结构修复（`MODEL_STRUCT_REPAIR`）与网络重试（`MODEL_NETWORK_RETRIES`）分别有界且**先预占费用**。
- 预算降级：`AI_SOFT_DAY` 软线（优先前瞻、维护、截止、关键更正，停低价值回填）；`AI_HARD_DAY` 硬线（确定性规则与人工仍可发布，其他排队并在状态页显示缺口）。
- 人工审核队列：可**直接依据保存的官方材料创建/修正候选**。
- Event / Milestone 合同：类型、节点类型、稳定 `milestone_key`、审核状态、事件状态、时间依据、时间精度。

**关键约束（红线）**

- **人工路径不依赖先取得一次模型结果。**
- 模型不获得用户数据、秘密、网络工具或写库权限；**自报置信度不能代替证据校验**。
- **达到硬线不能靠切便宜模型继续越额**——所有 profile 共用同一总账本，含失败与重试。
- 经济 profile 未通过 P0 质量与费用测试前保持未启用，**不得临时换陌生模型**。
- 只有日期不补成精确午夜；"预计维护五小时"不是实际开服；"更新后开放"不能猜固定时刻。跨年、省略年份、结束包含性无法唯一确定时进入审核。
- 身份不含日期，**改期不换 ID**；奖励截止与玩法结束分别保存。
- 恢复后按仍有时效价值排序，**不用陈旧积压耗尽新一天预算**。

> **本轮范围（2026-09-27 裁定）**：G-P0-MODEL 未开，且仓库**没有 AI 预算账本**
> （`usage_periods.pool` 的 CHECK 只允许四个邮件池）。本轮 P3-03 交付：
>
> - 规则路径：白名单模板自动发布，不匹配进审核；
> - 人工审核队列的**领域层与服务函数**：依据保存的 ArticleVersion 直接创建或修正候选；
> - Event / Milestone 合同与**候选 Schema 校验器**（纯函数；人工录入与将来的模型输出共用同一份）；
> - 模型路径**只留接口**：`AI_BILLING_PROFILE_CONFIGURED = false` 时一律不调用，改走审核。
>
> 拆出去的部分——模型调用、AI 预算账本（需要新迁移）、软线/硬线降级——归 **P3-09**，前置 G-P0-MODEL。
>
> **管理端缺口**：人工审核需要管理员会话与审核 API，但**目前没有任何任务卡负责**（§8.3 的管理员会话、
> 引导秘密换短期会话、Access 完整 JWT 校验）。本卡只做领域层，**不挂 HTTP 端点、不做管理员鉴权**；
> 缺口登记在 `BUILD_PLAN.md` §3「已知缺口」。

- `UID = feed_namespace + milestone_id + 固定日历命名空间`；`SEQUENCE = public_ical_revision + view_revision`，两者均单调不减。
- RFC 5545：CRLF、转义、UTF-8 安全折行、非包含 DTEND、稳定 UID、DISPLAY VALARM、默认 TRANSPARENT；**订阅文件不整体使用 METHOD:CANCEL**。精确时间输出 UTC `Z`，纯日期用 DATE，一个节点一个 VEVENT，**不凭空补结束时刻**。
- **缩水守卫**：按 `CONTRACTS_BASELINE.md` §5.2 实现，命中则 **503 + 告警**，并记录指标。
- 新鲜度：只输出未超过 `FEED_MAX_STALE` 的**当前完整发布代次**；新鲜度基于所需来源的成功核验水位，**不因重新组装或写缓存而续命**；私人 Feed **不回退到更旧发布代次**。
- 大小与条目上限：`FEED_BASE_NODE_MAX`、`FEED_PATCH_NODE_MAX`、`FEED_RESPONSE_MAX_BYTES`；超限返回明确错误与设置页诊断，**不截断**。
- ETag 来自实际内容与版本；304/HEAD 同样验证权限；`Cache-Control: private, no-store`。

**关键约束（红线）**

- **个人响应不放公共 CDN**，不用执行前缓存绕过权限。
- 授权数据库不可用返回 503，**即使有旧内容也不放行**。
- **公共浏览可展示陈旧缓存的策略不得移植为私人 Feed 的成功兜底。**
- 只有真实无匹配节点时才返回成功空 VCALENDAR。
- SEQUENCE 接近协议上限**停下并迁移，不回绕**。
- 时间窗口自然推进本身**不改公共版本**；相同内容重新进入集合**不意味着一条新的官方修订**。
- **不采用"某次 GET/304 成功后就清理撤销记录"**——一个 URL 可被多台客户端拉取，HTTP 成功既不证明已应用，也不证明所有客户端都已更新。

**D3 交接（2026-09-28 登记，D3 审定后生效）**：读路径须落库两项派生不出来的事实——最近一次成功输出的时间、最近一次被缩水守卫拦截的时间（条目数已有 `last_served_node_count`），供 P3-07 的日历视图区分"守卫拦截"与普通故障（`docs/D3_STATE_VIEWS.md` §2.6）。

### P3-08 · 抓取上限余量与截断一等成态

| 项 | 内容 |
| --- | --- |
| 前置 | P3-02 |
| 允许改动范围 | `apps/worker/src/sources/registry.ts`、`guarded-fetch.ts`、`types.ts`、`articles/completeness.ts`、`articles/ingest.ts` |
| 继承合同 | §3.2、附录 A.1 `SOURCE_LIMIT_PROFILE` |
| 验收 ID | A-P3-TRUNCATE |
| 排期 | 不阻塞 P3-03…P3-07；**必须在 P5-01 受控上线前合入** |

**为什么有这张卡（P3-02 验收发现，2026-09-22）**

P3-01 把 `maxResponseBytes` 取成 `max_observed_content_bytes` **本身**——genshin 254,672 /
hsr 195,598 / zzz 153,329 / miyoushe 110,546，**零余量**。

公告正文端点一次返回**全部存续公告**（genshin 实测 41 条）。版本更新一次上架一批公告，
载荷必然超过历史最大值 → `guarded-fetch` 判 `response-too-large` → **整请求作废** →
`fetchArticle` 失败 → P3-02 按"抓取失败不落任何行"处理 → **零行写入、零缺口标记**。
整个来源静默熄火，没有任何待审行提示有人去看。

这是红线「缺口不得转成"无活动"」的另一扇门：不是"缺口变无活动"，而是
**"缺口变成什么都没有"**——更难发现，因为连一条待审记录都不留。

P3-02 已实现 `gap-body-truncated` 判定，但当前管线到不了它（截断在 `guarded-fetch` 层
就把整请求作废了）。这条状态是**朝错误方向**不可达的：截断本该落到有人看得见的缺口，
实际落到了没人知道的空。

**交付物**

- `maxResponseBytes` 与观测值解耦：给出明确余量并写进 `SOURCE_LIMIT_PROFILE` 注册项，
  余量的取值理由写在注册表注释里（不是随手乘 2——要说明按什么增长模型留的）。
- 截断成为**一等抓取结果**：`ArticleFetchResult` 增加截断态，经 `completeness` 映射到
  `gap-body-truncated`，落成可被人看见的行。
- 超限产生**可观测信号**（`ENGINEERING.md` §5.5 遥测口径），不能只体现为"这批没数据"。

**关键约束**

- **超限不得表现为零写入零标记。** 要么落缺口行，要么发出告警，两者至少其一。
- 提高上限不等于取消上限——成本护栏（`ENGINEERING.md` §4.1）仍然生效。余量要有上界，
  并说明这个上界为什么不会打穿付费套餐。
- 不得为了绕过上限去做分片重试、换通道或降级请求（与 §3.1「遇到访问限制不实施绕过」同源）。
- 本卡只修上限与截断成态，**不动差分与游标语义**。
  （原写"不动文章版本语义"——这条限制挡住了下面这个缺陷的修复，2026-09-27 由验收方解除，仅限下一段。）
- **不动 `apps/worker/src/executors/pipeline/**`**：该目录属 P3-03 的范围，两张卡可能并行；确需改动先停下来说明。

> **返工（2026-09-27 验收）：降级抓取结果不得覆盖已有的真实内容**——已完成：`1579bfe` 随 #20 合入，
> 验收方用上一轮实证失败的两条场景复核，版本历史均只剩一个完整版本。
>
> 实证：完整 v1 → 截断 → 恢复同样正文，结果 `created 2 / unchanged 1`，最新版本停在 v2 `gap-body-truncated`。
> 一次截断会让该来源全部文章一起卡住；P3-04 按最新版本发布时，这些活动会从日历里消失——
> 这正是 P3-02 红线二（抓取失败不得自动取消事件）要挡的。执行者已在报告中如实申报此边界，
> 未修是因为本卡原先写了"不动文章版本语义"。
>
> **不变量：最新版本 = 最后一次真正取得的内容。**"这次没拿到正文"是抓取状态，不是内容变化。
>
> 1. 文章尚无版本：降级结果照旧写只含标题的缺口版本（新文章只能靠它被看见）。
> 2. 最新版本真正拿到过正文：降级结果**不写新版本**；缺口仍须可见（截断已有 `source_response_truncated`，
>    集合缺条/暂空要有同等的结构化信号）；这次失败不算一次成功的复查。
> 3. 最新版本本身是降级版本：内容变化时可写新的降级版本。
> 4. "是否降级"按**这次是否真的拿到正文**判定，不只看 completeness 标签（米游社的 `review-image-borne`
>    就产生于正文通道不可用）。判定写成单一来源的函数。
>
> 同时修复 P3-02 既有的 `missing-from-content-set` 同类问题。不许改迁移与 `UNIQUE` 约束。

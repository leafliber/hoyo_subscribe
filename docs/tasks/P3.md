# P3 · 事实发布与个人 ICS

> 唯一主要目标：**把官方公告变成有证据、有版本、可被外部日历正确消费的事实。**
> 依据：主方案 §3 全章、§6 全章、§8.1、§10.3。
> 前置门禁：**G-P1**、**G-P0-SOURCE**（P3-01/02）、**G-P0-MODEL**（P3-03 的模型路径）、**G-P2**（P3-07）。
> **G-P0-CAL 未开时**：P3-06 可以实现并测试，但对外**不得出现"日历提醒可用"的表述**（§1.2）。

### P3-01 · 来源适配器与采集

| 项 | 内容 |
| --- | --- |
| 前置 | G-P1、G-P0-SOURCE |
| 允许改动范围 | `apps/worker/src/sources/**`、`apps/worker/src/executors/pipeline/**` |
| 继承合同 | §3.1、§3.2 前半、附录 A.1 的 `SOURCE_*` |
| 验收 ID | A-P3-FETCH |

**交付物**

- 适配器接口 `list(cursor, limit) → { items, next_cursor, complete }` 与 `fetchArticle(stub)`。
- 来源注册项：`source_id / game / region / adapter / approved_hosts / verified_publishers / cursor / poll_policy / last_success_at / verification_state`，从 P0-02 的登记结果导入。
- 轮询：`SOURCE_POLL` 常规 / `SOURCE_HOT_POLL` 热点；**保留重叠窗口**；每批有上限。

> **P0-02 实测推翻了原假设，采集模型必须按来源分开（证据：`docs/evidence/p0/source-params.md`）：**
> - **三个公告 API 不分页**。`page_size` 与 `page` 被服务端忽略，单请求即返回全集；`getAnnContent`
>   同样忽略 `announcement_id`，一次返回全部正文（实测约 254 KiB）。因此这三个来源是
>   **「每请求全量快照 + ann_id 差分」**，不是页码游标；`SOURCE_RECHECK_WINDOW` 的"按篇复查"
>   在这里等价于全量重拉，不要实现一个并不存在的单篇通道。
> - **米游社只有列表**。`post/wapi/getNewsList` 已 404（现行为 `painter/wapi/getNewsList`），
>   `getPostFull` 返回 403 访问控制。该来源按 `maintenance-required-list-only` 登记，
>   适配器只能贡献标题/图片级信息，**不得为了拿正文去试 UA 伪装、SSR 页面或第三方聚合后端**。
> - 公告 API 的**内容按玩家等级门控**（`level` + 登出态哑 `uid`）。该参数选择已由所有者确认，
>   适配器沿用 `fixtures/sources/registry.draft.json` 登记的参数集，不自行调整。
- 复查：`SOURCE_RECHECK_WINDOW` 内的近期公告按 `SOURCE_RECHECK_INTERVAL` 复查正文；仍关联活跃节点的公告继续跟踪。
- 请求限制：域名白名单、重定向、超时、大小与类型（`SOURCE_LIMIT_PROFILE`）。

**关键约束**

- **不能仅按最大 ID 推进水位。**
- `complete` 表示扫描范围**真的完成**；HTTP 成功 ≠ 正文完整。
- 遇到鉴权、验证码或访问限制：**停用该来源并提示维护，不实施绕过**。
- 不提供公开通用抓取代理；生产只访问经审核的官方地址；第三方聚合后端不得冒充官方来源。
- 上游 ID 存字符串。

### P3-02 · 文章版本、证据与完整性状态

| 项 | 内容 |
| --- | --- |
| 前置 | P3-01 |
| 允许改动范围 | `apps/worker/src/sources/articles/**` |
| 继承合同 | §3.2 后半、§8.1 来源与正文组 |
| 验收 ID | A-P3-ARTICLE |

**交付物**

- `(source_id, external_id)` 标识文章；语义内容变化新增**不可变** ArticleVersion，保存正文块、内容 hash、官方 URL、发布时间、抓取时间、媒体引用、`completeness`。
- 去噪：去掉阅读量等噪声，**但不得去掉时间和阶段文本**。
- 缺口/审核状态：正文截断、图片承载关键日期、来源暂空。

**关键约束（红线）**

- **缺口不得转成"无活动"。**
- **没有官方取消证据时，抓取失败、文章删除或列表为空都不能自动取消事件。**
- 引用图片只有 URL 没有内容验证时，**不声称可以发现同 URL 换图**。
- 首版不做全量视频转录；必要图片日期由人工核验或另行批准的视觉流程处理。

### P3-03 · 三路抽取与候选审核队列

| 项 | 内容 |
| --- | --- |
| 前置 | P3-02；模型路径另需 G-P0-MODEL |
| 允许改动范围 | `apps/worker/src/extraction/**`、`apps/worker/src/executors/pipeline/**` |
| 继承合同 | §3.3、§3.4、§3.5、附录 A.3 |
| 验收 ID | A-P3-EXTRACT |

**交付物**

- 三条发布路径：确定性规则模板 → 模型 profile → 人工审核队列。
- 规则路径：**只有明确事件类别、完整时间和区域均有证据的白名单模式可自动发布**；模板不匹配就进审核。
- 模型路径：一次提交分类、多个事件、节点、变更关系、证据块引用及歧义；Schema 限定类型、枚举、长度、数组、空值和**未知字段**；**来源身份由服务器注入**。
- 可重放：同一 `article_version + extractor/prompt/schema/model_profile` 的成功结果可重放；结构修复（`MODEL_STRUCT_REPAIR`）与网络重试（`MODEL_NETWORK_RETRIES`）分别有界且**先预占费用**。
- 预算降级：`AI_SOFT_DAY` 软线（优先前瞻、维护、截止、关键更正，停低价值回填）；`AI_HARD_DAY` 硬线（确定性规则与人工仍可发布，其他排队并在状态页显示缺口）。
- 人工审核队列：可**直接依据保存的官方材料创建/修正候选**。
- Event / Milestone 合同：类型、节点类型、稳定 `milestone_key`、审核状态、事件状态、时间依据、时间精度。

**关键约束（红线）**

- **人工路径不依赖先取得一次模型结果。**
- 模型不获得用户数据、秘密、网络工具或写库权限；**自报置信度不能代替证据校验**。
- **达到硬线不能靠切便宜模型继续越额**——所有 profile 共用同一总账本，含失败与重试。
- 经济 profile 未通过 P0 质量与费用测试前保持未启用，**不得临时换陌生模型**。
- 只有日期不补成精确午夜；"预计维护五小时"不是实际开服；"更新后开放"不能猜固定时刻。跨年、省略年份、结束包含性无法唯一确定时进入审核。
- 身份不含日期，**改期不换 ID**；奖励截止与玩法结束分别保存。
- 恢复后按仍有时效价值排序，**不用陈旧积压耗尽新一天预算**。

### P3-04 · 原子发布与三类版本

| 项 | 内容 |
| --- | --- |
| 前置 | P3-03、P1-05 |
| 允许改动范围 | `apps/worker/src/publishing/**` |
| 继承合同 | §3.6、§8.1 理解与事实组；`CONTRACTS_BASELINE.md` §5 |
| 验收 ID | A-P3-PUBLISH |

**交付物**

- 一次条件提交同时更新：Event、Milestone、证据关联、不可变修订、必要日历投影、outbox、快照待更新状态。
- 三层去重：文章身份 / 抽取版本 / 业务事件关联。
- 三类版本：`event_revision`（任何修订）、`schedule_revision`（仅时刻或提醒语义变化）、`public_ical_revision`（影响该节点日历表现）。
- 人工保护字段只能通过**带理由的操作**修改。

**关键约束**

- **D1 batch 的 SQL 失败回滚 ≠ CAS 零行自动失败**：必须用统一条件守卫或约束让整批相关写入一起成立或一起失败（§3.6）。
- 不同公告可能描述同一活动，**标题相似不足以自动合并**。
- 迟到的旧模型结果**只能留历史**，不得覆盖新状态；旧文章版本、旧租约、旧配置不能覆盖新状态。
- 完整快照**先构建后切换可见代次，禁止跨代拼接**。

### P3-05 · 公共快照与共享更正层

| 项 | 内容 |
| --- | --- |
| 前置 | P3-04 |
| 允许改动范围 | `apps/worker/src/calendar/public/**` |
| 继承合同 | §6.3、附录 A.3 的 `CAL_PATCH_*`、`PUBLIC_CACHE_FRESH`；`CONTRACTS_BASELINE.md` §5.1 |
| 验收 ID | A-P3-PATCH |

**交付物**

- 公共快照按完整发布代次构建；公共模板**不含最终个人 UID**。
- 共享更正层 `calendar_patches`：**按 Milestone 保存，不按用户复制**。覆盖 §6.3 表格的五种变化。
- 保留截止 = `max(最后更正时间 + CAL_PATCH_MIN_DAYS, 仍需覆盖的旧节点最晚时间 + CAL_PATCH_TAIL_DAYS)`；连续改期**累计**旧时间保留水位。
- 容量保护：`CAL_PATCH_GLOBAL_MAX` 告警、归档已可回收记录、必要时暂停新非关键发布。

**关键约束（红线）**

- **更正层条目与基础节点走同一套用户筛选**——组装时只输出按该用户**当前** `scope`、`calendar.event_types/node_types` 及提醒关联节点仍匹配的更正条目。用户隐藏了某类节点却凭空收到"某活动已取消"，是最坏的结果。
- 用户改筛选后不再匹配的更正条目，**按完整快照语义自然缺席即可**，不需要再补一条取消。
- 纯自然窗口退出或用户隐藏**不得伪称官方取消**。
- 延期但新时间未知：用最近已发布时间输出 CANCELLED 并说明事实原因，**不虚构新日期**。
- 同一 Feed 同一 UID **最多一条**。
- 更正层随公共事实变化增长，**不随用户保存筛选增长**；容量故障不得导致无关用户配置无法保存，也不得以成功空日历掩盖。

### P3-06 · 个人 ICS 组装、缩水守卫与读路径缓存

| 项 | 内容 |
| --- | --- |
| 前置 | P3-05、G-P2 |
| 允许改动范围 | `apps/worker/src/calendar/feed/**` |
| 继承合同 | §6.1—§6.6、附录 A.3 的 `FEED_*`、[R11]；`CONTRACTS_BASELINE.md` §5 |
| 验收 ID | A-P3-ICS |

**交付物**

- `GET|HEAD /feeds/u/{token}.ics`，按 `CONTRACTS_BASELINE.md` §5.3 的读路径顺序实现。
- 完整快照语义：缺席即删除。**不实现任何个人撤销池**。
- `UID = feed_namespace + milestone_id + 固定日历命名空间`；`SEQUENCE = public_ical_revision + view_revision`，两者均单调不减。
- RFC 5545：CRLF、转义、UTF-8 安全折行、非包含 DTEND、稳定 UID、DISPLAY VALARM、默认 TRANSPARENT；**订阅文件不整体使用 METHOD:CANCEL**。精确时间输出 UTC `Z`，纯日期用 DATE，一个节点一个 VEVENT，**不凭空补结束时刻**。
- **缩水守卫**：按 `CONTRACTS_BASELINE.md` §5.2 实现，命中则 **503 + 告警**，并记录指标。
- 新鲜度：只输出未超过 `FEED_MAX_STALE` 的**当前完整发布代次**；新鲜度基于所需来源的成功核验水位，**不因重新组装或写缓存而续命**；私人 Feed **不回退到更旧发布代次**。
- 大小与条目上限：`FEED_BASE_NODE_MAX`、`FEED_PATCH_NODE_MAX`、`FEED_RESPONSE_MAX_BYTES`；超限返回明确错误与设置页诊断，**不截断**。
- ETag 来自实际内容与版本；304/HEAD 同样验证权限；`Cache-Control: private, no-store`。

**关键约束（红线）**

- **个人响应不放公共 CDN**，不用执行前缓存绕过权限。
- 授权数据库不可用返回 503，**即使有旧内容也不放行**。
- **公共浏览可展示陈旧缓存的策略不得移植为私人 Feed 的成功兜底。**
- 只有真实无匹配节点时才返回成功空 VCALENDAR。
- SEQUENCE 接近协议上限**停下并迁移，不回绕**。
- 时间窗口自然推进本身**不改公共版本**；相同内容重新进入集合**不意味着一条新的官方修订**。
- **不采用"某次 GET/304 成功后就清理撤销记录"**——一个 URL 可被多台客户端拉取，HTTP 成功既不证明已应用，也不证明所有客户端都已更新。

### P3-07 · Feed 管理 API 与活动水位

| 项 | 内容 |
| --- | --- |
| 前置 | P3-06 |
| 允许改动范围 | `apps/worker/src/calendar/manage/**`、`apps/worker/src/accounts/activity/**` |
| 继承合同 | §6.1、§6.6 末段、§8.2、§9.4 |
| 验收 ID | A-P3-FEEDAPI |

**交付物**

- `GET /api/v2/me/calendar`（专用所有者接口读取完整 URL，**不混入普通账号摘要**）。
- `POST` enable / disable / reset：统一会话权限，幂等换凭证。停用永久撤销当前 token；再次启用或重置生成新 token，但**保留逻辑 Feed 的 namespace 和 `view_revision`**。
- token hash 用于校验，另存认证密文供所有者再次复制同一地址（长期凭证"只存 hash"原则的明确例外）。
- `last_feed_poll_at`：随授权查询在**同一条 D1 条件更新**里完成，每 `FEED_ACTIVITY_WRITE_INTERVAL` 最多写一次；不创建逐请求记录，不续登录会话、不修改配置。
- `activity_write_failures` 指标；指标异常或最近成功写入早于 `RECLAIM_TELEMETRY_STALE_HOURS` 时 → **全局暂停账号与席位回收**的开关。

**关键约束**

- Feed 管理**不要求额外 OTP**（§4.7）；reset 与 disable→enable 权限等价——邮箱失联时也能撤销只读地址。
- 修改筛选、退出、换设备**不改变 URL**。
- 写入失败**不改变本次日历内容**，但必须计入指标：一个被设计成可以静默失败的写入，不能单独决定删不删用户的账号。
- 服务端**不能擦除**已经下载的文件或客户端副本。
- 提供 URL ≠ 提醒必达；外部日历刷新频率由客户端决定。

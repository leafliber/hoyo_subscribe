## P5 · 受控上线

唯一主要目标：**在开放给真实用户之前，确认"出了问题能看见、能关掉、能恢复"。**

### P5-01 · 观测指标与运行开关

| 项 | 内容 |
| --- | --- |
| 前置 | P4 全部 |
| 允许改动范围 | `apps/worker/src/shell/observability/**`、各模块的指标埋点 |
| 继承合同 | §10.1 |
| 验收 ID | A-P5-OBS |

**必须实现的指标**（§10.1 明确列出，每一项都对应一个**会静默发生**的故障）：

| 指标 | 盯的故障 |
| --- | --- |
| 当日认证池剩余、是否跌破 `MAIL_AUTH_FLOOR` | 当天的登录能力被烧光而无人察觉（日模型下次日自动恢复，但当天用户登不进来） |
| 各池当日余额与耗尽时刻 | 某个池天天在同一时段耗尽，说明额度分配与真实需求不匹配 |
| 缩水守卫命中次数与被拦响应 | 构造 bug 正在向客户端下达错误的删除指令 |
| 活动水位写入失败数、回收是否处于暂停 | 遥测坏了却仍在回收活跃用户的账号与席位 |
| 邮件合并率（每封平均承载的 Delivery 数） | 每日一封的额度是否真的送出了当天全部内容 |
| 席位自动续租与实际释放的比例 | 是否在摘掉"只用外部日历"的正常用户 |

**其余观测**：公开页按游戏显示来源最新成功、数据代次、待审核缺口；后台显示认证排队、账户/席位存量、当日各池余额、各优先级等待时间与跳过原因、退订延迟、邮件 unknown/抑制、Queue DLQ、Feed 完整性、真实 CPU/读写/存储。

**P3-08 已登记的来源截断信号**：`source_response_truncated_total` 按官方主机聚合 `source_response_truncated` 结构化日志（固定事件名、`source`、`reason_code=response_cap_exceeded`、`count=1`；不含 URL/正文）。单次命中即告警并核验来源载荷与 `SOURCE_LIMIT_PROFILE`；不得自动抬上限或重试绕过。P5-01 将此信号接入受控上线的指标与告警面板。

**P3-06 / P4-03 登记的两条告警（2026-09-30 所有者裁定）**：这两类故障不再有自动兜底，只能靠告警发现。
- **管线滞后**：公共快照重建积压太久（`snapshot_rebuild` outbox 长时间停在 pending，或构建连续失败）即告警。
  Feed 的新鲜度只看来源水位，下游卡住时 Feed 仍报"新鲜"（见 P3-06 卡末裁定）。阈值取已登记参数（如 `FEED_MAX_STALE`），需要新参数先进注册表。
- **邮件 unknown**：`mail_provider_failed` 中 `reason_code=provider_unknown` 单次即告警，并显示当日次数与认证池余额。
  unknown 不再触发全局暂停（见 P4-03 卡末裁定），平台只超时、不报错时，这是唯一的发现途径。

**独立开关**必须覆盖：注册、新邮件名额、常规提醒邮件层、业务邮件、全部外发、Push、模型、自动发布、单来源、账号与席位回收、只读维护。

**关键约束**：达到预算先停止低价值扩大，**不用假空数据和假成功遮蔽**。账单告警只是监控，**不是平台收费绝对封顶**。

**D3 交接（2026-09-28 登记；D3 已于 2026-09-30 审定，生效）**：运行开关的对外部分（各能力是否开放）进公开状态视图，缺失按 unknown（`docs/D3_STATE_VIEWS.md` §2.1）。

**P4-07 交接（2026-09-30 验收登记）**：
- 反馈表的到期清理与再关联只在有 Queue 流量时顺带做（每封入库前一页、批末一页）。没有流量时要由定期任务调用
  `mail/feedback/store.ts` 的 `pruneFeedbackPage` 与 `reconcileFeedbackPage`：有限页、在 `EXECUTOR_BATCH_WALL_LIMIT` 内循环（ENGINEERING §5.6）。
- 告警：反馈表逼近 `MAIL_FEEDBACK_MAX`、未关联逼近 `MAIL_UNMATCHED_MAX`、DLQ 有积压；匿名计数
  `mail_feedback:unmatched_expired:*` 持续上涨（说明有大量关联不上的反馈）也要告警。

**P4-04 交接（2026-09-30 晚验收登记，P4-04 返工合入后生效）**：
- `system_state` 的 `mail_retry_budget_not_scheduled` 累计计数（含四个用途）进告警：已外调、被明确可重试拒绝的邮件首版不自动补发，只能靠它发现。
- `delivery_budget_failed`、`delivery_dispatch_failed` 固定原因日志，以及 `delivery:budget-backoff`、`delivery:dispatch-backoff`、`delivery:dispatch`
  进入 failed 状态，都要告警：业务预算维护与业务批次各自停下，不影响认证发信。

**开工交接（2026-10-02，第十二批）**：仍须 P4 全部验收合入，尤其 #57 平台冒烟与真实退订头签名覆盖关闭后才能开始。新分支 `p5/P5-01-observability-controls`。首个提交先交指标/开关清单、数据来源、现有参数、缺失值与测试骨架，再实现。

为兑现本卡已有交付物，批准最小接线：`packages/contracts/src/` 新增本卡指标/开关 schema、闭合枚举与纯推导及测试，index.ts 只追加导出；`apps/worker/src/index.ts` 只挂本卡路由/依赖；`apps/worker/src/executors/pipeline/controls.ts` 替换预留读取点；`apps/worker/src/scheduled/**` 只接本卡已有反馈清理/再关联交接；各既有模块仅加本卡指标与相应开关读取，不重构业务。观测与管理逻辑集中原允许的 shell/observability/**，管理写操作复用管理员会话、绑定 CSRF、理由与审计，不开无鉴权管理口。公开状态只给能力事实/unknown，不公开预算、账号或秘密；运行开关关闭不得阻断退订、停用等终止能力。

本卡不实施 P5-02 回收策略或 P5-03 备份，不新增 Cloudflare 资源/计量项，不把本地 CPU 当平台 CPU。真实平台指标缺失写 unknown 与待取证；新阈值仍先提具体值由所有者定，不借用不相干参数。后台可复用现有管理员 API/只读输出完成观测，不夹带 F6 页面扩建。交付时把部署配置差异、关闭注册与全部外发的首次部署操作写进 PR，供验收方整理给所有者；所有者亲自部署。

### P5-02 · 生命周期回收与暂停回收

| 项 | 内容 |
| --- | --- |
| 前置 | P5-01、P3-07 |
| 允许改动范围 | `apps/worker/src/accounts/reclaim/**`、`apps/worker/src/executors/cron/**` |
| 继承合同 | §9.4、§9.5、§9.6、附录 A.2 的 `ACCOUNT_*` 与 `RECLAIM_*` |
| 验收 ID | A-P5-RECLAIM |

**交付物**

- 逐对象回收信号（§9.4 表）：注册预占/验证码/完成回执、pending Session、正式会话、邮件名额、Push、账号。
- 账号活动水位 `max(last_interactive_at, last_feed_poll_at, last_push_processed_at)`，**低频合并写入，不每 GET 写 last_seen**。
- `ACCOUNT_IDLE_DAYS` → 回收宽限 `ACCOUNT_GRACE_DAYS` → 清理。
- **回收前的维护者可见待回收清单复核**入口。
- 活动水位不可信（指标异常或最近成功写入早于 `RECLAIM_TELEMETRY_STALE_HOURS`）时 → **全局暂停账号与席位回收**。
- 保留与清理：附录 A.5 的全部 TTL 与容量上限。

**关键约束（红线）**

- **持续使用外部日历但不访问网页的用户不会仅因缺少网页登录被清理。**
- **邮件席位按活动信号自动续租**，不要求用户专门回网页。
- 邮件服务商接受、邮件扫描器访问退订页**不算用户活跃**。
- **不在无人确认的情况下直接清理。**
- 删除/清理释放实际存量；**已消耗的日创建、尝试和发送额度不退款**。
- 无活动清理规则从注册时明确展示，**不得事后无提示缩短**。
- 到期任务不能因为删除 Delivery 就重新展开；正式证据、未过有效期的更正、未完成发送和合法退订依赖**优先于机械 TTL**。
- 不承诺自动识别所有僵尸或攻击者——恶意持续占满容量时暂停注册并由维护者处理。

**P3-07 交接（2026-09-30 晚验收登记）**：
- 回收前调用 `accounts/activity/telemetry.ts` 的 `readReclaimGate`，账号与席位共用这一道门。
- 它的默认是"暂停"：`system_state.reclaim_paused` 没有记录、不是 `false`、指标过期或本 isolate 写失败过，都算暂停；
  水位写失败会持久置为暂停，成功拉取不会自动解除。本卡要提供维护者核实后解除的受控操作（带理由与审计），
  并补一条"没有记录时按暂停"的用例（P3-07 复核时这条变异存活）。

**P4-05 交接（2026-10-01 验收登记）**：
- 席位续租的后台扫描由本卡做：有界分页调用 `mail/channel/lease.ts` 的 `renewEmailSeat`。它只看三种账号活动水位，发信与投递成功不算。
- 通道关闭后的同意历史按 `CONSENT_AUDIT_AFTER_CLOSE` 清理。

**P3-10 交接（2026-10-01 验收登记）**：系统审计没有保留期，也没人清理。
- 注册预占到期释放时写的审计，`expires_at` 取的是预占自己的到期时刻，写入时就已到期，之后一直累积。
- 本卡按附录 A.5 的清理职责一并处理：要么给系统审计定保留期并接到期清理，要么不再写这类审计。定保留期需要新参数的，先按硬规则 2 进注册表。
- 管理员审计的清理已由 P3-10 负责（`ADMIN_AUDIT_TTL`）。

**所有者裁定与实施范围（2026-10-02，第十二批）**：系统审计保留期已批准为 180 天，见 [ADR-0007](../adr/0007-system-audit-retention.md)，不再等同一裁定。前置仍为 P5-01、P3-07 验收合入；届时新分支 `p5/P5-02-lifecycle-reclaim`。

除原范围外，批准最小改动 contracts 参数注册表/PARAMS/PARAM_META、verify.ts、参数测试，生成 APPENDIX_A.generated 并按 AGENTS 例外同步 CONTRACTS_BASELINE §11；`apps/worker/src/accounts/admission/registration.ts` 只修系统审计 expiresAt 的参数消费及相关测试；`apps/worker/src/scheduled/**` 接有界回收；`storage/schema.test.ts` 只加清理 rows_read 基准。确需索引时可加顺序迁移及相应 expected-schema，编号按开工 main 下一个号，撞号改号重跑。旧系统行先按 created_at 校正再清理，不改管理员审计。回收前维护者清单确认、遥测不可信即暂停、Feed 使用不误删、席位自动续租均是必测；只用合成数据，不实际删除生产资源或数据。

| 项 | 内容 |

**交付物**

- 恢复 runbook，严格按顺序：隔离环境关外发 → 校验 Schema/密文/证据 → **使用旧快照之外的当前恢复 epoch 废止旧会话与认证结果** → 对账撤销和版本 → 恢复公开读及账号控制 → **最后**恢复发送。

**关键约束（红线）**

- **Time Travel 不是独立备份。**
- 没有可信的新近撤销清单时：恢复的邮件/Push **默认暂停**，旧 Feed token **默认撤销**；恢复码的已消费状态不确定也不能直接恢复使用。
- **禁止向可能已退订的地址群发重新确认。**
- 能证明高水位时保留 UID 并抬高版本；**无法证明时暂停受影响 Feed，进行明确的新订阅迁移**，不承诺无损透明回滚。
- 代码回滚不等于数据库回滚。

**所有者托管选择与开工交接（2026-10-02，第十二批）**：所有者选择“全部 Cloudflare 托管，如果有不能上传的，交给我本地保管”。这确定了托管偏好和本地保管兜底，不代表备份位置已经建好、已执行备份或授权新增 R2 等计量项。前置 P5-01 验收合入后，新建 `p5/P5-03-backup-restore`，只改 scripts/backup/**、docs/runbooks/**。

先给具体的导出、加密、保存与恢复方案：优先核实现有 Cloudflare 能力能否在现有费用护栏内形成独立备份；不能满足独立性、费用或分离保管的产物交所有者本地保存。不得用 D1 Time Travel、原库内另一张表或同一份旧快照冒充独立备份/当前恢复 epoch。字段密钥、退订验证密钥、VAPID（首版未启用则如实标不适用）、备份解密材料和旧快照之外的当前恢复 epoch 必须与备份分开；可交所有者离线保管，秘密不通过 PR/仓库/日志交付。

若具体方案需要新增 Cloudflare 产品、计量项、资源或权限，先在 PR 给出 ADR/最小配置与费用边界，由所有者选择和操作，不能因“全部托管”自行开通。先完成不依赖云操作的本地加密导出、校验与隔离恢复演练，脚本支持所有者执行；目标环境导出阻塞/恢复时间由部署阶段取证，不冒充已测。

### P5-05 · 站点静态资源接入 Worker 项目（F1-06 中途复核发现的缺口，2026-10-01 立卡）

| 项 | 内容 |
| --- | --- |
| 前置 | F1-06 合入（带 `_redirects` 与详情壳页） |
| 允许改动范围 | `apps/worker/wrangler.jsonc`（只加 `assets` 一段）；`apps/worker/worker-configuration.d.ts`（加了静态资源绑定时按 wrangler 重新生成）；根目录 `package.json` 的 build 编排（只在需要保证"先构建网页、再做 Worker dry-run"时改）；`scripts/` 下新增的本地冒烟脚本 |
| 继承合同 | 主方案 §2.1（一个 Worker 项目；静态资源直达，账号 API、Feed、退订等动态路径进 Worker）、§8.2；前端 §2.1、§12.1、§12.3 |
| 验收 ID | A-P5-SITE（新增） |

主方案 §2.1 定的是一个 Worker 项目、静态资源直达。现在 `wrangler.jsonc` 没有 `assets`，网页的构建产物还没有任何上线路径；
F1-06 的详情直达依赖平台的 `_redirects`，也要在这里落地验证。

**交付物**

- `wrangler.jsonc` 加 `assets`，目录指向网页构建产物。
  - 动态路径 `/api/*`、`/feeds/*`、`/unsubscribe/*`、`/email/one-click/*` 一律先进 Worker（`run_worker_first`），静态文件和 `_redirects` 遮不住它们。
  - 不用单页应用式兜底（`not_found_handling` 不设为 `single-page-application`）：未知路径要 404，不能变成首页。
- `pnpm build` 保证先构建网页、再做 Worker dry-run；dry-run 的输出里能看到静态资源。
- 本地冒烟脚本（`wrangler dev` 纯本地运行，不连任何远端资源），逐条断言：
  - `/`、`/subscription`、`/login` 等页面返回静态 HTML；
  - `/events/<任意 ID>` 返回详情壳页，状态 200，地址不变；
  - `/api/v2/status` 进 Worker；`/feeds/u/<任意>` 进 Worker 并按 Feed 协议拒绝；`/unsubscribe/<任意>` 与 POST `/email/one-click/<任意>` 进 Worker；
  - 未知路径返回 404。
- 报告写明哪些请求会计入 Worker 调用：动态路径，以及没有对应静态文件、落到 Worker 返回 404 的未知路径；命中静态文件和 `_redirects` 的请求不计。

**关键约束（红线）**

- 不部署，不创建、修改或删除任何 Cloudflare 资源；只改仓库里的配置。真正上线由所有者按 `DEPLOYMENT_PREREQUISITES.md` 执行。
- 网页产物里不能有任何秘密；构建期变量只有 `PUBLIC_` 开头的公开值。
- 个人 Feed、退订与所有 `/api/*` 路径不能被静态规则或 `_redirects` 截走。

**P4-06 交接（2026-10-01，PR #57 中途范围裁定）**：退订能力还有 `/email/one-click/{token}`，不可只配置 `/unsubscribe/*`。

## P6 · 可选 Web Push

唯一主要目标：**在不把 Push 当成掩盖日历主通道未验收的借口的前提下，做一个归属清晰、能真正验证接收的通道。**

### P6-01 · 绑定创建与可见激活

| 项 | 内容 |
| --- | --- |
| 前置 | G-P2、P5-01 |
| 允许改动范围 | `apps/worker/src/push/**` |
| 继承合同 | §7.8、§8.2、附录 A.4 的 `PUSH_*`、[R15] |
| 验收 ID | A-P6-BIND |

**交付物**

- 用户主动授权当前浏览器后，由**会话 + CSRF** 校验创建归属账号的 pending 绑定；验证精确 HTTPS 推送服务域名、端点与加密密钥；发送可见激活通知。
- Service Worker 使用**狭窄 receipt token + 随机 challenge** 确认后转 active。
- `PUSH_ACTIVATION_TTL`、`PUSH_ACTIVATION_ATTEMPTS`、`PUSH_TEST_COOLDOWN`、`PUSH_TEST_DAY`、`PUSH_USER_MAX`、`PUSH_ACTIVE_MAX`、`PUSH_PENDING_MAX`、`PUSH_NEW_DAY` 全部生效。

**关键约束（红线）**

- 同 endpoint 同 owner 可幂等；**不同 owner 冲突，不 UPSERT 抢占**。
- receipt token **不能获取邮箱、修改账号或管理其他设备**；管理和改偏好仍必须账号会话。
- 接口**不得成为任意 Webhook/SSRF 入口**。
- **不自动跟随登录开启**；用户主动点击前不申请系统权限、不创建绑定、不发测试。

**P2-05 交接（2026-09-28 验收方登记）**：紧急停用与恢复登录的安全暂停必须同时暂停 Push——把本通道的效果挂进 P2-05 导出的安全暂停挂接点，并加一条"紧急停用后本通道立即失效"的用例；首次启用前还须核对恢复码已保存确认（P2-05 导出的判定，§4.6）。

**D3 交接（2026-09-28 登记；D3 已于 2026-09-30 审定，生效）**：只给事实，不给服务端算好的动作表（D3 §1.2）。`GET /api/v2/me/push-bindings` 按 `docs/D3_STATE_VIEWS.md` §2.8 给出各绑定的状态、激活时间、租期；当前浏览器按本机持有的绑定 ID 判断，不按 endpoint 认领。

### P6-02 · 发送、租期、失效与退避

| 项 | 内容 |
| --- | --- |

**交付物**

- 发送预算：`PUSH_SEND_DAY`（含业务、激活、测试、重试）、`PUSH_CRITICAL_RESERVED_DAY`。
- 租期：`PUSH_LEASE`、`PUSH_STALE_GRACE`；真实业务处理确认或账号操作可续期；`PUSH_RECEIPT_WRITE_INTERVAL` 合并写入。
- 失效处理：明确 404/410 停用端点；**401/403 先检查 VAPID/配置，不批量删除用户**；临时错误退避。

**关键约束**：平台接受**不是**客户端存活证明；**不发静默心跳**；激活通过也不承诺未来每条必达。

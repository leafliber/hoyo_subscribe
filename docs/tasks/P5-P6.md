**必须实现的指标**（§10.1 明确列出，每一项都对应一个**会静默发生**的故障）：

| 指标 | 盯的故障 |
| --- | --- |
| 当日认证池剩余、是否跌破 `MAIL_AUTH_FLOOR` | 当天的登录能力被烧光而无人察觉（日模型下次日自动恢复，但当天用户登不进来） |
| 各池当日余额与耗尽时刻 | 某个池天天在同一时段耗尽，说明额度分配与真实需求不匹配 |

| 活动水位写入失败数、回收是否处于暂停 | 遥测坏了却仍在回收活跃用户的账号与席位 |
| 邮件合并率（每封平均承载的 Delivery 数） | 每日一封的额度是否真的送出了当天全部内容 |
| 席位自动续租与实际释放的比例 | 是否在摘掉"只用外部日历"的正常用户 |

**其余观测**：公开页按游戏显示来源最新成功、数据代次、待审核缺口；后台显示认证排队、账户/席位存量、当日各池余额、各优先级等待时间与跳过原因、退订延迟、邮件 unknown/抑制、Queue DLQ、Feed 完整性、真实 CPU/读写/存储。

**P3-08 已登记的来源截断信号**：`source_response_truncated_total` 按官方主机聚合 `source_response_truncated` 结构化日志（固定事件名、`source`、`reason_code=response_cap_exceeded`、`count=1`；不含 URL/正文）。单次命中即告警并核验来源载荷与 `SOURCE_LIMIT_PROFILE`；不得自动抬上限或重试绕过。P5-01 将此信号接入受控上线的指标与告警面板。

**P3-06 / P4-03 登记的两条告警（2026-09-30 所有者裁定）**：这两类故障不再有自动兜底，只能靠告警发现。
- **管线滞后**：公共快照重建积压太久（`snapshot_rebuild` outbox 长时间停在 pending，或构建连续失败）即告警。
  Feed 的新鲜度只看来源水位，下游卡住时 Feed 仍报"新鲜"（见 P3-06 卡末裁定）。阈值取已登记参数（如 `FEED_MAX_STALE`），需要新参数先进注册表。
- **邮件 unknown**：`mail_provider_failed` 中 `reason_code=provider_unknown` 单次即告警，并显示当日次数与认证池余额。
  unknown 不再触发全局暂停（见 P4-03 卡末裁定），平台只超时、不报错时，这是唯一的发现途径。

**独立开关**必须覆盖：注册、新邮件名额、常规提醒邮件层、业务邮件、全部外发、Push、模型、自动发布、单来源、账号与席位回收、只读维护。

## P6 · 可选 Web Push

唯一主要目标：**在不把 Push 当成掩盖日历主通道未验收的借口的前提下，做一个归属清晰、能真正验证接收的通道。**

### P6-01 · 绑定创建与可见激活

| 项 | 内容 |
| --- | --- |
| 前置 | G-P2、P5-01 |
| 允许改动范围 | `apps/worker/src/push/**` |
| 继承合同 | §7.8、§8.2、附录 A.4 的 `PUSH_*`、[R15] |
| 验收 ID | A-P6-BIND |

**交付物**

- 用户主动授权当前浏览器后，由**会话 + CSRF** 校验创建归属账号的 pending 绑定；验证精确 HTTPS 推送服务域名、端点与加密密钥；发送可见激活通知。
- Service Worker 使用**狭窄 receipt token + 随机 challenge** 确认后转 active。
- `PUSH_ACTIVATION_TTL`、`PUSH_ACTIVATION_ATTEMPTS`、`PUSH_TEST_COOLDOWN`、`PUSH_TEST_DAY`、`PUSH_USER_MAX`、`PUSH_ACTIVE_MAX`、`PUSH_PENDING_MAX`、`PUSH_NEW_DAY` 全部生效。

**关键约束（红线）**

- 同 endpoint 同 owner 可幂等；**不同 owner 冲突，不 UPSERT 抢占**。
- receipt token **不能获取邮箱、修改账号或管理其他设备**；管理和改偏好仍必须账号会话。
- 接口**不得成为任意 Webhook/SSRF 入口**。
- **不自动跟随登录开启**；用户主动点击前不申请系统权限、不创建绑定、不发测试。

**P2-05 交接（2026-09-28 验收方登记）**：紧急停用与恢复登录的安全暂停必须同时暂停 Push——把本通道的效果挂进 P2-05 导出的安全暂停挂接点，并加一条"紧急停用后本通道立即失效"的用例；首次启用前还须核对恢复码已保存确认（P2-05 导出的判定，§4.6）。

**D3 交接（2026-09-28 登记；D3 已于 2026-09-30 审定，生效）**：只给事实，不给服务端算好的动作表（D3 §1.2）。`GET /api/v2/me/push-bindings` 按 `docs/D3_STATE_VIEWS.md` §2.8 给出各绑定的状态、激活时间、租期；当前浏览器按本机持有的绑定 ID 判断，不按 endpoint 认领。

### P6-02 · 发送、租期、失效与退避

| 项 | 内容 |
| --- | --- |
| 前置 | P6-01、P4-01 |
| 允许改动范围 | `apps/worker/src/push/**` |
| 继承合同 | §7.8、附录 A.4 |
| 验收 ID | A-P6-SEND |

**交付物**

- 发送预算：`PUSH_SEND_DAY`（含业务、激活、测试、重试）、`PUSH_CRITICAL_RESERVED_DAY`。
- 租期：`PUSH_LEASE`、`PUSH_STALE_GRACE`；真实业务处理确认或账号操作可续期；`PUSH_RECEIPT_WRITE_INTERVAL` 合并写入。
- 失效处理：明确 404/410 停用端点；**401/403 先检查 VAPID/配置，不批量删除用户**；临时错误退避。

**关键约束**：平台接受**不是**客户端存活证明；**不发静默心跳**；激活通过也不承诺未来每条必达。

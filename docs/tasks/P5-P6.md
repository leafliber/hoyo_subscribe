## P5 · 受控上线

唯一主要目标：**在开放给真实用户之前，确认"出了问题能看见、能关掉、能恢复"。**

### P5-01 · 观测指标与运行开关

| 项 | 内容 |
| --- | --- |
| 前置 | P4 全部 |
| 允许改动范围 | `apps/worker/src/shell/observability/**`、各模块的指标埋点 |
| 继承合同 | §10.1 |
| 验收 ID | A-P5-OBS |

**必须实现的指标**（§10.1 明确列出，每一项都对应一个**会静默发生**的故障）：

| 指标 | 盯的故障 |
| --- | --- |
| 认证池软线状态、剩余月额、是否跌破 `MAIL_AUTH_FLOOR` | 登录能力提前几周耗尽，而表面上每天都没超日限 |
| 基础池 `carry` 与当日 `E` | envelope 归零导致的静默停发 |
| 缩水守卫命中次数与被拦响应 | 构造 bug 正在向客户端下达错误的删除指令 |
| 活动水位写入失败数、回收是否处于暂停 | 遥测坏了却仍在回收活跃用户的账号与席位 |
| 邮件合并率（每封平均承载的 Delivery 数） | 每日一封的额度是否真的送出了当天全部内容 |
| 席位自动续租与实际释放的比例 | 是否在摘掉"只用外部日历"的正常用户 |

**其余观测**：公开页按游戏显示来源最新成功、数据代次、待审核缺口；后台显示认证排队、账户/席位存量、预算剩余与当日 envelope、各优先级等待时间与跳过原因、退订延迟、邮件 unknown/抑制、Queue DLQ、Feed 完整性、真实 CPU/读写/存储。

**独立开关**必须覆盖：注册、新邮件名额、常规提醒邮件层、业务邮件、全部外发、Push、模型、自动发布、单来源、账号与席位回收、只读维护。

**关键约束**：达到预算先停止低价值扩大，**不用假空数据和假成功遮蔽**。账单告警只是监控，**不是平台收费绝对封顶**。

### P5-02 · 生命周期回收与暂停回收

| 项 | 内容 |
| --- | --- |
| 前置 | P5-01、P3-07 |
| 允许改动范围 | `apps/worker/src/accounts/reclaim/**`、`apps/worker/src/executors/cron/**` |
| 继承合同 | §9.4、§9.5、§9.6、附录 A.2 的 `ACCOUNT_*` 与 `RECLAIM_*` |
| 验收 ID | A-P5-RECLAIM |

**交付物**

- 逐对象回收信号（§9.4 表）：注册预占/验证码/完成回执、pending Session、正式会话、邮件名额、Push、账号。
- 账号活动水位 `max(last_interactive_at, last_feed_poll_at, last_push_processed_at)`，**低频合并写入，不每 GET 写 last_seen**。
- `ACCOUNT_IDLE_DAYS` → 回收宽限 `ACCOUNT_GRACE_DAYS` → 清理。
- **回收前的维护者可见待回收清单复核**入口。
- 活动水位不可信（指标异常或最近成功写入早于 `RECLAIM_TELEMETRY_STALE_HOURS`）时 → **全局暂停账号与席位回收**。
- 保留与清理：附录 A.5 的全部 TTL 与容量上限。

**关键约束（红线）**

- **持续使用外部日历但不访问网页的用户不会仅因缺少网页登录被清理。**
- **邮件席位按活动信号自动续租**，不要求用户专门回网页。
- 邮件服务商接受、邮件扫描器访问退订页**不算用户活跃**。
- **不在无人确认的情况下直接清理。**
- 删除/清理释放实际存量；**已消耗的日创建、尝试和发送额度不退款**。
- 无活动清理规则从注册时明确展示，**不得事后无提示缩短**。
- 到期任务不能因为删除 Delivery 就重新展开；正式证据、未过有效期的更正、未完成发送和合法退订依赖**优先于机械 TTL**。
- 不承诺自动识别所有僵尸或攻击者——恶意持续占满容量时暂停注册并由维护者处理。

### P5-03 · 独立加密备份与恢复演练

| 项 | 内容 |
| --- | --- |
| 前置 | P5-01 |
| 允许改动范围 | `scripts/backup/**`、`docs/runbooks/**` |
| 继承合同 | §10.2、附录 A.5 的 `BACKUP_*`、[R17] |
| 验收 ID | A-P5-BACKUP |

**交付物**

- 独立加密备份（`BACKUP_INTERVAL`、`BACKUP_COPIES`）：正式事件、证据、UID/版本、用户同意与撤销、必要运行状态。字段密钥、退订验证密钥、VAPID 和恢复 epoch **分开保管**。
- 恢复 runbook，严格按顺序：隔离环境关外发 → 校验 Schema/密文/证据 → **使用旧快照之外的当前恢复 epoch 废止旧会话与认证结果** → 对账撤销和版本 → 恢复公开读及账号控制 → **最后**恢复发送。
- 一次实际恢复演练的记录（E2/E3）。

**关键约束（红线）**

- **Time Travel 不是独立备份。**
- 没有可信的新近撤销清单时：恢复的邮件/Push **默认暂停**，旧 Feed token **默认撤销**；恢复码的已消费状态不确定也不能直接恢复使用。
- **禁止向可能已退订的地址群发重新确认。**
- 能证明高水位时保留 UID 并抬高版本；**无法证明时暂停受影响 Feed，进行明确的新订阅迁移**，不承诺无损透明回滚。
- 代码回滚不等于数据库回滚。

## P6 · 可选 Web Push

唯一主要目标：**在不把 Push 当成掩盖日历主通道未验收的借口的前提下，做一个归属清晰、能真正验证接收的通道。**

### P6-01 · 绑定创建与可见激活

| 项 | 内容 |
| --- | --- |
| 前置 | G-P2、P5-01 |
| 允许改动范围 | `apps/worker/src/push/**` |
| 继承合同 | §7.8、§8.2、附录 A.4 的 `PUSH_*`、[R15] |
| 验收 ID | A-P6-BIND |

**交付物**

- 用户主动授权当前浏览器后，由**会话 + CSRF** 校验创建归属账号的 pending 绑定；验证精确 HTTPS 推送服务域名、端点与加密密钥；发送可见激活通知。
- Service Worker 使用**狭窄 receipt token + 随机 challenge** 确认后转 active。
- `PUSH_ACTIVATION_TTL`、`PUSH_ACTIVATION_ATTEMPTS`、`PUSH_TEST_COOLDOWN`、`PUSH_TEST_DAY`、`PUSH_USER_MAX`、`PUSH_ACTIVE_MAX`、`PUSH_PENDING_MAX`、`PUSH_NEW_DAY` 全部生效。

**关键约束（红线）**

- 同 endpoint 同 owner 可幂等；**不同 owner 冲突，不 UPSERT 抢占**。
- receipt token **不能获取邮箱、修改账号或管理其他设备**；管理和改偏好仍必须账号会话。
- 接口**不得成为任意 Webhook/SSRF 入口**。
- **不自动跟随登录开启**；用户主动点击前不申请系统权限、不创建绑定、不发测试。

### P6-02 · 发送、租期、失效与退避

| 项 | 内容 |
| --- | --- |
| 前置 | P6-01、P4-01 |
| 允许改动范围 | `apps/worker/src/push/**` |
| 继承合同 | §7.8、附录 A.4 |
| 验收 ID | A-P6-SEND |

**交付物**

- 发送预算：`PUSH_SEND_DAY`（含业务、激活、测试、重试）、`PUSH_CRITICAL_RESERVED_DAY`。
- 租期：`PUSH_LEASE`、`PUSH_STALE_GRACE`；真实业务处理确认或账号操作可续期；`PUSH_RECEIPT_WRITE_INTERVAL` 合并写入。
- 失效处理：明确 404/410 停用端点；**401/403 先检查 VAPID/配置，不批量删除用户**；临时错误退避。

**关键约束**：平台接受**不是**客户端存活证明；**不发静默心跳**；激活通过也不承诺未来每条必达。

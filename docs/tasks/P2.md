# P2 · 账号与云配置纵向闭环

> 唯一主要目标：**一个用户能用邮箱验证码登录、在两台设备上维护同一份配置、在邮箱不可用时仍能取回控制权。**
> 依据：主方案 §4 全章、§5.1、§5.4、§8.2、附录 A.2。
> 前置门禁：**G-P1**（P1 八张卡全部验收通过）。

---

### P2-01 · 预认证上下文与申请验证码前的准入

| 项 | 内容 |
| --- | --- |
| 前置 | G-P1 |
| 允许改动范围 | `apps/worker/src/auth/preauth/**`、`apps/worker/src/accounts/admission/**` |
| 继承合同 | §4.2、§4.3 前半、附录 A.2、[R09] |
| 验收 ID | A-P2-PREAUTH |

**交付物**

- `POST /api/v2/auth/preauth`：同源初始化 `__Host-preauth`（Secure、HttpOnly、SameSite=Lax、Path=/、**不设 Domain**），预认证 CSRF 与该 Cookie 绑定，携带服务端认证的签发/截止信息。
- **固定的检查顺序**：请求结构与尺寸 → 同源/CSRF → 近似限速 → Turnstile 服务端校验 → 邮箱与全局配额 → 原子预占 → 创建挑战及发信任务。
- 注册准入：`/status` 公布全局 `registration_open`；**不提供按邮箱查询是否注册的接口**。
- 注册槽预占：验证码有效期间保留，验证成功转账号存量，过期释放；同一规范邮箱共享有限预占防并发超卖；**已有用户登录不占新注册槽**。

**关键约束**

- 满额或关闭注册时，未知邮箱**不生成实际发信任务**，但公开响应与普通申请**同形**（"符合条件的请求将发送验证码"）。**不得回显"该邮箱不存在"**。
- Turnstile 是单次验证，不替代会话或配额。
- 不承诺邮箱、IP 或 Turnstile 能证明真人唯一性。

**不在范围**：OTP 生成与消费。

### P2-02 · OTP 挑战生命周期

| 项 | 内容 |
| --- | --- |
| 前置 | P2-01 |
| 允许改动范围 | `apps/worker/src/auth/challenges/**` |
| 继承合同 | §4.1、§4.3、附录 A.2、A.5 认证时序等式 |
| 验收 ID | A-P2-OTP |

**交付物**

- `POST /api/v2/auth/challenges`、`.../resend`、`.../verify`。
- 验证码均匀随机（`OTP_DIGITS`）；验证表存带独立 pepper 的 MAC，**绑定用途、challenge_id、email_key、地址版本、generation 和验证码**。
- 已有身份：验证码**只发到数据库中已验证的实际地址**，不按请求中不同大小写的地址改投。
- 新地址挑战绑定实际投递串与注册预占；消费时检查身份/地址版本。
- 预认证 Cookie 续期**同一个值**，保留期限覆盖该上下文所有未过期挑战的最晚结束时间 + `AUTH_COMPLETION_TTL` + `PREAUTH_MARGIN`。
- 网络重试沿用绑定预认证上下文的 `idempotency_key`；**明确重发才创建新发送意图**。

**关键约束（最易错，逐条写测试）**

- 重发只旋转本挑战的 generation：**不重置累计失败次数、不延长挑战最初截止、不废掉其他浏览器的挑战**。
- 错误尝试**持久扣减**，不能被返回错误的事务回滚抵消。
- 活动 Cookie 临近到期不影响新验证码；Cookie 丢失或响应丢失导致的失败**不得误报为验证码错误**。
- `PREAUTH_MIN_TTL` 的下限本身要满足等式（附录 A.2 已取 1,320 秒）。

**不在范围**：消费与会话创建。

### P2-03 · 原子消费、账号建立与完成回执

| 项 | 内容 |
| --- | --- |
| 前置 | P2-02 |
| 允许改动范围 | `apps/worker/src/auth/consume/**`、`apps/worker/src/accounts/users/**`；**获准的注入点**见下方「2026-09-27 裁定」 |
| 继承合同 | §4.1 末段、§4.4、§5.1、附录 A.1 `SUBSCRIPTION_INIT_STATE` |
| 验收 ID | A-P2-CONSUME |

**交付物**

- 正确验证后一致提交：挑战消费、可能的新账号、注册容量转换、pending Session。
- `POST /api/v2/auth/complete`：凭原 preauth + 操作幂等键领取同一待激活会话；保存加密的待交付 Cookie 值；客户端完成激活后**立即清除**可恢复值，到期由清理任务兜底。
- 新账号的订阅行以 `uninitialized` 写入。

**关键约束**

- 并发消费**最多一次成功**；不得出现"会话已创建但挑战仍可用"。
- **不写入任何代替用户选择的游戏、事件或节点默认值。**`DEFAULT_*` 只是界面预选。
- `uninitialized` 账号可浏览、登录、管理会话、删除账号，但**不能启用 Feed / 邮件 / Push，也不产生任何通知发生项匹配**。
- 回执仅在 `AUTH_COMPLETION_TTL` 内、pending 状态、原浏览器上下文匹配时可取；**不能凭 challenge_id 单独领取**，也不是重新开放验证码。
- 消费一次性凭证前，预认证上下文必须已建立且具备完成交付所需的剩余期限；不足则先要求续期，**不能先消费恢复码**。
- 并发期间若同规范键已被另一个实际地址建立，**不能把验证码成功直接转成该账号登录**，须重走向已验证地址发送的流程。

> **2026-09-27 裁定：挑战绑定的投递地址独立落库**
>
> 新账号的 `users.email_ciphertext` 必须是**验证码实际送达的那个串**（挑战创建时绑定、本地部分保留大小写），
> **不是 verify 请求里的串**——两者规范键相同，本地部分大小写却可能不同，而证明过所有权的只有前者（§4.1）。
> 这个串目前**只存在于 `otp-mail-payload` 里**，而该载荷按 §4.3 在发送被接受后就要清除。
> P4 一旦实现「发送后清除」，消费与重发都会失去来源。
>
> 做法：挑战创建时把实际投递地址另存为受控密文（`auth_challenges` 新列；记录类型 `delivery-email-address`，
> AAD 记录 ID = `auth_challenges.id`），**随挑战生命周期（消费/过期/终止）清除，不随发送清除**。
> 验证码载荷照旧在发送后清除。消费建号、重发都从这一列取地址；取不到一律失败关闭。
>
> 因此本卡获准改动（逐条在文件头写理由）：
> - `migrations/`：新增一个迁移，只加这一列；
> - `auth/challenges/create-challenge.ts`：创建时写入该列（login 与 signup 都写）；
> - `auth/challenges/resend.ts`：地址来源改为优先读该列，**login 的失败关闭语义不得变**；
> - `auth/challenges/verify.ts`：只改 MAC 命中后的成功出口，注入原子消费；
> - `apps/worker/src/index.ts`：挂载 `POST /api/v2/auth/complete`；
> - `accounts/admission/registration.ts`：只可**新增**预占转换所需的导出函数，不改既有函数语义。

### P2-04 · 会话生命周期

| 项 | 内容 |
| --- | --- |
| 前置 | P2-03 |
| 允许改动范围 | `apps/worker/src/auth/sessions/**`；**获准的跨卡改动**见下方「P2-04 开工前还要解决的两处跨卡问题」 |
| 继承合同 | §4.5、§9.3、附录 A.2、[R10]；前端 §12.2、§13.3 |
| 验收 ID | A-P2-SESSION |

**交付物**

- `__Host-session`（与预认证分离）、`SECRET_BITS` 随机强度、**常态只存 hash**，不放 URL / localStorage / 配置导出。
- 状态机：`pending --浏览器带新 Cookie 确认--> active --到期/撤销--> revoked`；pending 超时清理且**不计入 active 名额**。
- 绝对期限：**创建会话时**取 `SESSION_ABSOLUTE_TTL ± SESSION_ABSOLUTE_JITTER` 内的随机值并固定写入。
- 续期：`POST /api/v2/auth/renew`，每会话最多按 `SESSION_RENEW_INTERVAL` 一次，且 `expires_at ≤ created_at + 本会话抖动后的绝对期限`。
- `GET /api/v2/me/sessions`：返回**标签**（用户自填，缺省为创建时间 + 粗粒度平台：桌面/移动/未知）、`created_at`、`renewed_at`，以及 `renewed_at` **最多滞后一个 `SESSION_RENEW_INTERVAL`** 的说明。
- `DELETE /api/v2/me/sessions/{id}`；`POST /api/v2/auth/logout` 仅撤销当前会话。
- active 名额满时：由用户明确选择撤销哪个旧会话后**原子激活**。
- 临近到期（`SESSION_EXPIRY_NOTICE`）在网页提示重新验证。

**关键约束**

- **不自动淘汰最早创建的会话**；未拿到 Cookie 的孤儿不得把正常设备挤下线。
- **"真实前台操作"的定义不得放宽**：只有保存订阅、启用/停用通道、管理会话或设备、换邮箱、轮换恢复码、导出数据之后才允许一次续期 POST。页面加载、被动 GET、预取、后台标签页、Service Worker、外部日历拉取、收到邮件**都不算**。
- 设备标签只是显示信息；**IP/UA 指纹不参与鉴权**，不据此推断真人身份。
- 不能靠一封可能同样被抑制的提醒邮件保障恢复。

**开工前必读（P2-03 交接，2026-09-27 验收登记）**

- pending 会话由 P2-03 创建：Cookie `__Host-session`，库里存 `token_hash = SHA-256(Cookie 值)`
  （`auth/consume/session.ts` 的 `makePendingSession`）。查会话用同一算法，**不要另做 HMAC**。
- `absolute_expires_at` 已在创建时按 `SESSION_ABSOLUTE_TTL ± SESSION_ABSOLUTE_JITTER` 定死，触发器禁止改写——
  激活与续期都不得试图改它。
- **激活事务里必须带上 `activatedReceiptClearEffect(sessionId, now)`**（`auth/consume/cleanup.ts`），
  否则完成回执里可恢复的 Cookie 值会在激活后继续存活（§4.4 "激活后立即清除"）。
- `label` / `platform_hint` 目前是占位的 `unknown`，由本卡按 §4.5 补真实值。
- pending 数量上限 `SESSION_PENDING_PER_USER` 已在消费 CAS 里执行；active 名额是本卡的事。

**P2-04 开工前还要解决的两处跨卡问题（2026-09-28 验收方排查）**

1. **会话 Cookie 名有两个常量且值不同**：`shell/domains.ts` 的 `USER_SESSION_COOKIE_NAME = "__Host-hoyo_session"`，
   `auth/consume/session.ts` 的 `SESSION_COOKIE_NAME = "__Host-session"`（P2-03 已按后者下发）。主方案 §4.5 定的是
   `__Host-session`。收成**一个**：`domains.ts` 的常量改为 `"__Host-session"`，`session.ts` 改为引用它。
   不收的话，本卡的鉴权器读不到 P2-03 下发的 Cookie——所有人登录后仍是未登录。
2. **pending 会话不得拿到普通用户权限**：`ShellAuth` 目前只带 `userId`，路由对任何 session 放行。
   §4.5：pending 只允许查看脱敏设备列表与完成激活。鉴权结果要带上会话状态，**user 域路由默认只接受 active**，
   只有设备列表与激活两处显式接受 pending。

获准改动（逐条在文件头写理由）：`shell/domains.ts`、`shell/router.ts`（最小改动）、
`auth/consume/session.ts`（仅 Cookie 名改为引用）、`apps/worker/src/index.ts`（替换鉴权器桩、挂载路由）。

另：会话阶段的写路由 CSRF 绑定**会话 token 散列**（`shell/csrf.ts` 的绑定值由本卡提供）；激活成功时签发绑定新会话的
CSRF token。激活请求本身怎么绑定由本卡决定并在报告里说明，**不得让激活绕过 CSRF**。

### P2-05 · 离线恢复码

| 项 | 内容 |
| --- | --- |
| 前置 | P2-04；**并须先完成下方「开工前必做」** |
| 允许改动范围 | `apps/worker/src/auth/recovery/**`、`packages/contracts/src/**`（仅用途枚举上移） |
| 继承合同 | §4.6、§4.7、§8.2、附录 A.2；前端 §7.4 |
| 验收 ID | A-P2-RECOVERY |

**开工前必做（P2-02 遗留，2026-09-22 验收登记）**

挑战用途枚举（`login / signup / email_change / recovery`）目前在
`apps/worker/src/auth/challenges/purposes.ts`——P2-02 的改动范围只允许 `challenges/**`，
未能上移。**本卡引入 `recovery` 用途，是第二条挑战创建路径**，所以上移到
`packages/contracts` 必须先做，否则两条路径各定一份用途串，MAC 绑定的「用途」字段
就有了两个来源（`AGENTS.md` 硬规则 3）。

上移只搬枚举与 `isChallengePurpose`；`purposeOfAdmissionIntent`（创建侧映射）留在 worker。

**交付物**

- 首次登录后交付 `recovery_id + 高熵随机秘密`，服务端只存 hash。**首次开启长期 Feed / 邮件 / Push 前要求完成保存确认**。
- `POST /api/v2/auth/recovery` 带明确 `action`：
  - `emergency_stop`：撤销所有会话与 Feed、关闭业务邮件、暂停 Push；**不返回任何私人数据**；**不消费恢复码**；幂等。
  - `recover_login`：**消费**该码，执行同样的安全暂停，创建 pending 恢复会话；激活后**立即交付新恢复码**。
- 恢复会话在用户完成新码保存确认前，**只允许查看、导出、保存新码、删除账号**；启用任何通道与换邮箱一律拒绝。
- 限速：按 `recovery_id` 与来源分别限制 `RECOVERY_ATTEMPTS_HOUR` / `RECOVERY_ATTEMPTS_DAY`，超出返回统一的稍后重试。
- 沿用预认证绑定、用途限定、一次消费与短期完成回执。

**关键约束**

- **紧急停用不消费恢复码**——持码者本来就能走恢复登录，消费它只会让合法用户在停用之后失去唯一回账路径。这条是红线。
- `recovery_id` 与秘密**一起**校验；单独提交 `recovery_id` 不得产生存在性差异。
- 恢复码**不证明新邮箱所有权**；换邮箱仍须验证新邮箱。
- 恢复入口**不依赖发信预算**（认证降级期间的唯一保障，§9.2）。
- 旧邮箱、会话、恢复码全丢时，**不提供"凭自述邮件接管"**。
- 恢复权限是新的认证入口，属高价值凭证；报告中不得写成"没有增加恢复攻击面"。

**开工前还要知道的（2026-09-28 验收方排查）**

1. **`recovery_epoch` 不是恢复码代次。**`users` / `sessions` 上的 `recovery_epoch` 是**灾备还原** epoch
   （主方案备份与恢复一节、P5-03："使用旧快照之外的当前恢复 epoch 废止旧会话"）。本卡不得拿它表示恢复码的使用或轮换。
   紧急停用与恢复登录撤销全部会话，用**递增 `users.auth_epoch`**：P2-04 鉴权器逐请求核对它，下一次请求即失效，
   pending 会话一并作废。不要写"按 user_id 把会话行标 revoked"这种可能零行的依赖效果——无会话时它会让
   `conditionalCommit` 抛不变量错误，而紧急停用恰恰要在"无既有会话"时也能执行（见 `ENGINEERING.md` §5.4）。
2. **安全暂停里的 Feed / 邮件 / Push**：三类通道的启用入口还没有卡实现（P3-07、P4-05、P6-01），库里不会有可用行。
   本卡把"安全暂停"做成可扩展的一处（会话部分由本卡实现），**导出挂接点**；三张通道卡各自挂上本通道的效果，
   并各带一条"紧急停用后本通道立即失效"的用例（已写进那三张卡）。本卡**不替后续卡发明通道状态值**。
   同时导出"当前恢复码已保存确认"的判定，供三张通道卡在首次启用前核对（§4.6）。
3. **恢复会话的能力限制落在会话上，不从用户状态推导。**若按"当前恢复码未确认"推导，另一台设备正常 OTP 登录的
   会话也会被锁住，而新码只在恢复会话里显示过——它永远解不开。所以：
   - 新增迁移给 `sessions` 加一列标记恢复会话（形式由本卡定），同步 `apps/worker/src/storage/expected-schema.ts`；
   - `ShellAuth` 的 user 会话带上该标记；外壳对受限会话的**写路由默认拒绝**，只放行显式声明的路由：激活、登出、
     新码的生成与保存确认、删除账号（P2-07 届时声明）。读路由（查看、导出）照常。这样 P2-06 等并行卡的写路由
     自动被挡，不需要它们知道本卡；
   - 拒绝用 `401 unauthorized`，在 contracts 的 `UnauthorizedReason` 闭合枚举里新增一个原因
     （如 `recovery_code_unconfirmed`），同步 `errors/codes.test.ts`。
4. **新码"只显示一次"与响应丢失**：§4.6 同时要求"重新显示旧码不可行"和"避免响应丢失把用户唯一的码消耗掉"。
   验收方建议：保存确认之前，允许本人会话**作废并重新生成**未确认的新码（是重新生成，不是重新显示），确认后才固定。
   报告里写清由谁、在什么条件下能生成与重新生成，以及**持有会话者能否借此给账号植入一个用户不知道的恢复码**——
   攻击面如实写。首次登录后的那份码同理。
5. **恢复登录复用 P2-03 的机制**：挑战用途 `recovery`（开工前必做就是为它上移枚举）；pending 会话用
   `makePendingSession`，散列只用 `hashSessionToken`（P2-04 返工后的唯一实现）；响应丢失沿用完成回执与
   `/api/v2/auth/complete`；激活仍走 P2-04 的 `/api/v2/auth/activate`，**不改激活的通用语义**——
   "激活后立即交付新码"由前端在激活成功后立刻调本卡的新码端点实现（有更好的方案就在报告里论证）。
6. **入口形态**：紧急停用"无邮件、无既有会话"也要能用，所以恢复端点属 public 域，绑定预认证上下文，CSRF 绑定 preauth
   （照 P2-01/P2-02）。单独提交 `recovery_id` 不得产生存在性差异——响应与时序都要折叠，参照 P2-01 的折叠与
   P2-08 的交替采样测试。来源维度的限速参照 P2-01 的近似限速门（[R16]：近似限速只挡突发），`recovery_id` 维度的
   精确计数走 D1；不落 IP 原文。

### P2-07 · 换邮箱、删除账号与数据导出

| 项 | 内容 |
| --- | --- |
| 前置 | P2-05、P2-06 |
| 允许改动范围 | `apps/worker/src/accounts/lifecycle/**`、`apps/worker/src/auth/recent-auth/**` |
| 继承合同 | §4.7、§9.5、§9.6、§8.2 |
| 验收 ID | A-P2-ACCOUNT |

**交付物**

- 最近认证证明：来自本次实际成功的 OTP 或恢复码校验，绑定 Session、用途、目标摘要与 `RECENT_AUTH_TTL`，**消费后失效**，不能由客户端提交时间戳冒充。
- `POST /api/v2/me/email-change`：要求"当前邮箱 OTP 或恢复码证明" + "新邮箱 OTP"；原子更新实际地址、`email_key`、`email_version`、`auth_epoch`，撤销旧会话与未完成挑战，停止旧地址待发任务，为当前操作交付新会话；**新邮箱业务邮件默认关闭**；`user_id` 与订阅不变。
- `POST /api/v2/me/recovery-code`（轮换，需最近认证）。
- `POST /api/v2/me/delete`：原子标记 `deleting`、增加 `auth_epoch`、撤销 Feed 与会话、关闭邮件与 Push，**立即阻止新的私人读取和发送**；之后分页清理，清理完成才释放存量。
- `GET /api/v2/me/export`：本人配置及必要数据，**不导出秘密**（邮箱、会话、恢复码、Feed/退订 URL、Push 密钥、通道同意均排除于可分享偏好）。
- Feed 管理动作的权限定义：**enable / disable / reset 只需有效会话 + CSRF + 显式确认 + 限速，不要求额外 OTP**；reset 与 disable→enable 权限等价。

**关键约束**

- 终止路径（退订、Feed 停用、会话撤销、紧急停用、删除）**不被 `USER_MUTATIONS_DAY` 阻断**；已停止的对象再次停止不重复写库。
- 删除释放存量，但**已消耗的日创建、尝试与发送额度不退款**。
- 不得宣传匿名化或自动满足所有地区法规——HMAC 邮箱键仍是可能关联的个人数据。
- 平台整体不可用时返回真实错误，**不得伪称已经停用**。

### P2-08 · 并行负载下的测试抖动治理

| 项 | 内容 |
| --- | --- |
| 前置 | P2-02 |
| 允许改动范围 | `apps/worker/src/auth/preauth/admission.test.ts`、`apps/worker/src/storage/crypto/mac.test.ts`、`apps/worker/vitest.config.*`（仅当需要隔离计时类用例） |

| 验收 ID | A-P2-TIMING |

**为什么有这张卡（2026-09-27 验收发现）**

`ENGINEERING.md` §7 规定：复现率上升即按缺陷处理并单独开卡。验收时 6 轮全量并行 `pnpm test`，
**2 轮各挂 1 条，且是两条不同的测试**：

| 测试 | 情况 |
| --- | --- |
| `auth/preauth/admission.test.ts` › 四条路径同形 › 耗时中位数无系统性差异 | **新出现**。单独跑 8/8 全过，只在全量并行负载下失败 |
| `storage/crypto/mac.test.ts` › OTP 验证 MAC › 验证：正确绑定通过… | §7 早已登记，P1 期起就在抖 |

计时测试用的是 `recordingEffect()` 替身，P2-02 的真实发信开销不在比较范围内——
**这不是侧信道回归，是测试方法问题**：四条路径**各自连续**采 15 个样本，负载波动只要压在其中一段上，
那一段的中位数就偏了。

**交付物**

- 计时比较改为**交替采样**（四条路径轮转，每轮各采一次），让负载漂移平均落到每条路径上。
  这是计时侧信道比较的标准做法。
- `mac.test.ts`：**先复现，再定因。**报告写清失败时的实际断言输出与根因。若确属负载下的计时或超时问题，
  按根因修；若 50 轮全量仍无法复现，如实记录复现尝试与结论，不做推测性修改。
- 连续 20 轮全量并行 `pnpm test` 零失败，汇总行贴进报告。

**关键约束（红线）**

- **不得放宽 2.5 倍比值上限**，不得减少样本数，不得删除或 `skip` 计时断言。
- **不得加 `retry`，不得无依据地加长超时。**这些是把红灯调暗，不是修好它——CI 偶发红比测试缺失更伤。
- **修完的测试必须保留检出能力。**反向验证：临时给已注册路径注入稳定的额外延迟（如 30ms），
  确认测试**必然失败**，验证后还原。变异要先 `grep -c` 确认落地（`ACCEPTANCE.md` §2.1）。
  如果修复让这个变异也能通过，就是把测试修瞎了。
- 不改被测实现（`pipeline.ts`、`mac.ts` 等）；变异只能是临时的。
